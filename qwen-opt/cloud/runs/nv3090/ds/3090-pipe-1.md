# Brief: GGML_CUDA_MMVQ_PIPE — software-pipelined multi-column MMVQ on NVIDIA (bit-exact, default off)

## Goal
Raise the DRAM bandwidth of the 5-column MMVQ (speculative verify of Qwen3.8-27B UD-Q6_K_M, MTP n=4 → 5 columns) on
an RTX 3090 (sm_86, 82 SMs, 936 GB/s). nsys on the card (2026-10-20, kernel durations, 197 verify steps):
MMVQ is ~38 ms of a ~41 ms step. Achieved bandwidth per launch shape (bytes / mean kernel time):

| launch (grid × 2 rows, regs) | what | mean µs | GB/s |
|---|---|---|---|
| 17408 blocks, 154 regs, gate-fused | Q6_K ffn_up + gate fused, 2×17408×5120 | 263.5 | **555** |
| 8704 blocks, 148 regs | Q6_K 17408×5120 (ffn_up alone) | 129.6 | **564** |
| 8192 blocks, 154 regs | Q6_K 16384×5120 fused | 126.2 | **546** |
| 6144 / 5120 blocks, 148 regs | Q6_K 12288×5120, 10240×5120 | 92.8 / 78.2 | **556 / 550** |
| 2560 blocks, 154 regs | Q6_K ffn_down 5120×17408 (K=17408) | 94.7 | 772 |
| 8704 blocks, 127 regs | Q5_K 17408×5120 | 93.9 | 652 |
| 2560 blocks, 128 regs | Q5_K 5120×17408 (K=17408) | 79.3 | 773 |
| 124160 blocks, 80 regs | Q8_0 LM head 248320×5120 | 1564 | 864 |

Q6_K with K=5120 (20 super-blocks per row = only 5 loop iterations per thread with nwarps=2, vdr=4) reaches ~555 GB/s,
the same type with K=17408 (17 iterations) 772 GB/s. Register use (148–154) limits residency to 6 blocks = 12 warps/SM,
so each warp must keep more bytes in flight: the loop today issues its weight loads, waits, then unpacks/dots.

## Where (worktree /home/jaro/wt/nv-3090-pipe, branch nv-3090-pipe — edit only here)
`ggml/src/ggml-cuda/mmvq.cu`, kernel `mul_mat_vec_q` (~1524):
- There is already a software-pipelined multi path: `use_pipeline` (~1711) — loads the NEXT iteration's raw weights

  is enabled only for `table_id == MMVQ_PARAMETERS_RDNA3_0`, `!has_gate_fusion`, and `mmvq_r3_pipeline()` (~1510,
  Q6_K n=5 only). Types with raw slices: `mmvq_has_xraw()` (~360): Q4_K, Q5_K, Q6_K, IQ4_XS.
- The non-pipelined multi path calls `vec_dot_q_multi` (~802) = `mmvq_load_x` (→ load_xraw + unpack for xraw types,
  check ~486) + `vec_dot_q_multi_xs`, i.e. the same arithmetic in the same order → the pipelined path is bit-exact.
- The gate-fused launches (`has_gate_fusion`, `use_gate`, `tmp_gate`, `xr_gate`) — the largest Q6_K launches — are
  excluded from the pipeline today.
- Env precedent for selecting a template instance at runtime on NVIDIA: `GGML_CUDA_MMVQ_N1_ROWS` (`mmvq_n1_rows_nv()`
  ~1419) and its use in `mul_mat_vec_q_switch_ncols_dst()` (~2200) / `mul_mat_vec_q_switch_fusion()` (~2100).

## Change
1. Env `GGML_CUDA_MMVQ_PIPE` (default unset = OFF = today's kernels and code paths, no new instance selected):
   `=1` selects pipelined instances on NVIDIA (`!GGML_USE_HIP`) for `mmvq_has_xraw` types at ncols_dst 2..8
   (at least 4..6 if compile time explodes — report it), plain and fused launches.
2. Implement it as a new bool template parameter (e.g. `pipe`) of `mul_mat_vec_q`, so `use_pipeline` becomes
   `use_multi && mmvq_has_xraw(type) && (rdna3_condition_as_today || pipe)`; the RDNA3 behaviour must stay exactly
   as is.
3. Extend the pipeline to gate fusion when `pipe` is set: load the next iteration's raw slices of both `xr` and
   `xr_gate` (when `use_gate`), unpack/dot both like the non-pipelined code (`tmp_gate` accumulated by the same
   `vec_dot_q_multi_xs`). Keep bias/GLU epilogue untouched.
4. Optional second variant (`=2`): prefetch distance 2 (two raw slices in flight) if registers allow — report regs.
5. Bit-exact: no change of nwarps, rows per block, vdr, thread→(kbx,kqs) mapping, accumulation order (each iteration
   still adds the same values to `tmp[j][r]` in the same order), or the reduction. Past-the-end prefetch must stay a
   harmless in-row re-read (as the existing code does with `min(kbx + blocks_per_iter, kbx_last)`). Comment why it is
   bitwise identical, style of the `[GGML_CUDA_MMVQ_N1_ROWS]` comment.
6. Touch only `mmvq.cu` (and `mmvq.cuh` for a declaration if strictly necessary).
