## 1. ROCprofiler-SDK: kernel replay, PC sampling, skill, ATT

### 1.1 PC sampling: tylko Instinct
- Tabela „Supported AMD Instinct GPUs” w docs rocprofiler-sdk wymienia wyłącznie MI355X/MI350X/MI350P/MI325X/MI300X/MI300A (stochastic + host-trap) i MI250X/MI250/MI210 (tylko host-trap) [R2].
- Przegląd SDK: „HOST_TRAP … MI200+ (gfx90a+)”, „STOCHASTIC … MI300+ (gfx942+)”. Stall reason daje tylko STOCHASTIC [R3].
- Compute Profiler: „Host Trap … MI200 Series and later … Stochastic … MI300 Series and later” [R10].
- Release notes 10.1: większy bufor PC sampling „applies only to AMD Instinct MI300 and MI350” [R1].
- **Skill „pc-sampling”** (`rocm-systems/projects/rocprofiler-sdk/skills/pc-sampling/SKILL.md`): pierwszy warunek to „The GPU must support PC sampling … `rocprofv3-avail info --pc-sampling`” [R11]. Na gfx1100 skill nie ma czego uruchomić. Przydatne z niego:
  - skrypt `scripts/analyze_pc_sampling.py` (top miejsc i top powodów stallu);
  - `resources/stall-reasons.md`.
  Oba można przerobić na parser wyjścia ATT.
- Werdykt: **nie dotyczy gfx1100.** Benefit 0.

### 1.2 Kernel replay (beta)
- Co robi:
  - jedno uruchomienie aplikacji zbiera wiele grup liczników;
  - SDK snapshotuje „tracked coarse-grained device allocations” i zmienne modułu, a potem je odtwarza między przebiegami;
  - flagi: `--replay-mode kernel --kernel-replay-beta-enabled`, tylko z `--pmc`;
  - nie łączy się z `--att`, PC sampling ani `--spm` [R1].
- Dla nas:
  - pomaga tylko wtedy, gdy liczniki w ogóle działają (§1.3);
  - nie widzi dispatchy PM4, bo replay jest w callbackach dispatchy HIP/HSA. Jak zwykłe rocprofv3: `GGML_HIP_PM4=0` `[SZACUNEK]`;
  - ryzyko „Beta Risk”: stan poza śledzonymi alokacjami (np. bufory hosta, stan GDN w pamięci fine-grained) może się nie odtworzyć.
- Werdykt: **mały zysk.** Wygoda, gdy będziemy zbierać ≥2 grupy PMC naraz (np. `SQ_WAIT_INST_ANY` + `TCC_HIT/MISS`).

### 1.3 Dlaczego PMC dawały 0 na gfx1100 (i co z tym zrobić)
- Docs SDK, sekcja „Supported hardware”: „On gfx11 and gfx12 architectures (AMD Radeon RX 7000 series and later), counter collection requires a stable power state. Use `amd-smi` to set the power state before profiling.” [R6]
- Definicje liczników dla `gfx11` / `gfx1100` są w `basic_counters.xml` naszego 10.0. Brak liczników nie wynika więc z braku tabel.
- Test (GPU, sudo, cofa się sam po restarcie albo przez `AUTO`):
  ```bash
  sudo /opt/rocm/core-10.0/bin/amd-smi set -g 0 --perf-level STABLE_STD   # albo echo profile_standard > .../power_dpm_force_performance_level
  GGML_HIP_PM4=0 rocprofv3 --pmc SQ_WAVES GRBM_GUI_ACTIVE SQ_INSTS_VALU --kernel-include-regex mul_mat_vec_q -- <logits_dump …>
  sudo /opt/rocm/core-10.0/bin/amd-smi set -g 0 --perf-level AUTO
  ```
  (`amd-smi set --help` w 10.0: poziomy `AUTO, LOW, HIGH, MANUAL, STABLE_STD, STABLE_PEAK, …, DETERMINISM`.)
- Pomiar pod STABLE_STD ma inne zegary. Liczniki służą do proporcji (VALU/wave, trafienia L2), nie do czasów.

### 1.4 ATT (thread trace): właściwe narzędzie na RDNA3
- Tabela „Supported devices”: „RDNA3 | AMD Radeon (discrete) | Trace-only | gfx1100, gfx1101, gfx1102” [R4].
- Kolumny wyjścia:
  - `Hitcount`;
  - `Latency` (na gfx10+ = stall + execute);
  - `Stall`;
  - `Idle`;
  - `Source` per instrukcja [R4].
- „Trace-only” = bez `--att-perfcounters` [R3].
- **Już mamy:** `/opt/rocm/core-10.0/lib/librocprof-trace-decoder.so.0.2.0`. `rocprofv3 --help` w 10.0 pokazuje `--att-target-cu`, `--att-simd-select`, `--att-shader-engine-mask`, `--att-buffer-size` i `--att-no-intercept`.
- **Co dokłada 10.1** [R1]:
  - ATT w live attach (`rocprofv3 --pid`);
  - eksperymentalny „SQTT quick scan” bez wstawiania pakietów i bez przechwytywania kolejki;
  - Python API dekodera;
  - wersjonowany dekoder (`.so.0.2.2` w tarballu 10.1);
  - poprawka utraty końcówki trace po `roctxProfilerPause/Resume`.
- **PM4 a ATT:** zwykłe ATT wstawia pakiety start/stop wokół dispatchy AQL. Dispatche w naszej taśmie PM4 będą więc niewidoczne, tak jak dla rocprofv3 `[SZACUNEK]`. Do profilowania kerneli: `GGML_HIP_PM4=0` (ISA ten sam). Quick scan „without packet insertion” *może* złapać też taśmę PM4. Warto to sprawdzić osobno, bo dałoby obraz granic kerneli w PM4 `[SZACUNEK]`.
- Flagi pod Navi są już opisane w `research/repos/25-atrex-kernel-agent.md` (P1):
  - `--att-simd-select` to ID SIMD (0–3), nie maska;
  - `--att-target-cu` to WGP;
  - maska SE `0x3f` dla Navi31.
- Werdykt: **duży zysk, koszt 2–4 h, ryzyko niskie.** Do zrobienia na 10.0, bez czekania na upgrade. 10.1 to tylko wygoda (Python API dekodera).

- **FP contraction:** w żadnym z 1045 kerneli nie zmienił się statyczny mix f32 fma / mul / add, liczony łącznie z połówkami `v_dual_*`. Brak śladu zmiany kontrakcji, czyli tego, co zepsuło bitowość w rundzie 6.

- **VOPD:** w MMQ Q4_K +497 (więcej parowania f32 add w epilogu 0070), w MMVQ −105. Bez wpływu na wynik (VOPD to te same operacje).
- **Wzrost instrukcji to głównie SALU** (MMVQ: SALU +34 339, VALU −3 065), czyli inne planowanie adresów i pętli. Wpływ na czas `[SZACUNEK: ±1–2%, do zmierzenia]`.

### 3.3 Ryzyko dla bazowych md5
- Na podstawie powyższego: GDN bitowo identyczny (dowód emulatorem). W MMVQ / MMQ / kvq ten sam mix operacji f32 i te same intrynsyki.
- Kolejność sumowania jest w naszych kernelach jawna (DPP, `warp_reduce`), a LLVM bez fast-math nie reasocjuje fadd. **Spodziewam się bitowo tych samych md5** `[SZACUNEK]`.
- Mimo to zmiana ISA w 98% kerneli wymaga twardego testu `greedy.sh` + hash logitów (§10). Statyczne liczniki nie wykluczają zamiany operandów ani innej kolejności w nieobjętych kernelach (rms_norm, quantize, set_rows, topk).

### 3.4 LTO, nowy driver offload, czas przebudowy
- **Zmiana domyślna, której nie ma w release notes.** Z `-###` na tym samym pliku:
  - clang 10.1 kompiluje HIP przez **`--offload-new-driver`** (`clang-linker-wrapper`, `-flto=full` dla urządzenia);
  - 10.0 używa starej ścieżki (`clang-offload-bundler` + `lld` z `lto-partitions=8`).
- Format fatbin w `.o` jest ten sam (`.hip_fatbin`, `__CLANG_OFFLOAD_BUNDLE__`), więc runtime i nasze skrypty ISA działają (sprawdzone `isa2.sh`).
- „Caching partycji LTO” [R1] dotyczy łączenia kodu urządzenia z wielu TU (`-fgpu-rdc` / device LTO). ggml-hip kompiluje bez RDC, więc dla nas cache nie ma czego trzymać `[SZACUNEK]`.
- Pomiar (pełne `-c`, 2 rundy, ta sama maszyna, inne agenty mogły obciążać CPU):

| TU | 10.0 (s) | 10.1 (s) |
|---|---|---|
| mmq-instance-q4_k | 12.46 / 11.99 | 12.38 / 10.89 |
| fattn-kvq | 4.17 / 4.25 | 4.66 / 4.06 |
| mmvq | 71.12 / 66.03 | 80.05 / 69.80 |

  → **brak przyspieszenia przebudowy** dla naszego builda.
- Uwaga z notatki upgrade'owej [R12]: `clang_major` = 24. W naszym drzewie nie ma warunków na wersję clanga, ale skrypty ze ścieżką `core-10.0` (`isa.sh`, `greedy.sh`, `run-llm.sh`) trzeba sparametryzować.

## 5. hipFile / AMD Infinity Storage
- **Wsparcie:**
  - tabela komponentów: „hipFile 0.4.0 ⇒ 0.5.0 | Linux · Instinct” [R1];
  - TheRock Windows: hipFile „Unsupported” [R13].
  - Konsumenckie Radeony nie są wspierane.
- **Wymagania fastpath (`ais-check`)** [R14]:
  - P2PDMA w jądrze;
  - HIP z `hipAmdFileRead/Write`;
  - amdgpu z symbolem `kfd_ais_rw_file`;
  - wolumen xfs albo ext4 (`data=ordered`) **bezpośrednio na partycji NVMe**. LVM, dm-crypt, MD RAID i loop wymuszają fallback POSIX [R15].
- **Nasza maszyna:**
  - `CONFIG_PCI_P2PDMA=y`, ale `grep -c kfd_ais_rw_file /proc/kallsyms` = 0 (amdgpu z jądra 6.8, bez DKMS);
  - `/` stoi na `/dev/mapper/ubuntu--vg-ubuntu--lv` (LVM), a modele leżą na `/`;
  - fastpath wykluczony bez zmiany sprzętu i systemu.
- **Wczytanie modelu (17 GB, czas do pierwszego czatu):**
  - wąskie gardło to odczyt NVMe (PCIe 4.0, rząd 7 GB/s → ≥ ~2.5 s na zimno) `[SZACUNEK]`;
  - kopia przez RAM (memcpy ≥10 GB/s, PCIe 4.0 x16 ~25 GB/s) jest szybsza, więc fastpath oszczędza głównie CPU i page cache, a nie sekundy `[SZACUNEK]`;
  - przy ciepłym starcie (page cache) mmap jest szybszy niż O_DIRECT.
- **Integracja w llama.cpp, gdyby kiedyś:**
  - miejsce: `llama_model_loader::load_all_data`, ścieżka bez mmap z asynchronicznym uploadem;
  - zamiana `read → pinned → hipMemcpyAsync` na `hipFileReadAsync` do bufora backendu;
  - przeszkody: offsety tensorów w GGUF są wyrównane do 32 B (`general.alignment`), a O_DIRECT wymaga 4 KiB. Trzeba by czytać wyrównane zakresy obejmujące wiele tensorów;
  - async fastpath w 0.5.0 „will not retry on the fallback backend” [R1].
- **Offload ekspertów MoE / KV z NVMe:** per token za wolne o rzędy wielkości (wniosek z `research/repos/REPOS-PODSUMOWANIE.md`: PCIe 20–40× za wolne na wagi per token). hipFile tego nie zmienia.
- Werdykt: **nie dotyczy** (ani gfx1100, ani Windows, ani nasz dysk). Koszt integracji 2–3 dni `[SZACUNEK]`, zysk ≈0.

## 6. WSL2 tech preview

### 6.1 Co to jest
- Release notes: WSL2 „Technical preview”; ROCr wykrywa `/dev/dxg` i ładuje `librocdxg` (teraz w artefaktach TheRock, `HSA_ENABLE_DXG_DETECTION`).
  - „Profiling, debugging, and KFD-dependent tooling are not supported in WSL2”.
  - Paczki tylko `.deb` + wheels [R1].
- Znane problemy:
  - zawieszenia przy asercjach po stronie urządzenia, **wprost na RX 7900 XTX** (TheRock#8791);
  - błędy pamięci urządzenia mogą zawiesić proces (HIP 7.16 known issue) [R1].
- Lista GPU dla ROCDXG zawiera RX 7900 XTX/XT/GRE, 7800 XT, W7900/W7800/W7700, RX 9070/9060, R9700 i Ryzen AI Max/300 [R7].
- **Ścieżka runtime:** HIP → ROCr (linuksowy, ten sam co u nas) → `libhsakmt` w wariancie `dxg` (`librocdxg`, źródło `rocm-systems/projects/rocr-runtime/libhsakmt/src/dxg`) → `/dev/dxg` → dxgkrnl → sterownik Adrenalin (WDDM). Nie ma `/dev/kfd` ani amdgpu.
- **Czy nasz build HIP tam ruszy:** tak, w zasadzie. To ten sam linuksowy userspace, a kod GPU nie zależy od runtime `[SZACUNEK]`. W przeciwieństwie do natywnego Windows (PAL) jest tam ROCr, więc `hsa_queue_create`, loader extension itd. istnieją.

### 6.2 Co się dzieje z PM4 (0060) i profilowaniem: z kodu `dxg/wddm/queue.cpp`
- Kolejka AQL działa w jednym z dwóch trybów, zależnie od sterownika:
  - **natywny AQL** (`use_hws && IsAqlSupported()`, Microsoft HWS);
  - **tłumaczenie AQL → PM4 w wątku CPU** (`AqlToPm4Thread`, `"Submission type: PM4 packet (AQL->PM4 translation)"`).
- W trybie tłumaczenia pakiet vendor `AMD_AQL_FORMAT_PM4_IB`, którego używa 0060, jest obsługiwany przez `VendorSpecificAqlToPm4()`:
  - `process_packet = dxg_runtime->vendor_packet_process`, ustawiane tylko przez **`WSLKMT_VENDOR_PACKET=1`** (`openclose.cpp`);
  - **domyślnie IB jest pomijany, a sygnał zakończenia i tak dostaje 0** (`hsakmt_hsa_signal_store_screlease(packet->completion_signal, 0)`). Taśma PM4 zakończy się „sukcesem” bez wykonania żadnego kernela, więc wyniki będą śmieciowe, bez błędu;
  - z `WSLKMT_VENDOR_PACKET=1` IB jest kopiowany przez CPU (`memcpy`) do ramki o ograniczonym rozmiarze. Za duży IB jest znowu cicho pomijany („drop the PM4 payload but still retire the AQL packet”).
- Liczniki: `hsaKmtPmc*` zwracają `NOT_SUPPORTED` (`dxg/perfctr.cpp`). Profilowanie zgodne z release notes: brak.
- **Wniosek dla łatki:** `pm4_enabled()` w 0060 sprawdza dziś tylko env i `GGML_CUDA_CC_IS_RDNA3`. **Trzeba dodać warunek `access("/dev/kfd", F_OK) == 0`** (albo brak `/dev/dxg`), zanim ktokolwiek uruchomi nasz linuksowy build w WSL2. Predykat manifestu: `runtime: rocr-kfd`, a nie samo `rocr`.
- Koszt granicy kernela pod tłumaczeniem w wątku CPU jest nieznany i prawdopodobnie większy niż 2.75 µs na bare metal. Wartość naszych fuzji (mniej kerneli) może tam być **większa** `[SZACUNEK]`.

### 6.3 Wpływ na produkt (Windows AMD)
- Natywny Windows się nie zmienia: TheRock Windows nadal ma ROCR-Runtime, amdsmi, rocprofiler-sdk i hipFile jako „Unsupported” [R13], a HIP na Windows dalej idzie przez PAL (raport 08 §2).
- WSL2 to nie jest droga dla laika (Persona 1). Wymaga:
  - włączonego WSL2;
  - Ubuntu ≥ 24.04 (ROCm CLI [R16]);
  - instalacji ROCDXG z sudo;
  - Adrenalin z obsługą WSL.
- AMD w ROCm CLI na WSL2 i tak wybiera dla Lemonade **`llamacpp:vulkan`**, nie ROCm („WSL2 being the documented case”) [R17].
- Dla Persony 2 (entuzjasta) WSL2 to opcjonalny „tryb zaawansowany”: nasz linuksowy silnik HIP z łatkami kernelowymi, **bez PM4** i bez profilowania. Zysk wobec natywnego Windows to łatki zależne od ROCr poza PM4 (w 08: tylko 0060/0061 są ROCr-only), więc niewiele `[SZACUNEK]`.
- Werdykt: **niski priorytet.** Dodać predykat i blokadę PM4. Nie budować ścieżki WSL2 w fazie 1.

### 6.4 Proponowana zmiana PLAN §4.5 (naniesiona w PLAN.md)
- Wiersz „Sterownik / runtime AMD”, kolumna Windows: zamiast `[SZACUNEK]` fakt z raportu 08: HIP SDK = PAL, nie ROCr.
- Nowy wiersz „AMD przez WSL2 (ROCm 10.1 tech preview)”:
  - ROCr + `librocdxg` → `/dev/dxg` → WDDM;
  - PM4 cicho pomijany (`WSLKMT_VENDOR_PACKET`), więc 0060 wyłączone przez brak `/dev/kfd`;
  - brak PMC, ATT i rocprofv3;
  - znany hang na XTX przy asercjach urządzenia;
  - AMD (ROCm CLI) wybiera tam Vulkan.

## 7. AMD SMI zamiast rocm-smi: do detekcji i telemetrii w aplikacji?
- **Status:** ROCm SMI usunięty ze standardowego buildu TheRock („breaking change”) [R1]. Tabela komponentów: „AMD SMI 27.1.0 | Linux · Instinct/Radeon” [R1].
- **Rozjazd w źródłach.** Blog mówi „Linux and Windows”, ale:
  - TheRock Windows: amdsmi „Unsupported” [R13];
  - docs AMD SMI: „supports Linux bare metal and Linux virtual machine guest” + eksperymentalny backend WSL [R8];
  - na GitHubie otwarta prośba o oficjalne `amd-smi` na Windows (rocm-systems#8553, bez odpowiedzi AMD) [R9].
  Wniosek: **natywnego, redystrybuowalnego AMD SMI dla Windows nie ma.**
- **Backend WSL:**
  - tylko z `-DENABLE_WSL_BACKEND=ON` (domyślnie wyłączony);
  - telemetria przez `librocdxg`;
  - brak per-process i ECC [R1].
- **Licencja:**
  - biblioteka: MIT (`rocm-systems/projects/amdsmi/LICENSE`, „Copyright (c) 2026 Advanced Micro Devices”), redystrybucja z dołączoną notą;
  - **bindingi Rust:** w drzewie (`projects/amdsmi/rust-interface`, crate `amdsmi` 0.1.2, bindgen). `Cargo.toml` ma `license = "Copyright (c) 2019-2024 Advanced Micro Devices, Inc"`, czyli nie SPDX;
  - na crates.io pod nazwą `amdsmi` jest **cudzy** wrapper (joule-profiler, MIT), nie AMD. Dla daemona w Rust: własne FFI albo vendoring crate'u AMD po wyjaśnieniu licencji.
- **Rozmiar i zależności:** `libamd_smi.so.27.1.0` ma 5.3 MB i zależy od dołączonych `librocm_sysdeps_nl_3`, `_nl_genl_3`, `_mnl`.
- **Rekomendacja dla §4.2:**
  - Linux: inwentarz bez admina nadal z sysfs/DRM (nazwa, VRAM `mem_info_vram_total/used`, `pp_dpm_*`, `power_dpm_force_performance_level`, hwmon). Zero zależności i <300 ms;
  - AMD SMI tylko jako **opcjonalny `dlopen`**, gdy jest w systemie, dla bogatszej telemetrii: per-process VRAM, throttling, `perf-level` dla profilowania. ROCm CLI robi tak samo: „probes per-GPU VRAM (via `amd-smi`, or the amdgpu DRM sysfs counters when `amd-smi` is not installed)” [R17];
  - Windows: bez zmian (DXGI + ADLX).
- Koszt 1–2 dni, ryzyko niskie.

## 8. ROCm CLI v0.2.0 + AMD Skills: konkurent czy kanał?
- **ROCm CLI** (`ROCm/rocm-cli`, MIT, Rust; v0.2.0 wydane 2026-10-07; „Tech Preview”) [R17]:
  - jedna binarka na Linux, Windows i WSL2;
  - `rocm install sdk`, `rocm serve <model>` z silnikami **Lemonade** (llama.cpp GGUF, „Ryzen AI or Radeon”) i vLLM (Instinct);
  - TUI z telemetrią;
  - `rocm diagnose` / `rocm fix` z zamkniętym katalogiem awarii ROCm / PyTorch / **llama.cpp**;
  - `rocm diagnose --model` („czy model tu pójdzie”).
- **Konkurencja:**
  - pokrywa się z naszym wejściem L0 + L1 dla AMD: instalacja, diagnoza, „czy model się zmieści”, serwowanie GGUF;
  - **nie robi** pomiaru u użytkownika, strojenia, łatek kerneli ani spekulacji. Lemonade bierze llama.cpp z `lemonade-sdk/llama.cpp` (czasem „releases/latest”, bez pinu).
  Nasz wyróżnik (L2/L3, „ten sam model, szybciej, te same odpowiedzi”) zostaje. Dodać do raportu 01 jako konkurenta AMD-first.
- **Kanał partnerski:** CLI odkrywa zewnętrzne silniki jako pliki `rocm-engine-<engine>` w `<data_dir>/engines/plugins`, ale „selecting one by name from the CLI is not supported while the engine set is limited to the two built-ins” [R18]. Dziś nie da się nas tam podpiąć. Za to idealnie pasuje do rozmowy z AMD (PLAN faza 3 „rozmowy OEM / AMD”): nasz silnik jako trzeci adapter.
- **AMD Skills** (`amd/skills`, MIT) [R19]:
  - katalog: `rocm-doctor`, `local-ai-use`, `local-ai-app-integration`, `lemonade-router-builder`, `quark-install`, `quark-torch-llm-ptq`, `serving-llms-on-instinct`, `serving-llms-on-epyc`, `hyperloom-workload-optimizer`, `magpie-kernel-evaluator`, `tracelens-analysis-orchestrator`;
  - „optimize LLM inference” to skille vLLM/SGLang na **Instinct** (Hyperloom, Magpie, TraceLens). Nie dotyczą llama.cpp na RDNA;
  - skill PC sampling leży w `rocm-systems` (nie w katalogu) i wymaga Instinct (§1.1).
- **Czy nasi agenci mogą ich używać:** tak (MIT, `npx skills add amd/skills --skill rocm-doctor --agent claude-code`).
  - Realnie przydatny: **`rocm-doctor`** (diagnoza środowiska; katalog fixów warto przejrzeć jako wzór dla L0, np. `fix-2-unset-override`, iGPU+dGPU, `/dev/kfd`, WSL2);
  - `magpie-kernel-evaluator` raczej nie (vLLM/SGLang);
  - PC sampling: nie na gfx1100. Nasz odpowiednik to własny skill „ATT na Navi” (flagi z §1.4 + parser w stylu `analyze_pc_sampling.py`).

## 9. Runtime 10.1 a PM4 / ROCr internals (łatka 0060)
- 0060 używa:
  - `hsa_init`;
  - `hsa_system_get_major_extension_table(HSA_EXTENSION_AMD_LOADER, 1, …)` (loader 1.03: `iterate_executables`, `query_host_address`, `loaded_code_object_get_info`, `executable_iterate_loaded_code_objects`);
  - `hsa_queue_create`, `hsa_amd_memory_pool_allocate(… EXECUTABLE_FLAG)`;
  - pakiet vendor `AMD_AQL_FORMAT_PM4_IB`;
  - parser metadanych code object (`hidden_*`) (`patches/0060…:340-731`).
- **Diff nagłówków 10.0 → 10.1 (tarball vs system):**
  - `hsa_ven_amd_loader.h`: **0 zmian**;
  - `amd_hsa_kernel_code.h`, `amd_hsa_signal.h`, `amd_hsa_common.h`: 0 zmian;
  - `amd_hsa_queue.h`: tylko `#define AMD_QUEUE_HAS_V2 1`;
  - `hsa.h`: nowy atrybut `HSA_AMD_SYSTEM_INFO_HOST_ALLOC_DMA_BUF_SUPPORTED`;
  - `hsa_ext_amd.h`: interfejs 1.30 → 1.32 (`HSA_AMD_QUEUE_INFO_READ/WRITE_POINTER`, `hsa_amd_svm_discard_and_prefetch_batch_async`, stała obrazów WDDM). **Same dopiski, nic nie usunięte ani nie przenumerowane.**
- **Wersja ROCr:** `libhsa-runtime64.so.1.21.0` w obu (system 10.0 i tarball 10.1). Release notes też podają „ROCr Runtime | 1.21.0” bez strzałki zmiany [R1].
- **Code object:** metadane `hidden_*` i bity user SGPR naszych kerneli identyczne w 10.0 i 10.1 (§3.2), fatbin w tym samym formacie (§3.4). Parser 0060 i tak odrzuca nieznane rodzaje argumentów (`ARG_UNSUPPORTED` → stara ścieżka grafu), więc ewentualna zmiana jest „bezpieczna, ale wolniejsza”.
- **Zmiany runtime z notatek, potencjalnie istotne:**
  - HIP 7.16 naprawia wyciek sygnałów przy `hipStreamCreate()`;
  - ROCr VMM obsługuje też pule CPU [R1].
  Nic z tego nie dotyka przetwarzania pakietów vendor ani kolejek.
- **Ryzyko złamania PM4 na Linuxie: niskie** `[SZACUNEK]` (źródeł ROCr 10.0 i 10.1 nie diffowałem). **Pod WSL2: wysokie** (§6.2). Test: `pm4_soak.py` + `GGML_HIP_PM4_DEBUG=1` (taśma zbudowana, zero fallbacków „no host copy”).
