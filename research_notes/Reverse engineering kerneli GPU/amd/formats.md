## KQ1. AMDGPU code objects: ELF layout, metadata, kernel descriptor (what to parse first)

### Takeaway
An AMD GPU kernel binary ("code object", `.hsaco`/`.co`) is an ordinary 64-bit ELF with `e_machine = EM_AMDGPU (224)`, ABI version byte 2/3/4 for code-object V4/V5/V6 (V5 is the current default), a `.text` with kernel code, a 64-byte kernel descriptor symbol `<kernel>.kd` in `.rodata` whose `COMPUTE_PGM_RSRC1/2/3` words encode VGPR/SGPR granules, wave32/64, WGP mode and LDS, and a `.note` record `NT_AMDGPU_METADATA` (type 32) holding msgpack with per-kernel `.vgpr_count`, `.sgpr_count`, `.group_segment_fixed_size`, `.wavefront_size`, `.args[]`. Everything is specified in one document, LLVM's AMDGPUUsage.

### Cited Findings
- ELF header: `e_machine` `EM_AMDGPU` = 224; `e_ident[EI_ABIVERSION]`: `ELFABIVERSION_AMDGPU_HSA_V4` = 2, `_V5` = 3, `_V6` = 4; V5 "is the default code object version if not specified"; `EI_OSABI` `ELFOSABI_AMDGPU_HSA` = 64 (also `_PAL` = 65, `_MESA3D` = 66). Code object V2/V3 generation is "no longer supported by this version of LLVM" (LLVM main, 2026-10) — [LLVM AMDGPUUsage](https://llvm.org/docs/AMDGPUUsage.html)
- `e_flags`: `EF_AMDGPU_MACH` mask 0x0ff; `EF_AMDGPU_MACH_AMDGCN_GFX1100` = 0x041; XNACK bits (V4+) mask 0x300 (ON 0x300 / OFF 0x200 / ANY 0x100 / UNSUPPORTED 0); SRAMECC mask 0xc00 (ON 0xc00 / OFF 0x800 / ANY 0x400). Generic-target version in bits 0xff000000 (generic processors exist only on code object V6+). — [LLVM AMDGPUUsage](https://llvm.org/docs/AMDGPUUsage.html)
- Sections: `.text` (SHT_PROGBITS, ALLOC+EXECINSTR, "kernels and the functions they call"), `.rodata`, `.data`, `.bss`, `.note` (SHT_NOTE), `.dynsym`/`.dynstr`/`.hash`/`.dynamic`/`.got`, `.rela.dyn`, `.debug_*`, plus `.amdgpu.info`/`.amdgpu.strtab` (SHF_EXCLUDE). The HSA loader requires an `ET_DYN` object; the backend emits `ET_REL` and `lld` links it to `ET_DYN`. — [LLVM AMDGPUUsage](https://llvm.org/docs/AMDGPUUsage.html)
- Note records: `NT_AMDGPU_METADATA` = 32, vendor "AMDGPU", metadata "encoded as a map in the Message Pack binary data format"; `NT_AMDGPU_KFD_CORE_STATE` = 33 (GPU core-dump state); types 0–31 reserved. — [LLVM AMDGPUUsage](https://llvm.org/docs/AMDGPUUsage.html)
- Symbols: kernel entry = `STT_FUNC` in `.text` (symbol = link name); kernel descriptor = `<link-name>.kd`, `STT_OBJECT`, in `.rodata`; the AQL dispatch packet references the *descriptor* address, not the entry point. LDS variables are `STT_OBJECT` in special section `SHN_AMDGPU_LDS`. — [LLVM AMDGPUUsage](https://llvm.org/docs/AMDGPUUsage.html)
- Relocations: `R_AMDGPU_ABS32` = 6 (S+A), `R_AMDGPU_GOTPCREL` = 7, `R_AMDGPU_REL32_LO` = 10 (`(S+A-P) & 0xFFFFFFFF`), `R_AMDGPU_REL32_HI` = 11 (`(S+A-P) >> 32`), `R_AMDGPU_ABS64` = 3, `R_AMDGPU_RELATIVE64` = 13 (dynamic, B+A). — [LLVM AMDGPUUsage](https://llvm.org/docs/AMDGPUUsage.html)
- Metadata map (`amdhsa.version`): V3 = [1,0], V4 = [1,1], V5 = [1,2] ("Currently 1 ... Currently 2"); V4+ adds `amdhsa.target` = `<target-triple>[-<target-id>]`; V6 = V5 plus `.cluster_dims` (3 integers) in each kernel map. — [LLVM AMDGPUUsage](https://llvm.org/docs/AMDGPUUsage.html) (local rst lines 5839–6010)
- `amdhsa.kernels[]` keys: `.name`, `.symbol` (the `.kd` ELF symbol), `.language` (e.g. OpenCL C, HIP, Assembler), `.args[]`, `.kernarg_segment_size`, `.kernarg_segment_align`, `.group_segment_fixed_size` (LDS bytes), `.private_segment_fixed_size` (scratch bytes), `.wavefront_size` (power of 2), `.sgpr_count`, `.vgpr_count`, `.agpr_count` (GFX908/GFX90A only), `.max_flat_workgroup_size`, `.sgpr_spill_count`, `.vgpr_spill_count`, `.kind` (normal/init/fini), `.max_num_work_groups_{x,y,z}`; V5 adds `.uses_dynamic_stack`, `.workgroup_processor_mode` (GFX10+, controls WGP mode), `.uniform_work_group_size`. — [LLVM AMDGPUUsage](https://llvm.org/docs/AMDGPUUsage.html)
- `.args[]` keys: `.size`, `.offset` (required), `.value_kind` ∈ {by_value, global_buffer, dynamic_shared_pointer, sampler, image, pipe, queue, hidden_* (V5: hidden_block_count_{x,y,z}, hidden_group_size_{x,y,z}, hidden_remainder_{x,y,z}, hidden_grid_dims, hidden_heap_v1, hidden_dynamic_lds_size, hidden_private_base, hidden_shared_base, hidden_queue_ptr)}, `.address_space`, `.is_const/.is_restrict/.is_volatile`, `.pointee_align`. — [LLVM AMDGPUUsage](https://llvm.org/docs/AMDGPUUsage.html)
- Kernel descriptor (64 bytes, 64-byte aligned) layout by byte offset: 0 `GROUP_SEGMENT_FIXED_SIZE` (u32), 4 `PRIVATE_SEGMENT_FIXED_SIZE` (u32), 8 `KERNARG_SIZE` (u32), 16 `KERNEL_CODE_ENTRY_BYTE_OFFSET` (i64, entry must be 256-byte aligned), 44 `COMPUTE_PGM_RSRC3`, 48 `COMPUTE_PGM_RSRC1`, 52 `COMPUTE_PGM_RSRC2`, 56 kernel code properties (u16), 58 `KERNARG_PRELOAD_SPEC_LENGTH` (bits 470:464) / `_OFFSET` (479:471) (GFX90A/GFX942). — [LLVM AMDGPUUsage](https://llvm.org/docs/AMDGPUUsage.html)
- Kernel code properties bits: 0 `ENABLE_SGPR_PRIVATE_SEGMENT_BUFFER`, 1 `ENABLE_SGPR_DISPATCH_PTR`, 2 `ENABLE_SGPR_QUEUE_PTR`, 3 `ENABLE_SGPR_KERNARG_SEGMENT_PTR`, 4 `ENABLE_SGPR_DISPATCH_ID`, 5 `ENABLE_SGPR_FLAT_SCRATCH_INIT`, 6 `ENABLE_SGPR_PRIVATE_SEGMENT_SIZE`, **10 `ENABLE_WAVEFRONT_SIZE32` (GFX10–GFX11; 0 = wave64, 1 = wave32)**, 11 `USES_DYNAMIC_STACK` (V5+). — [LLVM AMDGPUUsage](https://llvm.org/docs/AMDGPUUsage.html)
- `COMPUTE_PGM_RSRC1` bits: 5:0 `GRANULATED_WORKITEM_VGPR_COUNT`; **GFX10–GFX12 wave64: `max(0, ceil(vgprs_used/4) - 1)`; wave32: `max(0, ceil(vgprs_used/8) - 1)`**, `vgprs_used` = highest VGPR referenced + 1, max_vgpr 1..256 (GFX125X wave32 uses /16, up to 1024); 9:6 `GRANULATED_WAVEFRONT_SGPR_COUNT` — on GFX10–GFX12 reserved, must be 0; 13:12 `FLOAT_ROUND_MODE_32`, 15:14 `FLOAT_ROUND_MODE_16_64`, 17:16 `FLOAT_DENORM_MODE_32`, 19:18 `FLOAT_DENORM_MODE_16_64`, 21 `ENABLE_DX10_CLAMP` (GFX9–11), 23 `ENABLE_IEEE_MODE` (GFX9–11), 26 `FP16_OVFL`, **29 `WGP_MODE` (0 = CU mode, 1 = WGP mode, GFX10–12)**, 30 `MEM_ORDERED`, 31 `FWD_PROGRESS`. — [LLVM AMDGPUUsage](https://llvm.org/docs/AMDGPUUsage.html) (local rst lines 6374–6400)
- `COMPUTE_PGM_RSRC2` bits: 0 `ENABLE_PRIVATE_SEGMENT`, 5:1 `USER_SGPR_COUNT`, 7/8/9 `ENABLE_SGPR_WORKGROUP_ID_X/Y/Z`, 10 `ENABLE_SGPR_WORKGROUP_INFO`, 12:11 `ENABLE_VGPR_WORKITEM_ID` (0 = X, 1 = X,Y, 2 = X,Y,Z), 23:15 `GRANULATED_LDS_SIZE` "Must be 0" (CP writes the actual value from the dispatch), 24–30 FP/int exception enables. — [LLVM AMDGPUUsage](https://llvm.org/docs/AMDGPUUsage.html)
- `COMPUTE_PGM_RSRC3` (GFX10–GFX11): 3:0 `SHARED_VGPR_COUNT` (must be 0 for wave32), **9:4 `INST_PREF_SIZE` (GFX11, instruction prefetch, granularity 128 bytes, 0–63)**, 10 `TRAP_ON_START`, 11 `TRAP_ON_END`, 31 `IMAGE_OP`. — [LLVM AMDGPUUsage](https://llvm.org/docs/AMDGPUUsage.html)
- Work-item ID VGPR packing (GFX90A+/GFX11): X in bits 0:9, Y 10:19, Z 20:29 of a single VGPR; Y/Z only if `enable_vgpr_workitem_id` > 0 / > 1. — [LLVM AMDGPUUsage](https://llvm.org/docs/AMDGPUUsage.html)
- Assembler directives (table "AMDHSA Kernel Assembler Directives"): `.amdhsa_kernel <name>` ... `.end_amdhsa_kernel` creates the aligned KD + `<name>.kd` symbol (only valid for OS `amdhsa`); required: `.amdhsa_next_free_vgpr`, `.amdhsa_next_free_sgpr`; others with defaults: `.amdhsa_group_segment_fixed_size` 0, `.amdhsa_private_segment_fixed_size` 0, `.amdhsa_kernarg_size` 0, `.amdhsa_user_sgpr_count` 0, `.amdhsa_user_sgpr_kernarg_segment_ptr` 0, `.amdhsa_wavefront_size32` (default = Target, GFX10–12), `.amdhsa_workgroup_processor_mode` (Target, GFX10–12), `.amdhsa_shared_vgpr_count` 0 (GFX10–11), `.amdhsa_inst_pref_size` 0 (GFX11–12), `.amdhsa_system_sgpr_workgroup_id_x` 1, `.amdhsa_system_vgpr_workitem_id` 0, `.amdhsa_reserve_vcc` 1, `.amdhsa_dx10_clamp` 1 (GFX6–11), `.amdhsa_ieee_mode` 1 (GFX6–11), `.amdhsa_float_denorm_mode_16_64` 3, `.amdhsa_memory_ordered` 1, `.amdhsa_forward_progress` 1, `.amdhsa_uses_dynamic_stack` 0. Also `.amdgcn_target "<triple>-<target-id>"`, `.amdhsa_code_object_version <n>`, `.amdgpu_metadata ... .end_amdgpu_metadata` (YAML with the same keys as the msgpack note). — [LLVM AMDGPUUsage](https://llvm.org/docs/AMDGPUUsage.html) (local rst lines 21813–21995)
- Minimal kernel example in the doc: `.text / .globl hello_world / .p2align 8 / .type hello_world,@function` ... `s_endpgm`, then `.rodata / .p2align 6 / .amdhsa_kernel hello_world / .amdhsa_user_sgpr_kernarg_segment_ptr 1 / .amdhsa_next_free_vgpr .amdgcn.next_free_vgpr / .amdhsa_next_free_sgpr .amdgcn.next_free_sgpr / .end_amdhsa_kernel`, followed by `.amdgpu_metadata` YAML (`.wavefront_size: 64`, `.sgpr_count: 2`, `.vgpr_count: 3`, `.max_flat_workgroup_size: 256`, `.args: - .size: 8 ...`). — [LLVM AMDGPUUsage](https://llvm.org/docs/AMDGPUUsage.html) (local rst lines 22056–22100)
- ISA reference for gfx1100 cited by LLVM as `[AMD-GCN-GFX11-RDNA3]` "RDNA 3 Instruction Set Architecture"; a copy is in the scratchpad (`rdna3-shader-instruction-set-architecture-feb-2023.pdf`, Feb 2023). — [LLVM AMDGPUUsage](https://llvm.org/docs/AMDGPUUsage.html)

### Inferences
- For occupancy reasoning on gfx1100 the two fields that matter are read straight from the KD: `ENABLE_WAVEFRONT_SIZE32` (byte 56, bit 10) and `GRANULATED_WORKITEM_VGPR_COUNT` (byte 48, bits 5:0): real VGPR allocation = (granule+1)×8 for wave32 or (granule+1)×4 for wave64; LDS comes from byte 0 (`GROUP_SEGMENT_FIXED_SIZE`) plus any dynamic LDS at dispatch. `INST_PREF_SIZE` (rsrc3 bits 9:4) is an RDNA3-specific knob worth checking in vendor kernels.
- Because the metadata note is YAML-equivalent to the `.amdgpu_metadata` directive, a round-trip "disassemble -> edit -> reassemble with `clang -x assembler -target amdgcn-amd-amdhsa -mcpu=gfx1100`" is feasible with the KD directives above *(exact assemble command line not quoted in the doc excerpt I retrieved; it is the standard clang driver form)*.

### Gaps
- I did not retrieve the LLVM doc's exact `llvm-mc`/`clang` command example for assembling `.s` to a code object (the page is 585 kB; the section with command lines was not in the fetched windows).
- LDS allocation granularity for GFX11 (bytes per block) was not found in the AMDGPUUsage text I grep'd; the KD only says `GRANULATED_LDS_SIZE` is written by CP.

## KQ2. Fat binaries, offload bundles and the extraction/disassembly toolchain

### Takeaway
HIP host binaries embed device code as a Clang offload bundle (magic `__CLANG_OFFLOAD_BUNDLE__`, entry IDs like `hipv4-amdgcn-amd-amdhsa--gfx1100`) in a `.hip_fatbin` section, optionally zstd/zlib-compressed (`CCOB` header). The supported extraction path in 2025–2026 is `llvm-objdump --offloading [--arch-name=gfx1100] <binary>` (roc-obj-ls/roc-obj-extract were deprecated in ROCm 6.4), then `llvm-objdump -d --mcpu=gfx1100` / `llvm-readelf --notes` on the extracted `.hsaco`.

### Cited Findings
- Bundle format: file begins with the 24-byte magic `__CLANG_OFFLOAD_BUNDLE__`, then number of entries, and per entry: code-object offset, size, ID length, ID; code objects follow the header. Entry ID = `<offload kind>-<triple>-<target id>`; kinds include `host`, `hip`, `hipv4`, `openmp`; host entry is always first; only 4-field triples accepted; target ID syntax `gfx906:sramecc+:xnack+` (features sorted alphabetically). `hipv4` "is used for AMD GPU code objects at ABI V4 or later". Fat binaries "can be loaded from a file or embedded in the host object as a `.hip_fatbin` data section". — [Clang Offload Bundler](https://clang.llvm.org/docs/ClangOffloadBundler.html)
- Compressed bundles (`-compress`): header magic `CCOB`, u16 version (current 3), u16 compression method (zlib or zstd), total size, uncompressed size, 64-bit truncated MD5; env `COMPRESSED_BUNDLE_FORMAT_VERSION=2` for older HIP runtimes. — [Clang Offload Bundler](https://clang.llvm.org/docs/ClangOffloadBundler.html)
- Bundler CLI: `clang-offload-bundler --list` (print bundle IDs), `-unbundle -type=o -inputs=a.o -targets=hipv4-amdgcn-amd-amdhsa--gfx1100 -outputs=a-gfx1100.hsaco`; `-type` ∈ {o, a (archive), ll, bc, ii, ...}; `--allow-missing-bundles`; archive unbundling produces files named `<Parent Bundle Name>-<TargetID>` with `:` replaced by `_`. — [Clang Offload Bundler](https://clang.llvm.org/docs/ClangOffloadBundler.html)
- ROCm 6.4.3 release notes (2025-08-07): "ROCm Object Tooling tools `roc-obj-ls`, `roc-obj-extract`, and `roc-obj` are deprecated in ROCm 6.4 and will be removed in a future release. Functionality has been added to the `llvm-objdump --offloading` tool option to extract all clang-offload-bundles into individual code objects found within the objects or executables passed as input. The `llvm-objdump --offloading` tool option also supports the `--arch-name` option, and only extracts code objects found with the specified target architecture." — [ROCm 6.4.3 release notes](https://rocm.docs.amd.com/en/docs-6.4.3/about/release-notes.html)
- ROCm llvm-objdump doc (page last updated 2026-05-21): `--offloading` = "Display the content of the LLVM offloading section. Extract Clang offload binaries into code objects."; `--disassemble-symbols=<sym1,sym2>`; `--mcpu=<cpu>` (`--mcpu=help` lists CPUs); `-d`, `-D`, `-j/--section`, `-r` (relocs), `-s` (full contents), `-l` (source line numbers), `--show-all-symbols`. `--symbolize-operands` is only AArch64/BPF/PowerPC/X86. — [ROCm llvm-objdump](https://rocm.docs.amd.com/projects/llvm-project/en/latest/LLVM/llvm/html/CommandGuide/llvm-objdump.html)
- HIP compilers doc: "With the `--offloading` flag, [llvm-objdump] can list and extract information from the contents of ROCm binaries ... In current releases, the tool additionally extracts HIP fat-binary bundle entries into standalone code object files." and "The `llvm-readobj` tool, used with the `--offloading` flag, provides a complete listing of HIP fat-binary offload bundle entries." Example compile: `amdclang++ --offload-arch=gfx942 kernel.cpp -o kernel.out`; `gfx1100 — RDNA3 (RX 7900 series)`; static device libs via `-fgpu-rdc` / `--emit-static-lib`. — [HIP compilers](https://rocm.docs.amd.com/projects/HIP/en/latest/understand/compilers.html)
- Legacy roc-obj tooling (still documented; Debian hipcc 5.7.1 man page, April 2025): `roc-obj [-t REGEXP] [-o OUTDIR] [-d] EXECUTABLE...`; `-d` = disassemble with llvm-objdump (`: .s llvm-objdump -d - ;`); extracted files named `<file>:<TargetID>`. — [roc-obj(1)](https://dyn.manpages.debian.org/trixie/hipcc/roc-obj.1.en.html)
- roc-obj-ls/extract URI grammar: `file://<path>#offset=<n>&size=<n>` or `memory://<pid>#offset=&size=`; `roc-obj-ls -v exe` lists bundle number, entry ID, URI; `roc-obj-extract -o - <uri>` writes to stdout; extracted file name `<executable_name>-[pid]-offset-size.co`. Example pipeline: `roc-obj-ls -v <exe> | awk '/gfx906/{print $3}' | roc-obj-extract -o - | llvm-objdump -d - > <exe>.gfx906.isa`; check e_flags: `... | llvm-readelf -h - | grep Flags`. — [HIP obj_tooling.md (rocm-5.0.2)](https://github.com/ROCm-Developer-Tools/HIP/blob/rocm-5.0.2/docs/markdown/obj_tooling.md)
- The HIP runtime itself (ROCm/clr main, 2026-10-17) parses the same magic: `constexpr char const* CLANG_OFFLOAD_BUNDLER_MAGIC_STR = "__CLANG_OFFLOAD_BUNDLE__";` in `hipamd/src/hip_comgr_helper.cpp:29`. `__hipRegisterFatBinary(const void* data)` (`hipamd/src/hip_platform.cpp:180`) reads a `__CudaFatBinaryWrapper` (`magic`, `version` must be 1, `binary`), accepts `__hipFatMAGIC2` ("Normal HIPF path") or a new `kHipkMagic` ("HIPK ... kpack'd binary with external device code", gated by `ROCM_KPACK_ENABLED`), and calls `PlatformState::Instance().StatCO().AddFatBinary(...)`. — [ROCm/clr](https://github.com/ROCm/clr) (local clone `re_amd/clr`)
- `--save-temps` in ROCm HIP docs: "saves the compiler generated intermediate files". The clang driver test for HIP save-temps (`clang -### -ccc-print-bindings --target=x86_64-linux-gnu -nogpulib -save-temps -fno-gpu-rdc -nogpuinc --offload-arch=gfx906 -c`) shows the device chain `clang (amdgpu9.06-amd-amdhsa): .hip -> preprocessed -> bitcode -> bitcode`, then `Offload::Packager` -> `Offload::Linker` producing the fat binary (LLVM main, new offload driver). — [HIP compilers](https://rocm.docs.amd.com/projects/HIP/en/latest/understand/compilers.html); [clang hip-save-temps.hip](https://raw.githubusercontent.com/llvm/llvm-project/main/clang/test/Driver/hip-save-temps.hip)
- `-Rpass-analysis=kernel-resource-usage` emits per-kernel remarks (function name, SGPR/VGPR counts, scratch/spill, occupancy) that TileLang parses from clang output; TileLang exposes `hipcc_remark_flag()` for passing it through hipcc. — [tilelang hip_resource_info](https://tilelang.com/autoapi/tilelang/contrib/hip_resource_info/index.html); backing LLVM pass: [AMDGPUResourceUsageAnalysis.h](https://codebrowser.dev/llvm/llvm/lib/Target/AMDGPU/AMDGPUResourceUsageAnalysis.h.html)

### Inferences
- Practical gfx1100 recipe (2026): `llvm-objdump --offloading --arch-name=gfx1100 libfoo.so` (extracts `.hsaco` files) -> `llvm-readelf --notes x.hsaco` (msgpack metadata incl. vgpr/sgpr/lds) -> `llvm-objdump -d --mcpu=gfx1100 --disassemble-symbols=<kernel> x.hsaco` -> `llvm-objdump -s -j .rodata x.hsaco` to read the 64-byte KD at the `<kernel>.kd` symbol. `/opt/rocm/llvm/bin/` ships all three.
- If a `.hip_fatbin` entry is compressed (`CCOB`), `clang-offload-bundler --unbundle` from the same ROCm LLVM decompresses transparently; manual zstd is not needed.
- Device-side `.s` from `--save-temps` on hipcc is the easiest way to get *annotated* ISA with the `.amdhsa_*` directives and `; NumVgprs/ScratchSize/Occupancy` comments; file-name pattern commonly `<src>-hip-amdgcn-amd-amdhsa-gfx1100.s` *(name pattern unverified in a primary source)*.

### Gaps
- Exact file names that `llvm-objdump --offloading` writes for extracted code objects are not documented on the ROCm pages fetched.
- `llvm-readobj` has no dedicated "dump AMDGPU msgpack metadata as YAML" flag in the fetched docs; `llvm-readelf --notes` prints the note (format of the decoded output not verified here).
- I could not confirm in which ROCm release (if any, as of 7.x) roc-obj-* were actually removed; only "deprecated in 6.4".

## KQ3. Vendor-library kernels: rocBLAS/Tensile, hipBLASLt, MIOpen, CK, AITER, llama.cpp, PyTorch

### Takeaway
rocBLAS ships gfx1100 GEMM kernels as `/opt/rocm/lib/rocblas/library/TensileLibrary_Type_*_gfx1100.co` plus `Kernels.so-000-gfx1100.hsaco` (rocBLAS 7.2.4); kernel names visible in `rocprofv3 --kernel-trace` (`Cijk_Ailk_Bljk_HHS_BH_MT128x128x16_...`) encode the Tensile solution parameters (MT = macro tile M×N×DepthU, then alphabetized `<ABBR><value>` tokens, abbreviation = uppercase letters of the parameter name). MIOpen caches compiled kernels in `$HOME/.cache/miopen` and sqlite `.kdb` system DBs; AITER's hand-written ASM kernels (`hsa/gfx942`, `gfx950`, `gfx1250`) are CDNA-only — nothing for gfx1100.

### Cited Findings
- rocBLAS 7.2.4 (Arch Linux package, 3,715 files) under `/opt/rocm/lib/rocblas/library/`: `Kernels.so-000-gfx1100.hsaco`; `TensileLibrary_Type_BB_HPA_Contraction_l_{Ailk_Bjlk,Ailk_Bljk,Alik_Bjlk,Alik_Bljk}_Cijk_Dijk_gfx1100.co` + matching `.dat`; fallback kernels `TensileLibrary_Type_{BB_HPA,4xi8I_HPA,BS_HPA,CC}_Contraction_l_*_fallback_gfx1100.hsaco`. Pattern: `TensileLibrary_Type_<DataType>_Contraction_l_<Layout>_Cijk_Dijk_<gfxNNNN|fallback_gfxNNNN>.<co|dat|hsaco>`. — [Arch rocblas 7.2.4 file list](https://archlinux.org/packages/extra/x86_64/rocblas/files/)
- A ROCm 5.6 container shows the lazy-loading variant `TensileLibrary_lazy_gfx1100.dat` next to `Kernels.so-000-gfx1100.hsaco`; rocBLAS can be switched to the hipBLASLt backend with `ROCBLAS_USE_HIPBLASLT=1`, which changes which kernels appear in a trace. — [rocBLAS issue 1339](https://github.com/ROCm/rocBLAS/issues/1339); [rocBLAS design notes](https://rocm.docs.amd.com/projects/rocBLAS/en/latest/how-to/what-is-rocblas.html)
- Tensile kernel-name structure: `Cijk_Ailk_Bjlk_SB_MT64x256x16_<PARAMETERS>` — first segment = operation (tensor index strings), then data type (`S` = single, `B` = "can use beta"), `MT<M>x<N>x<DepthU>` macro tile (third number is the unroll depth), then "an alphabetized list of parameter abbreviations and their values". Abbreviations: `MT` MacroTile (= WorkGroup × ThreadTile), `DU` DepthU, `VW` VectorWidth (VW=4 reads a float4), `WG` WorkGroup `[dim0, dim1, LocalSplitU]` (default [16,16,1]), `GSU` GlobalSplitU, `PLR` PrefetchLocalRead, `PGR` PrefetchGlobalRead, `MI` MatrixInstruction, `WGM` WorkGroupMapping (default 8), `KL` KernelLanguage ("Source (HIP) or assembly"), `1LDSB`, `SU` StaggerU (32), `SUS` StaggerUStride (256). — [Tensile kernel parameters](https://rocm.docs.amd.com/projects/Tensile/en/latest/src/conceptual/kernel-parameters.html)

## KQ4. Vulkan path on RADV (llama.cpp Vulkan backend) and Radeon GPU Analyzer

### Takeaway
On Mesa/RADV the compiled ACO ISA for llama.cpp's compute shaders can be dumped with `RADV_DEBUG=shaders` (plus `asm,cs` to limit to compute-stage disassembly and `shaderstats` for SGPR/VGPR/LDS/occupancy), with the shader disk cache disabled via `RADV_DEBUG=nocache` or `MESA_SHADER_CACHE_DISABLE=true`. Radeon GPU Analyzer (RGA) offers offline compilation for gfx1100 (Vulkan GLSL/SPIR-V and OpenCL) and a Binary Analysis mode for code objects, but has no HIP source mode.

## KQ5. Runtime dumping: catching code objects as they are loaded

### Takeaway
Three runtime hooks exist without writing any code: (1) `GPU_DUMP_CODE_OBJECT=1` in the HIP runtime (CLR) dumps every code object at the ISA stage; (2) the ROCr loader honours `LOADER_OPTIONS_APPEND="-dump-code -dump-isa -dump-dir=<dir>"` and writes `amdcode000.hsaco` / `amdcode000.isa` per loaded code object; (3) `rocgdb`'s `info sharedlibrary` lists GPU code objects as `file://...#offset=&size=` or `memory://<pid>#offset=&size=` URIs. For custom hooks the HIP entry points are `__hipRegisterFatBinary` (hip_platform.cpp) and `hipModuleLoadData[Ex]` (hip_module.cpp).

### Cited Findings
- HIP env vars (ROCm docs, latest 2026): `GPU_DUMP_CODE_OBJECT` (default 0) "Dumps code objects"; `AMD_LOG_LEVEL` 0–5 (1 errors, 2 +warnings, 3 +info, 4 +debug, 5 +extra debug), `AMD_LOG_LEVEL_FILE` (default stderr), `AMD_LOG_MASK` (default 0x7FFFFFFF; 0x1 API, 0x2 kernels/copies, 0x8 decoded AQL packets, **0x80 kernel creation and arguments, 0x4000 code creation debug**, 0x2000 raw AQL bytes); `AMD_SERIALIZE_KERNEL` 0–3; `AMD_COMGR_SAVE_TEMPS` (non-zero keeps Comgr temp files "in a platform-specific temp directory"), `AMD_COMGR_EMIT_VERBOSE_LOGS`, `AMD_COMGR_REDIRECT_LOGS` (stdout/stderr/file), `HIPRTC_COMPILE_OPTIONS_APPEND` (e.g. `--gpu-architecture=gfx906:sramecc+:xnack`); `HIP_FORCE_DEV_KERNARG` (default 1, saves 2–3 µs); `GPU_MAX_HW_QUEUES` (default 4); `HSA_CU_MASK` (e.g. `1:0-8`). — [HIP environment variables](https://rocm.docs.amd.com/projects/HIP/en/latest/reference/env_variables.html)
- CLR source (main, 2026-10-17): `rocclr/utils/flags.hpp:150` `release(bool, GPU_DUMP_CODE_OBJECT, false, "Enable dump code object")`; used in `rocclr/device/devprogram.cpp:795` in the `FILE_TYPE_ISA` case: `if (GPU_DUMP_CODE_OBJECT) { dumpCodeObject(std::string{(const char*)isaBinary.first, isaBinary.second}); }` right before `createKernels(...)`. Also `GPU_DUMP_BLIT_KERNELS` ("Dump the kernels for blit manager"). — [ROCm/clr](https://github.com/ROCm/clr) (local clone)
- CLR hook points: `hipModuleLoad` / `hipModuleLoadData` / `hipModuleLoadDataEx` are defined in `hipamd/src/hip_module.cpp:44–55` (and re-exported via `hip_table_interface.cpp:1974–1979` dispatch table); `hipLibraryLoadData` in `hipamd/src/hip_library.cpp:135`; `__hipRegisterFatBinary` in `hipamd/src/hip_platform.cpp:180` (wrapper `{magic, version==1, binary}`; `HIP_ENABLE_DEFERRED_LOADING` env read in `__hipRegisterFunction`). — [ROCm/clr](https://github.com/ROCm/clr) (local clone)
- ROCr loader (ROCR-Runtime main, `runtime/hsa-runtime/loader/executable.cpp`): `LoaderOptions` defines `-help`, `-dump-code` ("Dump finalizer output code object"), `-dump-isa` ("Dump finalizer output to ISA text file"), `-dump-exec` ("Dump executable to text file"), `-dump-all`, `-dump-dir` ("Dump directory"), `-substitute` ("Substitute code object with given index or index range on loading from file"); options are parsed from the load-code-object `options` string **and from `getenv("LOADER_OPTIONS_APPEND")`** (line 1188); dump prefix `amdcode`, file names via `DumpFileName(dir, "amdcode", ext, n)` = `<dir>/amdcode<NNN>.hsaco|.isa|.exec` (3-digit zero-padded counter). `.isa` is produced by `AmdHsaCode::PrintToFile` -> `Print()` which prints notes and calls `PrintDisassembly(...)` on `.text`. Option parser accepts tokens starting with `-`, usage form `-name=[value]`. Also `LOADER_ENABLE_LOGGING` (loader logger) and `HSA_LOADER_ENABLE_MMAP_URI=1` (`core/util/flag.h:203`). — [ROCm/ROCR-Runtime](https://github.com/ROCm/ROCR-Runtime) (local clone)
- ROCgdb manual: "The 'info sharedlibrary' command will show the AMD GPU code objects together with the CPU code objects"; "AMD GPU code objects are loaded into each AMD GPU device separately ... will therefore show the same code object loaded multiple times"; "The HIP runtime currently loads code objects from memory, including when loading modules from a file" (so URIs are `memory://`); `HSA_LOADER_ENABLE_MMAP_URI` "can be used to request that the AMD ROCm runtime attempt to determine the file containing the code object memory" (gives `file://` URIs); `HIP_ENABLE_DEFERRED_LOADING` "can be used to disable deferred code object loading"; set `HSA_ENABLE_DEBUG=1` before runtime init; `info agents`, `info queues`, `info dispatches`; `set amdgpu precise-memory`; `set debug amd-dbgapi`. — [ROCgdb AMD GPU](https://rocm.docs.amd.com/projects/ROCgdb/en/latest/ROCgdb/gdb/doc/gdb/AMD-GPU.html)
- GDB's `solib-rocm.c`: code objects become `so_list` entries whose `so_name` is the URI; `rocm_solib_bfd_open` opens them with BFD target `"elf64-amdgcn"` and requires HSA ABI V3+; `rocm_bfd_iovec_open` parses `file://` (reads via target fileio) and `memory://<pid>` (copies `size` bytes at `offset` from inferior memory into a snapshot "so that an inferior [that] re-uses this memory" does not break GDB). — [binutils-gdb solib-rocm.c](https://gnu.googlesource.com/binutils-gdb/+/refs/heads/binutils-2_41-branch/gdb/solib-rocm.c)
- ROCdbgapi URI definition: `offset` "is a 0-based byte offset to the start of the code object. For a file URI, it is from the start of the file ... defaults to 0"; `size` "For a file URI, if omitted it defaults to the size of the file. It is required for a memory URI"; example `file:///dir3/dir4/file2#offset=0x2000&size=3000`. — [ROCdbgapi Code Objects](https://rocm.docs.amd.com/projects/ROCdbgapi/en/latest/doxygen/html/group__code__object__group.html)
- REA (morluto/rea, local clone): has a Frida layer (`src/frida/FridaInstrumentationManager.ts`, `src/server/registerFridaTools.ts`) but **no AMDGPU/amdgcn/hsaco-specific code** (grep for `amdgpu|amdgcn|hsaco` returned nothing). — [morluto/rea](https://github.com/morluto/rea)

### Inferences
- Lowest-effort universal dump on the 7900 XTX: `LOADER_OPTIONS_APPEND="-dump-all -dump-dir=/tmp/co" ./llama-cli ...` captures every code object the ROCr loader sees (rocBLAS, hipBLASLt, llama.cpp's own, hipRTC output) as `.hsaco` plus a text `.isa` disassembly, independent of which library loaded it. Because the option parser is shared with the `options` argument of `hsa_executable_load_agent_code_object`, this should work for HIP's loads *(not executed here; verify once on the box)*.
- `GPU_DUMP_CODE_OBJECT=1` is the HIP-level equivalent; the output file naming lives in `dumpCodeObject()` which I did not read — check `AMD_LOG_LEVEL=4` output for the path.
- For hipRTC/OpenCL JIT (e.g. MIOpen, Triton-free paths), `AMD_COMGR_SAVE_TEMPS=1 AMD_COMGR_EMIT_VERBOSE_LOGS=1 AMD_COMGR_REDIRECT_LOGS=stderr` keeps the `.bc/.s/.o` Comgr intermediates in `$TMPDIR`.
- An LD_PRELOAD shim exporting `__hipRegisterFatBinary` that writes `wrapper->binary` (the `__CLANG_OFFLOAD_BUNDLE__` blob) to disk, then `dlsym(RTLD_NEXT, ...)`, is the simplest custom hook; `hipModuleLoadData(module, image)` receives either a raw ELF code object or a bundle and is the hook for libraries that load `.co` files at runtime (rocBLAS/Tensile does so). REA's Frida tooling can attach to these symbols, but it offers nothing GPU-aware beyond that.

### Gaps
- `dumpCodeObject()` implementation (file name/location of `GPU_DUMP_CODE_OBJECT` output) was not read.
- Whether `LOADER_OPTIONS_APPEND` is honoured in the released ROCm 7.x `libhsa-runtime64.so` (vs. main) is unverified, as is whether the `.isa` text uses the LLVM disassembler for gfx1100 encodings.

- `cyrozap/ghidra-radeon-f32` is "AMD Radeon F32 processor module for Ghidra" for "the custom 'F32' CPU core used for various management tasks in many AMD Radeon GPUs" — firmware, not shader ISA. — [ghidra-radeon-f32](https://github.com/cyrozap/ghidra-radeon-f32)
- Ghidra's GnuDisassembler extension "provides the ability to leverage the binutils disassembler capabilities for various processors as a means of verifying Sleigh disassembler output" — relevant only if binutils had an amdgcn target. — [Ghidra GnuDisassembler](https://git.sudo.is/mirrors/ghidra/src/branch/master/GPL/GnuDisassembler)
- roc-obj's `-d` disassembles with `llvm-objdump` (not GNU objdump), and the tools are located under `HIP_CLANG_PATH` or `../../llvm/bin`. — [roc-obj(1)](https://dyn.manpages.debian.org/trixie/hipcc/roc-obj.1.en.html)
- `llvm-objdump --mcpu=help` lists available AMDGPU CPUs; `--disassemble-symbols` restricts to named kernels. — [ROCm llvm-objdump](https://rocm.docs.amd.com/projects/llvm-project/en/latest/LLVM/llvm/html/CommandGuide/llvm-objdump.html)
- RGA "Binary Analysis" mode analyzes "pre-compiled binary Code Object files" offline (no driver needed); source-to-ISA correlation for code objects added in RGA 2.15. — [RGA README](https://github.com/GPUOpen-Tools/radeon_gpu_analyzer); [RGA releases](https://github.com/GPUOpen-Tools/radeon_gpu_analyzer/releases)
- Ghidra SLEIGH is the mechanism for adding a new processor (bit-encoding -> assembly + p-code semantics); a worked tutorial exists (PT Swarm, V8 bytecode). — [SLEIGH docs](https://ghidra.re/ghidra_docs/languages/html/sleigh.html); [PT Swarm tutorial](https://swarm.ptsecurity.com/?p=2648)

### Inferences
- For RE of gfx1100 kernels the practical stack is: LLVM tools for disassembly + `llvm-readelf --notes` for metadata + RGA `bin` mode for per-instruction live-VGPR/CFG views + the RDNA3 ISA PDF for encodings/latency. A Ghidra SLEIGH for RDNA3 would be a large project (VOP3/VOPD/VINTERP encodings, 32/64-bit instruction words with literal constants).
- "Decompilation" in the ML-kernel sense is better done by pattern-matching the ISA (ds_load/ds_store for LDS tiling, v_wmma_* for tensor cores, s_waitcnt/s_delay_alu for scheduling, buffer/global load widths) than by waiting for a decompiler that does not exist.
