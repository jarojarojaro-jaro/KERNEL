# Verification: AMD track, "Code object formats and kernel extraction" (formats.md)

Verified 2026-10-17 by an adversarial fact-check pass. Method: each cited URL was fetched (WebFetch); for LLVM AMDGPUUsage (585 kB page, fetch window too small) the local mirror `scratchpad/re_amd/llvm/llvm-project/llvm/docs/AMDGPUUsage.rst` (same document, LLVM main) was grep'd; ROCR-Runtime and CLR claims were checked against the local clones named in the note. Independent WebSearch could NOT be run: the shared per-turn web-search budget was already exhausted when this check started, so "independent evidence" below comes from second primary pages fetched directly (HIP env-var docs, ROCm llvm-objdump docs, Debian man page, obj_tooling.md), not from search engines.

Result: 8/8 load-bearing claims confirmed (two with small wording caveats); 1 extra citation problem found in the rest of the note.

## Confirmed

1. "AMDGPU code objects are ELF with e_machine EM_AMDGPU=224, EI_ABIVERSION 2/3/4 for code object V4/V5/V6 (V5 default), EF_AMDGPU_MACH_AMDGCN_GFX1100=0x041, kernel entry STT_FUNC in .text and a 64-byte STT_OBJECT <kernel>.kd descriptor in .rodata; metadata is a msgpack NT_AMDGPU_METADATA (type 32) note with .vgpr_count/.sgpr_count/.group_segment_fixed_size/.wavefront_size/.args."
   - AMDGPUUsage.rst (LLVM main mirror): `EM_AMDGPU 224` (l.3127); `ELFABIVERSION_AMDGPU_HSA_V4 2 / _V5 3 / _V6 4` (l.3134-3136); `-mcode-object-version=5 ... This is the default code object version` (l.3180); `EF_AMDGPU_MACH_AMDGCN_GFX1100 0x041` (l.3416); `NT_AMDGPU_METADATA 32`, "Metadata in Message Pack" (l.3785/3801); symbol table: `<link-name>.kd STT_OBJECT .rodata Kernel descriptor`, `<link-name> STT_FUNC .text Kernel entry point` (l.3829-3830); KD "Total size 64 bytes" (l.6363). The live https://llvm.org/docs/AMDGPUUsage.html is the rendered form of this file (the first 100 kB fetched matched the mirror's text on generic targets / XNACK defaults).

2. "Kernel descriptor COMPUTE_PGM_RSRC1 bits 5:0 encode VGPR granules as max(0, ceil(vgprs_used/4)-1) for wave64 and ceil(vgprs_used/8)-1 for wave32 on GFX10-GFX12; bit 29 is WGP_MODE; kernel_code_properties bit 10 is ENABLE_WAVEFRONT_SIZE32; RSRC3 bits 9:4 are INST_PREF_SIZE (GFX11, 128-byte granularity); GRANULATED_LDS_SIZE must be 0 and is written by CP."
   - AMDGPUUsage.rst: RSRC1 5:0 table lists exactly "GFX10-GFX12 (wavefront size 64) max(0, ceil(vgprs_used / 4) - 1)" and "(wavefront size 32) max(0, ceil(vgprs_used / 8) - 1)" (l.6374ff); bit 29 `WGP_MODE` GFX10-GFX12 (l.6642); KD bit 458 = kernel_code_properties bit 10 `ENABLE_WAVEFRONT_SIZE32` (l.6332; table lists GFX10-GFX11); RSRC3 GFX10-GFX11 table: `9:4 INST_PREF_SIZE` GFX11 "0..63 with a granularity of 128 bytes" (l.6924); RSRC2 `23:15 GRANULATED_LDS_SIZE Must be 0 ... CP writes directly to COMPUTE_PGM_RSRC2.LDS_SIZE` (l.6834).
   - Caveat (not an error): on GFX12 the RSRC3 field is `11:4 INST_PREF_SIZE` (8 bits, 0..255, 128-byte granularity) — the note correctly scopes 9:4 to GFX11.

3. "HIP fat binaries use the Clang offload bundle format (24-byte magic __CLANG_OFFLOAD_BUNDLE__, entry IDs like hipv4-amdgcn-amd-amdhsa--gfx1100, embedded in a .hip_fatbin section, optional CCOB v3 zlib/zstd compression); clang-offload-bundler --list / -unbundle -type=o operate on them."
   - https://clang.llvm.org/docs/ClangOffloadBundler.html: magic listed as 24 bytes "__CLANG_OFFLOAD_BUNDLE__"; ID grammar `<offload-kind>-<target-triple>[-<target-id>]`, "the bundler only accepts target triples in the 4-field format" (hence `amdgcn-amd-amdhsa-` + `-gfx1100` = the double dash); `hipv4` "Used for AMD GPU code objects with at least ABI version V4 and above"; "embedded in the host code object as a data section with the name .hip_fatbin"; compressed header magic "CCOB", "The current version is 3", method "either zlib or zstd"; `--list` "List bundle IDs in the bundled file", `--unbundle` "Unbundle bundled file into several output files", `-type` o = object. Independent corroboration: CLR `hipamd/src/hip_comgr_helper.cpp:29` defines `CLANG_OFFLOAD_BUNDLER_MAGIC_STR = "__CLANG_OFFLOAD_BUNDLE__"`.
   - Caveat: the literal example string `hipv4-amdgcn-amd-amdhsa--gfx1100` does not appear on the page (its only full example is `openmp-amdgcn-amdhsa-gfx906:sramecc+:xnack+`); it is derived from the stated grammar. The page spells the flag `--unbundle` (double dash); LLVM's option parser accepts the single-dash form the note uses.

4. "roc-obj-ls, roc-obj-extract and roc-obj were deprecated in ROCm 6.4 (release notes dated 2025-08-07); llvm-objdump --offloading now extracts all clang-offload-bundles into individual code objects and supports --arch-name to restrict to one target."
   - https://rocm.docs.amd.com/en/docs-6.4.3/about/release-notes.html: ROCm 6.4.3 dated "2025-08-07"; "`roc-obj-ls`, `roc-obj-extract`, and `roc-obj` are deprecated in ROCm 6.4, and will be removed in a future release"; "Functionality has been added to the `llvm-objdump --offloading` tool option ..."; with `--arch-name` it "only extracts code objects found with the specified target architecture". Independent: ROCm llvm-objdump CommandGuide (last updated 2026-05-21) documents `--offloading` = "Display the content of the LLVM offloading section. Extract Clang offload binaries into code objects." and `--arch-name`.

5. "The ROCr loader reads LOADER_OPTIONS_APPEND and supports -dump-code / -dump-isa / -dump-exec / -dump-all / -dump-dir options, writing amdcode<NNN>.hsaco and .isa files for every code object loaded (ROCR-Runtime main, loader/executable.cpp, 2026-10-17 clone); HIP additionally exposes GPU_DUMP_CODE_OBJECT=1."
   - Local clone `re_amd/rocr/runtime/hsa-runtime/loader/executable.cpp`: options defined at l.135-139 (`dump-code`, `dump-isa`, `dump-exec`, `dump-all`, `dump-dir`, plus `substitute`); `LOADER_DUMP_PREFIX = "amdcode"` (l.167); `getenv("LOADER_OPTIONS_APPEND")` parsed in `LoadCodeObject` (l.1188); per loaded code object `code->SaveToFile(DumpFileName(dir, "amdcode", "hsaco", codeNum))` and `PrintToFile(..., "isa", codeNum)` (l.1242/1247), `"exec"` at l.1322. Independent: HIP env-var reference page lists `GPU_DUMP_CODE_OBJECT` default 0, "Dump code object"; CLR `rocclr/utils/flags.hpp:150` / `devprogram.cpp:795` as the note states.
   - Caveat: the local ROCR-Runtime clone's HEAD commit is dated 2025-08-11 (clone date 2026-10-17 as the note says); the HIP env-var page does not mention LOADER_OPTIONS_APPEND, so whether released ROCm 7.x `libhsa-runtime64.so` still honours it remains unverified (the note already flags this as a gap).

6. "TensileLite/hipBLASLt solution names are decoded by taking the uppercase letters of each parameter name as its abbreviation (PrefetchGlobalRead->PGR, ScheduleIterAlg->SIA), with anchors MT{MacroTile0}x{MacroTile1}x{DepthU} and MI{M}x{N}x{B}, and values encoded as 1/0, n<int>, 0p50, or uppercase strings (AMD ROCm blog, 2026-08-04)."
   - https://rocm.blogs.amd.com/artificial-intelligence/reverse-hipblaslt-tensilelite/README.html: published August 04, 2026, authors Yuchen Lin, Clement Lin, Chunhung Wang; "The prefix keeps only the uppercase letters of the parameter name" (PGR, SIA examples; AFEM collision noted); anchors `MT{MacroTile0}x{MacroTile1}x{DepthU}` (e.g. MT32x16x256) and `MI{M}x{N}x{B}` (e.g. MI16x16x1, no K); values: bool 1/0, negative `n`+magnitude (LWPMn1), float "integer part, then p, then two hundredths digits" (0p50), string = uppercase letters (GSUAMB).

## Refuted with corrections

- Extra 1 (KQ4, line 120): "RGA 2.9.1 also renamed the ROCm OpenCL mode: `-s rocm-cl` was replaced with "Offline OpenCL" `-s opencl`. — [GPUOpen RGA post](https://gpuopen.com/?p=56959)"
  - Refuted as a citation: https://gpuopen.com/?p=56959 resolves to the generic GPUOpen portal home page; it contains nothing about RGA 2.9.1, `-s rocm-cl` or `-s opencl` (the only RGA mention is a 2.15 headline). The rename itself may be true (the note itself marks it "from search snippet; page not fetched") but it is unsupported by the cited URL. Correction: drop this URL; cite the RGA 2.9.1 GitHub release notes (https://github.com/GPUOpen-Tools/radeon_gpu_analyzer/releases/tag/2.9.1) once the rename text is confirmed there, or move the sentence to "unverified".
