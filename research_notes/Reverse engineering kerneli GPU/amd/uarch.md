## Key question 1 — Microbenchmark studies (Chips and Cheese RDNA3/RDNA4/Strix Halo/MI300X, academic CDNA papers, WMMA, Nemes, clpeak)

### Takeaway
The canonical public RDNA3 microarchitecture numbers come from Chips and Cheese's January 2023 RX 7900 XTX article (OpenCL + Nemes's Vulkan suite + clpeak), corrected in June 2023 for Infinity-Fabric power-state effects; the open-source harnesses they used (ChipsandCheese/Microbenchmarks `GpuMemLatency` in OpenCL, Nemes's `gpuperftests` in Vulkan) are directly runnable on a 7900 XTX. Academic CDNA3 (MI300X/MI300A) dissections exist (2025-2026, arXiv) but mostly cover the memory hierarchy and matrix-core/concurrency behaviour at a high level; no public paper reports per-instruction MFMA latencies in cycles for MI300X, and no WMMA-specific RDNA3 microbenchmark with latency numbers was found.

### Cited Findings

**RDNA3 / RX 7900 XTX (Navi 31) — Chips and Cheese, 2023-01-07**
- Cache sizes measured/confirmed: scalar cache 16 KB 4-way; L0 vector 32 KB per CU 32-way (2x RDNA2); L1 256 KB 16-way per shader array (RDNA2: 128 KB); L2 6 MB 16-way (RDNA2: 4 MB); Infinity Cache 96 MB (RDNA2: 128 MB); LDS 128 KB per WGP built from two 64 KB blocks with 32 banks each, 32-bit wide — [Chips and Cheese, Microbenchmarking AMD's RDNA 3](https://chipsandcheese.com/p/microbenchmarking-amds-rdna-3-graphics-architecture)
- Scalar cache load-to-use latency 15.4 ns (RDNA3) vs 17.4 ns (RDNA2); common FP ops 5 cycles latency on RDNA3 (same as prior RDNA; Nvidia 4 cycles) — [same](https://chipsandcheese.com/p/microbenchmarking-amds-rdna-3-graphics-architecture)
- Measured FP32 FMA throughput 62.9 TFLOPS (AMD's press-deck figure 61 TFLOPS at 2.5 GHz); AMD's "123 TFLOPS FP16" is only reachable with specific VOPD packed-math instructions; FP64 is 4 ops/clk per WGP on RDNA3 (8 on RDNA2); reciprocal quarter rate; INT32 multiply ~1/4 of FP32 rate; clocks were locked at 1 GHz for per-clock dual-issue tests — [same](https://chipsandcheese.com/p/microbenchmarking-amds-rdna-3-graphics-architecture)
- Dual issue (VOPD): only wave32 VOPD encodings exist (8 bytes each); dual issue observed mainly for FP32 adds, FMA rarely dual-issued, INT32 has no VOPD form; constraints: operands in the same position cannot share a register bank, destinations cannot both be even or both be odd; each bank has a register cache with three read ports; wave64 can execute a 64-wide wavefront in one cycle when instructions dual-issue — [same](https://chipsandcheese.com/p/microbenchmarking-amds-rdna-3-graphics-architecture)
- Bandwidth: L0 and L1 roughly 2x RDNA2; Infinity Cache 1.8x measured vs 2.7x theoretical (pure read); 384-bit VRAM bus; no absolute GB/s given in the text (charts only) — [same](https://chipsandcheese.com/p/microbenchmarking-amds-rdna-3-graphics-architecture)
- Methods: custom OpenCL microbenchmarks (latency, bandwidth, LDS, dual issue, instruction throughput, single-WGP and occupancy-scaled tests), Nemes's Vulkan-based suite (full-GPU throughput/bandwidth), clpeak (launch latency, FP cross-check), Radeon GPU Profiler for instruction mix (run on RDNA2), AMD ISA manual for VOPD/bank constraints — [same](https://chipsandcheese.com/p/microbenchmarking-amds-rdna-3-graphics-architecture)
- Correction (2023-06-15): Navi 31 manages the Infinity Fabric power state separately from the shader array; with sparse requests the IF clock drops and latency tests overstate. Corrected RX 7900 XTX figures: Infinity Cache 128.4 ns scalar (was 161 ns) / 150.3 ns vector (was 199 ns); VRAM (1 GB test) 221.24 ns scalar / 234.55 ns vector; the author forced a high power state with a triple-monitor setup; L0/L1/L2 (shader-clock domain) showed no notable difference between power states — [Chips and Cheese, Latency testing is hard](https://chipsandcheese.com/p/latency-testing-is-hard-rdna-3-power-saving)
- RX 7600 follow-up: the 7900 XTX takes 58% longer to get data from its Infinity Cache than the 7600 XT, attributed to Navi 31's chiplet (MCD) layout — [Chips and Cheese, RX 7600](https://chipsandcheese.com/p/amds-rx-7600-small-rdna-3-appears) (via search snippet)
- RDNA3 WMMA (AMD GPUOpen, posted 2023-01-10, updated 2024-02-06): theoretical FLOPS/clock/CU for RX 7900 XTX vs RX 6950 XT: FP16 512 vs 256; BF16 512 vs N/A; IU8 512 vs 512; IU4 1024 vs 1024. Only 16x16x16 tiles; intrinsics `__builtin_amdgcn_wmma_{f32,f16,bf16,i32}_16x16x16_{f16,bf16,iu8,iu4}_w{32,64}` (12 total); A/B fragments use 8 VGPRs (FP16/BF16), 4 (IU8), 2 (IU4); C/D use 8 VGPRs in wave32 and 4 in wave64; A/B must be replicated across lanes 0-15 and 16-31 (and 32-63 in wave64); A column-major, B/C/D row-major; `OPSEL` selects half of the VGPR for 16-bit C/D — [GPUOpen WMMA on RDNA3](https://gpuopen.com/learn/wmma_on_rdna3/)

**RDNA4 and Strix Halo (RDNA3.5) — comparison points**
- RDNA4 (Hot Chips 2025, article 2025-09-13): largest parts have 8 MB L2 (RDNA3 6 MB, RDNA2 4 MB); the mid-level L1 is gone; hitting Infinity Cache adds >50 ns over an L2 hit on both RDNA2 and RDNA4; Infinity Fabric 1024 bits/clock => ~2.5 TB/s theoretical Infinity Cache bandwidth — [Chips and Cheese, RDNA4 at Hot Chips 2025](https://chipsandcheese.com/p/amds-rdna4-gpu-architecture-at-hot)
- Strix Halo iGPU (2025-10-31): 2 shader arrays each with 256 KB L1, 2 MB L2, 32 MB Infinity Cache (MALL); Infinity Cache bandwidth just under 1 TB/s measured with Nemes's Vulkan bandwidth test; FCLK 2 GHz => inferred 512 B/cycle GPU-to-fabric path; Infinity Cache latency "slightly higher than discrete cards"; methods: Nemes's Vulkan test, Chester Lam's OpenCL microbenchmarks, OpenCL SVM test (256 MB), Data-Fabric PMU counters — [Chips and Cheese, Strix Halo memory subsystem](https://chipsandcheese.com/p/strix-halos-memory-subsystem-tackling)

**CDNA3 / MI300X — Chips and Cheese, 2024-06-25 (OpenCL microbenchmarks)**
- 8 XCDs x 38 CUs, 4 MB L2 per XCD, 256 MB Infinity Cache across four IODs, 8 HBM3 stacks 5.3 TB/s / 192 GB, boost 2.1 GHz; L1 32 KB per CU, 64 KB LDS per CU; cache line 128 B; Infinity Cache latency ~218 ns; TLB miss penalty ~47.1 ns, latency jump at 64 MB; Infinity Cache bandwidth 11.9 TB/s measured vs 17 TB/s theoretical; global atomics latency ~116 ns to 202.5 ns depending on workgroup pair (high end = different XCDs); INT16 packed double rate, INT32 add not double rate; special-function ops 4 per SIMD cycle — [Chips and Cheese, Testing AMD's Giant MI300X](https://chipsandcheese.com/p/testing-amds-giant-mi300x)

**Academic CDNA dissections (2025-2026)**
- "Dissecting How Die Scaling Breaks GPU Fine-grained Scheduling" (arXiv:2609.24270, submitted 2026-09-21, Fan et al.): lightweight characterization of per-chip compute topology and memory affinity; topology-oblivious CU allocation causes up to 1.33x performance variation; remote accesses raise HBM latency up to 67% and nearly double L2 latency; asymmetry-aware scheduling improves kernels up to 1.22x and multiplexed LLM inference up to 14.3% — [arXiv 2609.24270](https://arxiv.org/abs/2609.24270)
- "Microbenchmark-Driven Analytical Performance Modeling Across Modern GPU Architectures" (arXiv:2605.04178, 2026-05-05, Jarmusch & Chandrasekaran): MI300A model captures Infinity Cache hierarchy, VGPR constraints and occupancy; 0.09% MAE across 27 kernels vs >95% error for naive roofline; MI250X as secondary check — [arXiv 2605.04178](https://arxiv.org/abs/2605.04178)
- "Execution-Centric Characterization of FP8 Matrix Cores, Asynchronous Execution, and Structured Sparsity on AMD MI300A" (arXiv:2602.10262, 2026-02-10, Jarmusch, Vitz, Chandrasekaran): targeted microbenchmarks for FP8 MFMA execution, ACE concurrency and 2:4 sparsity; quantifies occupancy thresholds/fairness/throughput trade-offs; abstract gives no cycle numbers — [arXiv 2602.10262](https://arxiv.org/abs/2602.10262)
- UC Riverside/AMD pointer-chasing study (MI300A, MI300X, MI250X): MI300A and MI300X show nearly identical latency profiles; NPS4 partitioning reduces latency by up to 1.42x in MALL and 1.31x in HBM — [eScholarship 3b8311qq](https://escholarship.org/uc/item/3b8311qq) (search snippet; full text fetch returned empty)

**Open-source harnesses**
- ChipsandCheese/Microbenchmarks (GitHub) contains `GpuMemLatency/` with OpenCL sources: `latency_test.c`, `bw_test.c`, `instruction_rate.c`, `instruction_rate_fp16_kernel.cl`, `instruction_rate_fp64_kernel.cl`, `local_mem_latency_kernel.cl`, `atomic_test.c`, `texturetest.c` (verified in local clone) — [ChipsandCheese/Microbenchmarks](https://github.com/ChipsandCheese/Microbenchmarks)
- Nemes's suite is "GPUPerfTests": Vulkan microbenchmarks for compute throughput and cache/memory characteristics with GUI (OpenGL) and CLI; donated to Chips and Cheese, mirrored as `gpuperftests` under the ChipsandCheese GitHub org (last update seen 2024-07-11) — [nemez.net projects](https://nemez.net/projects/), [ChipsandCheese GitHub](https://github.com/ChipsandCheese)
- clpeak: synthetic peak-throughput/bandwidth/launch-latency benchmark with optional Vulkan backend — [clpeak package page](https://summer.exherbo.org/packages/sys-apps/clpeak/index.html); used by Chips and Cheese for launch latency — [Chips and Cheese RDNA3](https://chipsandcheese.com/p/microbenchmarking-amds-rdna-3-graphics-architecture)

### Inferences
- For a 7900 XTX under headless Ubuntu, the June-2023 power-state lesson is critical: any latency/bandwidth microbenchmark must keep the Infinity Fabric clocked up (busy-loop a second queue, or pin `power_dpm_force_performance_level` to `profile_standard`/`STABLE_STD` as the rocprofv3 docs require for counters, see Q3), otherwise Infinity Cache/VRAM latencies read ~25-30% too high.
- Dual-issue (VOPD) is the single most RDNA3-specific thing a kernel RE should look for in disassembly: `v_dual_*` opcodes, wave32 only, bank/parity constraints; the Chips and Cheese finding that FMA "rarely dual-issues" explains why measured FP32 falls well short of AMD's 123 TFLOPS marketing number.
- WMMA on RDNA3 doubles FP16 matrix FLOPS/clock/CU vs RDNA2 but not INT8/INT4; for llama.cpp-style int8 dot products the RDNA3 advantage is smaller than for FP16.

### Gaps
- No published RDNA3 WMMA microbenchmark with instruction latency (cycles) or achieved vs peak throughput was found; needs own measurement (e.g., `v_wmma_f16_16x16x16_f16` chains in inline asm).
- Chips and Cheese absolute L0/L1/L2 latency (ns) and per-level bandwidth (TB/s) for the 7900 XTX live in charts; the text only gives the corrected Infinity Cache/VRAM numbers.
- No paper reporting MFMA per-instruction latency in cycles for MI300X was found (the 2026 MI300A FP8 paper may contain them, but the abstract does not).
- `mixbench` and `gpu-burn` were not researched (not found in the tool-call budget).

## Key question 2 — Thread trace: `rocprofv3 --att` + rocprof-trace-decoder; SQTT in RGP

### Takeaway
`rocprofv3 --att` (ROCprofiler-SDK thread trace, decoded by the ROCprof Trace Decoder plugin, bundled since ROCm 7.13) is officially supported on gfx1100/gfx1101/gfx1102 in "trace-only" mode (instruction timing and occupancy, no streamed perfcounters) and produces per-instruction `Hitcount/Latency/Stall/Idle` CSVs plus JSON for ROCprof Compute Viewer; RGP's instruction-timing SQTT view for OpenCL/HIP compute is Windows-only, and on Linux RGP is Vulkan-only via RADV's `MESA_VK_TRACE=rgp`.

### Cited Findings
- Supported devices (ROCm 10.1.0 docs): CDNA4 gfx950, CDNA3 gfx942, CDNA2 gfx90a = Full; RDNA2 gfx1030, RDNA3 discrete gfx1100/gfx1101/gfx1102, RDNA3.5 gfx1150-gfx1153, RDNA4 gfx1200/gfx1201 = Trace-only; trace-only architectures do not support `--att-perfcounters`; MI100 gfx908 expected to work but not validated — [ROCm docs 10.1.0, Using thread trace](https://rocm.docs.amd.com/projects/rocprofiler-sdk/en/docs-10.1.0/how-to/using-thread-trace.html); same table in develop docs — [develop](https://rocm.docs.amd.com/projects/rocprofiler-sdk/en/develop/how-to/using-thread-trace.html)
- ROCprofiler-SDK overview quote: "RDNA2-4 (gfx10-12) are trace-only and don't support `--att-perfcounters`"; gfx11/gfx12 counter collection needs a stable power state — [What is ROCprofiler-SDK (v1.4.1)](https://rocm.docs.amd.com/projects/rocprofiler-sdk/en/latest/what-is-rocprofiler-sdk.html)
- Pipeline: tracing via ROCprofiler-SDK thread-trace service -> decoding via ROCprof Trace Decoder API (runs automatically after the app exits) -> visualization in ROCprof Compute Viewer — [ROCm docs 10.1.0](https://rocm.docs.amd.com/projects/rocprofiler-sdk/en/docs-10.1.0/how-to/using-thread-trace.html)
- Decoder: `rocprof-trace-decoder` is a plugin library for rocprofiler-sdk that transforms binary `.att` data; "Users on ROCm >= 7.13 do not need to install this package separately"; source moved to `ROCm/rocm-systems/projects/rocprof-trace-decoder`; supported devices "AMD Radeon: 6000, 7000, 9000 series; AMD Instinct: MI200 and MI300 series"; headers MIT, binaries under a custom EULA; custom path via `rocprofv3 --att --att-library-path /path/to/lib -- ./a.out`; API `rocprofiler_thread_trace_decoder_create(&decoder, "/opt/rocm/lib")` — [rocprof-trace-decoder README](https://github.com/ROCm/rocprof-trace-decoder) (local clone)
- Decoder changelog 0.1.6: "s_barrier behaved differently on RDNA2/3: time spent waiting on s_barrier was mostly reported as idle time; it is now changed to stalled/wait time starting from the last executed instruction (an approximation, closer to what RDNA4 and MI series report)"; fixed scalar prefetch classification (was SALU) — [rocprof-trace-decoder CHANGELOG](https://github.com/ROCm/rocprof-trace-decoder/blob/main/CHANGELOG.md) (local clone)
- Prerequisites (develop docs via search): install ROCprof Trace Decoder; aqlprofile needs a ROCm 7.x build, otherwise rocprofv3 fails with `INVALID_SHADER_DATA` or "Agent not supported" — [develop docs](https://rocm.docs.amd.com/projects/rocprofiler-sdk/en/develop/how-to/using-thread-trace.html) (search snippet)
- Commands: default `rocprofv3 --att -d <output_dir> -- <application_path>`; Instinct perfmon streaming `rocprofv3 --att --att-activity 8 -- <app>`; Radeon `rocprofv3 --att --att-simd-select 0x0 -- <app>`; marker-controlled `rocprofv3 --att --selected-regions -d <dir> -- <app>` with `roctxProfilerResume(0)` / `roctxProfilerPause(0)`; resource mode `--att-resource-mode {default,hsa,code-object}` (default = code-object); env `ROCPROFILER_SQTT_FORCE_HSA`, `ROCPROF_ATT_PARAM_RESOURCE_MODE` — [ROCm docs 10.1.0](https://rocm.docs.amd.com/projects/rocprofiler-sdk/en/docs-10.1.0/how-to/using-thread-trace.html), [develop](https://rocm.docs.amd.com/projects/rocprofiler-sdk/en/develop/how-to/using-thread-trace.html)
- Flags: `--att-target-cu` (0-15, typical 1; "CU" = WGP on Navi), `--att-shader-engine-mask` (default 0x1), `--att-simd-select` (gfx9 bitmask default 0xF; Navi SIMD_ID, docs conflict: text says Radeon defaults to 3, table says 0x0), `--att-buffer-size` (1 MB-2 GB, default 96 MB, shared across SEs), `--att-serialize-all`, `--att-perfcounters` / `--att-perfcounter-ctrl` (1-32) / `--att-activity` (1-16) — gfx9 only, SQ block only, `--att-no-detail` (occupancy without instruction detail), `--att-gpu-index`, `--att-consecutive-kernels N` (incompatible with `--selected-regions`), `--kernel-iteration-range`, `--kernel-include-regex` / `--kernel-exclude-regex`; by default only the first instance of each kernel is traced; input-file keys use snake_case (`att_target_cu`, ...) — [ROCm docs 10.1.0](https://rocm.docs.amd.com/projects/rocprofiler-sdk/en/docs-10.1.0/how-to/using-thread-trace.html)
- Output files: `stats_*.csv` (per-kernel per-instruction summary), `ui_output_agent_{agent_id}_dispatch_{dispatch_id}/` (JSON for RCV), `.att` (raw SQTT), `.out` (code object binaries for ISA tools). `stats_*.csv` columns: `Codeobj`, `Vaddr`, `Instruction`, `Hitcount`, `Latency` (= Stall + Issue cycles on gfx9, Stall + Execute cycles on gfx10+), `Stall` (pipe could not issue, often TCP/LDS backpressure), `Idle` (gap between previous completion and this issue: arbiter loss, register dependency, I-cache miss), `Source` (needs debug symbols) — [ROCm docs 10.1.0](https://rocm.docs.amd.com/projects/rocprofiler-sdk/en/docs-10.1.0/how-to/using-thread-trace.html)
- Empty stats troubleshooting: trace covers one CU per SE (`att-target-cu`); if a dispatch does not reach that CU, launch more waves, change target CU, widen `--att-shader-engine-mask` (e.g., 0x11111111 or 0xFFFFFFFF, risk of packet loss/full buffer), or use `HSA_CU_MASK` to mask out all other CUs — [ROCm docs 10.1.0](https://rocm.docs.amd.com/projects/rocprofiler-sdk/en/docs-10.1.0/how-to/using-thread-trace.html)
- ROCprof Compute Viewer (RCV): Qt desktop GUI, Linux; loads `ui_output_agent_*` via Menu > Import > Rocprofv3 UI Output or `./rocprof-compute-viewer <dir>`; raw `.att`/`.out` import needs a decoder-enabled build and `scripts/generate_snapshot.py` (needs `llvm-objdump`, `pyelftools`, `-g` for source mapping); requires aqlprofile/ROCprofiler-SDK from ROCm 7.0+, decoder bundled since ROCm 7.13 — [RCV how-to](https://rocm.docs.amd.com/projects/rocprof-compute-viewer/en/latest/how-to/using_compute_viewer.html)
- RCV views: Instructions (ISA) with `Hitcount` and `Latency` (mean/sum per wave or all waves, or per loop iteration), arrows linking memory ops to the `s_waitcnt` that waits on them; Compute Unit view per wave by SIMD-slot with wave-state colouring (IDLE/EXEC/STALL/WAIT tab being folded into Counters); Utilization per SIMD by VALU/VMEM/SCALAR/OTHER showing ISSUE (gfx9) or EXECUTION (gfx10+) and bubbles; Hotspot histogram (EXECUTE+STALL only); Flamegraph per CU/SIMD over source+ISA; Global view of all waves per SE; Occupancy per SE; Kernel Dispatches; Counters (SQ counters, derived `MFMA_util`, `VALU_util`, `LDS_util`); Summary view "available with AMD Instinct MI200 and MI300" — [RCV views reference](https://rocm.docs.amd.com/projects/rocprof-compute-viewer/en/latest/reference/views.html)
- ROCm's own workflow: system level (rocprof-sys) -> kernel level (rocprof-compute or `rocprofv3 --pmc`) -> instruction level (`rocprofv3 --att` + RCV) "only if kernel analysis points to an instruction-level issue, such as LDS bank conflicts"; ATT traces are large and serialize the traced kernel — [Choosing the right ROCm profiling tool](https://rocm.docs.amd.com/en/latest/components/profiling-tools-selection.html)

**RGP / SQTT**
- RGP v2.7.1 manual: graphics APIs DX12 and Vulkan; compute APIs OpenCL and HIP; graphics OSes Windows 11 and Ubuntu 24.04 LTS (Vulkan only); compute OSes Windows 11 only; GPUs RX 9000/7000/6000/5000 and Ryzen APUs; with 25.20-based Linux drivers AMDVLK is no longer shipped and RADV is default, and the Radeon Developer Panel cannot capture Vulkan apps with these drivers — workaround: 25.10-based driver or RADV's built-in `MESA_VK_TRACE` capture (not supported by RDP) — [RGP manual index](https://gpuopen.com/manuals/rgp_manual/rgp_manual-index/)
- Historical: RGP 1.14 (2022) added RX 7000 support and HIP profiling "available on the Windows platform"; RGP 2.1 added "Instruction timing capture and visualization for OpenCL and HIP applications (requires RDNA-based hardware and at least a 22.10-based driver)" and pre-issue stall visualization — [RGP 1.14 notes](https://gpuopen.com/learn/rgp_1_14/), [RGP 2.1 via search](https://gpuopen.com/rgp/)
- RGP Instruction timing pane: per-instruction issue latency from hardware (no recompilation/instrumentation); `Latency` = time from issuing an instruction to issuing the next; bars coloured green (hidden by VALU), yellow (SALU/SMEM), hatched (both), red (unhidden); black hatch = pre-issue stall; hit count; instruction cost = share of total issue latency; `s_waitcnt` long issue interval reflects waiting on earlier loads (the load itself shows short latency); data limited to a single shader engine and a subset of its CUs; per-instruction average active lanes (divergence) from RX 9000 series, needs "Enable shader instrumentation" in RDP; `s_swappc`/`s_setpc` call targets listed for HIP kernels that call functions; `s_code_end` shows zero hits on RDNA — [RGP manual, Instruction timing](https://gpuopen.com/manuals/rgp_manual/rgp_manual-events_windows/)
- RADV SQTT capture env vars (Linux, Vulkan only): `MESA_VK_TRACE=rgp`, `MESA_VK_TRACE_FRAME`, `MESA_VK_TRACE_TRIGGER`, `MESA_VK_TRACE_PER_SUBMIT`, `RADV_THREAD_TRACE_BUFFER_SIZE` (default 32 MiB), `RADV_THREAD_TRACE_INSTRUCTION_TIMING` (on by default), `RADV_THREAD_TRACE_INSTRUCTION_TIMING_SE_MASK` (default 0xFFFFFFFF), `RADV_THREAD_TRACE_CACHE_COUNTERS` (GFX10+, on), `RADV_THREAD_TRACE_QUEUE_EVENTS`, `RADV_SPM_COUNTERS_CONFIG`, `RADV_PROFILE_PSTATE` (`standard|min_sclk|min_mclk|peak`, default `peak`) — [Mesa envvars](https://docs.mesa3d.org/envvars.html)

### Inferences
- On a 7900 XTX under Linux the realistic instruction-timing path for HIP/ROCm kernels (e.g., llama.cpp HIP backend) is `rocprofv3 --att` + RCV; for llama.cpp's Vulkan backend the path is RADV `MESA_VK_TRACE=rgp` then opening the `.rgp` in RGP (RGP itself runs on Linux for Vulkan). RGP's OpenCL/HIP instruction timing is not available on Linux.
- Because RDNA is "trace-only", the ATT `Counters` view and `--att-activity` are not usable on gfx1100; the useful RCV views are Instructions/ISA, Compute Unit timeline, Utilization, Hotspot, Flamegraph and Occupancy.
- Decoder changelog shows RDNA2/3 token semantics differ from RDNA4/MI (e.g., s_barrier accounting is approximated), so stall/idle attribution on gfx1100 should be read as approximate.

### Gaps
- Whether `rocprofv3 --att` on gfx1100 requires the `STABLE_STD` power level (documented for PMC counters) is not stated explicitly for ATT.
- The exact `--att-simd-select` default on Radeon is contradictory in the docs (3 vs 0x0); must be tested.
- Radeon Developer Panel compute (OpenCL/HIP) capture on Linux: no 2025-2026 source confirms it; the current manual lists compute OS support as Windows 11 only.

## Key question 3 — Profilers: rocprofv3 counters on gfx11 vs CDNA, rocprof-compute, rocprof-sys, PC sampling, RGA, Mesa stats

### Takeaway
rocprofv3 counter collection works on gfx1100 but the counter set is small compared with CDNA (local `counter_defs.yaml` snapshot: 80 entries for gfx11 — 40 raw counters in SQ/GL2C/GRBM/TA blocks and 40 derived — vs 419 for gfx942), it requires forcing the `STABLE_STD`/`profile_standard` power level, and PC sampling is Instinct-only (host-trap MI200+, stochastic MI300+); rocprof-compute (3.10.0) does not support discrete RDNA3 at all ("development to support Radeon (RDNA) GPUs is in progress"), though it does support Strix Halo gfx1150-1153. Offline tools (RGA for ISA/live-VGPR, RADV `RADV_DEBUG=shaderstats`, llama.cpp `GGML_VK_PIPELINE_STATS`) fill the static-analysis side on gfx1100.

### Cited Findings

**rocprofv3 counters (`--pmc`)**
- Syntax `rocprofv3 --pmc SQ_WAVES GRBM_COUNT GRBM_GUI_ACTIVE -- <app>`; repeating `--pmc` creates separate passes; "Job fails if the entire set of counters can't be collected in a single pass"; output `pmc_n/counter_collection.csv` (and `pass_n/`); list counters with `rocprofv3 --list-avail` (or `rocprofv3 -L`, `rocprofv3-avail`); kernel replay beta `--replay-mode kernel --kernel-replay-beta-enabled` (cannot be combined with `--att`, PC sampling, `--spm`) — [Using rocprofv3](https://rocm.docs.amd.com/projects/rocprofiler-sdk/en/latest/how-to/using-rocprofv3.html)
- RDNA3 (Navi3x) and RDNA4 (Navi4x): the `AUTO` performance mode gates off the perfmon clock in some hardware blocks, disabling PMC profiling; set `STABLE_STD`: `sudo sh -c 'echo profile_standard > /sys/class/drm/card<N>/device/power_dpm_force_performance_level'` (restore `auto`) or `sudo /opt/rocm/bin/amd-smi set --gpu <N> --perf-level STABLE_STD` (verify `amd-smi metric --gpu <N> --perf-level`, restore `--perf-level AUTO`); described as "a hardware feature enablement requirement" — [Using rocprofv3](https://rocm.docs.amd.com/projects/rocprofiler-sdk/en/latest/how-to/using-rocprofv3.html)

## Key question 4 — Wave-level debugging: rocgdb, umr, amdgpu_top, debugfs

### Takeaway
rocgdb officially supports gfx1100/gfx1101/gfx1102 (and gfx11-generic) with full wave-as-thread debugging (`info agents/queues/dispatches/threads/lanes`, breakpoints in kernels, `stepi`, vector/scalar register groups, `set amdgpu precise-memory on`), with gfx1100-specific limitations only for cooperative groups and CU masking; umr (root/debugfs, LLVM disassembly) can halt live waves and dump `SQ_WAVE_*` registers, SGPRs/VGPRs and the full kernel from a KFD user queue (documented example literally uses an `ollama` process on gfx1201), and its `--profiler` gives a crude halt-sampling PC histogram.

### Cited Findings
- rocgdb supported architectures: gfx900, gfx906, gfx908, gfx90a, gfx942, gfx950, gfx1010, gfx1011, gfx1012, gfx1030, gfx1031, gfx1032, gfx1100, gfx1101, gfx1102, gfx1150, gfx1151, gfx1153, gfx1200, gfx1201, gfx1250 plus generic gfx9-generic, gfx9-4-generic, gfx10-1-generic, gfx10-3-generic, gfx11-generic, gfx12-generic — [ROCgdb AMD GPU docs](https://rocm.docs.amd.com/projects/ROCgdb/en/latest/ROCgdb/gdb/doc/gdb/AMD-GPU.html)
- Requirements: compatible AMD GPU driver with recognised debug-support level, compatible firmware per agent, compatible ROCm runtime; HIP fully supported (compile `-g` with `--offload-arch`, e.g. `amdclang++ -x hip --hip-link -O0 -g --offload-arch=gfx900`); assembly kernels supported; OpenCL/Fortran only as minimal pseudo-language (Code Object V3, DWARF 4) — [ROCgdb AMD GPU docs](https://rocm.docs.amd.com/projects/ROCgdb/en/latest/ROCgdb/gdb/doc/gdb/AMD-GPU.html)
- Commands: `info agents`, `info queues`, `info dispatches`, `info threads`, `info lanes`, `info sharedlibrary` (code objects as URIs), `queue find`, `dispatch find`; `set amdgpu precise-memory on|off`, `set amdgpu precise-alu-exceptions on|off`; `info registers general|vector|scalar|system`; flag registers `$mode`, `$status`, `$trapsts`; pseudo registers `$vcc`, `$exec`, `$flat_scratch`, `$xnack_mask`; convenience variables `$_wave_id`, `$_dispatch_pos`, `$_thread_workgroup_pos`, `$_lane_workgroup_pos`; `set scheduler-locking`; `set debug amd-dbgapi on`; `show amdgpu version` — [ROCgdb AMD GPU docs](https://rocm.docs.amd.com/projects/ROCgdb/en/latest/ROCgdb/gdb/doc/gdb/AMD-GPU.html)
- Wave control: a wave halts on `S_SETHALT 1`, on `$status` change, or on a signal; kernel breakpoints can be pending until the code object loads, `tbreak` recommended to reduce stop storms; single-stepping can appear to hang (Ctrl-C cancels); do not place breakpoints inside `s_clause` sequences — [ROCgdb AMD GPU docs](https://rocm.docs.amd.com/projects/ROCgdb/en/latest/ROCgdb/gdb/doc/gdb/AMD-GPU.html)
- Env vars: `HSA_ENABLE_DEBUG=1`, `HIP_ENABLE_DEFERRED_LOADING=0`, `HSA_LOADER_ENABLE_MMAP_URI=1`, `HSA_ENABLE_SDMA=0` — [ROCgdb AMD GPU docs](https://rocm.docs.amd.com/projects/ROCgdb/en/latest/ROCgdb/gdb/doc/gdb/AMD-GPU.html)
- Limitations: up to 4 hardware write watchpoints, no read/access watchpoints, DMA writes not reported; precise memory reporting off by default; no inferior function calls, gdbserver, OpenMP extensions, sanitizers; SR-IOV unsupported; "Cooperative groups and CU masking are unsupported on gfx1100, gfx1101, and gfx1102"; GPU core dumps never while rocgdb attached — [ROCgdb AMD GPU docs](https://rocm.docs.amd.com/projects/ROCgdb/en/latest/ROCgdb/gdb/doc/gdb/AMD-GPU.html)
- AMD HLRS training (2025-05-08, Giacomo Capodaglio): rocgdb tracks upstream GDB master, "focus on source line debugging, no symbolic variable debugging yet"; use `rocgdb --args`; compile with `-ggdb`; `set amdgpu precise-memory on` to get exceptions reported precisely; `info threads` (alias `i th`) lists GPU waves as "AMDGPU Wave" entries; `info agents` shows devices/SIMDs/max waves, `info queues` shows HSA queues with AQL packets read/written, `info dispatches` shows grid/group size and kernel; `AMD_LOG_LEVEL=3`; rocgdb usable with `-tui`, `cgdb -d rocgdb`, `gdbgui -g /opt/rocm/bin/rocgdb`; exercises at github.com/amd/HPCTrainingExamples/tree/main/Rocgdb; docs at `/opt/rocm<-version>/share/doc/rocgdb/rocgdb.pdf` — [HLRS 2025 Debugging with Rocgdb (PDF)](https://fs.hlrs.de/projects/par/events/2025/GPU-AMD/day4/13.Debugging_with_Rocgdb.pdf)
- Waves map to GDB threads with IDs in agent:queue:dispatch:wave format with work-group coordinates — [Tsukuba 2025 rocgdb PDF](https://www.ccs.tsukuba.ac.jp/wp-content/uploads/sites/14/2025/09/16.-Rocgdb_Debugger.pdf) (search snippet)
- umr: userspace debugging/diagnostic tool for AMD GPUs via the amdgpu kernel driver (limited driverless PCI mode); reads/writes MMIO registers, analyzes wavefronts, ring contents, performance tracking; supports SI onwards; needs kernel >= 4.10; builds with pciaccess, ncurses, libdrm, llvm (for disassembly; `UMR_NO_LLVM` to disable), sdl2 for GUI; `chmod +s $(which umr)` for non-root use with a warning that untrusted access "may lead to system compromises, instability, and hardware damage"; docs at umr.readthedocs.io — [umr README](https://gitlab.freedesktop.org/tomstdenis/umr) (local clone, HEAD 2026-10-15)
- umr wave status: `umr --waves [<ring> | uq | vmid@addr.size | none]`; output per `seN.shN.cuN.simdN.waveN` with `ixSQ_WAVE_STATUS`, `ixSQ_WAVE_PC_LO/HI`, `ixSQ_WAVE_EXEC_LO/HI`, `ixSQ_WAVE_HW_ID`, `ixSQ_WAVE_INST_DW0/1`, `ixSQ_WAVE_GPR_ALLOC`, `ixSQ_WAVE_LDS_ALLOC`, `ixSQ_WAVE_TRAPSTS`, `ixSQ_WAVE_IB_STS`, `ixSQ_WAVE_M0`, `ixSQ_WAVE_MODE`; SGPRs and (GFX9+) VGPRs printed when the wave is halted; `-O halt_waves` issues an SQ_CMD halt (display freezes while umr runs; a resume is issued at clean exit; after SIGKILL re-run with halt_waves to resume); `-O bits` alternative format; `-O skip_gprs`; `-O full_shader` disassembles the entire kernel from the dispatch packet; KFD user-queue example: `umr --user-queue kfd,comm=ollama,queue=2 --waves uq -O full_shader,halt_waves` prints `regCOMPUTE_PGM_RSRC1/2/3` and the full `s_load_b64 ... s_wait_kmcnt ...` listing (gfx1201 in the example); warning that `--waves` with GFX power gating enabled may hang the GPU if issued very rapidly — [umr docs wave_status.rst](https://gitlab.freedesktop.org/tomstdenis/umr/-/blob/main/doc/sphinx/source/wave_status.rst) (local clone), [umr man page](https://mankier.com/1/umr)
- umr profiler: `--profiler [pixel=|vertex=|compute=]<nsamples> [ring]` repeatedly issues SQ_CMD halt/resume and records where waves halt; a ring is considered halted when rptr/wptr do not move for 500 µs ("may not be enough for compute tasks resulting in race conditions"); output is a per-shader list of addresses/opcodes with hit counts and percentages (LLVM disassembly) — [umr docs profiler.rst](https://gitlab.freedesktop.org/tomstdenis/umr/-/blob/main/doc/sphinx/source/profiler.rst) (local clone)

- ROCR Debug Agent (`rocr_debug_agent`): prints wave states/registers on GPU faults without a full debugger — [ROCR Debug Agent user guide](https://rocm.docs.amd.com/projects/rocr_debug_agent/en/docs-6.2.2/conceptual/user-guide.html) (search listing only; not fetched)

### Inferences
- For reverse engineering a closed kernel (e.g., a vendor library) on gfx1100, rocgdb is the most practical path: break on dispatch (`info dispatches`, pending breakpoint on the kernel symbol), `x/20i $pc`, `info registers vector`, `stepi`, and `info sharedlibrary` to locate the loaded code object URI (`memory://` unless `HSA_LOADER_ENABLE_MMAP_URI=1`).
- umr complements rocgdb when the process cannot be stopped (hang) or when you want a raw hardware view (`SQ_WAVE_GPR_ALLOC`, `COMPUTE_PGM_RSRC1/2/3` as actually programmed); its KFD `--user-queue kfd,comm=<proc>` mode works for ROCm compute queues, as the `ollama` example shows.
- umr's `--profiler` is a poor substitute for PC sampling on compute (500 µs halt heuristic, race conditions), so on RDNA3 ATT remains the primary instruction-timing source.

### Gaps
- No gfx1100-specific rocgdb walkthrough (all tutorials target MI200/MI300); the docs give no gfx1100 limitation beyond cooperative groups/CU masking.
- `debugfs amdgpu tracepoints` (ftrace `amdgpu_*` events) were not researched.
- The ROCR debug agent page was not fetched.

## Key question 5 — Correlating ISA with time: finding stalls, s_waitcnt analysis, occupancy limits, roofline on RDNA

### Takeaway
On gfx1100 the only hardware-timed per-instruction source is ATT (`stats_*.csv` `Latency/Stall/Idle` + RCV's memory-op-to-`s_waitcnt` arrows and Hotspot/Flamegraph), plus RGP's instruction-timing pane for Vulkan via RADV SQTT; occupancy must be reasoned from `--save-temps` resource metadata (VGPR/SGPR/LDS) and the ATT Occupancy/Kernel Dispatches views, because rocprof-compute's speed-of-light/roofline and PC sampling are not available on discrete RDNA3.

### Cited Findings
- ATT per-instruction semantics: `Latency` = Stall + Execute cycles on gfx10+; `Stall` = hardware pipe could not issue (TCP/LDS backpressure); `Idle` = gap from previous instruction completion to this issue (arbiter loss, register dependency, I-cache miss); `Hitcount` summed over traced waves; `Source` line needs debug symbols — [ROCm docs 10.1.0, thread trace](https://rocm.docs.amd.com/projects/rocprofiler-sdk/en/docs-10.1.0/how-to/using-thread-trace.html)
- RCV: arrows link memory operations to the `s_waitcnt` that waits on them (per wave); Hotspot counts EXECUTE+STALL (not IDLE); Flamegraph supports weighting by Total or Non-hidden latency after hidden-latency analysis; Occupancy per SE and Kernel Dispatches views — [RCV views](https://rocm.docs.amd.com/projects/rocprof-compute-viewer/en/latest/reference/views.html)
- RGP: `s_waitcnt` shows long issue interval reflecting time waiting on earlier loads; latency bars coloured by what hid them (VALU/SALU/unhidden) and pre-issue stall hatch; instruction cost = share of total shader issue latency; data limited to one SE and some CUs — [RGP manual, Instruction timing](https://gpuopen.com/manuals/rgp_manual/rgp_manual-events_windows/)
- Stochastic PC sampling (Instinct only) reports per-sample `Stall_Reason` such as `WAITCNT`, `OTHER_WAIT`, `ALU_DEPENDENCY`, `NO_INSTRUCTION_AVAILABLE` and `arb_state_issue_*` / `arb_state_stall_*` fields — [Using PC sampling](https://rocm.docs.amd.com/projects/rocprofiler-sdk/en/latest/how-to/using-pc-sampling.html)
- Counters usable for stall attribution on gfx11 (snapshot): `SQ_WAIT_INST_ANY`, `SQ_WAIT_INST_LDS`, `SQ_WAIT_ANY`, `SQ_INST_LEVEL_LDS`, `SQ_INST_CYCLES_VMEM`, derived `ALUStalledByLDS`, `LdsLatency`, `WAVE_DEP_WAIT`, `WAVE_ISSUE_WAIT`, `LDSBankConflict`, `OccupancyPercent`, `MeanOccupancyPerCU` — [counter_defs.yaml](https://github.com/ROCm/rocprofiler-sdk/blob/amd-mainline/source/share/rocprofiler-sdk/counter_defs.yaml) (local clone, 2025-08 snapshot)
- Compiler-side scheduling knobs that change the s_waitcnt picture (RADV/ACO): `ACO_DEBUG=force-waitcnt`, `force-waitdeps`, `nosched`, `nosched-ilp`, `nosched-vopd`, `liveinfo` (register demand before scheduling) — [Mesa envvars](https://docs.mesa3d.org/envvars.html)
- Roofline/speed-of-light: rocprof-compute roofline micro-benchmarks need MI200+; RDNA support "in progress"; Strix Halo gfx1150-1153 supported since 3.7.0/3.8.0 — [What is ROCm Compute Profiler](https://rocm.docs.amd.com/projects/rocprofiler-compute/en/develop/what-is-rocprof-compute.html)
- Peak numbers for a hand-built 7900 XTX roofline: 62.9 TFLOPS FP32 measured; WMMA FP16 512 FLOPS/clk/CU theoretical; Infinity Cache ~128-150 ns, VRAM ~221-235 ns latency (2023 corrected) — [Chips and Cheese RDNA3](https://chipsandcheese.com/p/microbenchmarking-amds-rdna-3-graphics-architecture), [GPUOpen WMMA](https://gpuopen.com/learn/wmma_on_rdna3/), [Chips and Cheese latency correction](https://chipsandcheese.com/p/latency-testing-is-hard-rdna-3-power-saving)
- ATT trace limitations relevant to correlation: one CU per SE traced, only first instance of each kernel traced by default, traced kernel serialized, buffers 96 MB default; `--att-no-detail` for occupancy-only runs — [ROCm docs 10.1.0, thread trace](https://rocm.docs.amd.com/projects/rocprofiler-sdk/en/docs-10.1.0/how-to/using-thread-trace.html)

### Inferences
- A workable gfx1100 recipe: (1) `hipcc --save-temps` / `llvm-objdump -d` to get ISA and `.amdhsa_next_free_vgpr`/`sgpr`/`group_segment_fixed_size` metadata -> compute theoretical occupancy (RDNA3: 1536 VGPRs per SIMD lane in wave32 terms, 16 waves/SIMD max — **[unverified here; take from ISA guide]**); (2) `rocprofv3 --pmc SQ_WAVES SQ_WAVE_CYCLES SQ_BUSY_CYCLES SQ_WAIT_INST_ANY SQ_INST_LEVEL_LDS` with `profile_standard` to get achieved occupancy and wait fractions; (3) `rocprofv3 --att --att-shader-engine-mask 0x3F` (6 SEs on Navi 31 — **[unverified]**) on the hot kernel and read `stats_*.csv` sorted by `Latency*Hitcount`, then open RCV to follow `s_waitcnt` arrows back to the VMEM/LDS instruction that caused the wait.
- Because trace-only mode omits SQ counter streaming, "why" a stall occurred on gfx1100 is inferred from the instruction type preceding the `s_waitcnt` (VMEM vs LDS vs SMEM counters `vmcnt/lgkmcnt`), not from hardware stall reasons as on MI300 stochastic sampling.

### Gaps
