## KQ1. What REA is (version, license, stars, providers, Evidence model, targets, platforms)

### Takeaway
REA is an MIT-licensed Node.js CLI + MCP server (`rea-agents` npm, version 6.5.0 in the clone on 2026-10-17, ~300.7k GitHub stars) that wraps caller-supplied analysis engines (Hopper, Ghidra, IDA, GNU objdump, Rizin, GDB, Frida, Cutter bridge, pwntools) and returns every result as an "Evidence" record with SHA-256 artifact identity, limitations and unknowns. It is a generic native/JS/.NET/Android/firmware tool; nothing in its README, docs index or website mentions GPU, CUDA, HIP, AMD or shaders.

## KQ2. Does any REA provider understand AMDGPU code? (Ghidra, Rizin, GNU objdump vs llvm-objdump, pwntools layout)

### Takeaway
No REA provider disassembles AMDGPU: Ghidra ships no AMDGPU/GCN processor, Rizin has no amdgpu arch plugin, and GNU objdump has no amdgcn BFD target. The only working path is pointing `REA_OBJDUMP_COMMAND` at `llvm-objdump` for the `symbols`/`section_headers`/`file_headers`/`relocations`/`disassemble` operations (llvm-objdump auto-detects `gfx1100` from ELF `e_flags`), while `dwarf` and `architectures` operations break because they pass GNU-only `-W`/`-i` flags; `inspect_binary_layout` hard-rejects any ELF whose `e_machine` is not 62 (x86-64), so it cannot open an `EM_AMDGPU` (224) code object at all.

### Inferences
- `REA_OBJDUMP_COMMAND=/opt/rocm/llvm/bin/llvm-objdump` is a workable hack for the five operations whose flags exist in llvm-objdump (`-f -h -t -r -d -D`); because REA never passes `--mcpu`, correctness relies entirely on llvm-objdump's `tryGetCPUName()` from `e_flags` — which the LLVM source confirms for `EM_AMDGPU`, so a gfx1100 code object disassembles without extra flags. `dwarf` (`-W…`) and `architectures` (`-i`) will error, and REA's Evidence will be labelled "GNU objdump" even though llvm-objdump ran (identity is hard-coded; no `--version` probe).
- The raw `-d` listing from llvm-objdump will include the `.kd` kernel-descriptor bytes as `.long`/`.byte` data (AMDGCN pretty printer) and will not decode the msgpack note; use `llvm-readelf --notes` (outside REA) for `.vgpr_count`/`.sgpr_count`/`.group_segment_fixed_size`.
- Ghidra via REA could at best import an AMDGPU code object with `REA_GHIDRA_LANGUAGE_ID="DATA:LE:64:default"` (the `DATA` processor exists) to read sections/symbols/bytes (`read_bytes`, `list_segments`) with no disassembly — not verified in this session; Ghidra's ELF loader may still refuse an unknown `e_machine` 224 or map it oddly.
- Because `inspect_binary_layout` rejects `e_machine != 62` before pyelftools is even imported, the "pyelftools parses EM_AMDGPU" question is moot inside REA.

- Whether any community Ghidra AMDGPU/GCN/RDNA sleigh module exists in 2025-2026 could not be searched (WebSearch budget exhausted). The official processor list has none; treat "no Ghidra AMDGPU support" as confirmed for stock Ghidra 12.1.x only.
- `rz-asm -L` output was not run (no Rizin install here); the plugin-directory listing is the evidence, and the GitHub tree page notes it may be partial.
- GNU binutils' lack of an `amdgcn` BFD target was not independently fetched (search blocked); it is consistent with REA docs calling `-i` output "BFD targets compiled into the installed binary".

## KQ3. Host-side uses that work: Ghidra on stripped host binaries, fatbin extraction, Frida hooks, GDB/rocgdb

### Takeaway

### Inferences
- For llama.cpp (static fatbin), the kernel→host mapping lives in the HIP module constructor: every kernel's host stub is registered through `__hipRegisterFunction(modules, hostFunction, deviceFunction, deviceName, ...)`, so decompiling the `.init_array` constructor in `libggml-hip.so` with Ghidra via REA yields a `hostFunction` → mangled `deviceName` table; `xrefs` to `hipLaunchKernel`/`__hipPushCallConfiguration` from the ggml op dispatchers (e.g. mul_mat_q / flash-attention template instances) then give launch-site → kernel-name mapping. (The `hipLaunchKernel`/`__hipPushCallConfiguration` lowering of `<<<>>>` was not fetched from a source this session.)
- A Frida script hooking `__hipRegisterFatBinary` can read `args[0]` as `__CudaFatBinaryWrapper` (`magic` at +0 == 0x48495046, `binary` at +8) and dump from `binary` the bytes starting with `__CLANG_OFFLOAD_BUNDLE__`; since the wrapper has no size field, the script must parse the bundle header (count + per-entry offset/size, per the Clang docs' binary layout) or dump a generous range and let `clang-offload-bundler --list` validate it. Hooking `hipModuleLoadData(args[1])` covers hipRTC/Tensile-style dynamic loads (image pointer, again size-less: parse the bundle or ELF headers). Hooking `hsa_code_object_reader_create_from_memory(ptr, size)` in `libhsa-runtime64.so` gives size explicitly — plausible but the CLR path to that HSA call was not traced in this session.
- `REA_GDB_COMMAND=rocgdb` should work mechanically: ROCgdb is upstream GDB plus ROCdbgapi, REA only needs a GDB/MI3 prompt and `-gdb-set auto-load off`; GPU-specific commands (`info agents`, `info queues`, `info dispatches`, wave breakpoints) would be sent through `gdb_console`. Not tested; no source confirms MI3 in ROCgdb explicitly, but "ROCgdb 16.3" strongly suggests a GDB 16 base (MI3 exists since GDB 9).
- `--nx` disables `.gdbinit`, which is fine; but rocgdb needs `libamd_comgr.so.1` and `rocm-dbgapi` present on the Ubuntu Server box, and the inferior must be launched under rocgdb (or attached) for GPU dispatches to be visible.
- rocBLAS/Tensile dispatch: `librocblas.so` is a normal x86-64 ELF; Ghidra via REA can trace the solution-selection logic (strings with Tensile kernel names, `hipModuleLoadData` / `hipModuleGetFunction` call sites); the Tensile code objects themselves (`.co` files or embedded) still need llvm-objdump.

### Gaps
- The CLR path from `amd::Program::build/load` down to `hsa_code_object_reader_create_from_memory` / `hsa_executable_load_agent_code_object` was not fetched (ROCclr `device/rocm/rocprogram.cpp`); the HSA hook point is therefore marked unverified.
- ROCgdb's exact upstream GDB version and explicit GDB/MI support statement were not found in the fetched README/docs (only "based on GDB" and the "16.3" doc label).
- No REA docs or tests show a GDB session with a non-stock GDB binary; `REA_GDB_COMMAND=rocgdb` is untested.

## KQ4. Vulkan side (SPIR-V / GLSL shaders in llama.cpp Vulkan, RADV)

### Takeaway
REA has no SPIR-V, GLSL or shader tooling at all; for llama.cpp's Vulkan backend the SPIR-V is generated from `.comp` GLSL by `glslc` at build time and embedded as byte arrays in `libggml-vulkan`, so the right tools are `spirv-dis`, RGA (`-s vk-offline-spv`), and RADV's `RADV_DEBUG=shaders,asm,cs` / `MESA_SPIRV_DUMP_PATH` dumps; REA's only contribution is Ghidra `read_bytes` to carve the embedded SPIR-V blobs out of the host library.

### Cited Findings
- REA's docs index lists guides for native, Go, Rust, ELF layout, crashes, JS/Electron, .NET, Android, Apple, Harmony, firmware, WASM, EVM, browser, captures, process capture — no SPIR-V/GLSL/shader guide — [docs/index.md](https://github.com/morluto/rea/blob/main/docs/index.md)

### Inferences
- Because the per-shader `.cpp` files embed SPIR-V as data, the compiled `libggml-vulkan.so` contains the SPIR-V modules in `.rodata`; Ghidra via REA can locate them by the SPIR-V magic `0x07230203` (REA `read_bytes` + `list_segments`) and `address_to_file_offset` gives the carve offset — but `dd`/`objcopy` + `spirv-dis` finish the job outside REA. - REA's Frida integration could hook `vkCreateShaderModule` in `libvulkan.so`/the RADV ICD to dump `VkShaderModuleCreateInfo.pCode/codeSize` at runtime — a generic Frida use, not REA-specific; not verified.

## KQ5. Concrete recipe: inventory kernels in libggml-hip.so, extract gfx1100 code object, disassemble, map launch sites

### Takeaway
A workable 2026 pipeline is: REA (`inspect_binary_layout` / Ghidra) on the x86-64 host library to find `.hip_fatbin` and launch sites → `llvm-objcopy`/`clang-offload-bundler` (outside REA) to carve the `hipv4-amdgcn-amd-amdhsa--gfx1100` ELF → `llvm-readelf --notes` + `llvm-objdump -d` (optionally through `REA_OBJDUMP_COMMAND`) for kernel metadata and ISA → Ghidra decompile of the `__hipRegisterFunction` constructor to tie host stubs to kernel names → optional Frida/rocprofv3 at runtime to see which kernels actually launch for Qwen3-27B. Steps marked [unverified] were not executed here.

### Cited Findings
Recipe (commands assembled from the sources cited in KQ2–KQ3; every flag traced to a source unless marked):

1. Host ELF layout (REA, pwntools engine). `REA_PWNTOOLS_PYTHON=/abs/venv/bin/python rea inspect-binary-layout /abs/path/libggml-hip.so --json` or MCP `{"name":"inspect_binary_layout","arguments":{"path":"/abs/path/libggml-hip.so","detail":"summary"}}` then `inspect_analysis_view` for the `.hip_fatbin` section's file offset/size — [docs/binary-diagnostics.md](https://github.com/morluto/rea/blob/main/docs/binary-diagnostics.md). Alternative with GNU objdump: `rea inspect-with-objdump /abs/path/libggml-hip.so section_headers` (`-h`) — [docs/reverse-engineering-tools.md](https://github.com/morluto/rea/blob/main/docs/reverse-engineering-tools.md). The section name `.hip_fatbin` is the documented embedding location — [ClangOffloadBundler](https://clang.llvm.org/docs/ClangOffloadBundler.html)
2. Carve the bundle [outside REA; flags unverified this session]: `llvm-objcopy --dump-section .hip_fatbin=fatbin.bin libggml-hip.so` (or `objcopy -O binary --only-section=.hip_fatbin`). 3. 4. Kernel inventory + resource usage (outside REA): `llvm-readelf --notes ggml-hip.gfx1100.co` prints the `AMDGPU` note `NT_AMDGPU_METADATA` (type 32) msgpack map: `amdhsa.kernels[]` with `.name`, `.symbol`, `.vgpr_count`, `.sgpr_count`, `.agpr_count`, `.group_segment_fixed_size` (LDS bytes), `.private_segment_fixed_size` (scratch), `.wavefront_size`, `.max_flat_workgroup_size`, `.sgpr_spill_count`, `.vgpr_spill_count`, `.kernarg_segment_size`; `llvm-readelf -s` lists `<kernel>.kd` descriptor objects in `.rodata` — [LLVM AMDGPUUsage](https://llvm.org/docs/AMDGPUUsage.html); [llvm-readelf](https://llvm.org/docs/CommandGuide/llvm-readelf.html). 5. Disassemble: `llvm-objdump -d ggml-hip.gfx1100.co` (CPU auto-detected from `e_flags` 0x041 → gfx1100; add `--disassemble-symbols=<mangled name>` to limit to one kernel) — [llvm-objdump.cpp](https://github.com/llvm/llvm-project/blob/main/llvm/tools/llvm-objdump/llvm-objdump.cpp); [llvm-objdump CommandGuide](https://llvm.org/docs/CommandGuide/llvm-objdump.html). ## KQ6. Limitations and alternatives: where dedicated tools must take over; REA caveats

### Takeaway
For the GPU half of the problem REA is at best a thin wrapper around `llvm-objdump`; ISA-level work (disassembly, register/occupancy stats, live GPU state, kernel profiling) belongs to `llvm-objdump`/`llvm-readelf`, `rocprofv3`, `rocgdb`, RGA and `umr`. REA's operational caveats (Linux `ps` requirement, caller-installed providers, 16 MiB provider capture, 10 MiB MCP reply, Ghidra 12.1.x + JDK 21, pwntools 4.15.0 pinned) all apply on the user's Ubuntu Server box.

### Cited Findings
- REA Linux prerequisite: "REA's shared process supervisor requires a procps-compatible `ps` on REA's `PATH` for ownership checks before launching a child. Ghidra, JADX, firmware tools and static JavaScript/Electron analysis use these checks... A missing or incompatible command causes a refusal before the supervised child starts." — [docs/installation.md](https://github.com/morluto/rea/blob/main/docs/installation.md)
- REA never installs providers: "REA setup never installs or upgrades Node.js, npm, Homebrew, Java, Ghidra, IDA, JADX, Kuna, Binwalk, or Unblob"; Ghidra needs "an existing Ghidra 12.1.x installation and a 64-bit JDK 21 or newer" — [SKILL.md](https://github.com/morluto/rea/blob/main/.agents/skills/reverse-engineer-anything/SKILL.md); [rea.tools/guides/native/](https://rea.tools/guides/native/)
- Output limits: objdump/Rizin/GDB/Frida captures "retained up to a 16 MiB combined limit"; MCP results prepared "within the pinned stdio client's 10 MiB" buffer, override with `REA_MCP_MAX_RESPONSE_BYTES` and a client `StdioClientTransport({ maxBufferSize })`; `inspect_binary_layout` has "32 MiB input, 64 MiB reply, 1 MiB combined diagnostics and 30-second owned command deadline", `REA_PWNTOOLS_MAX_INPUT_BYTES` up to 1 GiB — [docs/reverse-engineering-tools.md](https://github.com/morluto/rea/blob/main/docs/reverse-engineering-tools.md); [docs/mcp-contracts.md](https://github.com/morluto/rea/blob/main/docs/mcp-contracts.md); [docs/binary-diagnostics.md](https://github.com/morluto/rea/blob/main/docs/binary-diagnostics.md)
- Session-retirement rule: "unrestricted Rizin and Cutter commands, GDB console commands, Rizin debugger start/close, and GDB debugger close retire any active binary analysis session... call `open_binary` explicitly before continuing analysis"; "An active Ghidra analysis session must be closed explicitly before an external mutation can run" — [docs/reverse-engineering-tools.md](https://github.com/morluto/rea/blob/main/docs/reverse-engineering-tools.md)
- Security posture: GDB console and Rizin commands "run with the REA process user's security context and may access files, the network, or perform other actions"; Frida scripts run with the target's authority — [docs/reverse-engineering-tools.md](https://github.com/morluto/rea/blob/main/docs/reverse-engineering-tools.md); [docs/frida-instrumentation.md](https://github.com/morluto/rea/blob/main/docs/frida-instrumentation.md)
- Dedicated tools: `rocprofv3 --kernel-trace`, `--hip-trace`, `--hsa-trace`, `--memory-copy-trace`, `--scratch-memory-trace`, `--pmc`, `--list-avail`, `--replay-mode kernel --kernel-replay-beta-enabled`, `-E/--extra-counters` YAML — [rocprofv3 docs](https://rocm.docs.amd.com/projects/rocprofiler-sdk/en/latest/how-to/using-rocprofv3.html); RGA `-s bin` for pre-compiled code objects, `-s vk-offline-spv` for SPIR-V, outputs ISA, live-register analysis, CFG, resource stats — [radeon_gpu_analyzer](https://github.com/GPUOpen-Tools/radeon_gpu_analyzer); ROCgdb "standard GDB commands for both CPU and GPU code debugging", requires `rocm-dbgapi` — [ROCgdb README-ROCM](https://github.com/ROCm/ROCgdb/blob/amd-master/README-ROCM.md); LLVM `llvm-objdump`/`llvm-readelf` for ISA + metadata — [LLVM AMDGPUUsage](https://llvm.org/docs/AMDGPUUsage.html)

### Inferences
- Division of labour: REA = host-side static analysis with provenance + process/Frida orchestration; LLVM tools = code-object inventory/ISA; rocprofv3 = which kernels run and their VGPR/SGPR/LDS/duration; rocgdb (optionally through REA's GDB/MI session) = wave-level stepping; RGA = offline recompilation/what-if; umr = raw hardware wave/register state (needs root + amdgpu debugfs).
- On the headless Ubuntu Server, Hopper (GUI-oriented) and IDA (Windows) are impractical; Ghidra headless (`analyzeHeadless`, which REA drives) is the realistic REA provider, plus the objdump/pwntools/Frida/GDB paths.
