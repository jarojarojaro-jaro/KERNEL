## KQ1. Tensile / rocBLAS / hipBLASLt: how Tensile generates assembly from YAML, the kernel naming scheme, tuning flow, RDNA weaknesses, hipBLASLt tuning tables

### Takeaway
Tensile is a Python generator (`KernelWriterAssembly.py`) that emits GCN/RDNA assembly directly from a parameter dictionary; the kernel name encodes the macro tile, DepthU, matrix-instruction shape and an alphabetized list of abbreviated parameters, so a rocprof kernel name can be decoded back into the tiling. hipBLASLt adds a per-shape "solution index" selection that can be overridden by a tuning file; indices are only valid for one (architecture, library version) pair, which is exactly how Strata ships its gfx1100 tables.

### Cited Findings
- Kernel naming scheme (official docs, Tensile "latest", read 2026-10-17): example name `Cijk_Ailk_Bjlk_SB_MT64x256x16_<PARAMETERS>`; `Cijk_Ailk_Bjlk` = operation/index layout, `SB` = data type (S = single) + beta support, `MT64x256x16` = macro tile 64x256 with the third number being the unroll depth `DepthU`, followed by an alphabetized list of parameter abbreviations — [Tensile docs: Kernel parameters](https://rocm.docs.amd.com/projects/Tensile/en/latest/src/conceptual/kernel-parameters.html)
- Abbreviations and defaults from the same page: `MT` MacroTile (= WorkGroup x ThreadTile), `DU` DepthU (default -1, = LoopUnroll x SplitU), `GRVW` GlobalReadVectorWidth (-1), `PGR` PrefetchGlobalRead (True, "outer loop prefetches global data one iteration ahead"), `PLR` PrefetchLocalRead (1, "inner loop prefetches local data one iteration ahead"), `LRVW` LocalReadVectorWidth (-1), `VW` VectorWidth (-1; "VectorWidth=4 implies that a thread will read a float4"), `WG` WorkGroup ([16,16,1] = dim0, dim1, LocalSplitU), `WGM` WorkGroupMapping (8, order in which work-groups compute C, affects caching), `GSU` GlobalSplitU (1, split summation across work-groups), `MI` MatrixInstruction ([]), `LDSB` 1LDSBuffer (0), `SU` StaggerU (32), `SUS` StaggerUStride (256), `SUM` StaggerUMapping (0), `LPA`/`LPB` LdsPadA/B (0), `TLDS` TransposeLDS (0) — [Tensile docs: Kernel parameters](https://rocm.docs.amd.com/projects/Tensile/en/latest/src/conceptual/kernel-parameters.html)
- Name generation code (`Solution.getNameMin`, Tensile @ e8a8999e): name = `ProblemType_` + `MT%ux%ux%u_` (MacroTile0, MacroTile1, DepthU) + `MI%ux%ux%ux%u_` (MatrixInstM, N, K, B) + `SE_`/`SN_` (LdcEqualsLdd) + sorted abbreviated params; value abbreviation rules: bool -> `1`/`0`, negative int -> `n1`, strings -> uppercase letters only, lists joined with `_`, floats as `1p50` — [Tensile/SolutionStructs.py](https://github.com/ROCm/Tensile/blob/develop/Tensile/SolutionStructs.py)
- Parameter semantics from `Tensile/Common.py` comments (@ e8a8999e): PrefetchLocalRead: "number of VGPRs buffer = min(PLR+1, LoopIters); LoopIters = DepthU / LocalSplitU (/= MatrixInstruction_K); ex. MT64x128x16_MI32x32x4x2_PLR1 -> 4 LoopIters, prefetch read 1 iteration, 2 VGPR buffers". 1LDSBuffer: "We use double LDS buffer when PrefetchGlobalRead... If we can make sure all data are read from LDS to register before writing data to LDS, we can use 1 LDS buffer to save LDS memory... or help to increase Occupancy". StaggerU: "requires BufferLoad==1... StaggerUStride=256 is recommended since this is the width of memory channel... each click will start in a new memory channel and spread traffic among the 16 available channels". DepthULdsDivisor: "divide the G2L buffer into N portions and write each portion to LDS... cut down LDS usage". StoreRemap: "MI output data between each threads are along N dims. But global memory is along M dim continuous... store performance for MI instruction is poor". StorePriorityOpt: "If we issue store in short period of time, kernel will become from compute bound to memory bound". StreamK: "0: uses workspace to store partial tiles, accumulate in deterministic fix-up step; 1: uses atomics" — [Tensile/Common.py](https://github.com/ROCm/Tensile/blob/develop/Tensile/Common.py)
- RDNA/WMMA support in Tensile (@ e8a8999e): `validWMMA = [[16,16,16,1]]` (only one WMMA shape); capability probing via `tryAssembler(isaVersion, "v_wmma_f32_16x16x16_f16 v[0:3], v[8:15], v[16:23], v[0:3]")` sets `HasWMMA`; arch flags `HasWave32 = isaVersion[0] in (10,11,12)`, `SeparateVscnt = isaVersion[0] in (10,11)`, `VgprBank = isaVersion[0] in (10,11,12)`, `InstRename = isaVersion[0] >= 11`; gfx1100/1101/1102 map to navi31/32/33; gfx1151 listed. The emitter `WMMASelection` in `Tensile/Components/MFMA.py` prints `v_wmma_<out>_<M>x<N>x<K>_<in> v[...], src0, src1, src2` with `neg_lo:[1,1,1]` for i8 — [Tensile/Common.py](https://github.com/ROCm/Tensile/blob/develop/Tensile/Common.py), [Tensile/Components/MFMA.py](https://github.com/ROCm/Tensile/blob/develop/Tensile/Components/MFMA.py)
- rocprofv3 demangles kernel names by default (drops arguments); `--mangled-kernels` keeps mangled names; kernel-name filtering is documented — [rocprofiler-sdk: Kernel naming and filtering](https://rocm.docs.amd.com/projects/rocprofiler-sdk/en/develop/how-to/kernel-naming-filtering.html)
- hipBLASLt offline tuning flow (docs "latest", read 2026-10-17): (1) `export HIPBLASLT_LOG_MASK=32` makes the library print a ready-to-run `hipblaslt-bench` command per GEMM ending in `--algo_method index --solution_index <N>`; (2) `export HIPBLASLT_TUNING_FILE=tuning.txt` then run `hipblaslt-bench <flags>` (tuning-mode defaults: `--iters 1000`, `--cold_iters 1000`, `--requested_solution -1`, `--rotating 512`; `HIPBLASLT_TUNING_USER_MAX_WORKSPACE` caps workspace, default 128*1024*1024) and read the `Winner:` block; (3) `export HIPBLASLT_TUNING_OVERRIDE_FILE=tuning.txt` and verify with `--algo_method heuristic --requested_solution 1 --print_kernel_info`. "Solution indices cannot be reused across library releases or across device architectures." — [hipBLASLt: Using offline tuning](https://rocm.docs.amd.com/projects/hipBLASLt/en/latest/how-to/how-to-use-hipblaslt-offline-tuning.html); same non-portability caveat in [ROCm blog: GEMM tuning within hipBLASLt Part 2](https://rocm.blogs.amd.com/software-tools-optimization/hipblaslt-offline-tuning-part2/README.html)
- Strata (@ 477ac13c, 2026-10-16) ships per-arch tables `tools/hip/<arch>-hipblaslt-<version>.txt` (gfx1100 for hipBLASLt 100100/100200/100202/100401/100500, plus gfx1103/1150/1151/1200/1201); format: header `STRATA_HIPBLASLT_TUNING_V1 gfx1100 100500` then rows `dtype M N K lda solution_id`, e.g. `bf16 1 2560 1 4096 1035`, `bf16 128 2560 128 8192 1036`; docs: "A table's solution ids are valid only for that pair, and the engine refuses any other table"; generated with `tools/hip/tune_hipblaslt.cpp`; on gfx103x (RDNA2, "no hipBLASLt kernels") a rocBLAS table is used instead — [Strata docs/AMD_HIP.md](https://github.com/Niko1221/Strata/blob/main/docs/AMD_HIP.md), [Strata tools/hip](https://github.com/Niko1221/Strata/tree/main/tools/hip)
- Strata AMD_HIP_PERFORMANCE.md: measured arm uses `STRATA_PREFILL_MMQ=1`, `STRATA_HIPBLASLT_TUNING="$PWD/tools/hip/gfx1100-hipblaslt-100100.txt"`, `STRATA_PREFILL_RING=96`; "The runtime guards architecture, library version and actual shape/stride/workspace requirements, falling back when a table entry is unavailable" — [Strata docs/AMD_HIP_PERFORMANCE.md](https://github.com/Niko1221/Strata/blob/main/docs/AMD_HIP_PERFORMANCE.md)
- Community report (llama.cpp issue, 2025): on gfx1100 "the HIP backend's matmul path ... relied on rocBLAS and hipBLAS kernels that performed poorly on some RDNA shapes", with Vulkan reported ~2x and a theoretical ~4x gap vs the HIP backend at the time — [llama.cpp issue #13565](https://github.com/ggml-org/llama.cpp/issues/13565) (single user report; treat as anecdotal)

### Inferences
- To decode a Tensile kernel seen in `rocprofv3 --kernel-trace` on gfx1100, read: `MT<M>x<N>x<DepthU>` -> macro tile and K-unroll; `MI16x16x16x1` -> WMMA path (the only valid WMMA shape); then `PGR`, `PLR`, `GRVW`, `LRVW`, `TLDS`, `LPA/LPB`, `GSU`, `WGM`, `SU`/`SUS` -> prefetch depth, load vector widths, LDS transpose/padding, split-K, work-group swizzle and memory-channel staggering. A hipBLASLt tuning table changes only which pre-compiled solution (one of these parameter combinations) is chosen per (dtype, M, N, K, ld) — it does not generate new code.
- Tensile's StaggerU/WGM/StoreRemap comments are the "what the vendor learned from ISA" artifacts: memory-channel spreading, L2-friendly work-group order, and the poor store coalescing of matrix-instruction output layouts are the three recurrent problems, and they apply on RDNA3 just as on CDNA.
- The RDNA weakness is a logic-coverage problem (few tuned WMMA solutions, one WMMA shape, `HasWave32`-specific paths), not an emitter problem; this is why Strata and llama.cpp both avoid rocBLAS/hipBLAS for quantized matmuls on gfx1100 and keep hipBLASLt only for dense BF16/FP16 projections with a pre-tuned table.

### Gaps
- Could not locate navi31/gfx1100 logic YAML files in the Tensile clone (`Tensile/Logic` had no navi3 entries); the shipped RDNA3 solution set likely lives in rocBLAS/hipBLASLt's own library directories, not verified.
- No primary benchmark comparing hipBLASLt default heuristic vs tuned table on gfx1100 was found beyond Strata's own docs (which report request-level t/s, not per-GEMM TFLOPS).
- Tensile's current `rocm-libraries` monorepo version of `Common.py` was not read; parameter names cited are from the June 2025 standalone repo.

## KQ2. AITER (ROCm/aiter): hand-written assembly kernels and the techniques visible in them; transferability to RDNA3

### Takeaway
AITER's assembly kernels ship only as compiled code objects (`hsa/<gfx>/**/*.co`, 3,155 files at 2026-10-16) with CSV metadata, so the only way to "read" them is to disassemble; the techniques are nevertheless visible in AITER's C++/HIP "opus" kernels, which use inline asm for `buffer_load ... lds` (LDS-DMA), `s_setprio`, `sched_group_barrier`/`sched_barrier` pipelines and static AGPR ring maps. All of that is gfx942/gfx950-specific (MFMA, AGPRs, LDS-DMA); RDNA3 is only supported for Triton/HIP element-wise and some GEMM/attention kernels.

### Cited Findings
- README (@ 2cc8c750, 2026-10-16): "Multiple kernel backends — Triton, Composable Kernel (CK), and hand-tuned ASM"; footnote: "On RDNA, Triton and most FlyDSL kernels run, as do most HIP kernels (norm, RoPE, quant, activation, plus some GEMM/attention). Most CK and ASM kernels are CDNA-only... Ongoing RDNA optimization work — attention, MoE, GEMM and beyond — lands here first." Backends enumerated: "Triton/Gluon, HIP, ASM, CK, OPUS or FlyDSL" — [ROCm/aiter README](https://github.com/ROCm/aiter/blob/main/README.md)
- Asm kernel inventory (local clone): under `hsa/` there are 3,155 `.co` files and 117 `.csv`, zero `.s`/`.asm` sources. Largest families: `hsa/gfx950/fmoe/silu` (441), `hsa/gfx950/fmoe/gelu` (435), `hsa/gfx942/fmoe/silu` (422), `hsa/gfx942/fmoe_2stages` (186), `hsa/gfx942/fmha_v3_bwd` (156), `hsa/gfx950/mla` (89), `hsa/gfx950/pa` (87), `hsa/gfx950/f4gemm`/`f6gemm` (35 each), `hsa/gfx942/bf16gemm` (22), `hsa/gfx1250/fmha_v3_bwd` (22), `hsa/gfx1250/mxfp8fp4gemm` (12). No `hsa/gfx11*` directory exists — [ROCm/aiter hsa/](https://github.com/ROCm/aiter/tree/main/hsa)
- Kernel names encode tiling, e.g. `MLA_A16W16_1TG_4W_32mx1_16nx1_Coex0_Msk1_QH16.co`, `mla_a16w16_qh16_m16x4_n16x1_coex0_mask1_ps.co`, `flatmm_uk_gfx9_f16f8_128x256x128_1x4x1_16x16x32.co` (tile 128x256x128, wave layout 1x4x1, MFMA 16x16x32), `fmoe_fp8_g1u1_multix_subGU_256.co`; CSV metadata columns `tile_m,tile_n,splitK,bpreshuffle,knl_name,co_name` (e.g. `112,256,0,1,_ZN5aiter42I8gemm_bf16_perTokenI8_BpreShuffle_112x256E,...`); `hsa/codegen.py` merges CSVs into a C++ header ("ASM Kernel Config Code Generator") — [ROCm/aiter hsa/readme.md](https://github.com/ROCm/aiter/blob/main/hsa/readme.md)
- Inline-asm LDS-DMA in the opus MLA decode kernel (`csrc/kernels/mla/opus/mla_decode_a8w8_32mx4_64nx1.hpp`): `asm volatile("s_mov_b32 m0, %0\n\ts_nop 0\n\tbuffer_load_dwordx4 %1, %2, 0 offen lds" :: "s"(m0_val), "v"(voff), "s"(rsrc) : "memory")`, with the comment: "M0 = the wave-uniform LDS destination, the hardware adds lane * BYTES. Asm so that the compiler does not know LDS-DMA is in flight: it keeps alias books on LDS-DMA, cannot tell the KV slots apart, and answers with a vmcnt(0) in front of LDS reads. s_nop: an M0 write needs one wait state before an LDS-DMA" and "async_load's builtin is exactly the compiler-visible LDS-DMA (measured: 7 more vmcnt(0) in the 32mx4 loop)" — [aiter csrc/kernels/mla/opus](https://github.com/ROCm/aiter/tree/main/csrc/kernels/mla/opus)
- Static register maps in the same file: `static_assert(KV_AGPR_BASE<T> + T::K_DEPTH * K_AGPR_PER_STEP<T> <= 256, "K ring past a255")` — K/V tiles live in a ring of AGPRs sized at compile time; `readfirstlane_f32` via `__builtin_amdgcn_readfirstlane` moves wave-uniform floats into SGPRs — [aiter csrc/kernels/mla/opus](https://github.com/ROCm/aiter/tree/main/csrc/kernels/mla/opus)
- Priority and scheduling in `mla_decode_a8w8_16mx8_32nx1.hpp`: stage comment "stage1 [compute]: gemm0 QK(t) [12 MFMA]; softmax-tail(t-1) [4 EXP + ~18 VALU]" bracketed by `__builtin_amdgcn_s_setprio(1)` ... `__builtin_amdgcn_s_setprio(0)`, `__builtin_amdgcn_sched_barrier(0)` between stages, explicit `s_waitcnt_lgkmcnt(number<T::k_nope_ds_read_insts>{})` counting outstanding `ds_read`s, and `sched_compute_qk<QK_MFMA_CNT, 1>()` helpers — [aiter csrc/kernels/mla/opus](https://github.com/ROCm/aiter/tree/main/csrc/kernels/mla/opus)
- Paged-attention HIP kernel (`csrc/cpp_itfs/pa/pa_kernels.cuh`) interleaves with `__builtin_amdgcn_sched_group_barrier(0x0020, n_global_load_per_fragment, 0); // VMEM read`, `(0x0100, 2, 0); // LDS read`, `(0x008, 1, 0); // MFMA`, and switches MFMA shape by arch: `#if defined(__gfx950__)` -> `gcn_mfma16x16x32_instr`, else 2x `gcn_mfma16x16x16_instr` — [aiter csrc/cpp_itfs/pa/pa_kernels.cuh](https://github.com/ROCm/aiter/blob/main/csrc/cpp_itfs/pa/pa_kernels.cuh)
- Counts across `csrc/` + `aiter/ops/` (grep, 2026-10-16 clone): files using `s_setprio` 46, `sched_group_barrier` 24, `sched_barrier` 92, `asm volatile` 55, `buffer_load ... lds` 42, `v_mfma` 17, `ds_read_b128|ds_read_b64_tr` 27, `s_waitcnt` 101, `__builtin_amdgcn_perm` 29, `waves_per_eu` 906 — local grep of [ROCm/aiter](https://github.com/ROCm/aiter)
- `aiter/jit/core.py` lists gfx1100/1101/1102/1103/1150/1151/1152/1153 as recognized targets (so JIT HIP/Triton paths build for RDNA3) — [aiter/jit/core.py](https://github.com/ROCm/aiter/blob/main/aiter/jit/core.py)
- HipKittens (arXiv 2511.08083, Nov 2025) reports AITER asm attention as the baseline: "AITER: 272 and 384 TFLOPS (causal and non-causal) at sequence length 8192" on MI355X, HK 1.0–2.1x over AITER on attention forward, and MHA bwd 4-wave HK 1091 TFLOPS vs AITER asm 1169 at seq 8192 — [HipKittens arXiv HTML](https://arxiv.org/html/2511.08083v1)

### Inferences
- "Reverse engineering AITER asm" in practice = `llvm-objdump -d --mcpu=gfx942 hsa/gfx942/<kernel>.co` (AMD code objects are ELF; the `.co` name doubles as the kernel's tile signature) plus reading the opus C++ twins, which document the same tricks in comments. The CSV side tables show the dispatcher's heuristic (tile_m/tile_n/splitK/bpreshuffle per shape).
- Techniques that transfer to RDNA3: static register budgeting with `static_assert`s, `readfirstlane` scalarization, `sched_group_barrier` masks (0x0020 VMEM read, 0x0100 DS read, 0x008 MFMA — on RDNA3 the "MFMA" mask would need to target WMMA/VALU), explicit `s_waitcnt lgkmcnt(N)` counting, `s_setprio` around the compute stage, and B-matrix pre-shuffling (`bpreshuffle`) to match the matrix-instruction operand layout. Techniques that do NOT transfer: `buffer_load ... lds` (LDS-DMA; RDNA3 lacks the LDS-DMA form used here), AGPRs (CDNA only), MFMA 16x16x32/32x32x16 shapes, 160 KB LDS.

### Gaps
- No AITER assembly source (`.s`) is public; the asm generation flow (likely an internal generator) is undocumented in the repo.
- No RDNA3 performance numbers for any AITER kernel were found; the README's RDNA claims are qualitative.

## KQ3. GPU MODE x AMD Developer Challenge 2025 (MI300X: FP8 GEMM, MoE, MLA) and the 2026 MI355X E2E speedrun; winners' techniques; the kernelbot dataset

### Takeaway
The 2025 challenge problems are fully specified in `gpu-mode/reference-kernels` (DeepSeek-R1 shapes with speed-of-light targets), the ~110K submitted kernels are on Hugging Face (`GPUMODE/kernelbot-data`), and the grand-prize RadeonFlow FP8 GEMM write-up ranks its wins as: transposed inputs for L2 hit rate, batched global->LDS loads, LDS padding against bank conflicts, split-K, load/compute pipelining, unsafe fp32->bf16 cast, and block swizzling; the 2026 round moved to MI355X with MXFP4 MoE, MLA decode and MXFP4 GEMM, with AITER's `fused_moe` and `mla_decode_fwd` as the reference baselines.

### Cited Findings
- Competition scale: the kernelboard team "built the infrastructure for the AMD $100K kernel competition, which ran for 2 months, with over 30,000 submissions from 163+ teams" — [gpu-mode/kernelboard PR #49](https://github.com/gpu-mode/kernelboard/pull/49)
- FP8 GEMM task (`problems/amd/fp8-mm/task.yml`, reference-kernels @ f3295bb6): "custom fp8-blockwise matmul kernel optimized for MI300"; `a` is M x K column-major e4m3fnuz, `b` is N x K column-major e4m3fnuz, `a_scale` M x K//128 fp32, `b_scale` N//128 x K//128 fp32, `c` M x N row-major bf16; "`m` and `n` are divisible by 64, `k` is divisible by 128"; ranking = geometric mean; speed-of-light table: (1024,1536,7168) 8.63 us, (1024,4608,7168) 25.89 us, (6144,1536,7168) 51.78 us, (6144,4608,7168) 155.30 us, (1024,7168,256) 3.17 us, (6144,7168,256) 17.27 us; templates `template.py` (Python/Triton) and `template-hip.py` (inline HIP) — [reference-kernels problems/amd/fp8-mm](https://github.com/gpu-mode/reference-kernels/tree/main/problems/amd/fp8-mm)
- MLA decode task (`problems/amd/mla-decode/README.md`): bf16 Q/K/V, non-paged latent KV cache, bs=128, sk in {1024, 6144}, sq=1, dim=7168, v_head_dim=128, n_heads=128; speed-of-light 106.65 us (sk=1024) and 280.87 us (sk=6144) — [reference-kernels problems/amd/mla-decode](https://github.com/gpu-mode/reference-kernels/tree/main/problems/amd/mla-decode)
- 2026 round (`problems/amd_202602/`): `mxfp4-mm`, `moe-mxfp4`, `mixed-mla`, "optimized for AMD Instinct MI355X". MoE: DeepSeek-R1 hidden 7168, intermediate 2048, 256 experts (32 with EP), top-k 8 + 1 shared; reference = "AITER `fused_moe` with `QuantType.per_1x32`"; weights also provided pre-shuffled: "`shuffle_weight(w, layout=(16,16))` + `e8m0_shuffle(scale)` ... rearranges weight tiles for coalesced memory access by CK GEMM instructions". MLA: reference "aiter MLA a8w8 decode kernel (`mla_decode_fwd`, fp8 Q + fp8 KV, persistent mode)", kernels named `mla_a8w8_qh16_qseqlen1_gqaratio16_ps` / `mla_a16w8_qh16_m16x4_n16x1_coex0_mask1_ps` / `mla_a16w16_...`; reference latency on MI355X bs=256 kv=8k: a8w8 ~349 us vs a16w16 ~814 us (2.3x) — [reference-kernels problems/amd_202602](https://github.com/gpu-mode/reference-kernels/tree/main/problems/amd_202602)
- 2026 event: qualifiers March 6 – April 6, 2026 with MXFP4 MoE, MLA Decode and MXFP4 GEMM; top 10 teams advanced to finals on end-to-end DeepSeek-R1 / Kimi K2.5 inference; awards scheduled May 18, 2026 — [AMD: New GPU MODE Virtual Hackathon: E2E Model Speedrun](https://www.amd.com/en/developer/resources/technical-articles/2026/new-gpumode-virtual-hackathon--e2e-model-speedrun.html)
- Dataset: "GPUMODE/kernelbot-data ... created from the first and second AMD $100K kernel competitions ... roughly 110K kernels for fp8-gemm, moe, mla, all2all, gemm+reducescatter, and allgather+gemm, optimized to run on MI300"; configs `submissions`, `successful_submissions`, `leaderboards` (parquet); ~566k rows shown on the dataset page; license shown inconsistently (MIT in metadata vs cc-by-4.0/"other" in the sidebar) — [HF: GPUMODE/kernelbot-data README](https://huggingface.co/datasets/GPUMODE/kernelbot-data/blob/refs%2Fpr%2F9/README.md)
- Grand prize: RadeonFlow Kernels "won the grand prize in the AMD Developer Challenge 2025 (Inference Sprint)"; kernels: FP8 blockwise GEMM (HIP), MoE (HIP), MLA (PyTorch); claims ">= 8x speedup over AMD's PyTorch reference"; sample `gemm_checker` output: "Overall GeoMean: 92.03 us, 360.59 TFLOPS (best)", per-case best 184–496 TFLOPS; tooling: LibTorch, hipBLASLt, ROCm 6.3.1, rocprof, rocprof-compute, `scripts/gen_submission.py`, HF kernel-builder — [RadeonFlow_Kernels README](https://github.com/RadeonFlow/RadeonFlow_Kernels/blob/main/README.md)
- RadeonFlow technical report (FP8 GEMM, HIP + rocWMMA): `gemm_kernel` supports only BM=256, BN=128, BK=128; two accumulator sets (per-fragment, then scaled over K = hierarchical accumulation for blockwise scales); optimizations "in listed order of importance: 1. Transposing inputs to improve L2 hit rate and HBM bandwidth use; 2. Batching global-to-LDS loads; 3. Padding shared memory to avoid bank conflicts; 4. Split-K ... when M and N are small and K is large; 5. Pipelining global-to-LDS loads with matrix core compute (doubles register buffers); 6. Fast but unsafe float-to-bfloat16 casting; 7. Block swizzling to further raise L2 hit rate"; "Currently uses 8-element padding per row... Future work is swizzling in LDS to remove the padding"; "Buffer loads with the LDS suffix could reduce register pressure. Early inline-assembly experiments showed manual instruction scheduling is required." ## KQ4. AMD blogs and guides: ROCm lab notes (register pressure, LDS, matrix cores), Triton on MI300X, CK-Tile, MI300X workload tuning, GPUOpen RDNA guides, Mesa ACO

### Takeaway
AMD's own guidance is split: ROCm blogs document CDNA (MFMA layouts fixed by the instruction, LDS phase/bank behaviour, register-occupancy trade-offs), while GPUOpen's RDNA performance guide gives the RDNA-specific rules (wave32, workgroups a multiple of 64, 32 x 32-bit LDS banks, 256-byte coalesced writes, scalarization with `readFirstLane`, FP16 to cut VGPRs). Mesa's ACO shows what an RDNA3-aware compiler does differently (VOPD pairing, wave32 by default, RDNA-tuned scheduling heuristics).

### Cited Findings
- Register pressure (CDNA2 post): "practical demo ... on controlling register usage on MI200-series GPUs using ROCm 5.4", link between registers and occupancy — [ROCm blog: Register pressure in AMD CDNA2 GPUs](https://rocm.blogs.amd.com/software-tools-optimization/register-pressure/README.html)

- GPUOpen RDNA performance guide (posted 2023-03-22, updated for RDNA3): "RDNA runs shader threads in groups of 32 known as wave32"; "Make the workgroup size a multiple of 64 to obtain best performance across all GPU generations"; LDS "32 banks, each 32 bits (one DWORD) wide", bank conflicts "increase instruction latency", fix with struct-of-arrays or padding (example: 8 conflicts reading X from a float4 array vs 2 for an array of floats); write "coalesced 256-byte blocks per wave"; reduce VGPRs with FP16 and scalarization via `readFirstLane`; transcendentals run at quarter rate — [GPUOpen: RDNA Performance Guide](https://gpuopen.com/learn/rdna-performance-guide/)
- RDNA architecture deck: each SIMD32 has 1024 physical VGPRs, 256 per wave cap, "A Wave64 wave consumes double the registers of a Wave32 wave"; 128 kB LDS per WGP, up to 64 kB per workgroup, 32 banks; wave32 gives "lower latency and wave lifetime, faster ramp-up after barriers" — [GPUOpen: RDNA Architecture (PDF)](https://gpuopen.com/download/RDNA_Architecture_public.pdf)
- rocprofiler-compute RDNA docs: RDNA3.5 "supports both Wave32 (primary execution mode) and Wave64", "wavefront size is fixed per kernel at compile time", VGPR allocation per wave limits occupancy — [rocprofiler-compute: Workgroup processor (WGP)](https://rocm.docs.amd.com/projects/rocprofiler-compute/en/latest/conceptual/rdna/wgp.html)
- Mesa ACO: VOPD scheduler "creates VOPD instruction pairs using a post-RA list scheduler" (Mesa 24.1, Feb 2024) — [Phoronix: VOPD scheduler for ACO](https://www.phoronix.com/news/RADV-ACO-VOPD-Scheduler); ACO scheduling heuristic retuned from Polaris to RDNA's larger wave capacity and register files (Mesa 25.3, Aug 2025) — [Phoronix: ACO scheduler heuristics](https://www.phoronix.com/news/ACO-Scheduler-Heuristics); RADV RT shaders moved from wave64 to wave32 on RDNA3/4 because "ACO got a lot better at forming VOPD instructions", ~14% in Black Myth: Wukong on Navi 31 (Mesa 26.0, Jan 2026) — [Phoronix: RADV RT wave32](https://www.phoronix.com/news/RADV-RT-RDNA3-RDNA4-Wave32)

### Inferences
- For gfx1100 the actionable checklist from vendor material is: wave32 kernels, workgroup multiple of 64, LDS access patterns verified against 32 x 4-byte banks (padding/SoA), 256-byte coalesced stores per wave, FP16/packed math and `readfirstlane` to cut VGPRs, and VOPD-friendly VALU streams (independent FP32 op pairs). The HipKittens "phase" finding (ds_read_b128 = 4 phases of 16 lanes) is CDNA-measured; on wave32 RDNA the same solver approach (microbenchmark + `SQ_LDS_BANK_CONFLICT`) is the way to learn the undocumented phase mapping.
- Mesa ACO is the best public, readable example of an RDNA3-specific code generator; its VOPD pass and wave32 default are the compiler-side mirrors of the GPUOpen rules.

- The "AMD lab notes" GPUOpen series pages (Laplacian part 3 on register pressure/occupancy) were only seen via search snippets, not fetched.

## KQ5. Inference engines on RDNA3: llama.cpp HIP backend, llama.cpp Vulkan, Strata, exllamav3-rocm, vLLM on RDNA4; what each learned from ISA

### Takeaway
llama.cpp compiles its CUDA kernels for HIP with arch macros (`RDNA3` from `__GFX11__`, `AMD_WMMA_AVAILABLE` for RDNA3/RDNA4) and since Dec 2025 runs quantized MMQ on RDNA3 WMMA with per-type batch-size cut-offs decided from measurements; Strata reaches the same hardware via `__builtin_amdgcn_wmma_f32_16x16x16_{f16,bf16}_w32`, `__builtin_amdgcn_perm`, `permlanex16` and `sudot4`, plus hipBLASLt tables. The general lesson is that on RDNA3 dot-product (`v_dot4`) and WMMA paths beat rocBLAS/hipBLAS for quantized inference, and that RDNA3's WMMA operand layout ("mirrored", 16-wide) is different from RDNA4's and must be handled separately.

## KQ6. Triton on AMD: lowering pipeline, knobs, how to dump ISA, RDNA3 status

### Takeaway
Triton's AMD backend (`third_party/amd/backend/compiler.py`) is a documented pass pipeline (`add_accelerate_matmul`, `add_schedule_loops`, `add_pipeline`, `add_block_pingpong`, `add_in_thread_transpose`, `add_convert_to_buffer_ops`) feeding LLVM AMDGPU, with `AMDGCN_ENABLE_DUMP=1` printing the ISA; RDNA (gfx10+) is handled as `warp_size = 32`, and RDNA3 WMMA is exposed in Gluon (`triton.experimental.gluon.language.amd.rdna3.wmma`), while `matrix_instr_nonkdim`, `kpack`, `waves_per_eu` are MFMA/CDNA-oriented knobs.

### Cited Findings
- `HIPOptions` defaults (main, read 2026-10-17): `num_warps=4`, `waves_per_eu=0`, `num_stages=2`, `matrix_instr_nonkdim=0`, `kpack=1`, `allow_flush_denorm=False`, `supported_fp8_dtypes=("fp8e4nv","fp8e5","fp8e5b16","fp8e4b8")`, `allowed_dot_input_precisions=("ieee","bf16x3","bf16x6")`, `schedule_hint=''`, `wgp_cu_mode="wgp"` (gfx11 and gfx120x); `warp_size = 32 if gfx_major >= 10 else 64`; arch checks like `"gfx110" in arch` / `"gfx120" in arch` for in-thread transpose — [triton third_party/amd/backend/compiler.py](https://github.com/triton-lang/triton/blob/main/third_party/amd/backend/compiler.py)
- Pass pipeline: ttgir stage runs `add_coalesce`, `add_f32_dot_tc`, `add_accelerate_matmul`, `add_optimize_epilogue`, `add_optimize_dot_operands`, `add_schedule_loops`, `add_pipeline`, `add_coalesce_async_copy`, `add_block_pingpong`, `add_in_thread_transpose`, `add_convert_to_buffer_ops`; llir stage `add_allocate_shared_memory`, `add_membar`, `add_to_llvmir`; `make_amdgcn` -> `libtriton_amd_codegen` (`triton_amdgpu_compile`) or `llvm.translate_mir_to_asm` when `swap_mir`; `make_hsaco` -> `assemble_amdgcn` + `amd.link_hsaco` — [triton compiler.py](https://github.com/triton-lang/triton/blob/main/third_party/amd/backend/compiler.py)

## KQ7. Cross-cutting: what reading source + ISA teaches, and the transfer map to RX 7900 XTX / llama.cpp

### Takeaway
Across Tensile, AITER, the challenge winners and HipKittens the same five levers recur: (1) memory-system-aware tile traversal (WGM/XCD swizzle, StaggerU), (2) wide, batched, coalesced loads (GRVW/`buffer_load_dwordx4`/128-bit), (3) bank-conflict-free LDS via padding or swizzle (LdsPad, 8-element padding, HipKittens swizzle), (4) explicit software pipelining with compiler scheduling hints (PGR/PLR, `sched_group_barrier`, `s_setprio`, counted `s_waitcnt`), and (5) matching the matrix-instruction operand layout exactly (B pre-shuffle, StoreRemap, mirrored WMMA layouts). Only the instruction-level specifics (MFMA shapes, AGPRs, LDS-DMA) fail to transfer to RDNA3.

### Cited Findings
- HipKittens schedules: 8-wave ping-pong (two waves per SIMD alternating MFMA vs memory, conditional barrier) vs 4-wave interleave (one wave per SIMD, finely interleaved): FP8 GEMM 3222 vs 3327 TFLOPS (48 vs 183 LoC), MHA bwd 894 vs 1091 TFLOPS; wave specialization reaches only ~80% of BF16 peak on MI355X because "registers are statically divided across waves"; 0P/8C 256x256 tile = 1610 TFLOPS vs 4P/8C 128x256 = 893; register pinning raised MHA bwd 855 -> 1024 TFLOPS at seq 4096 — [HipKittens arXiv HTML](https://arxiv.org/html/2511.08083v1)
- HipKittens LDS swizzle: "For a 16x32 BF16 tile, the swizzle swaps the first 8 columns with the last 8, starting at row 8. This removes 2-way conflicts for row loads and enables conflict-free `ds_read_b64_tr_b16` column reads"; "For direct-to-LDS loads, swizzling is done by permuting HBM addresses, not LDS addresses" — [HipKittens arXiv HTML](https://arxiv.org/html/2511.08083v1)
- RadeonFlow's ranked list puts input transposition (L2 hit rate) and batched global->LDS loads above LDS padding and pipelining — [RadeonFlow TechnicalReport.md](https://github.com/RadeonFlow/RadeonFlow_Kernels/blob/main/TechnicalReport.md)
- Tensile encodes the same lessons as parameters (WGM, StaggerU, GRVW, LdsPad/TLDS, PGR/PLR, StoreRemap) — [Tensile/Common.py](https://github.com/ROCm/Tensile/blob/develop/Tensile/Common.py)
- AITER's opus kernels document compiler-vs-hand trade-offs in comments ("7 more vmcnt(0)" when the compiler sees LDS-DMA) — [aiter csrc/kernels/mla/opus](https://github.com/ROCm/aiter/tree/main/csrc/kernels/mla/opus)
- llama.cpp's RDNA3 WMMA MMQ path shows that even with WMMA, some quant types lose to hipBLAS at batch >= 128 on RDNA3.0 (Q6_K, Q2_K thresholds) — [llama.cpp mmq.cu](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/mmq.cu)
