# Verification of nvidia/cases.md (dimension: case studies where RE produced faster kernels)

Verified 2026-10-17 by fetching every cited URL. Independent WebSearch was NOT possible in this run (the shared per-turn search budget was already exhausted), so "independent evidence" below comes only from additional primary sources fetched directly (official DeepGEMM README, pranjalssh/fast.cu README, HN thread, DeepSeek-V3 PDF text extracted with pdftotext, the actual interleave_ffma.py source).

## Confirmed

1. **Claim:** maxas SGEMM beat cuBLAS by 4.8% at 4096x4096 and up to 25% on small matrices on GM204 by reverse-engineering Maxwell's 4 register banks (bank = reg mod 4), the 8-byte-per-slot operand reuse cache and control codes; it also found a bank-conflict flaw in cuBLAS's own SGEMM (~28 GFLOPS lost).
   - Source quotes (maxas wiki SGEMM): "At the 4096 size we're beating cublas by 4.8%"; "performing as much as 25% over cublas"; "On Maxwell there are 4 register banks"; "The Maxwell assignment is just the register number modulo 4"; "The operand reuse cache has 8 bytes of data per source operand slot"; "for the first FFMA it chooses a C register (3) with a blocking register bank conflict ... On GM204 this bug is costing cublas sgemm 28 Gflops"; benchmarks on "GM204 clocked at 1607 sustained"; "within 2% of the theoretical flops".
   - Nuance: the SGEMM page mentions control codes only in passing ("every 4th instruction is a control code"); the control-code details live on the separate maxas wiki "Control Codes" page. Numbers are the author's own (2014-2017), no third-party re-run found.

2. **Claim:** DeepGEMM's interleave_ffma.py dumps SASS with cuobjdump -sass, locates runs of >=16 FFMA instructions and flips the yield (bit 45) and reuse (bit 59) bits of the high 64-bit word in place via mmap on the compiled .so, giving 10%+ speedup on fine-grained FP8 GEMMs; the trick was discovered by diffing NVCC 12.2 vs 12.3 SASS and NVCC 12.9 later adopted it.
   - Script source (fetched raw): `[f'{CUDA_HOME}/bin/cuobjdump', '-sass', file_path]`; `if len(current) >= 16` on collected lines; `reused = (high_hex & 0x0800000000000000) != 0` (bit 59); `high_hex ^= 0x0800200000000000` (bits 59 and 45; 0x2000_00000000 = 2^45); `mmap.mmap(f.fileno(), 0, access=mmap.ACCESS_WRITE)`; env var `DG_PRINT_REG_REUSE`.
   - README mirror (AlignmentResearch): kernel improved "between NVCC 12.2 and 12.3"; "one bit in a series of FADD instructions is flipped in an interleaving pattern"; "this bit controls yield ... (just a guess ...)"; "registers cannot be reused if the warp is yielded"; "10%+ in some cases".
   - Official deepseek-ai/DeepGEMM README (2025.07.20 news): "As NVCC 12.9 will automatically do the FFMA interleaving, all post optimizations will be no longer supported."
   - Precision correction (minor, does not change verdict): the threshold is 16 *lines*, and each FFMA occupies two lines (instruction line + encoding-comment line), so a run is >=8 FFMA instructions, not >=16. The note's own wording ("runs of >=16 consecutive FFMA lines") is correct; the task's paraphrase ">=16 FFMA instructions" is not. Also the script only patches the first `len*9//16` lines of each run (`num_lines = (len(ffma_lines) * 9 // 16) // 2 * 2`), and the bits are *cleared* (asserted set, then XORed) on FFMAs whose destination register is first seen or where the previous FFMA reused the same destination. The official DeepGEMM README no longer carries the FFMA section (only mirrors do).

3. **Claim:** DeepSeek-V3 found Hopper FP8 tensor-core accumulation retains only ~14 bits, so they promote partials to FP32 on CUDA cores every N_C=128 elements (4 WGMMAs), overlapped across two warpgroups; they also used warp specialization on 20 SMs and 'customized PTX instructions' with auto-tuned chunk sizes for all-to-all communication to reduce L2 use.
   - PDF text (pdftotext of arXiv:2412.19437): "the accumulation precision of FP8 GEMM on NVIDIA H800 GPUs is limited to retaining around 14 bits"; "the Tensor Core only uses the highest 14 bits of each mantissa product for addition, and truncates bits exceeding this range"; "partial results will be copied to FP32 registers on CUDA Cores"; "it is typical for two WGMMA to persist concurrently: while one warpgroup performs the promotion operation, the other is able to execute the MMA operation"; "setting N_C = 128 elements, equivalent to 4 WGMMAs"; "we employ the warp specialization technique (Bauer et al., 2014) and partition 20 SMs into 10 communication channels"; "we employ customized PTX (Parallel Thread Execution) instructions and auto-tune the communication chunk size, which significantly reduces the use of the L2 cache and the interference to other SMs".
   - Nuance: the paper attributes the promotion strategy to CUTLASS (Thakkar et al., 2023), i.e. the fix is not DeepSeek's invention, only the 14-bit measurement is.

4. **Claim:** fast.cu (Nov 29 2024, H100 SXM, CUDA 12.6, bf16 4096^3) went from 32 to 764 TFLOPS vs cuBLAS 716 via WGMMA+TMA (317), warp specialization (498), 128x256 tiles with register reallocation (631), persistent kernel with L2-grouped tile order (400->660), raw mbarrier PTX (704), clusters+TMA multicast (734), SMEM-staged TMA stores (758) and Hilbert tile order (764); L2 hit rate 83% vs cuBLAS 70%.
   - Worklog: Nov 29 2024; H100 SXM 132 SMs; CUDA 12.6 V12.6.68; M=N=K=4096 bf16; cuBLAS 716; kernels 1..11 = 32, 317, 423, 498, 610->631 (setmaxnreg), 400->660 (persistent, grouped 16x8), 704 (mbarrier PTX), 734 (2x1 clusters + TMA multicast), 747, 758 (SMEM + TMA store), 764 (Hilbert); L2 hit 83% vs 70%; ~107% of cuBLAS.
   - Independent: pranjalssh/fast.cu README gives 763 vs 716 at N=4096 and 808 vs 795 at N=8192 (consistent).

5. **Claim:** The ACCU 'Reverse-Engineering cuBLAS' article (June 2024, A5000 HGEMM) read cuBLAS SASS and found the main loop starts with MMA, loads bypass registers via asynchronous cp.async interleaved with math, and waits on a different pending-group count; copying that structure took the kernel from 60 to 91 TFLOPS, 1 TFLOP behind cuBLAS, which ships ~5000 GEMM kernels (~100 MB).
   - ACCU Overload 32(181), June 2024, Fabian Schuetze (GitHub original 14 Mar 2024); A5000, FP16 tensor cores (HMMA.16816); main loop "starts with a matrix multiply rather than a memory load"; LDGSTS (cp.async) bypasses registers; `DEPBAR.LE SB0, 0x1` vs `0x0` = CP_ASYNC_WAIT_GROUP(1); instructions interleaved; 60 -> 73 -> 89 (95% of cuBLAS) -> 91 TFLOPS, "1 TFLOP behind"; "about 5000" kernels with GEMM in the name; cuBLAS ~100 MB.
   - Nuance: the article itself is internally loose (earlier says cuBLAS ~90 TFLOPS, later "1 TFLOP behind" at 91); quote the "1 TFLOP behind" statement as the author's.

6. **Claim:** llama.cpp PR #7676 (merged 10 Jun 2024) added int8 tensor-core MMQ via inline PTX mma.sync in ggml-cuda/mma.cuh (WMMA rejected because it has no defined memory layout for applying block scales), giving 1.65-1.77x over the dp4a MMQ on RTX 3090/4090 at pp512 and up to 2.08x over the cuBLAS FP16 path at microbatch 128, while falling slightly below cuBLAS at batch >=1024.
   - PR page: opened May 31 2024, merged Jun 10 2024, commit 1f0dabda...; `ggml-cuda/mma.cuh`; WMMA "no defined memory layout" so scales cannot be applied -> PTX; pp512 batch 512: 4090 Q4_0 1.65x, Q8_0 1.72x; 3090 Q4_0 1.67x, Q8_0 1.77x; vs cuBLAS 4090 Q4_0 batch 128 3578.31 -> 7443.66 (2.08x); 3090 batch 512 Q4_0 1.01x, Q5_0 0.92x; slaren 3090 Ti batch 1024: Q4_0 0.94, Q5_0 0.86, "a bit slower than f16 cuBLAS with large batch sizes".
   - Nuance: at batch 512 on the 3090 it was already at/below cuBLAS for some quants (Q5_0 0.92x), not only at >=1024.

7. **Claim:** Machete (Oct 14 2024) diagnosed that Marlin's reliance on mma.sync instead of wgmma loses ~37% of Hopper peak and rebuilt the W4A16 GEMM on CUTLASS 3.5.1 with pre-shuffled weights, in-register upconversion, TMA and warp specialization, yielding geomean +29%/+32% (70B, 1xH100) and +42% (405B, 4xH100) token throughput at >=3 req/s.
   - Red Hat article dated Oct 14 2024: Marlin uses "outdated 'mma' tensor core operations", "approximately 37% of peak compute throughput" lost (the article cites external sources for the 37%); "built on top of the work highlighted in CUTLASS 3.5.1"; pre-shuffled weights, in-register upconversion, TMA, producer/consumer warp specialization; 70B 1xH100 geomean +29% input / +32% output; 405B 4xH100 +42%; at 3+ req/s.

8. **Claim:** The 2025 paper 'Analyzing Modern NVIDIA GPU cores' (RTX A6000, also Turing) reverse-engineers the issue scheduler, register file cache and memory pipeline, showing that the compiler guides the hardware via per-instruction control bits and that software-based dependence management beats a hardware scoreboard; the model reaches 13.98% MAPE vs real hardware, confirming the maxas-era mechanisms persist.
   - arXiv:2503.20481, submitted 26 Mar 2025 (Huerta, Abaie Shoushtary, Cruz, González): reverse-engineers issue logic/scheduler policy, register file and its cache, memory pipeline features; "the compiler guides hardware during execution"; software-based dependence management "outperforms a hardware scoreboard mechanism in both performance and area"; 13.98% average error vs RTX A6000; model also applies to Turing.
   - Nuance: the abstract says "compiler guides hardware" without the words "control bits"; the control-bit framing is the paper body's/the note's interpretation. "Confirming the maxas-era mechanisms persist" is the note's inference, not a statement in the paper.

## Refuted with corrections

- **Claim (KQ5 Cited Findings, Marlin bullet):** "Marlin: W4A16 kernel fusing INT4 unpacking/dequant into the GEMM with an asynchronous pipeline; uses `mma.sync.m16n8k16` + `cp.async.cg.shared.global` (from a third-party plan document; secondary). — search summary citing [arXiv:2607.11368]"
  - arXiv:2607.11368 exists but is "Decomposing Runtime, Kernel, and Quantization Speedups via a Matched FP16 Intermediate: A Hardware-Conditioned Case Study on Four NVIDIA RTX A5000 GPUs" (Han & Qu, 13 Jul 2026), a serving-stack attribution study; its abstract does not mention Marlin, mma.sync.m16n8k16 or cp.async. It is not a Marlin design document. Correction: cite Marlin's own paper/repo (Frantar et al., "MARLIN: Mixed-Precision Auto-Regressive Parallel Inference on Large Language Models", 2024, IST-DASLab/marlin) for the mma.sync.m16n8k16 + cp.async claims, and drop 2607.11368, or verify its full text before keeping it. (The instruction-level facts themselves are plausible and consistent with the Machete article; only the citation is wrong.)

## Other issues

- Tool flags: `cuobjdump -sass`, `cuobjdump --list-text` (`-ltext`) and `cuobjdump -fun <name>` are all real options per the CUDA Binary Utilities docs (Table 2). Note that `-fun` selects which function's fat binary structures are dumped and is intended for use together with `-sass`; fine as written.
- Supporting numbers re-checked and found accurate: FA3 blog (35% FA2, 570->620, 620->640-660, 740 TFLOPS/75%, ~1.2 PFLOPS FP8, 2.6x lower error, 3.9 TFLOPS special functions = 256x, mma.sync ~2/3 of peak); ThunderKittens blog (12 May 2024, "Keep the tensor core fed. That's it.", 989 vs ~60 TFLOPS, 63% without wgmma, swizzle layouts "flat-out incorrectly documented", ~30-cycle SMEM, 30% over FA2, 75% on 4090, ~100/~60 lines); CuAsmRL (arXiv:2501.08071, 14 Jan 2025, CGO 2025, up to 26% / 9% avg); CUDA-L2 (arXiv:2512.02551, 2 Dec 2025, +19.2/+16.8/+11.4 offline, +26.0/+22.4/+15.9 server, ~1000 configs, GPU not named in abstract); siboehm (RTX A6000, Dec 2022, 309/1986.5/2980.3/8474.7/15971.7/18237.3/19721/21779.3 vs 23249.6; kernels 7-8 dropped); llama.cpp PR #21074 (merged 1 Apr 2026, RTX 5090 +26.8% Qwen3-0.6B, +191.2% Qwen3.5-27B, reuses vec_dot_q8_0_16_q8_1_mma); HN 43179478 quotes (Scott Gray 2015, 3-person Volta SASS team, CUTLASS within ~10% of cuBLAS, cuBLASLt FP8 ~1.35 P on H200).
- Minor wording: FA3's "256x" figure is for special functions in general (3.9 vs 989 TFLOPS), of which exp is the relevant one; the note's "exp is 256x slower than matmul" is acceptable shorthand.
