Verified 2026-10-17 against `formats.md`. Method: every cited URL was re-fetched (WebFetch); local read-only clones in the scratchpad (`re_nvidia/cudaparsers`, `re_nvidia/fatbin-decomp`) were grepped for the struct layouts. The per-claim independent WebSearch could NOT be run: the shared per-turn WebSearch budget was already exhausted by sibling agents. As a substitute, independent primary sources were fetched directly (CUDA Toolkit release notes, NVCC 13.4 docs, CUDA Programming Guide lazy-loading page, JEB ICudaCubinEntry API doc, repository source code). Where that substitute could not cover a claim it is said so.

## Confirmed

1. **Claim (verbatim):** "The host-side wrapper __fatBinC_Wrapper_t (magic 0x466243B1, version 1, data pointer, filename_or_fatbins) sits in .nvFatBinSegment and points via an R_X86_64_64 relocation at the fatbin blob in .nv_fatbin (or __nv_relfatbin for -rdc); the fatbin header magic is 0xBA55ED50 with 16-byte header, and entry fields are kind@0, header size@4, padded payload size@8, compressed size@0x10, arch@0x1c, flags@0x28."
   - Source https://www.thesoftwarefrontier.com/p/how-cuda-binaries-actually-work (dated Jul 31, 2026) states all of it: `FATBINC_MAGIC 0x466243B1`, `FATBINC_VERSION 1`, fields `magic/version/data/filename_or_fatbins`, `.nvFatBinSegment` (control) / `.nv_fatbin` (data) / `__nv_relfatbin` (with `-rdc=true`), `readelf -rW` showing `R_X86_64_64 .nv_fatbin + 0`, "16-byte header whose magic is 0xBA55ED50", and the offsets 0/4/8/0x10/0x1c/0x28.
   - Independent cross-check: the offsets are byte-exact with n-eiling's packed `struct fat_text_header` (kind u16@0, header_size u32@4, size u64@8, compressed_size u32@0x10, arch u32@0x1c, flags u64@0x28) in the local clone `fatbin-decompress.h`. Caveat: the blog calls the wrapper "24-byte", see Other issues.

2. **Claim (verbatim):** "Fatbin entry headers are 64 bytes (kind 1=PTX, 2=ELF cubin, version 0x0101, header_size, padded_payload_size, payload_size, sm_version, ..., uncompressed_payload); when uncompressed_payload != 0 the payload is LZ4-block compressed and a kind-2 payload decompresses to an ELF starting 7F 45 4C 46; .nv.info.<kernel> items are format byte (EIFMT_NVAL=1/BVAL/HVAL/SVAL) + attribute byte + value, with EIATTR_KPARAM_INFO a 12-byte record (index u32, ordinal u16, offset u16, packed log_alignment/space/cbank/size)."
   - The GitHub README at https://github.com/vivekpanyam/cudaparsers does NOT contain these details (it only says cubin parsing is tested against cuobjdump on thousands of files, Apache-2.0, Rust). The details are in the repository source, verified in the local clone: `src/fatbin.rs` (`assert_eq!(size_of::<FatbinData>(), 64)`, `version == 0x0101 && (kind == 1 || kind == 2)`, `lz4::block::decompress(..., uncompressed_payload)`, ELF magic check `[0x7f,'E','L','F']` for kind 2) and `src/cubin.rs` (`EIFMT_NVAL = 0x01, EIFMT_BVAL, EIFMT_HVAL, EIFMT_SVAL`; `KParamInfoValue` with `value_size == 12`, `index: u32, ordinal: u16, offset: u16`, then `log_alignment = tmp & 0xff`, `space = (tmp>>8)&0xf`, `cbank = (tmp>>12)&0x1f`, `size_bytes = (tmp>>18)`). Last commit in the clone: 2023-12-29.
   - Independent: JEB's API doc (https://pnfsoftware.com/jeb/apidoc_md/com.pnfsoftware.jeb.core.units.code.cuda.ICudaCubinEntry.md) confirms kinds PTX=1 / SASS=2 and an LZ4 compression flag (8192).

3. **Claim (verbatim):** "Cubins are ELF with EM_CUDA=190, ELFOSABI_CUDA=51 (V2=41), ABI version 7/8; e_flags encode the SM as EF_CUDA_SM mask 0xff before Blackwell and EF_CUDA_SM_MASK 0xff00 (offset 8) after Blackwell, with EF_CUDA_SM120=0x78 and EF_CUDA_SM121=0x79, EF_CUDA_64BIT_ADDRESS=0x400, EF_CUDA_ACCELERATORS_V1=0x800 (sm_90a), EF_CUDA_VIRTUAL_SM=0xff0000 and EF_CUDA_ACCELERATORS=0x8 for sm_100a-style variants in the new ABI."
   - LLVM `ELF.h` (main) fetched verbatim: `EM_CUDA = 190`, `ELFOSABI_CUDA = 51`, `ELFOSABI_CUDA_V2 = 41`, `ELFABIVERSION_CUDA_V1 = 7`, `ELFABIVERSION_CUDA_V2 = 8`, `EF_CUDA_SM = 0xff` ("prior to blackwell"), `EF_CUDA_SM_MASK = 0xff00`, `EF_CUDA_SM_OFFSET = 8` ("following blackwell"), `EF_CUDA_SM120 = 0x78`, `EF_CUDA_SM121 = 0x79`, `EF_CUDA_64BIT_ADDRESS = 0x400`, `EF_CUDA_ACCELERATORS_V1 = 0x800` ("sm_90a"), `EF_CUDA_VIRTUAL_SM = 0xff0000`, `EF_CUDA_ACCELERATORS = 0x8` ("sm_100a in the new ABI"). Exact match. (Independent WebSearch not available; LLVM header is itself a primary source for these constants.)

4. **Claim (verbatim):** "CUDA Binary Utilities 13.4 (last updated 2026-10-12): cuobjdump accepts host binaries and offers -sass/-elf/-symbols/-ptx/-res-usage/-lelf/-lptx/-xelf/-xptx/-all/-fun/-arch; nvdisasm accepts only cubins and offers -b SMxx, -cfg, -bbcfg, -hex, -plr, -lrm, -g, -gi, -gp, -json, -raw, -ndf; both list sm_120/sm_120a/sm_120f (cuobjdump) and SM120/SM120a (nvdisasm) among supported targets from sm_75 to sm_121; nvprune example: nvprune -arch sm_120 libcublas_static.a -o libcublas_static120.a."
   - https://docs.nvidia.com/cuda/cuda-binary-utilities/index.html header "v13.4", tail "Last updated on Oct 12, 2026", sample producer "nvdisasm V13.4.0". All listed short flags present. cuobjdump `-arch` list: sm_75 ... sm_120, sm_120a, sm_120f, sm_121, sm_121a, sm_121f. nvdisasm `-b` list: SM75 ... SM120, SM120a, SM121, SM121a (note: no SM120f/SM121f/SM100f/SM110f, only SM107f, exactly as the note records). nvprune example verbatim.

5. **Claim (verbatim):** "CUDA 13.0 removed offline compilation (nvcc) and library support for compute capabilities 5.x, 6.x, 7.0 and 7.2 (Maxwell, Pascal, Volta), making Turing 7.5 the floor; driver branch 580 is the final LTS branch for pre-7.5 GPUs (supported until mid-2028); nvcc --list-gpu-arch on CUDA 12.9 already lists compute_120 and compute_121."
   - Confirmed with an attribution correction. The cited NVIDIA blog (Aug 04, 2025) says offline compilation for architectures before CC 7.5 (Maxwell 5.x, Pascal 6.x, Volta 7.0/7.2) is removed in CUDA 13.0, that branch 580 "is the final branch that supports GPUs before CC 7.5" (LTS, three years, "until mid-year 2028"), and prints the 12.9 `--list-gpu-arch` output ending in compute_120, compute_121. It does NOT say "library support" and never names Turing explicitly. The library part is supported instead by the CUDA Toolkit release notes (https://docs.nvidia.com/cuda/cuda-toolkit-release-notes/index.html): cuFFT 13.0 "Removed support for Maxwell, Pascal, and Volta GPUs, corresponding to compute capabilities earlier than Turing" and cuSPARSE 13.0 "Dropped support for pre-Turing architectures". So the sentence holds but "library support" should cite the release notes, not the blog.

6. **Claim (verbatim):** "Lazy loading was introduced in CUDA 11.7, became the Linux default in 12.2 and the default on all platforms in 12.3, requires driver >= 515; kernels are loaded on first use (forceable with cuModuleGetFunction()/cudaFuncGetAttributes()), and CUDA_MODULE_LOADING=EAGER disables it; the JIT cache defaults to ~/.nv/ComputeCache with CUDA_CACHE_MAXSIZE default 1 GiB (max 4 GiB) and CUDA_FORCE_PTX_JIT=1 forces PTX JIT over embedded cubins."
   - The environment-variables page (cited) confirms `CUDA_MODULE_LOADING` DEFAULT/LAZY/EAGER (DEFAULT = LAZY), `CUDA_CACHE_PATH` Linux `~/.nv/ComputeCache`, `CUDA_CACHE_MAXSIZE` default 1073741824 (256 MiB embedded), max 4294967296, `CUDA_FORCE_PTX_JIT=1`. It says nothing about 11.7/12.2/12.3/515; those facts are on the lazy-loading page (https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/lazy-loading.html), which the note cites separately and which confirms: introduced 11.7 (off), default on Linux in 12.2, "As of CUDA 12.3 lazy loading is enabled by default on all platforms", driver 515+, `cuModuleGetFunction()` / `cudaFuncGetAttributes()` force loading, `CUDA_MODULE_LOADING=EAGER` disables.

8. **Claim (verbatim):** "nvcc compresses fatbins by default; a raw fatbin can be extracted with objcopy -O binary --only-section=.nv_fatbin <in> <out> and decompressed with the open-source cuda-fatbin-decompression tool, whose header struct shows flags FATBIN_FLAG_64BIT 0x1, DEBUG 0x2, LINUX 0x10 and COMPRESS (LZ4) 0x2000, and whose output was validated against an nvcc -no-compress build."
   - Confirmed with attribution corrections. The README at https://github.com/n-eiling/cuda-fatbin-decompression gives the exact `objcopy` command and says to validate against `nvcc -no-compress` output. The flag constants are real but live in `fatbin-decompress.c` (lines 22-26: `FATBIN_TEXT_MAGIC 0xBA55ED50`, `FATBIN_FLAG_64BIT 0x1`, `FATBIN_FLAG_DEBUG 0x2`, `FATBIN_FLAG_LINUX 0x10`, `FATBIN_FLAG_COMPRESS 0x2000`), not in the header file. The repo never uses the word "LZ4" (its `decompress()` is a hand-written LZ4-block-style token decoder) and never says nvcc compresses by default; "LZ4" is supported by cudaparsers (`lz4::block::decompress`) and JEB (flag 8192 = LZ4), and "by default" by the NVCC 13.4 docs (`--compress-mode default` "is currently equivalent to `speed`", `--no-compress`/`none` turn it off).

## Refuted with corrections

7. **Claim (verbatim):** "JEB 5.31 (2025-08-15) ships the only generic-RE-tool SASS disassembler plus experimental decompiler, covering sm_70 through sm_121 (Volta to Blackwell), identifying cubins by EM_CUDA (190), validated against cuobjdump/nvdisasm on >100M unique instructions across ~620k kernels; all Volta+ instructions are fixed 16 bytes; kernel arguments live in constant bank 0 at 0x160 (sm_70-89), 0x210 (sm_90) and 0x380 (sm_100-12x); relocations and ET_REL cubins are unsupported."
   - Refuted only for "the only generic-RE-tool SASS disassembler": the cited PNF blog (https://pnfsoftware.com/blog/reversing-nvidia-cuda-sass-code/) makes no exclusivity claim; that is the note's own inference from its search results (note line 189) and must not be attributed to the source. **Correction:** "JEB 5.31 (posted 2025-08-15, updated 2025-08-18) ships a SASS disassembler plus an experimental, proof-of-concept decompiler ..."; present "only generic RE tool" as an inference/gap. Everything else in the claim is confirmed verbatim by the blog: sm_70-sm_121, pre-Volta unsupported, EM_CUDA 190, "100+ million unique instructions across about 620,000 kernels", fixed 16-byte instructions, c[0x0] bases 0x160 / 0x210 / 0x380, relocations not applied, ET_REL not processed. (Independent WebSearch for a competing Ghidra/Binary Ninja/IDA SASS plugin could not be run, budget exhausted.)

## Other issues (scan of the rest of the note)

- **Note line 12 (Takeaway):** "a 16-byte host-side wrapper struct in `.nvFatBinSegment`" — wrong size. The struct is `int magic; int version; const unsigned long long* data; void* filename_or_fatbins` = 24 bytes on x86_64, and the cited blog itself says "a 24-byte wrapper in .nvFatBinSegment". Verdict: refuted; correction: 24-byte wrapper (16 bytes applies to the fatbin header, not the wrapper).
- **Note line 192:** "partial IR (only 4-operand FMNMX ...)" — the blog says the 5-operand FMNMX is only partially converted. Verdict: refuted; correction: "5-operand FMNMX".
- **Note line 29 / line 189:** "the old flag spelling was `-Xfatbin --compress-all`" — the README only says compressed fatbins are produced "e.g., by using the `-Xfatbin --compress-all` flag"; nothing calls it old or superseded. Low severity. Line 189's "the only mature generic-RE-tool SASS disassembler is commercial (JEB)" is the same unsourced exclusivity claim as item 7 and should be labelled as an inference. Also note line 19 cites a `generationalwealth.duckdns.org/venv/...` URL (someone's exposed virtualenv, HTTP 503) as the source for `fatbinary_section.h`; it is already marked unverified, but it should be replaced by the CUDA Toolkit's own `include/fatbinary_section.h` (the blog quotes the same defines from it). Verdict: unverifiable/low-quality source, not a hallucination.
- No hallucinated tool flags were found: every cuobjdump/nvdisasm flag and `-arch`/`-b` value in the note matches the 13.4 doc verbatim; `-poolmgr` is correctly reported as non-existent.
