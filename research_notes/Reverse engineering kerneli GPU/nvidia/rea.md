# REA (Reverse Engineer Anything) applied to NVIDIA kernel reverse engineering (NVIDIA track)

Research date: 2026-10-17. Local read-only clone of morluto/rea inspected at commit `060eb43b` (2026-10-17, "docs: celebrate 300,000 GitHub stars"). llama.cpp inspected at commit `2744e48d` (2026-10-17). All version numbers below carry the date they were observed.

## Key question 1: What REA is (version, license, popularity, providers, Evidence model, targets, platforms)

### Takeaway
REA is an MIT-licensed Node.js MCP server + CLI (`rea-agents` 6.5.0 on npm as of 2026-10-17, ~300.7k GitHub stars) that wraps caller-installed reverse-engineering engines (Hopper, Ghidra, IDA, Kuna, JEB, GNU objdump, Rizin, GDB, Frida, Cutter) and returns "Evidence" records with digests, limitations and unknowns; nothing in its docs, source or changelog mentions CUDA, NVIDIA, PTX, SASS, cubin or fatbin.

### Inferences
- REA is a host-CPU-oriented orchestration layer; its value for GPU work is limited to whatever the wrapped engines can do with the *host* ELF/PE around the kernels, plus runtime hooking via Frida/GDB.

## Key question 2: Does any REA provider understand GPU code (SASS / NVPTX)? What can REA see inside a cubin?

### Takeaway
No REA provider can disassemble or decompile NVIDIA device code: Ghidra ships no NVIDIA/PTX/SASS processor module, Rizin has no GPU arch plugin, GNU objdump's BFD has no NVIDIA target, and LLVM's NVPTX backend has no MC disassembler; moreover REA's own ELF front-ends explicitly reject a cubin (e_machine 190 = EM_CUDA), so REA can see a cubin only as an opaque blob inside an x86-64 host binary.

### Cited Findings
- EM_CUDA = 190 "NVIDIA CUDA architecture" in the generic ELF ABI machine table — [SCO gABI ELF Header](https://au.sco.com/developers/gabi/latest/ch4.eheader.html); same value in glibc's `glibcelf.py` patch — [sourceware libc-alpha](https://inbox.sourceware.org/libc-alpha/87k0bhzeaz.fsf@igel.home/T).
- NVIDIA: "A CUDA binary (also referred to as cubin) file is an ELF-formatted file which consists of CUDA executable code sections as well as other sections containing symbols, relocators, debug info, etc." — [CUDA Binary Utilities (archive 11.0 PDF)](https://docs.nvidia.com/cuda/archive/11.0/pdf/CUDA_Binary_Utilities.pdf); "`nvdisasm` only accepts cubin files" while "`cuobjdump` accepts both cubin files and host binaries" — [CUDA Binary Utilities v13.4](https://docs.nvidia.com/cuda/cuda-binary-utilities/index.html).
- REA `open_binary` ELF whitelist (`elfArchitecture()` in `src/domain/elfFixedHeader.ts`): only e_machine 3 (x86), 62 (x86_64), 8 (mips), 20 (powerpc), 40 (arm), 183 (arm64), 243 (riscv); anything else → `err("unsupported ELF architecture")` in `src/domain/binaryTarget.ts` line 210 — [elfFixedHeader.ts](https://github.com/morluto/rea/blob/main/src/domain/elfFixedHeader.ts), [binaryTarget.ts](https://github.com/morluto/rea/blob/main/src/domain/binaryTarget.ts). A cubin (190) is therefore refused before any provider starts.
- REA `inspect_binary_layout` (pwntools/pyelftools bridge): `bridge/pwntools/layout_impl.py` raises `LayoutFailure("unsupported-target", "Initial layout profile requires x86-64 ELF objects.")` (line 124) and `"Initial layout profile requires x86-64 ELF64 little-endian objects."` (line 172); the TypeScript result schema is `machine: z.literal("EM_X86_64")` in `src/domain/native/binaryLayout.ts` — [layout_impl.py](https://github.com/morluto/rea/blob/main/bridge/pwntools/layout_impl.py), [binaryLayout.ts](https://github.com/morluto/rea/blob/main/src/domain/native/binaryLayout.ts). Docs confirm: "Initial real verification covers Linux x64, ELF64 x86-64 little-endian EXEC/DYN/REL"; requires "unchanged pwntools 4.15.0, pyelftools 0.33 and Unicorn 2.1.2" via `REA_PWNTOOLS_PYTHON` — [docs/binary-diagnostics.md](https://github.com/morluto/rea/blob/main/docs/binary-diagnostics.md).
- REA raw-binary route (`--target-format raw-binary --architecture ...`) accepts only `x86`, `x86_64`, `arm`, `arm64`, `6502`, `m68k` mapped to fixed Ghidra language IDs — [docs/raw-binary.md](https://github.com/morluto/rea/blob/main/docs/raw-binary.md). `REA_GHIDRA_LANGUAGE_ID`/`REA_GHIDRA_COMPILER_SPEC_ID` can override the Ghidra language, but REA's catalog only reads what exists under `Ghidra/Processors` and `Ghidra/Extensions` — [src/ghidra/GhidraLanguageCatalog.ts](https://github.com/morluto/rea/blob/main/src/ghidra/GhidraLanguageCatalog.ts), [docs/ghidra-mips.md](https://github.com/morluto/rea/blob/main/docs/ghidra-mips.md).
- Ghidra master `Ghidra/Processors` lists 39 modules (6502, 68000, 8048, 8051, 8085, AARCH64, ARM, Atmel, BPF, CP1600, CR16, DATA, Dalvik, HCS08, HCS12, Hexagon, JVM, Loongarch, M16C, M8C, MC6800, MCS96, MIPS, NDS32, PA-RISC, PIC, PowerPC, RISCV, Sparc, SuperH, SuperH4, TI_MSP430, Toy, V850, Xtensa, Z80, eBPF, tricore, x86) — no NVIDIA/PTX/SASS/AMDGPU entry — [github.com/NationalSecurityAgency/ghidra/tree/master/Ghidra/Processors](https://github.com/NationalSecurityAgency/ghidra/tree/master/Ghidra/Processors) (fetched 2026-10-17).
- Web search for a community SLEIGH module for SASS/PTX found only generic SLEIGH tutorials (PT Security V8-bytecode module, Ghidra SLEIGH docs); no NVIDIA module surfaced — [swarm.ptsecurity.com](https://swarm.ptsecurity.com/?p=2648), [ghidra.re SLEIGH](https://ghidra.re/ghidra_docs/languages/html/sleigh.html).
- Rizin `librz/arch/p` plugin files (67) include arch_6502 … arch_x86_zydis, arch_wasm, arch_hexagon, arch_amd29k (AMD 29000 CPU, not GPU); no nvidia/ptx/sass/cuda/amdgpu/gcn plugin — [github.com/rizinorg/rizin/tree/dev/librz/arch/p](https://github.com/rizinorg/rizin/tree/dev/librz/arch/p) (fetched 2026-10-17). `rz-asm -L` lists plugins, `rz-asm -m <plugin>` lists CPUs — [rz-asm man page](https://man.archlinux.org/man/rz-asm.1.en).
- GNU objdump: the Ubuntu 24.04 build "GNU objdump (GNU Binutils for Ubuntu) 2.42" `objdump -i` lists only elf64-x86-64, elf32-i386, elf32-iamcu, elf32-x86-64, pei-i386, pe-x86-64, pei-x86-64, elf64-little, elf64-big with i386/iamcu architectures (run locally 2026-10-17). REA exposes this exact capability probe as `inspect_with_objdump {"operation":"architectures"}` / `rea list-objdump-architectures` (maps to `-i`), described as "BFD targets compiled into the installed binary, not a guarantee that a target is supported" — [docs/reverse-engineering-tools.md](https://github.com/morluto/rea/blob/main/docs/reverse-engineering-tools.md).
- LLVM: `llvm-objdump-18 --version` on the research host registers targets `nvptx - NVIDIA PTX 32-bit`, `nvptx64 - NVIDIA PTX 64-bit`, `amdgcn - AMD GCN GPUs` (run locally 2026-10-17), but the `llvm/lib/Target/NVPTX` tree contains only `MCTargetDesc` and `TargetInfo` subdirectories — no `Disassembler` and no `AsmParser` directory (unlike AMDGPU/x86) — [github.com/llvm/llvm-project/tree/main/llvm/lib/Target/NVPTX](https://github.com/llvm/llvm-project/tree/main/llvm/lib/Target/NVPTX) (fetched 2026-10-17). Numba, for example, shells out to `nvdisasm` with `-gi`/`-cfg` because "nvdisasm only accepts input from a file" — [numba cuda codegen.py mirror](https://decoder-genetics.wustl.edu/software/conda/lib/python3.1/site-packages/numba/cuda/codegen.py).
- REA's objdump operations are fixed: `file_headers`→`-f`, `section_headers`→`-h`, `symbols`→`-t`, `relocations`→`-r`, `dwarf`→`-W` (+`-WK`/`-WN`), `disassemble`→`-d`, `disassemble_all`→`-D`, `architectures`→`-i`; there is no `-s`/`-j` (section hexdump), no `-T` (dynamic symbols), no `-x` — [src/objdump/ObjdumpCommand.ts](https://github.com/morluto/rea/blob/main/src/objdump/ObjdumpCommand.ts).
- Rizin one-shot: `execute_rizin_command` / `rea execute-rizin-command ./program iI` runs with `-N -q -c`; "REA preserves raw output" — [docs/reverse-engineering-tools.md](https://github.com/morluto/rea/blob/main/docs/reverse-engineering-tools.md).

### Inferences
- Even with the Ghidra language override, there is nothing to override *to*: no NVIDIA language exists in the Ghidra catalog REA reads, so a cubin can at best be loaded as data (and REA's own header check blocks it before Ghidra anyway).
- What REA *can* see of a cubin is indirect: section header rows for `.nv_fatbin`/`.nvFatBinSegment` inside the x86-64 host `.so` (via `inspect_with_objdump section_headers` or `inspect_binary_layout`), and the host-side strings/relocations that reference kernel names. SASS semantics are entirely outside REA's reach; `cuobjdump`/`nvdisasm` must take over.
- `llvm-objdump` on a cubin would fail at the "no disassembler for target" stage because NVPTX has no MC disassembler, and SASS is not PTX anyway (the NVPTX backend emits PTX text, not SASS).

### Gaps
- Could not fetch `bfd/config.bfd` from sourceware (HTTP 403 via proxy) to quote the upstream target list; the claim "no NVIDIA BFD target" rests on the local Ubuntu `objdump -i` output and on NVIDIA's own statement that cubins need `cuobjdump`/`nvdisasm`.
- Did not find any community Ghidra SLEIGH module for SASS or PTX; absence of search results is not proof of non-existence.
- Did not verify what Ghidra's `ElfLoader` does with an unknown e_machine when driven outside REA (it would be moot for REA, which rejects 190 first).

## Key question 3: Host-side uses that DO work (launch sites, registration stubs, .nv_fatbin, Frida hooks, GDB / cuda-gdb)

### Takeaway
REA is useful on the *host* side: Ghidra via REA can enumerate functions, strings and cross-references in `libggml-cuda.so` to map `__cudaRegisterFunction` registrations and launch stubs to kernel names; objdump/pwntools via REA locate the `.nv_fatbin` section; the Frida tools can hook `libcuda.so.1` loaders at runtime; and the GDB tool launches whatever `REA_GDB_COMMAND` names with `--interpreter=mi3`, which should accept `cuda-gdb` (MI-capable, GDB 16.3-based) — unverified in practice.

### Cited Findings
- Fatbin embedding layout (Clang's CUDA codegen, mirrors nvcc's): wrapper `struct { int magic, int version, void * gpu_binary, void * dont_care }` with `CudaFatMagic = 0x466243b1`, version 1; sections `.nv_fatbin` (the fatbin bytes), `.nvFatBinSegment` (the wrapper struct), `__nv_relfatbin` (relocatable device code); module constructor calls `__cudaRegisterFatBinary`, then `__cudaRegisterFunction` per kernel (and `__cudaRegisterVar`), `__cudaRegisterFatBinaryEnd` when `CUDA_USES_FATBIN_REGISTER_END`, destructor `__cudaUnregisterFatBinary` — [clang/lib/CodeGen/CGCUDANV.cpp](https://llvm.googlesource.com/llvm-project/+/refs/heads/main/clang/lib/CodeGen/CGCUDANV.cpp). The same `FATBINC_MAGIC 0x466243B1` and `.nvFatBinSegment`/`.nv_fatbin` names appear in NVIDIA's `fatbinary_section.h` as bundled by Triton — [fatbinary_section.h (Triton wheel mirror)](https://generationalwealth.duckdns.org/venv/lib/python3.13/site-packages/triton/backends/nvidia/include/fatbinary_section.h).
- NVIDIA has not published the fatbin container format: "NVIDIA has not published how it packages SASS and PTX into an ELF object to create the fat binary" — [NVIDIA forum: Demistifying CUDA fat binaries](https://forums.developer.nvidia.com/t/demistifying-cuda-fat-binaries/65607).
- Driver API loaders to hook: `cuModuleLoadData(CUmodule*, const void* image)` and `cuModuleLoadFatBinary(CUmodule*, const void* fatCubin)` — [CUDA Driver API, Module Management](https://docs.nvidia.com/cuda/cuda-driver-api/cuda_driver_api/group__CUDA__MODULE.html); the `image` "may be a cubin or fatbin as output by nvcc, or a NULL-terminated PTX" — [cuda-python driver bindings](https://nvidia.github.io/cuda-python/pr-preview/pr-3095/cuda-bindings/latest/module/generated/driver_v2/cuda.bindings._v2.driver.module_load_data_ex.html). Precedent: ZLUDA's dumper hooks `cuModuleLoadData` and checks `*(raw_image as *const u32) == 0x464c457f` (ELF magic) before writing — [ZLUDA commit mirror](https://git.uoc.run.place/Applied-Software/ZLUDA/commit/a39dda67d1fb3897c5ea778ae00c4079e8e2939a).
- Frida 17 API (REA pins frida 17.23.2): static `Module.getExportByName()`, `findExportByName()`, `getBaseAddress()` etc. were removed in Frida 17.0.0 (2025-05-17); replacement is `Process.getModuleByName('libc.so').getExportByName('open')`, and `Module.getGlobalExportByName('open')` for module-less lookup — [Frida 17.0.0 release notes](https://frida.re/news/2025/05/17/frida-17-0-0-released/). `Interceptor.attach(target, callbacks[, data])` with `onEnter(args)`/`onLeave(retval)`, `args` as `NativePointer[]`, `NativePointer.readByteArray(length)` → `ArrayBuffer`, which can be sent "by passing it as the second argument to `send()`" — [Frida JavaScript API](https://frida.re/docs/javascript-api/).
- REA Frida semantics: "A spawned process starts paused so scripts can load first"; "Frida scripts execute inside the selected target with that process's memory, filesystem, and network authority"; "REA never kills the target"; capture bounded to 16 MiB — [docs/frida-instrumentation.md](https://github.com/morluto/rea/blob/main/docs/frida-instrumentation.md).
- Driver entry-point caveat: `cuGetProcAddress` was added in CUDA 11.3 and is how the runtime looks up driver function pointers; the CUinterwarp project intercepts driver-API calls via `LD_PRELOAD` and "works for intercepting Driver API calls such as cuInit and cuMemAlloc whether cudart is linked statically or dynamically" (tested on CUDA 12.2) — [github.com/fatlipp/CUinterwarp](https://github.com/fatlipp/CUinterwarp); NVIDIA's "Driver Entry Point Access" documents `cuGetProcAddress`/`cudaGetDriverEntryPointByVersion` — [CUDA Programming Guide 4.20](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/driver-entry-point-access.html).
- cuda-gdb 13.4 (2026 docs): "CUDA-GDB works with the GDB/MI interface in Emacs via `M-x gdb`" using `-i=mi`; base moved "from GDB 14.2 to 16.3" in 13.2; "The device SASS code can be disassembled using the standard GDB disassembly instructions such as `x/i` and `display/i`" and "For disassembly instruction to work properly, `cuobjdump` must be installed and present in your `$PATH`"; `set cuda break_on_launch application` breaks "on the first instruction of every launched kernel"; `info cuda devices|sms|warps|lanes|kernels|blocks|threads|...`; `cuda kernel <n>`; "Debugging is supported on all CUDA-capable GPUs supported by the current CUDA release"; Python 3.8–3.12 integration; Maxwell/Pascal/Volta deprecated since 12.8 — [CUDA-GDB 13.4 docs](https://docs.nvidia.com/cuda/cuda-gdb/index.html).
- REA GDB launch: `REA_GDB_COMMAND` "select[s] executable names or paths; otherwise REA searches `PATH`. Values are passed directly to process spawning, not expanded as shell command lines" — [docs/reverse-engineering-tools.md](https://github.com/morluto/rea/blob/main/docs/reverse-engineering-tools.md); the console "remains unrestricted and can run shell commands, change target state" — same source.
- Ghidra via REA, host-side primitives: `rea inspect PATH --provider ghidra --json`, `rea search PATH entry --kind procedures --provider ghidra --json`, `rea function PATH PROCEDURE`, `rea instructions`, `rea decompile`, `rea xrefs --address=<name-or-address>`, `rea trace --query=<text>`, `rea inspect-native-instruction`, `rea resolve-native-call-targets <binary> <call-site>`; MCP uses `open_binary`, `list_procedures`, `analyze_function`, `procedure_references`, `inspect_native_instruction` with `incoming_references`; Ghidra regex search uses Java Pattern semantics; "Ghidra function references cover the complete function-body AddressSet" — [docs/native-investigation.md](https://github.com/morluto/rea/blob/main/docs/native-investigation.md).
- REA Ghidra memory: `REA_GHIDRA_STARTUP_TIMEOUT_MS` for large binaries; Ghidra `java.lang.OutOfMemoryError` is reported as `resource_constraint` with `configured_jvm_max_heap` — [README.md](https://github.com/morluto/rea/blob/main/README.md), [docs/binary-diagnostics.md](https://github.com/morluto/rea/blob/main/docs/binary-diagnostics.md).
- llama.cpp host side: `ggml-cuda` links `CUDA::cudart_static CUDA::cublas` (static cudart inside the backend library) — [ggml/src/ggml-cuda/CMakeLists.txt](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/CMakeLists.txt) line 166; the library is built by `ggml_add_backend_library(ggml-cuda ...)`, which uses `add_library(${backend} MODULE ...)` when `GGML_BACKEND_DL` is on — [ggml/src/CMakeLists.txt](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/CMakeLists.txt) line 381+. Kernel launches use `<<<>>>` in most files and `cudaLaunchKernelEx` for programmatic dependent launch ("PDL host-side support (cudaLaunchKernelEx) requires CUDART >= 11.8") — [ggml/src/ggml-cuda/common.cuh](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/common.cuh) lines 119 and 1710.

### Inferences
- With static cudart, `cudaLaunchKernel`/`__cudaRegisterFunction` are *internal* functions of `libggml-cuda.so` (not imports), so in a stripped build they appear in Ghidra as unnamed `FUN_...`; the reliable anchor is the kernel-name *string* passed to `__cudaRegisterFunction` (mangled names such as `_Z13mul_mat_vec_qIL9ggml_type12ELi1ELb0ELb0ELb0EEvPKvS2_PKiK...`) — find it with `rea search ... --kind strings`, take its xrefs to the registration call in the module constructor, read the `hostFun` argument (host stub address), then xref the stub to find the launching host function. This chain is standard CUDA-runtime structure (CGCUDANV.cpp), but was not executed on a real `libggml-cuda.so` in this research.
- Because the host→driver path goes through `cuGetProcAddress` (CUDA ≥ 11.3), hooking the *exported* `cuModuleLoadData` symbol in `libcuda.so.1` with Frida may or may not catch the runtime's internal calls; the safer Frida target is `cuGetProcAddress` itself (log requested names and returned pointers, then `Interceptor.attach` the returned pointer) or `cuLibraryLoadData` (CUDA 12+) — not verified on CUDA 13.
- REA's GDB tool should drive `cuda-gdb` if `REA_GDB_COMMAND=/usr/local/cuda/bin/cuda-gdb`, since cuda-gdb 13.4 is GDB 16.3-based and MI-capable; REA's MI3→MI2 fallback and `set auto-load off` are unlikely to break it, but REA's docs make no claim about cuda-gdb and this was not tested here.

### Gaps
- Not verified: whether REA's `start_gdb_session` succeeds with `cuda-gdb` (MI3 prompt handshake, Python auto-load disabled, `inferior_tty` handling with a CUDA inferior).
- Not verified: whether the fatbin container magic commonly quoted as `0xBA55ED50` is correct — no primary source found; only the wrapper magic `0x466243b1` is sourced.
- Not verified: exact CUDA 13.x runtime behaviour for loading embedded fatbins (which of `cuModuleLoadData`, `cuModuleLoadFatBinary`, `cuLibraryLoadData` the static cudart calls, and whether lazily).

## Key question 4: Concrete recipe — "find and dump every kernel in libggml-cuda.so and identify which one Qwen3 Q4_K_M decode uses"

### Takeaway
REA covers steps 1–3 (locate `.nv_fatbin`, enumerate host symbols/strings, map stubs to kernel names), but extraction and SASS disassembly must be done with `cuobjdump -xelf all` / `cuobjdump -sass` / `nvdisasm`; for batch-1 decode of a Q4_K model on sm_120 the dispatch in llama.cpp source selects `mul_mat_vec_q<GGML_TYPE_Q4_K, ncols_dst=1, ...>` (MMVQ) for the quantized matmuls, with `flash_attn_ext_*` for attention.

### Cited Findings
- Step 1 (REA, objdump): `rea inspect-with-objdump /abs/libggml-cuda.so section_headers` (maps to `objdump -h`); MCP `inspect_with_objdump {"path": "/abs/libggml-cuda.so", "operation": "section_headers"}`; output retained up to 16 MiB; `REA_OBJDUMP_COMMAND` selects the binary — [docs/reverse-engineering-tools.md](https://github.com/morluto/rea/blob/main/docs/reverse-engineering-tools.md), [ObjdumpCommand.ts](https://github.com/morluto/rea/blob/main/src/objdump/ObjdumpCommand.ts). Section names to look for: `.nv_fatbin`, `.nvFatBinSegment`, `__nv_relfatbin` — [CGCUDANV.cpp](https://llvm.googlesource.com/llvm-project/+/refs/heads/main/clang/lib/CodeGen/CGCUDANV.cpp).
- Step 1b (REA, pwntools): `REA_PWNTOOLS_PYTHON=/abs/env/bin/python rea inspect-binary-layout /abs/libggml-cuda.so --json` (x86-64 ET_DYN is inside the supported profile); MCP `inspect_binary_layout {"path": ..., "detail": "summary"}` then `inspect_analysis_view` for one section/symbol page; "Complete results have a 32 MiB input ... `REA_PWNTOOLS_MAX_INPUT_BYTES` raises the input bound alone, up to 1 GiB" — [docs/binary-diagnostics.md](https://github.com/morluto/rea/blob/main/docs/binary-diagnostics.md).
- Step 2 (outside REA — extraction/disassembly): `cuobjdump -lelf libggml-cuda.so` lists embedded cubins; `cuobjdump -xelf all libggml-cuda.so` extracts them; `cuobjdump -sass -arch sm_120 libggml-cuda.so` dumps SASS; `cuobjdump -res-usage` prints register/shared-memory usage; `nvdisasm -c -cfg|-bbcfg|-plr|-json <cubin>` for CFG/liveness; `-g`/`-gi` need `.debug_line`; `cu++filt` demangles names like `_Z1fIiEbl` → `bool f<int>(long)` — [CUDA Binary Utilities v13.4](https://docs.nvidia.com/cuda/cuda-binary-utilities/index.html).
- Step 3 (REA, Ghidra): `rea inspect /abs/libggml-cuda.so --provider ghidra --json`; `rea search /abs/libggml-cuda.so "mul_mat_vec_q" --kind strings --provider ghidra --json` (strings kind is part of REA's search; regex per Java Pattern); `rea xrefs /abs/libggml-cuda.so --address=<string-address> --provider ghidra --json`; `rea function ... <registration-caller>`; `rea resolve-native-call-targets ... <call-site>`; `rea decompile ... --procedure=<host stub>` — [docs/native-investigation.md](https://github.com/morluto/rea/blob/main/docs/native-investigation.md).
- Which kernels exist (llama.cpp master 2026-10-17): `mul_mat_vec_q` (template `<ggml_type type, int ncols_dst, bool has_fusion, bool small_k=false, bool halve_iters=false>`, `__launch_bounds__(calc_nwarps(...)*warp_size, 1)`) and `mul_mat_vec_q_moe` in `mmvq.cu` (lines 623 and 882); `mul_mat_q` ("stream-k" partitioning, arXiv 2301.03598) and `mul_mat_q_stream_k_fixup` in `mmq.cuh` (lines 955, 1242); `flash_attn_ext_vec` (`fattn-vec.cuh`), `flash_attn_ext_f16` (`fattn-mma-f16.cuh`) — [mmvq.cu](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/mmvq.cu), [mmq.cuh](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/mmq.cuh), [fattn-vec.cuh](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/fattn-vec.cuh), [fattn-mma-f16.cuh](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/fattn-mma-f16.cuh).
- Dispatch rule for decode: `ggml_cuda_mul_mat` calls `ggml_cuda_mul_mat_vec_q` when `ggml_cuda_should_use_mmvq(src0->type, cc, ne11)` (ggml-cuda.cu line 2000); `ggml_cuda_should_use_mmvq` returns `ne11 <= 5` for `GGML_TYPE_Q4_K` on `GGML_CUDA_CC_BLACKWELL` ("tuned on RTX 5090"), `ne11 <= MMVQ_MAX_BATCH_SIZE` (= 8) on Ada; above that `mul_mat_q` (MMQ) or cuBLAS — [ggml-cuda.cu](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/ggml-cuda.cu), [mmvq.cu lines 318–343](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/mmvq.cu), [mmvq.cuh](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/mmvq.cuh) (`#define MMVQ_MAX_BATCH_SIZE 8`). ### Inferences
- For Qwen3-27B Q4_K_M at batch 1 on the RTX 5060 Ti (sm_120 → `GGML_CUDA_CC_BLACKWELL` branch), the per-token matmul kernels are `mul_mat_vec_q<GGML_TYPE_Q4_K, 1, has_fusion, ...>` for Q4_K tensors and the matching `mul_mat_vec_q<GGML_TYPE_Q6_K, 1, ...>`/`Q5_K` variants for the mixed tensors in a *_K_M quant; with `ne11` up to 5 (speculative/multi-sequence) still MMVQ, then MMQ. Attention is `flash_attn_ext_f16` when `turing_mma_available(cc)` (mma path) or `flash_attn_ext_vec` for small batch — see `fattn.cu` lines 147–171, 637; which one fires for Qwen3's head dim must be confirmed at runtime (ncu/nsys or Frida on launches).
- Because the stock build compresses the fatbin (`-compress-mode=size`), raw bytes carved from `.nv_fatbin` by hand are compressed; `cuobjdump -xelf` handles that transparently, hand-carving with REA's section offsets does not.
- A stripped release build has no `.symtab`; REA's `symbols` (`-t`) will print "no symbols", while `inspect_binary_layout` still reads `.dynsym` and the string tables, and Ghidra still recovers functions and strings.

### Gaps
- No step of this recipe was executed on a real `libggml-cuda.so` here (no CUDA toolkit, no GPU in the research host); every REA invocation is composed from documented CLI/MCP contracts and must be treated as untested.
- Did not verify the mangled symbol spelling for the Q4_K `mul_mat_vec_q` instantiation nor whether REA's string search finds it when the name is only in `.nv_fatbin` (compressed) rather than in a host `.rodata` string (the `__cudaRegisterFunction` call passes the device name as a C string, so it should be in `.rodata`, but this is inferred from CGCUDANV.cpp, not observed).
- Whether `GGML_BACKEND_DL` is on in the user's build (determines `libggml-cuda.so` as a MODULE loaded via `dlopen` vs. linked SHARED library) was not checked.

## Key question 5: Limitations and alternatives (where dedicated GPU tools must take over; REA caveats)

### Takeaway
Everything at the SASS level — disassembly, CFG, register liveness, occupancy, instruction-level profiling and binary instrumentation — belongs to `cuobjdump`/`nvdisasm`/`cu++filt`, Nsight Compute (`ncu`), NVBit and third-party assemblers (CuAssembler, turingas); REA's caveats are Linux process-ownership (`ps`), bring-your-own providers, 16 MiB provider capture and 10 MiB MCP response budgets, and x86-64-only ELF layout.

### Cited Findings
- nvdisasm vs cuobjdump feature split: "Control flow analysis and output: No / Yes; Advanced display options: No / Yes" (cuobjdump / nvdisasm) — [CUDA Binary Utilities v13.4](https://docs.nvidia.com/cuda/cuda-binary-utilities/index.html). `nvdisasm -b SM120` treats input as a raw instruction binary for that architecture; allowed `-arch` values include `sm_120`, `sm_120a`, `sm_120f`, `sm_121` — same source.
- NVBit 1.7: "a research prototype of a dynamic binary instrumentation library for NVIDIA GPUs" that lets tools "inspect and modify the assembly code (SASS) of a GPU application without requiring recompilation"; requirements "CUDA version: >= 12.0", "SM compute capability: >= 3.5 && <= 12.1", "Host CPU: x86_64, aarch64", "OS: Linux"; released as GitHub artifacts; "not part of the official CUDA toolkit" — [github.com/NVlabs/NVBit](https://github.com/NVlabs/NVBit), [README raw](https://raw.githubusercontent.com/NVlabs/NVBit/master/README.md). NVIDIA's older SASSI is deprecated in favour of NVBit — [github.com/NVlabs/SASSI](https://github.com/NVlabs/SASSI).
- Nsight Compute: Blackwell support added in 2024.4; 2025.2 "added scoreboard dependencies in SASS"; 2025.3 "the Source page now shows the instruction category in SASS and the instruction mix"; release notes list profiling support for some RTX 50 SKUs "with reduced metric support" (RTX 5090D named) — [Nsight Compute Release Notes](https://docs.nvidia.com/nsight-compute/ReleaseNotes/), [2025.3 updates](https://docs.nvidia.com/nsight-compute/2025.4/ReleaseNotes/topics/updates-2025-3.html).
- SASS assemblers: CuAssembler "an unofficial assembler for nvidia CUDA" that assembles nvdisasm output back into loadable cubins, "still in its infancy" — [github.com/cloudcores/CuAssembler Tutorial](https://github.com/cloudcores/CuAssembler/blob/master/Tutorial.md); turingas "open-source SASS assembler for Volta and Turing GPUs" — [NVIDIA forum](https://forums.developer.nvidia.com/t/an-open-source-sass-assembler-for-volta-and-turing-gpus/109011); "SASS is very lightly documented" — [Modal GPU Glossary](https://frontend.modal.com/gpu-glossary/device-software/streaming-assembler).
- pyelftools extension for GPU fat ELFs exists as pre-release: `elfgpu` "extend pyelftools so it can inspect CUDA and HIP/ROCm fat ELF binaries" — [pypi.org/project/elfgpu](https://pypi.org/project/elfgpu/) (not usable through REA, whose bridge requires unchanged pyelftools 0.33 and x86-64).
- REA caveats: "REA never installs Python, packages or GDB" and requires `REA_PWNTOOLS_PYTHON` pointing at an isolated env with "unchanged pwntools 4.15.0, pyelftools 0.33 and Unicorn 2.1.2" — [docs/binary-diagnostics.md](https://github.com/morluto/rea/blob/main/docs/binary-diagnostics.md); "REA setup never installs or upgrades Node.js, npm, Homebrew, Java, Ghidra, IDA, JADX, Kuna, Binwalk, or Unblob" — [SKILL.md](https://github.com/morluto/rea/blob/main/.agents/skills/reverse-engineer-anything/SKILL.md); procps `ps` requirement on Linux — [README.md](https://github.com/morluto/rea/blob/main/README.md); objdump/Rizin/GDB/Frida captures capped at 16 MiB with `output_truncated`, MCP default 10 MiB (`REA_MCP_MAX_RESPONSE_BYTES`) — [docs/reverse-engineering-tools.md](https://github.com/morluto/rea/blob/main/docs/reverse-engineering-tools.md), [docs/frida-instrumentation.md](https://github.com/morluto/rea/blob/main/docs/frida-instrumentation.md).
- REA session-retirement rule: "unrestricted Rizin and Cutter commands, GDB console commands, Rizin debugger start/close, and GDB debugger close retire any active binary analysis session ... call `open_binary` explicitly before continuing analysis" — [docs/reverse-engineering-tools.md](https://github.com/morluto/rea/blob/main/docs/reverse-engineering-tools.md).
- Security caveat: GDB console and Rizin commands "run with the REA process user's security context and may access files, the network, or perform other actions"; Frida scripts run "with that process's memory, filesystem, and network authority" — [docs/reverse-engineering-tools.md](https://github.com/morluto/rea/blob/main/docs/reverse-engineering-tools.md), [docs/frida-instrumentation.md](https://github.com/morluto/rea/blob/main/docs/frida-instrumentation.md).

### Inferences
- Practical division of labour for the user: REA + Ghidra for the host `.so` (who launches what, with which grid/args), REA + Frida/cuda-gdb for runtime confirmation and module dumps, then `cuobjdump -xelf`/`-sass`, `nvdisasm -cfg -plr`, `ncu` (Source/SASS view, needs `-lineinfo` for source correlation) and NVBit for the actual kernel-optimisation lessons.
- NVBit's stated upper bound "SM compute capability <= 12.1" covers sm_120 (RTX 5060 Ti) as of NVBit 1.7, so SASS-level instrumentation of llama.cpp kernels on the user's card is possible outside REA.
- A one-GPU headless Ubuntu server is the best-supported REA environment for the GDB/Rizin/Frida lanes (all "Linux only"), provided `procps` is installed.

### Gaps
- Did not find a dated changelog for NVBit 1.7 or confirmation of sm_120 by name; "<= 12.1" is the only sourced statement.
- Did not verify whether Nsight Compute's "reduced metric support" on RTX 50 consumer SKUs applies to the RTX 5060 Ti specifically.
- Did not test the elfgpu package or any Ghidra community effort for cubins; none was found in this research.
