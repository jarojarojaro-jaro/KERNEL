Verified 2026-10-17 against `uarch.md`. Method: every cited URL was fetched (WebFetch); for claim 1 the local `pdftotext` dump of arXiv 1804.06826 (`/tmp/claude-0/-home-user-KERNEL/2fec5121-746d-5a8c-9207-83ad66dddd8f/scratchpad/re_nvidia/volta/volta.txt`) was grepped as well. ## Confirmed

1. **Claim:** "Volta+ SASS uses one 128-bit word per instruction with a 21-bit control section: reuse flags (4 b), wait barrier mask (6 b), read barrier (3 b), write barrier (3 b), yield (1 b), stall cycles (4 b); Citadel measured V100 L1 hit 28 cycles, L2 ~193, shared 19, FFMA/IADD3 4-cycle dependent latency (2018)."
   **Source:** https://arxiv.org/pdf/1804.06826 (text dump §2.1, Table 3.1, Table 4.1). Verbatim: "Volta uses one 128-bit word to encode each instruction together with its corresponding control information"; "on Volta, each control section contains 2 zeroes as its most significant bits, and 1 section of 21 bits"; field table "Width (bits) 4 6 3 3 1 4 / Reuse flags, Wait barrier mask, Read barrier index, Write barrier index, Yield flag, Stall cycles"; Table 3.1 V100: L1 data hit latency 28, L2 hit latency ~193, shared no-conflict latency 19; Table 4.1 Volta: "IADD3, SHF, LOP3, SEL, MOV, FADD, FFMA, FMUL, ISETP, FSET, FSETP = 4". Submitted 2018-04-18 (arXiv abs page). Minor nuance: the paper also says "at least 23 bits are used to encode control information" (the 21-bit section plus its 2 leading zero bits) — the note already states both numbers.

2. **Claim:** "On H800 (2025) wgmma m64nNk16 FP16 latency scales 18->128 cycles for N=8->256 and only reaches peak (~729 of 756 TFLOPS) at N>=64; random inputs hit the 350 W limit, dropping clocks 1620->1275 MHz and throughput to ~595 TFLOPS; fine-grained P-chase shows L2 near/far hit 258/414 cycles; TMA adds ~170 cycles latency but >1800 GB/s."
   **Source:** https://arxiv.org/html/2501.12084v2 (v2 dated 2025-09-04; H800 PCIe, CUDA 12.6, driver 560.35.03). Table 9 (FP16 dense SS): N=8 18.0 cyc/158.2 TFLOPS, N=16 20.0/287.0, N=32 24.0/477.3, N=64 32.0/719.6, N=128 64.0/728.5, N=256 128.0/728.5; peak 756.5; recommends "N (>=64) whenever possible". Table 11: random inputs reach the 350 W limit, whitepaper clock 1620 MHz vs measured 1275 MHz, 595 TFLOPS (1.70 TFLOPS/W). Table 4: H800 L2 near hit 258.0, far hit 414.1 (A100 208.0/356.6). TMA: "approximately 170 cycles higher than regular access"; "over 1800GB/s".
   **Caveat (not a refutation):** the 595 TFLOPS figure is from Table 11's FP16 dense SS row; Table 8 reports 704.5 TFLOPS for m64n256k16 with random data at a different setting. The note already cites both numbers in different places, but a reader could take "729 -> 595" as the same experiment; it is not.

3. **Claim:** "RTX 5080 (GB203) vs H100 PCIe (2025-07): 128 KB vs 256 KB L1/shared, ~99 KB vs ~227 KB max shared per SM, L2 hit ~358 vs ~273 cycles, FP64 chain 63.6 vs 8.0 cycles, %clock64 overhead 1 vs 2 cycles, and tcgen05 'not yet implemented for sm_120a' (only GH100 has wgmma)."
   **Source:** https://arxiv.org/html/2507.10789v2 ("arXiv:2507.10789v2 [cs.DC] 21 Jul 2025"). Sec. VI-B: GH100 "up to 256 KB of combined L1/shared memory per SM", GB203 128 KB; "≈227 KB/SM on GH100 and ≈99 KB/SM on GB203". Sec. VI-C: "GB203 exhibits a fixed latency of approximately 358 cycles", "GH100 ... around 273 cycles". Table III pure FP64 true latency 63.57 (GB203) vs 8.04 (GH100). Sec. IV-A: "%clock64" subtracted value "is 1, compared to a value of 2 for GH100". Table IV lists wgmma only for GH100.
   **Correction of wording:** the paper's exact phrase (Table IV caption) is "tcgen05 is yet to be supported for the arch. sm_120a", not "not yet implemented for sm_120a" (the note puts the latter in quotation marks). The paper is also internally inconsistent: Sec. III-4 says "the new tcgen05 instructions can be used for warp-group computation" on Blackwell without qualifying consumer parts.

4. **Claim:** "B200 (2026-03, CUDA 12.6/13.0): tcgen05.mma issues in ~11 cycles vs wgmma 32/64/128 cycles for m64n64/128/256k16; TMEM is 256 KB/SM (512 cols x 128 lanes x 32-bit) with 16 TB/s read; measured FP16 1929.6 / FP8 3850.6 / FP4 7700.2 TFLOPS vs H200 1515/3027; SASS mapping FP8/FP6->QMMA, FP4->OMMA."
   **Source:** https://arxiv.org/html/2512.02189v3 (v3 dated 2026-03-02; arXiv abs shows v1 2025-12-01, v2 2026-02-20, v3 2026-03-02). Table V: tcgen05.mma 11.0/11.3/11.4 cycles (m64n64k16, m128n128k16, m256n256k16) vs wgmma 32.0/64.0/128.0 (m64n64/128/256k16). Sec. V-A: "256KB on-chip memory per SM", 512 columns x 128 lanes x 32-bit; "16 TB/s read bandwidth" appears in text only (no table/measurement backing). Table VII: FP16 1929.6 vs 1515.2, FP8 3850.6 vs 3026.9, FP4 7700.2 vs N/A. Table IV: FP8 (mxf8/f8f6f4) -> QMMA, FP6 (mxf6) -> QMMA, FP4 (mxf4/mxf4nvf4) -> OMMA. CUDA: Sec. VII-A "CUDA 12.6 (B200 and H200)", nvcc 12.6, driver 560.x; the Discussion says "CUDA 13.0 provides preliminary TMEM/CTA support" — so "CUDA 12.6/13.0" is a fair summary, but which toolkit produced the TMEM numbers is unclear in the paper.
   **Caveat:** Table VI vs Table VII disagree by ~2x (FP4 3850.1 vs 7700.2; FP16 964.8 vs 1929.6); the note already flags this.

5. **Claim:** "Nsight Compute warp sampling picks a random active warp per SM every 32-2048 cycles and attributes stalls per SASS instruction via smsp__pcsamp_warps_issue_stalled_<reason> (long_scoreboard, short_scoreboard, mio_throttle, math_pipe_throttle, wait, barrier, lg_throttle, no_instructions, warpgroup_arrive, ...); clocks are locked by default (--clock-control boost) and caches flushed between replay passes (--cache-control all)."
   **Source:** https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html §2.5.2: "The sampler selects a random active warp"; "On small devices, this can be every 32 cycles. On larger chips with more multiprocessors, this may be 2048 cycles."; §2.4.7 lists all 19 stall reasons as `smsp__pcsamp_warps_issue_stalled_<reason>` (barrier, branch_resolving, dispatch_stall, drain, imc_miss, lg_throttle, long_scoreboard, math_pipe_throttle, membar, mio_throttle, misc, no_instructions, not_selected, selected, short_scoreboard, sleeping, tex_throttle, wait, warpgroup_arrive); §2.6.3 "by default flushes all GPU caches before each replay pass"; "Nsight Compute locks SM clocks [by default]". Default values `--clock-control boost` and `--cache-control all` confirmed on https://docs.nvidia.com/nsight-compute/NsightComputeCli/index.html. Wording nuance: the guide's exact phrase is "every 32 cycles ... may be 2048 cycles", not "as low as ... up to" as quoted in the note's KQ3 bullet, but the meaning is the same.

6. **Claim:** "NVBit 1.7 (NVlabs) dynamically rewrites SASS of any precompiled CUDA/OpenCL/OpenACC binary at load time (inject device-function calls before/after any instruction, modify registers, remove instructions) on compute capability 3.5 through 12.1, Linux x86_64/aarch64, CUDA >= 12.0, under the CUDA Toolkit EULA."
   **Source:** https://github.com/NVlabs/NVBit/blob/master/README.md: "NVBit 1.7 is released and contains several breaking changes"; "research prototype of a dynamic binary instrumentation library for NVIDIA GPUs"; "inject one or more instrumentation calls to arbitrary device functions before (or after) a SASS instruction"; "It is also possible to remove SASS instructions"; "SM compute capability: >= 3.5 && <= 12.1"; "Host CPU: x86_64, aarch64"; "OS: Linux"; "CUDA version: >= 12.0"; "covered by the same End User License Agreement as that of the NVIDIA CUDA Toolkit".
   **Corrections:** (a) The README does not list languages — it says any precompiled application works "regardless of which compiler (or version) has been used (i.e. nvcc, pgicc, etc)"; the CUDA/OpenACC/OpenCL/CUDA-Fortran list comes from the MICRO 2019 publication page, which the note cites separately. (b) "modify registers" is not in the README (it is in the 2019 paper's capability list). (c) Newer evidence: https://github.com/NVlabs/NVBit/releases shows NVBit-1.8.1 as the latest release (29 Sep; CMake build, Blackwell URZ decoding fix) and NVBit-1.8 (06 Apr; alpha TMA support on Hopper/Blackwell, Green contexts, CUDA 13.2 headers); SM_120 support arrived in 1.7.4, SM_110 in 1.7.6. The README's "1.7" headline is stale; the note should say "NVBit 1.7.x/1.8.x".

7. **Claim:** "MMA-Sim (MICRO 2026) bit-accurately reverse-engineered 10 MMA units with >1M randomized probes: FP8 tensor-core MMA keeps only F=13 fraction bits in the fused sum on Ada and Hopper but F=25 on Blackwell and RTX Blackwell (RTX PRO 6000); NVIDIA rounds FP32 outputs RZ and FP16 outputs RNE; Hopper/Blackwell use F=25 for FP16/BF16/TF32 (Turing/Ampere F=24, Volta F=23)."
   **Source:** https://arxiv.org/html/2511.10909v3 ("arXiv:2511.10909v3 [cs.AR] 28 Sep 2026"; title "Bit-Accurate Modeling of GPU Matrix Multiply-Accumulate Units: Demystifying Numerical Discrepancy and Accuracy"; "all MMA instructions on ten GPU architectures"; GPUs V100, T4, A100, RTX 4090, H100, B200, RTX PRO 6000 Blackwell, MI100, MI250X, MI300X). Section IV-C table: Volta 23, Turing 24, Ampere 24, Hopper 25, Blackwell 25 (TF32/BF16/FP16); FP8 Ada (QMMA) 13, Hopper (QGMMA) 13, Blackwell (UTCQMMA) 25, RTX Blackwell (QMMA) 25; FP32 outputs RZ_FP32 (except FP8 on Ada/Hopper = RZ_E8M13; CDNA3 = RNE_FP32); FP16 outputs RNE_FP16. Venue confirmed independently: arXiv abs Comments "camera-ready for MICRO 2026"; https://github.com/microsoft/MMA-Sim citation block names MICRO 2026 and lists the ten architectures.
   **Correction:** the ">1M randomized probes" figure is not stated as a result count. The paper only says the original MMA-Sim takes "about 10-20 hours for one million Step 4 tests"; neither the abstract nor the README gives a total number of probes. Rephrase as "on the order of 1M differential tests per target (runtime figure), total not stated".

8. **Claim:** "Consumer Blackwell SM12x (RTX PRO 6000 / RTX 50-series) has no tcgen05 and no TMEM and uses warp-collective register-fed mma.sync with block scaling, e.g. mma.sync.aligned.kind::mxf4nvf4.block_scale.scale_vec::4X.m16n8k64.row.col.f32.e2m1.e2m1.f32.ue4m3; TMA is available; SM10x GEMM kernels will not run on SM12x; a tutorial NVFP4 GEMM reached ~60% of the 2000 TFLOP/s FP4 peak (2026-06, CUDA 13.2)."
   **Source:** https://research.colfax-intl.com/cutlass-tutorial-nvfp4-blockscaled-gemm-on-nvidia-rtx-pro-blackwell-gpus-sm12x/ (dated June 20, 2026): "We used CUDA Toolkit 13.2"; "All measurements were taken on an NVIDIA RTX Pro 6000 Blackwell Server Edition GPU"; "SM12x does not use tcgen05 or TMEM; instead, like with SM8x it uses warp-level mma.sync instructions"; operands "from register memory (RMEM)"; instruction string matches exactly; "Tensor Memory Accelerator (TMA) is available on SM12x"; "SM10x GEMM kernels are completely incompatible with SM12x and will not run on those devices"; "peak theoretical dense FP4 throughput of 2000 TFLOP/s"; "tops out at around 60% of peak theoretical throughput". Independent corroboration: https://nvidia.github.io/cccl/unstable/libcudacxx/ptx/instructions/tcgen05_mma.html lists tcgen05.mma targets as SM_100a/f, SM_103a/f, SM_107a/f, SM_110a/f — no SM_120; https://docs.nvidia.com/cuda/blackwell-tuning-guide/index.html confirms 48 warps/SM, 128 KB shared/SM, 99 KB/block for CC 12.0.

None of the eight load-bearing claims is contradicted by its cited source or by an independent primary source. Wording-level corrections are listed under the confirmed entries (claims 3, 6, 7) and below.

## Other issues (scan of the rest of the note)

- **CCCL tcgen05.mma target list is incomplete.** The note (KQ5) says the CCCL docs list "PTX ISA 8.6, sm_100a, sm_100f, sm_103a, sm_103f — no sm_120". The page actually lists "PTX ISA 86, SM_100a, SM_100f, SM_103a, SM_103f, SM_107a, SM_107f" (some variants add SM_110a/SM_110f; block16/block32 block-scale variants require PTX ISA 88). The conclusion (no sm_120) stands. Verdict: confirmed with correction. Source: https://nvidia.github.io/cccl/unstable/libcudacxx/ptx/instructions/tcgen05_mma.html
- **NVBit version is stale.** "NVBit 1.7 (README, 2026)" — the GitHub releases page shows 1.8.1 as the latest release (1.8 added alpha TMA instrumentation on Hopper/Blackwell and CUDA 13.2 headers; SM_120 support dates from 1.7.4). Verdict: confirmed with correction. Source: https://github.com/NVlabs/NVBit/releases
- **ncu CLI flag list (KQ3) checked in full:** `--clock-control base|boost|force-boost|none|reset` (default boost), `--cache-control all|none` (default all), `--replay-mode kernel|application|range|app-range`, `--app-replay-match grid`, `--print-source sass|ptx|tileir|cuda|cuda,sass`, `--query-metrics-mode base|suffix|all`, `--print-summary none|per-gpu|per-kernel|per-nvtx`, `--metrics` prefixes `regex:`/`group:`/`breakdown:`/`pmsampling:`, `--kernel-name-base function|demangled|mangled`, `--page details|raw|source|session`, `--import-source`, `--target-processes application-only|all`, `-o` macros `%h %p %i` — all present on https://docs.nvidia.com/nsight-compute/NsightComputeCli/index.html. No hallucinated flag found. Verdict: confirmed.
