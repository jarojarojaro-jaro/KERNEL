# Verification of practical.md (NVIDIA track, "Legal boundaries and a practical workflow for the RTX 5060 Ti")

Verified 2026-10-17 by fetching each cited URL and, where possible, an independent primary source. Note: the shared WebSearch budget for this run was exhausted, so independent evidence was gathered by fetching additional primary pages (NVIDIA EULA archive, EUR-Lex, GitHub releases, CUDA Programming Guide, Nsight Compute CLI docs, cuda-gdb docs) instead of a search engine.

## Confirmed

1. **Claim:** CUDA EULA v13.4 (Jan 26, 2026) §1.2 item 1: "You may not reverse engineer, decompile or disassemble, or remove copyright or other proprietary notices from any portion of the SDK or copies of the SDK"; item 8 bans RE of output "for the purpose of translating such output artifacts to target a non-NVIDIA platform"; §2.1 licenses the SDK "only for use in systems with NVIDIA GPUs"; there is no benchmarking/publication clause.
   - Source: https://docs.nvidia.com/cuda/eula/index.html — header "v13.4", body "Last updated: January 26, 2026" (footer "Oct 12, 2026"); §1.2 items 1 and 8 and §2.1 match verbatim; no benchmarking/publishing clause exists (only item 3 on sponsorship/endorsement claims).

4. **Claim:** NVIDIA open kernel modules: individual files MIT, the linked kernel module dual MIT/GPLv2; current version 615.78.08, Turing+ only, must be paired with GSP firmware and user-space from the matching release.
   - Sources: COPYING ("individual files within this package are licensed as MIT", "resulting Linux kernel module is dual licensed as MIT/GPLv2"); README (version 615.78.08, "any Turing or later GPU", GSP firmware + user-space from matching 615.78.08 release, `--no-kernel-modules`). Independent: https://github.com/NVIDIA/open-gpu-kernel-modules/releases marks 615.78.08 (07 Oct) as "Latest"; 595.104.02 (22 Sep) is the newest production-branch release.

5. **Claim:** CUDA 13.4 Update 2: existing CUDA 13.x apps run on drivers >=580 via minor-version compatibility, 13.4 uses driver branch R615, and from 13.4 the Linux toolkit no longer bundles the driver; cuBLAS has known issues specific to compute capability 12.0/12.1.
   - Source: https://docs.nvidia.com/cuda/cuda-toolkit-release-notes/index.html — title "CUDA Toolkit 13.4 Update 2 - Release Notes"; Table 2: R615; "CUDA 13.4 new features ... require an R615 or later driver"; Table 3: 13.x ">= 580"; "Existing CUDA 13.x applications run on drivers >=580 under CUDA minor version compatibility"; driver "no longer bundled" on Linux from 13.4. cuBLAS CC 12.0/12.1 issues (OOB reads in strided-batched GEMM with broadcast operands; wrong GEMV-like results with transposed matrix) are present. Caveat: those two issues are listed in the 13.0 Update 2 … 13.3 Update 1 sections, not in the 13.4 / 13.4 Update 1 sections — the note's phrasing "cuBLAS 13.x known issues" is accurate, but they may be fixed in 13.4.

6. **Claim:** Family-specific targets introduced in CUDA 12.9: sm_XXa has no forward compatibility for PTX or cubin, sm_XXf runs within the same major CC family; sm_100f currently covers 10.0 and 10.3 (consumer sm_120 is a separate family).
   - Source (blog): "There is no forward-compatibility for either PTX or a cubin when using the architecture-specific `a` suffix"; "Family-specific features are guaranteed to be available in the same family of GPUs" (same major CC, equal/higher minor); "Currently, this is 10.0 and 10.3 compute capability GPUs"; `code=sm_100` and `code=sm_100f` are aliases. The blog does NOT mention sm_120.
   - Independent primary source for the sm_120 part: CUDA Programming Guide 13.4, Compute Capabilities, Table 28: `compute_100f` = 10.0, 10.3, 10.7; `compute_103f` = 10.3, 10.7; `compute_110f` = 11.0; `compute_120f` = 12.0, 12.1; `compute_121f` = 12.1. So sm_120 is indeed a separate family. **Correction/update:** "currently 10.0 and 10.3" is the 2025 blog's state; as of CUDA 13.4 the sm_100f family is 10.0, 10.3 and 10.7.

7. **Claim:** On consumer Blackwell (RTX 5080, GB203) Hopper wgmma is not compatible, tcgen05 is not supported on sm_120a, FP4/FP6 require mma.sync with .kind::f8f6f4 (SASS QMMA/OMMA); measured L1 128 KB (max 99 KB shared), L2 hit ~358 cycles, DRAM ~877 cycles, register file 256 KB/SM.
   - Source: https://arxiv.org/html/2507.10789v2 — RTX 5080 (GB203) vs H100 PCIe; "the Hopper wgmma instructions are not compatible with Blackwell"; Table IV: "tcgen05 is yet to be supported for the arch. sm_120a" (the paper's Table IV is internally inconsistent, also listing tcgen05 under GB203); ".kind::f8f6f4 suffix must be explicitly specified"; FP8/FP6 → QMMA, OMMA observed only with ue8m0 block scaling (plain FP4 also produced QMMA); L1 128 KB/SM (Table II, stated not measured); shared ≈ 99 KB/SM dynamic (48 KB static); L2 hit ≈ 358 cycles; global ≈ 876.7 cycles (≈ 877); register file 256 KB/SM (Table II). Minor nuance: L1 and RF sizes are tabulated spec values, not microbenchmark measurements.

8. **Claim:** Nsight Compute profiling on Linux is blocked for non-root users on drivers 418.43+ (ERR_NVGPUCTRPERM); fix is a /etc/modprobe.d .conf with 'options nvidia NVreg_RestrictProfilingToAdminUsers=0' plus update-initramfs; drivers R610+ move to a capabilities-based system.
   - Source: ERR_NVGPUCTRPERM page — "driver versions 419.17+ on Windows or 418.43+ on Linux"; `.conf` in `/etc/modprobe.d` with `nvidia NVreg_RestrictProfilingToAdminUsers=0` (the page's text shows the option as `options nvidia NVreg_RestrictProfilingToAdminUsers=0` in the modprobe.d form); Debian: `update-initramfs -u -k all`; "Starting with driver version R610, NVIDIA introduces a capabilities-based permission system"; "In a future release, the regkey-based method will be removed."

## Refuted with corrections

2. **Claim:** The translation-layer clause appeared in the installed EULA from CUDA 11.6 (absent in 11.4/11.5 docs), spotted in March 2024 and tied by reporting to ZLUDA and Chinese GPU makers; NVIDIA made no official statement.
   - Cited source (Gigazine 2024-03-05) says, citing Tom's Hardware, that the clause is absent from the 11.4 and 11.5 *documentation* and appears from 11.6, that it "was first in the online EULA, and later also appeared in installed CUDA documentation", ties it to ZLUDA, Denglin and Moore Threads (MUSIFY), and reports no NVIDIA statement. It does NOT name "Longhorn" or an installed EULA.txt.
   - **Contradicting primary source:** NVIDIA's own EULA archive. https://docs.nvidia.com/cuda/archive/11.5.0/eula/index.html (EULA v11.5.0, agreement "Last updated: October 8, 2021") already contains §1.2 item 8 "You may not reverse engineer, decompile or disassemble any portion of the output generated using SDK elements for the purpose of translating such output artifacts to target a non-NVIDIA platform." https://docs.nvidia.com/cuda/archive/11.4.0/eula/index.html (v11.4.0, "May 24, 2021") and 11.3.0 do not contain it.
   - **Correction:** the clause first appears in the online CUDA EULA with v11.5 (October 8, 2021), not 11.6; the "from 11.6" wording in the 2024 reporting refers to the installed documentation/EULA.txt, and "absent in 11.5 docs" is wrong for the online archive. The "Longhorn" attribution and the "installed EULA.txt" detail are not in the cited Gigazine article (Tom's Hardware, OC3D and Phoronix bodies were not retrievable: 403/truncated). The ZLUDA/Chinese-GPU-maker link and the absence of an NVIDIA statement are supported by Gigazine.

3. **Claim:** EU Directive 2009/24/EC Art. 6 allows decompilation without authorisation when indispensable for interoperability of an independently created program, and Recital 17 declares contrary contractual provisions null and void.
   - Art. 6(1) is confirmed verbatim at https://www.legislation.gov.uk/eudr/2009/24/article/6 ("The authorisation of the rightholder shall not be required where reproduction of the code and translation of its form ... are indispensable to obtain the information necessary to achieve the interoperability of an independently created computer program with other programs").
   - **Recital number is wrong.** Both https://www.legislation.gov.uk/eudr/2009/24/data.htm and EUR-Lex https://eur-lex.europa.eu/eli/dir/2009/24/oj/eng place the "null and void" language in **Recital 16** ("any contractual provisions contrary to the provisions of this Directive laid down in respect of decompilation or to the exceptions provided for by this Directive ... should be null and void"). Recital 17 is about the Treaty competition rules (Art. 81/82) applying when a dominant supplier refuses to provide interoperability information. The cited article/6 page itself contains no recital text. Also note the binding provision is Art. 8 (second paragraph: contractual provisions contrary to Art. 6 or to Art. 5(2)/(3) are null and void) — recitals are not operative text.
   - **Correction:** replace "Recital 17" with "Recital 16 (and Art. 8, second paragraph)" in Q2 Takeaway and Cited Findings. Recital 11 ("ideas and principles ... not protected by copyright") and Art. 5(3) (observe/study/test while performing permitted acts) are confirmed on data.htm.
