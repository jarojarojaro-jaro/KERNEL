# NVIDIA track: case studies where reverse engineering produced faster kernels

Research note, 2026-10-17. Scope: documented cases where reverse engineering NVIDIA kernels/hardware (SASS dumps, microbenchmarking, cuBLAS inspection, binary patching) led to faster kernels, and the reusable optimization lessons. Every number carries a date/version from its source. Items I could not verify are marked "(unverified)" or moved to Gaps.

Terminology reminder for the Polish report: SASS = native NVIDIA machine code (output of `cuobjdump -sass` / `nvdisasm`); PTX = virtual ISA; "control codes" = per-instruction scheduling bits (stall count, yield, read/write dependency barriers, wait mask, register reuse flags) that NVIDIA does not document publicly.

## KQ1. Scott Gray maxas SGEMM vs cuBLAS on Maxwell; which lessons still hold

### Takeaway
maxas (2014-2017) is the canonical case: by reverse engineering the Maxwell SASS encoding (4 register banks, per-operand reuse cache, control codes for stall/yield/dual issue) Scott Gray hand-scheduled an SGEMM that reached ~96-98% of theoretical FLOPS and beat cuBLAS by 4.8% at 4096x4096 and up to 25% on small matrices (GM204, author's benchmarks). The micro-architectural lessons (register bank conflicts, reuse flags, LDS/FFMA interleaving, double buffering) are still the exact mechanisms DeepSeek exploited on Hopper in 2025 and that the 2025 "Analyzing Modern NVIDIA GPU cores" paper confirms are still present.

### Cited Findings
- maxas SGEMM, 256-thread version: "At the 4096 size we're beating cublas by 4.8%"; 64-thread version "performing as much as 25% over cublas" on small matrices; code runs "within 2% of the theoretical flops" (~98% on GM107, ~96% on GM204, GM204 at 1607 MHz). — [maxas wiki: SGEMM](https://github.com/NervanaSystems/maxas/wiki/SGEMM)
- Register bank model found by RE: Maxwell has 4 register banks, bank = register number mod 4; an FFMA can read at most one operand per bank per clock. Register layout used: R0-63 for the 8x8 C accumulators, R64-71/R80-87 double-buffered A, R72-79/R88-95 double-buffered B; this eliminates C-vs-blocking conflicts, leaving 16 unavoidable conflicts among blocking registers that the reuse cache hides. — [maxas wiki: SGEMM](https://github.com/NervanaSystems/maxas/wiki/SGEMM)
- The author found a flaw in cuBLAS's Maxwell SGEMM: the first FFMA placed on C register 3 causes a bank conflict that he estimates costs cuBLAS ~28 GFLOPS on GM204. — [maxas wiki: SGEMM](https://github.com/NervanaSystems/maxas/wiki/SGEMM)
- Operand reuse cache: 8 bytes per source-operand slot, 3 slots for FFMA; maxas sets reuse flags automatically. Ordering matters: row-by-row loop uses 4 of 8 bytes/slot, back-and-forth ordering gives 39% reuse, a "swirl" ordering 47%. Without the reuse cache the 16 remaining conflicts would add ~128 clocks to a 520-clock loop (~20%). — [maxas wiki: SGEMM](https://github.com/NervanaSystems/maxas/wiki/SGEMM)
- Instruction budget per unrolled loop (8 K-lines): 512 FFMA + 32 LDS (dual-issued) + 4 STS + 4 TLD + 4 IADD + 3 XOR + 1 SETP + 1 BAR + 1 BRA; 512/520 = 98.5% upper bound. LDS spaced two instructions apart "since the memory unit works best at half throughput"; BAR.SYNC between FFMA blocks 7 and 8; STS as late as possible. The author states ptxas tends to optimize away his double-buffered shared loading scheme, so ordering is hand-controlled. — [maxas wiki: SGEMM](https://github.com/NervanaSystems/maxas/wiki/SGEMM)
- Occupancy choice: both versions keep registers under 128 to hold 4 warps/scheduler; the measured instruction cache is 8 KB (practical limit ~768 instructions per loop). Failed experiments: double-buffered texture loads (slower; extra PSETP), block remapping (lower L2 hit rate). — [maxas wiki: SGEMM](https://github.com/NervanaSystems/maxas/wiki/SGEMM)
- Independent confirmation: the maxDNN paper (Jan 2015) describes maxas SGEMM reaching ~96% efficiency on GM204 using double-buffered global/shared loads and 128-bit loads, at 25% occupancy because each warp uses 127 registers. — [maxDNN, arXiv:1501.06633](https://arxiv.org/pdf/1501.06633)
- NVIDIA forum consensus: no official documentation of register banks; the community-RE model is 4 banks on Maxwell, with an argument reuse cache on Maxwell/Pascal; ptxas normally handles bank assignment. — [NVIDIA forum: register bank conflict](https://forums.developer.nvidia.com/t/about-register-bank-conflict/47853); [NVIDIA forum: Register Bank trace](https://forums.developer.nvidia.com/t/register-bank-trace/60315)
- The same fields still exist on Turing: per-instruction control word has reuse flags (4 bits), wait barrier mask (6), read barrier index (3), write barrier index (3), yield flag (1), stall cycles (4). — [Dissecting the NVIDIA Turing T4 GPU via Microbenchmarking, arXiv:1903.07486](https://arxiv.org/pdf/1903.07486); Volta encoding (incl. YIELD/BSYNC/WARPSYNC opcodes) in [Dissecting the NVIDIA Volta GPU Architecture, arXiv:1804.06826](https://arxiv.org/pdf/1804.06826)
- 2025 confirmation that these mechanisms persist: "Analyzing Modern NVIDIA GPU cores" (26 Mar 2025, RTX A6000 as reference, also applies to Turing) reverse-engineers the issue logic, the register file "and its associated cache", shows "the compiler guides hardware during execution" and that software-based dependence management (control bits) beats a hardware scoreboard in performance and area; their model reaches 13.98% MAPE vs real A6000. — [arXiv:2503.20481](https://arxiv.org/abs/2503.20481)
- HN commenter on the DeepGEMM thread: "Scott Grey worked out this exact thing and more for Maxwell in 2015"; another said a 3-person team at his former company RE'd most of Volta's SASS encoding and built a working assembler. — [HN thread 43179478](https://hn.svelte.dev/item/43179478)

### Inferences
- Still valid today: (1) register bank conflicts and the operand reuse cache (confirmed 2019 Turing, 2025 Ampere papers); (2) hand-controlling instruction interleaving of memory ops between math ops; (3) choosing low occupancy with large per-thread tiles when latency is covered by ILP; (4) double buffering at both register and shared-memory level. What changed: on Hopper/Blackwell the math is done by asynchronous WGMMA/tcgen05 from shared memory/TMEM, so the FFMA-level scheduling matters only for the CUDA-core parts (epilogues, softmax, FP8 promotion) - exactly where DeepSeek got its 10% (see KQ2).
- Scott Gray's tooling lineage: maxas (Maxwell) -> community CuAssembler (Pascal..Ampere, "subject to change") and TuringAs; redplait's denvdis (2025) is the latest community SASS disassembler with barrier/register dependency tracking. — [CuAssembler fork](https://github.com/bogan-FMA/CuAssembler); [denvdis](https://github.com/redplait/denvdis)

### Gaps
- No independent third-party re-run of maxas vs cuBLAS numbers; all figures are the author's own (2017 wiki, repo archived).
- The Nervana (neon) convolution kernels are mentioned in maxDNN but I did not find a separate write-up with numbers beyond the maxDNN paper.

## KQ2. DeepSeek DeepGEMM (FP8 GEMM on Hopper), FFMA interleaving / yield bit, FlashMLA, PTX warp specialization, lessons from CUTLASS

### Takeaway
DeepGEMM (Feb 2025) is the best-documented modern case: DeepSeek diffed SASS produced by NVCC 12.2 vs 12.3 for CUTLASS's FP8 kernel, noticed a single control bit flipping in an interleaved pattern on FADD instructions, guessed it was the "yield" bit, and wrote a script that patches the compiled `.so` in place (flipping yield bit 45 and reuse bit 59 of the high 64-bit word of selected FFMA instructions) for 10%+ speedup on fine-grained-scaling FP8 GEMMs; NVCC 12.9 later adopted the same interleaving so the hack was retired. DeepGEMM reports 1.0x-2.7x vs their CUTLASS 3.6 baseline and up to 1358-1550 TFLOPS on H800 (NVCC 12.8, 2025).

### Cited Findings
- DeepGEMM FFMA interleaving (original README text, mirrored): comparing SASS of NVCC 12.2 vs 12.3 showed "one bit in a series of FADD instructions is flipped in an interleaving pattern"; the authors "identified that this bit controls yield" (described as "just a guess"); they also flip the reuse bit "because registers cannot be reused if the warp is yielded"; script `deep_gemm/jit/interleave_ffma.py`; result "10%+ in some cases" for fine-grained scaling FP8 GEMMs. — [DeepGEMM README mirror (AlignmentResearch)](https://github.com/AlignmentResearch/DeepGEMM)
- Exact mechanics of `interleave_ffma.py`: dumps SASS with `cuobjdump -sass <file>`; collects runs of >=16 consecutive FFMA lines; parses the 128-bit encoding from `/* 0x... */` comments (low 64 bits + high 64 bits, little-endian); reuse detected via `high_hex & 0x0800000000000000` (bit 59); modification `high_hex ^= 0x0800200000000000` (flips bit 59 = reuse and bit 45 = yield) on FFMA pairs where the destination register is first seen or where the previous pair reused the same destination; patches the `.so` in place via `mmap` (no relink); debug env var `DG_PRINT_REG_REUSE`. — [interleave_ffma.py (mirror)](https://raw.githubusercontent.com/AlignmentResearch/DeepGEMM/main/deep_gemm/jit/interleave_ffma.py)
- Current DeepGEMM README: "As NVCC 12.9 will automatically do the FFMA interleaving, all post optimizations will be no longer supported"; "DeepGEMM now achieves up to 1550 TFLOPS on H800!" (news 2025.04.18); supports SM90 (NT layout only, FP32 scales) and SM100 (all layouts, packed UE8M0 scales); full JIT refactor 2025.07.20; latest news 2026.09.30 (Ascend port, locality-domain optimizations). — [deepseek-ai/DeepGEMM](https://github.com/deepseek-ai/DeepGEMM)
- Performance table (H800 SXM5, NVCC 12.8, vs internal CUTLASS 3.6-based baseline): dense GEMM speedups 1.0x-2.7x, best 2.7x at M=64,N=2112,K=7168 (206 TFLOPS), peak 1358 TFLOPS at M=4096,N=7168,K=16384 (1.2x); grouped contiguous (MoE) 1.1x-1.2x up to 1297 TFLOPS; grouped masked 1.1x-1.2x up to 1233 TFLOPS. — [DeepGEMM README mirror](https://github.com/AlignmentResearch/DeepGEMM)
- Other DeepGEMM techniques (all CUTLASS-derived or extended): persistent warp specialization overlapping TMA loads, tensor-core MMA and CUDA-core promotion; TMA for LHS/RHS/scales load, output store, TMA multicast (LHS only), TMA descriptor prefetch; unaligned block sizes (e.g. M=256,N=7168: 128x128 tiles use 112 of 132 SMs, block N=112 uses all 128 usable blocks); rasterization for L2 reuse; CUDA-core two-level accumulation ("promotion") for FP8; fully JIT so tile shapes, groups, pipeline stages are compile-time constants ("similar to the approach of the Triton compiler"). "DeepGEMM is inspired by the CUTLASS project." — [DeepGEMM README mirror](https://github.com/AlignmentResearch/DeepGEMM)
- Why promotion is needed (hardware finding from the DeepSeek-V3 report, Dec 2024): "the accumulation precision of FP8 GEMM on NVIDIA H800 GPUs is limited to retaining around 14 bits"; "the Tensor Core only uses the highest 14 bits of each mantissa product for addition ... and truncates bits exceeding this range"; fix: copy partials to FP32 registers on CUDA cores every N_C = 128 elements (= 4 WGMMAs), overlapped because "it is typical for two WGMMA to persist concurrently: while one warpgroup performs the promotion operation, the other is able to execute the MMA operation." — [DeepSeek-V3 Technical Report, arXiv:2412.19437](https://arxiv.org/pdf/2412.19437) (text extracted locally from the PDF)
- DeepSeek's PTX use (verbatim from the V3 report, section 3.2.2): "we employ the warp specialization technique (Bauer et al., 2014) and partition 20 SMs into 10 communication channels" for all-to-all; "we employ customized PTX (Parallel Thread Execution) instructions and auto-tune the communication chunk size, which significantly reduces the use of the L2 cache and the interference to other SMs." — [DeepSeek-V3 Technical Report](https://arxiv.org/pdf/2412.19437)
- Community interpretation of the control bits (unofficial): yield bit lets the scheduler switch warps; "When the yield bit is set, the reuse bit must be cleared"; this is a practical observation from the FP8 kernel write-up, not NVIDIA documentation. — [search summary of CuAssembler/Turing paper material](https://arxiv.org/pdf/1903.07486); HN discussion: commenters agree these details are only in internal NVIDIA docs. — [HN 43179478](https://hn.svelte.dev/item/43179478)
- Caveat on the DeepGEMM baseline: HN commenter notes CUTLASS GEMMs are usually within ~10% of cuBLAS, so a 2x-2.7x gain on small-M shapes mostly reflects the baseline's weakness on those shapes; another measured FP8 cuBLASLt on H200 peaking ~1.35 PFLOPS (~67% of advertised dense). — [HN 43179478](https://hn.svelte.dev/item/43179478)
- FlashMLA (Hopper -> Blackwell): 2025.04.22 new dense kernel up to 660 TFLOPS on H800 SXM5; 2025.08.01 SM100 MHA fwd/bwd 1460/1000 TFLOPS on B200 "as reported by NVIDIA"; 2026.09.10 fused norm-RoPE-attn-RoPE-cast kernel 1460 TFLOPS prefill / 950 decode on B200 with CUDA 13.3; Hopper support dropped 2026.09.30; deep-dive docs `docs/20250422-new-kernel-deep-dive.md`, `docs/20250929-hopper-fp8-sparse-deep-dive.md`. SM120 not mentioned. — [deepseek-ai/FlashMLA](https://github.com/deepseek-ai/FlashMLA)
- CuAsmRL (CGO 2025, Jan 2025): RL agent mutating `-O3` SASS schedules yields up to 26% speedup, 9% average, over existing specialized CUDA kernels, and "reveals optimization moves the agent learned automatically"; its stall counts come from dependency-based microbenchmarks (more accurate than clock-based). — [arXiv:2501.08071](https://arxiv.org/abs/2501.08071)

### Inferences
- The DeepGEMM yield-bit trick is a direct 2025 descendant of maxas: same bit class (control codes), same discovery method (diff SASS of two compilers), same tool (`cuobjdump -sass`). The reusable procedure: compile with two NVCC versions, `cuobjdump -sass` both, diff the `/* 0x... */` encodings, hypothesize the field, patch, benchmark. The fact that NVCC 12.9 adopted it shows the trick was a genuine compiler-heuristic gap, not a hardware secret.
- "Customized PTX" in DeepSeek-V3 is about communication kernels (all-to-all on 20 SMs) and cache-control (reducing L2 pollution, presumably via cache hints such as `ld.global.L2::evict_*`/`cp.async.bulk`), not about rewriting GEMMs in PTX; the GEMM-side tricks live in DeepGEMM and are CUDA + inline PTX + SASS patching. (The exact PTX instructions are not named in the report - see Gaps.)
- For the user's RTX 5060 Ti (sm_120): DeepGEMM and FlashMLA target SM90/SM100 only (TMA multicast, tcgen05/TMEM); none of the DeepSeek kernels run on consumer Blackwell as-is. The transferable lesson is the FP8 promotion pattern and the SASS-diff methodology, both usable with `cuobjdump` on any arch.

### Gaps
- Which PTX instructions DeepSeek used for the all-to-all kernels is not specified in the report; DeepEP source would answer it (not read).
- NVIDIA has never documented the yield/reuse bit positions; bit 45/59 are from DeepSeek's code and Jia et al.'s encoding tables, not from NVIDIA.
- FlashMLA's Hopper design details (ping-pong, seesaw scheduling) are in `docs/20250422-new-kernel-deep-dive.md`, which I did not fetch.

## KQ3. FlashAttention-2/3, "Outperforming cuBLAS on H100" (fast.cu), ThunderKittens, CUTLASS 3/4 CuTe; how authors study cuBLAS/cuDNN

### Takeaway
The H100-era write-ups show the 2024-2025 recipe that beats or matches NVIDIA libraries without SASS hacking: WGMMA + TMA + producer/consumer warp specialization + setmaxnreg register reallocation + persistent kernels with L2-aware tile ordering (Hilbert/grouped) + thread-block clusters with TMA multicast. fast.cu reached 764 TFLOPS bf16 vs cuBLAS 716 (107%) at 4096^3 on H100 SXM, CUDA 12.6 (Nov 2024); FA3 reached 740 TFLOPS FP16 (75% utilization) and ~1.2 PFLOPS FP8 (Jul 2024). Notably, these authors profiled their own kernels (in-kernel cycle counters, ncu stall reasons), and compared aggregate metrics with cuBLAS (e.g. L2 hit rate 83% vs 70%) rather than reading cuBLAS SASS.

### Cited Findings
- fast.cu worklog (29 Nov 2024, H100 SXM 132 SMs, 50 MB L2, CUDA 12.6 V12.6.68, bf16 M=N=K=4096) kernel progression in TFLOPS: K1 32 (SGEMM port) -> K2 317 (WGMMA + TMA, 128x128) -> K3 423 (BM=128,BN=128,BK=64, m64n128k16) -> K4 498 (producer/consumer warpgroups, QSIZE=5) -> K5 123->610->631 (128x256 tile; ptxas warning C7511 "insufficient register resources" at 123; 2 consumer warpgroups; per-warpgroup register reallocation to 168 regs/thread, 64512/block) -> K6 400->660 (persistent kernel on 132 blocks; linear tile order regressed to 400, grouped 16x8 L2-friendly order 660) -> K7 704 (raw PTX mbarrier, 98% of cuBLAS) -> K8 734 (clusters of 2 + TMA multicast, 102%) -> K9 747 (`__stwt` stores, accumulate flag) -> K10 758 (epilogue via SMEM + TMA store) -> K11 764 (Hilbert-curve tile order, ~107% of cuBLAS). cuBLAS baseline ~716 TFLOPS. L2 hit rate 83% vs cuBLAS 70%. Results by N: +2% at 512, +17% at 1024, +7-8% at 2048/4096, +1.5% at 8192 (power-capped at 700 W). — [Outperforming cuBLAS on H100: a Worklog](https://cudaforfun.substack.com/p/outperforming-cublas-on-h100-a-worklog); repo README: 763 vs 716 TFLOPS at N=4096, 808 vs 795 at N=8192. — [pranjalssh/fast.cu mirror](https://gitee.com/hotheart1982/fast.cu)
- The worklog explicitly does not read cuBLAS SASS; profiling was in-kernel cycle counting (Load ~1415, Tensor Core ~703, Store ~4572 cycles) and the only cuBLAS-specific measurement is the L2 hit rate; the author notes cuBLAS wins for small-K/matrix-vector shapes. — [cudaforfun worklog](https://cudaforfun.substack.com/p/outperforming-cublas-on-h100-a-worklog)
- FlashAttention-3 (paper v1 11 Jul 2024; blog Jul 2024): FA2 reached 35% of H100 FLOPS (~350 TFLOPS fwd FP16); plain Hopper rewrite (WGMMA+TMA, no overlap) 540-570; pingpong scheduling between two warpgroups (`bar.sync`) 570->620 (hdim 128, seqlen 8K); intra-warpgroup softmax/GEMM overlap 620->640-660 at higher register pressure; final up to 740 TFLOPS FP16 (75%), ~1.2 PFLOPS FP8 with 2.6x lower error via incoherent processing (random-sign Hadamard, O(d log d)). H100 numbers used: 989 TFLOPS FP16, 1978 FP8, 3.9 TFLOPS special functions (exp is 256x slower than matmul). Old `mma.sync` reaches only ~2/3 of Hopper peak. Built on CUTLASS; compared to FA2, Triton, cuDNN. — [Tri Dao FA3 blog](https://tridao.me/blog/2024/flash3/); [arXiv:2407.08608](https://arxiv.org/abs/2407.08608)
- ThunderKittens "GPUs Go Brrr" (12 May 2024): "Keep the tensor core fed. That's it."; H100 ~989 TFLOPS matmul vs ~60 TFLOPS other compute; without `wgmma.mma_async` the GPU tops out ~63% of peak; WGMMA swizzled layouts "are documented incorrectly"; SMEM ~30 cycle latency, 32 banks -> swizzle; TMA offloads address generation; occupancy matters less on H100 than on A100/RTX 4090; 16x16 tile is the basic "register"; ~100-line H100 attention kernel ~30% faster than FA2, ~60-line RTX 4090 kernel at ~75% utilization. — [Hazy Research blog](https://hazyresearch.stanford.edu/blog/2024-05-12-tk)
- Reverse-Engineering cuBLAS (ACCU Overload 32(181), June 2024; GitHub original 14 Mar 2024; A5000, tensor-core HGEMM): the author compared an abbreviated SASS listing of the cuBLAS kernel against his own and looked at per-instruction counts and stall reasons (long scoreboard). Lessons taken from cuBLAS SASS: main loop starts with the MMA rather than a load; loads bypass registers (`cp.async` global->shared), are asynchronous and interleaved with math; wait-group count differs (1 load in flight). Progression: 60 TFLOPS (sync loads) -> 73 (`cp.async`, 2 buffers) -> 89 (double buffering smem + registers, wait_group 1; 95% of cuBLAS) -> 91 (epilogue via SMEM; 1 TFLOP behind cuBLAS). cuBLAS ships ~5000 kernels with "GEMM" in the name, ~100 MB. — [ACCU: Reverse-Engineering cuBLAS](https://accu.org/journals/overload/32/181/schuetze/)
- siboehm worklog (Dec 2022, RTX A6000, FP32 4092^2): naive 309 GFLOPS (1.3% of cuBLAS) -> coalescing 1987 (8.5%) -> SMEM 2980 (12.8%) -> 1D blocktile 8475 (36.5%) -> 2D blocktile 15972 (68.7%) -> vectorized 18237 (78.4%) -> autotune 19721 (84.8%) -> warptiling 21779 (93.7%) vs cuBLAS 23250. Used `cuobjdump --list-text` to list cuBLAS SGEMM kernels and tracing to see that different kernels (incl. split-K at size 256) launch at different sizes; Godbolt PTX/SASS to confirm unrolling/vectorization (`float4` via `reinterpret_cast` needed for 128-bit loads); Nsight Compute stall reasons (MIO throttle). Kernels 7-8 (bank-conflict-free) were slower and dropped. — [siboehm: How to Optimize a CUDA Matmul Kernel](https://siboehm.com/articles/22/CUDA-MMM)
- Hamza El Shafie's 2025 H100 worklog follows the same path (WIP). — [bearblog worklog](https://hamzaelshafie.bearblog.dev/worklog-optimising-gemm-on-nvidia-h100-for-cublas-like-performance-wip)

### Inferences
- Two complementary RE styles: (a) "read the library's SASS" (ACCU article, siboehm's cuobjdump listing) to learn loop structure; (b) "measure, don't read" (fast.cu, FA3) using ncu metrics and in-kernel clocks and treating cuBLAS as a black-box baseline. Style (a) is what REA's `inspect_with_objdump`/Ghidra could help with only partially: Ghidra/objdump do not decode SASS; `cuobjdump`/`nvdisasm` from the CUDA toolkit are required (see KQ4).
- The biggest wins on H100 come from scheduling tiles for L2 (grouped/Hilbert ordering: 400->660->764 TFLOPS in fast.cu) and from asynchronous overlap, not from instruction-level tricks; instruction-level tricks remain decisive only on the CUDA-core critical path (FA3 softmax, DeepGEMM promotion).
- The WGMMA swizzle-layout documentation error noted by ThunderKittens is itself a RE finding (they had to probe layouts empirically).

### Gaps
- I could not find a write-up where FA3 or fast.cu authors read cuBLAS/cuDNN SASS with ncu "Source" view; their stated methods are profiler metrics and own-kernel counters.
- setmaxnreg values (24/240) and ablations are in the FA3 paper body, which I did not read (abstract only).

## KQ4. Reverse engineering vendor libraries: cuBLAS/cuBLASLt heuristics, cuDNN, kernel names; llama.cpp CUDA kernels as readable examples

### Takeaway
Nobody has published a decoding of cuBLAS's heuristic tables; what exists is (1) listing/dumping kernels with `cuobjdump --list-text` / `-sass` (siboehm, ACCU), (2) inferring tile/stage/pipeline parameters from kernel names (`ampere_h16816gemm_128x128_ldg8_stages_32x3_nn`: name parsing is community convention, NVIDIA says these names "won't be documented anywhere"), (3) cuBLASLt's own API (`cublasLtMatmulAlgoGetHeuristic`, algo config attributes, logging env vars) which exposes the selected tile/stages/split-K legally. llama.cpp's ggml-cuda is the best open, readable reference for quantized GEMM (MMQ with int8 `mma.sync` via inline PTX in `ggml-cuda/mma.cuh`, 1.65-1.77x over dp4a MMQ and up to 2.08x over cuBLAS at small batch on RTX 3090/4090, June 2024).

### Cited Findings
- cuBLAS contains ~5000 kernels with "GEMM" in the name (~100 MB) and picks "the best-performing kernel at runtime" (June 2024). — [ACCU article](https://accu.org/journals/overload/32/181/schuetze/)
- `cuobjdump --list-text` lists the SGEMM kernels inside libcublas; tracing shows different kernels per matrix size, including split-K at N=256 (Dec 2022). — [siboehm](https://siboehm.com/articles/22/CUDA-MMM)
- NVIDIA forum on `ampere_sgemm_128x128_nn`-style names: "It's probably coming from a cublas call, or a library that uses cublas, like cudnn"; such names won't be documented. A related thread shows `stages_64x3` and asks why minimum stage count is 3 on Ampere. — [NVIDIA forum ampere_sgemm_128x128_nn](https://forums.developer.nvidia.com/t/ampere-sgemm-128x128-nn/208602); [NVIDIA forum gemm stage on ampere](https://forums.developer.nvidia.com/t/gemm-stage-on-ampere/285751)
- Community reading of `ampere_h16816gemm_128x128_ldg8_stages_32x3`: arch prefix; `h16816` = FP16 `mma.sync.m16n8k16`; `128x128` = CTA output tile; `ldg8` = 8 x FP16 (16 B) vector global loads; `stages_32x3` = BK=32 with 3 pipeline stages (unverified convention, not an NVIDIA spec). — derived from the forum thread above and search summary; treat as inference.
- cuBLAS legacy logging env vars (cuBLAS docs v13.4): `CUBLAS_LOGINFO_DBG=1` turns logging on; `CUBLAS_LOGDEST_DBG=stdout|stderr|<file>`; `CUBLAS_WORKSPACE_CONFIG=:16:8` style workspace config; `CUBLAS_GEMM_AUTOTUNE` (legacy): "The library will benchmark a number of available algorithms and choose the optimal one for the given problem configuration." The cuBLASLt sections (3.1.2 "Heuristics Cache", 3.1.3 "cuBLASLt Logging", `cublasLtMatmulAlgoGetHeuristic`, `cublasLtMatmulTile_t`, `cublasLtMatmulStages_t`, `cublasLtMatmulAlgoConfigAttributes_t`) exist as headings in the same doc. — [cuBLAS documentation v13.4](https://docs.nvidia.com/cuda/cublas/index.html)
- cuBLASLt vs hand kernels (CUDA-L2, Dec 2025, HGEMM, 1000 configs; GPU not stated on abstract page): RL-generated kernels +19.2% vs cuBLAS, +16.8% vs cuBLASLt-heuristic, +11.4% vs cuBLASLt-AutoTuning (best of up to 100 candidates) offline; +26.0%/+22.4%/+15.9% in server mode. Shows the heuristic leaves measurable headroom vs exhaustive search. — [arXiv:2512.02551](https://arxiv.org/abs/2512.02551)

## KQ5. Inference-engine level: vLLM/SGLang/TensorRT-LLM kernels, Marlin/Machete, GPU MODE competitions (NVIDIA tracks), agentic kernel generation using profiler/SASS feedback

### Takeaway
Marlin (W4A16, `mma.sync.m16n8k16` + `cp.async`) was built from first principles for Ampere; Machete (Oct 2024, Neural Magic/Red Hat) explicitly diagnosed why Marlin loses ~37% of peak on Hopper (`mma` instead of `wgmma`) and rebuilt it on CUTLASS 3.5.1's mixed-input GEMM with pre-shuffled weights and TMA/warp specialization, giving 29-42% end-to-end throughput gains on H100 for Llama 3.1 70B/405B. The 2025-2026 NVIDIA x GPU MODE NVFP4 hackathon (Blackwell, CuTeDSL, TMEM/tcgen05) shows the current frontier; RL/LLM systems (CUDA-L2, CuAsmRL) now optimize at CUDA and even SASS level with runtime as reward.

### Cited Findings
- Machete (14 Oct 2024): weights pre-shuffled offline so one 32-bit SMEM load replaces four 8-bit loads and interleaving four tiles allows 128-bit loads (Marlin does this too); in-register upconversion (shift nibbles, mask, expand in parallel); computes Y^T = W^T X^T so weights are the WGMMA A operand from registers; layouts expressed with "CUTLASS CUTE layout algebra"; TMA + producer/consumer warps from CUTLASS; base = CUTLASS 3.5.1 Hopper mixed-dtype example. Marlin on Hopper: relies on older `mma` not `wgmma`, losing "approximately 37% of peak compute throughput", and its hand-derived shuffling is hard to adapt to wgmma layouts. Results: Llama 3.1 70B on 1x H100 at >=3 req/s: geomean +29% input / +32% output token throughput; 405B on 4x H100: +42%; competitive with FP16 at batch >=128. — [Red Hat: Introducing Machete](https://developers.redhat.com/articles/2024/10/14/introducing-machete-mixed-input-gemm-kernel-optimized-nvidia-hopper-gpus)
- Marlin: W4A16 kernel fusing INT4 unpacking/dequant into the GEMM with an asynchronous pipeline; uses `mma.sync.m16n8k16` + `cp.async.cg.shared.global` (from a third-party plan document; secondary). — search summary citing [arXiv:2607.11368](https://arxiv.org/pdf/2607.11368) and the MIT talk abstract [Machete talk](https://csail.mit.edu/event/scale-ml-lucas-wilkinson-machete-cutting-edge-mixed-input-gemm-gpu-kernel-targeting-nvidia)
- NVIDIA x GPU MODE "Blackwell NVFP4 Kernel Hackathon" (Nov 10 2025 - Feb 13 2026): four problems - NVFP4 Batched GEMV, NVFP4 GEMM, NVFP4 Gated Dual GEMM, NVFP4 Grouped GEMM; up to 13 winners, 3 per challenge, grand prize Dell Pro Max with GB300; winners to be announced on NVIDIA AI LinkedIn ~Feb 16 2026. — [NVIDIA forum announcement](https://forums.developer.nvidia.com/t/blackwell-nvfp4-kernel-hackathon/350212); [Terms](https://developer.download.nvidia.com/licenses/Blackwell-NVFP4-Hackathon-Terms-and-Conditions.pdf)
- Participant worklog (13 Mar 2026): CuTeDSL kernels; errors included TMEM limit "total allocated columns must be <= 512"; dual GEMM: two accumulators share TMEM so column offsets must be exact; SiLU epilogue rewritten in inline PTX (`ex2.approx`, `rcp.approx`) ~20% epilogue speedup; grouped GEMM: adapted CUTLASS grouped GEMM, 1-CTA warp-specialized (1 TMA warp, 1 MMA warp, 4 epilogue warps, TMEM->regs->SMEM->TMA store), 2-CTA cooperative gave marginal gain, persistent + CLC scheduling was slower for that size; placed 95th (63.21 us) on dual GEMM and 42nd (38.46 us) on grouped GEMM; reference timings 60-76 us and 132-391 us respectively. — [ramshankar07 Substack](https://ramshankar07.substack.com/p/gpu-mode-nvfp4-blackwell-challenge)
- GPU MODE infrastructure also ran the AMD $100K competitions (2025): >30,000 submissions from 163+ teams; dataset ~110K kernels (fp8-gemm, moe, mla, ...) for MI300. — [GPUMODE/kernelbot-data](https://huggingface.co/datasets/GPUMODE/kernelbot-data/blob/refs%2Fpr%2F9/README.md)
- CUDA-L2 (Dec 2025): LLM + RL with "CUDA execution speed as the RL reward", 1000 HGEMM configs; +19.2% vs cuBLAS, +11.4% vs cuBLASLt-AutoTuning offline. No mention of ncu/SASS feedback on the abstract page. — [arXiv:2512.02551](https://arxiv.org/abs/2512.02551)
- CuAsmRL (CGO 2025): RL directly on SASS schedules, up to 26% / avg 9% speedup over existing specialized kernels. — [arXiv:2501.08071](https://arxiv.org/abs/2501.08071)
- AlphaEvolve (DeepMind, 2025): 23% speedup of a Pallas/JAX matmul tiling heuristic for Gemini training (TPU, not NVIDIA); the "32.5% FlashAttention" figure circulating is unverified. — [AlphaEvolve summary](https://anukool.substack.com/p/alphaevolve-ai-driven-algorithm-design); [news.hada.io thread](https://news.hada.io/topic?id=20908)
- Consumer Blackwell (sm_120, user's RTX 5060 Ti): Colfax: SM12x "added blockscaling support to the existing mma.sync instruction", NVFP4/MXF4 under `.kind::mxf4nvf4`, with m16n8k64 the only supported shape for NVFP4 (Colfax examples are RTX PRO 6000 SM120 and DGX Spark SM121); CUTLASS 4.5.x changelogs mention SM120 blockscaled MMA fixes; community gist: RTX 5090 = GB202, CC 12.0, "TMEM hardware is physically absent" (unofficial); a community repo claims m16n8k32 and `mxf8f6f4.block_scale` (conflicts with Colfax; unofficial). tcgen05/TMEM (2x-4x WGMMA throughput) are SM100 data-center only per CUTLASS docs. — [Colfax NVFP4 on SM12x](https://research.colfax-intl.com/cutlass-tutorial-nvfp4-blockscaled-gemm-on-nvidia-rtx-pro-blackwell-gpus-sm12x/); [CUTLASS tcgen05 guide](https://docs.nvidia.com/cutlass/4.6.0/media/docs/pythonDSL/mma_docs/tcgen05_programming.html); [gist on GB202](https://gist.github.com/solatticus/aab6ec3a0436748b021cbbdd12e8c739)

### Inferences
- The Marlin->Machete story is the clearest "diagnose the instruction-level ceiling, then rebuild on the vendor's own abstractions" case: the RE step was measuring that `mma.sync` caps at ~63% of Hopper peak (consistent with ThunderKittens' 63% and FA3's "2/3" figures), not reading cuBLAS.
- For the user's sm_120 card the relevant programming model is Ampere-like (`mma.sync`, `cp.async`, no WGMMA/TMEM); Marlin-style kernels and llama.cpp MMQ are directly applicable, while Hopper/Blackwell-datacenter tricks (warpgroup-level async, TMEM) are not. NVFP4 via `mma.sync.kind::mxf4nvf4` m16n8k64 is the new sm_120-specific feature to study (llama.cpp PR #21074 already targets it).
- Agentic/RL kernel search is now beating cuBLASLt's heuristic by 10-20% on HGEMM (CUDA-L2) and squeezing 9% on average from SASS reordering (CuAsmRL); both use runtime as the reward rather than SASS/ncu feedback signals.

- Winner list and winning-kernel write-ups of the NVFP4 hackathon were not found (announcement on LinkedIn/Discord not indexed).
- "auto-gpu-kernel" (the agentic tool named in the brief) was not found in searches; no claim recorded.
- vLLM/SGLang/TensorRT-LLM internal kernel RE write-ups (beyond Machete) were not located within budget.

## KQ6. Driver/firmware RE: nouveau/NVK, envytools, GSP firmware; does it help kernel optimization?

### Takeaway
Open-source driver RE (nouveau, envytools, NVK) has produced a conformant Vulkan 1.4 driver and GSP-firmware-based reclocking for Turing+, but nothing in it feeds compute-kernel optimization: envytools' ISA disassemblers cover old architectures, modern firmware is signed (no reclocking on GM20x/GP10x/GV100), and the relevant RE for kernel speed is done at the SASS level with NVIDIA's own `cuobjdump`/`nvdisasm` plus microbenchmarks (Jia et al. 2018/2019, Huerta et al. 2025).

### Cited Findings
- nouveau status (page last edited 9 Oct 2026): "Automatic reclocking available for Turing and newer GPUs through GSP firmware" (GSP support merged in Linux 6.7, Nov 2023); manual pstates only on GM10x/Kepler/Tesla via `/sys/kernel/debug/dri/0/pstate`; for GM20x/GP10x/GV100 "there is little hope of reclocking becoming available" because firmware "now needs to be signed by NVIDIA". NVK: default in Mesa Feb 2024, Vulkan 1.4 conformant Dec 2024, Maxwell/Pascal/Volta Apr 2025, Blackwell + Kepler in Mesa 25.2 Aug 2025; Zink preferred OpenGL on Turing+ since Mesa 25.1. envytools listed as "RE tools and docs". — [nouveau.freedesktop.org](https://nouveau.freedesktop.org/)
- envytools package description: "tools used for debugging and development of the nouveau driver, including a disassembler for nvidia GPU ISAs and a tool for direct register access." — [Fedora envytools package](https://packages.fedoraproject.org/pkgs/envytools/envytools)
- NOVA (NVIDIA's Rust driver, successor to nouveau) merged as boilerplate in Linux 6.15 (Apr 2025), works only with RTX 20+ because it depends on GSP; Sep 2026: David Airlie adapted nouveau to NVIDIA R610 firmware since NVIDIA does not keep firmware images compatible across driver releases. — [Phoronix NOVA patches](https://www.phoronix.com/news/NOVA-16-Patches-Still-Early); [Phoronix nouveau on GB10](https://phoronix.com/news/Experiment-Nouveau-NVIDIA-GB10)
- Hardware-level RE that does help kernels is the microbenchmark line: Jia et al. Volta (2018) and Turing T4 (2019) papers map instruction encodings and control-code fields; Huerta et al. (2025) model issue logic, register file cache, and show software (compiler-set) dependence management; CuAsmRL (2025) uses dependency-based microbenchmarks to get stall counts. — [arXiv:1804.06826](https://arxiv.org/pdf/1804.06826); [arXiv:1903.07486](https://arxiv.org/pdf/1903.07486); [arXiv:2503.20481](https://arxiv.org/abs/2503.20481); [arXiv:2501.08071](https://arxiv.org/abs/2501.08071)
- Community SASS tooling in 2025: redplait's denvdis (~1200 lines Perl + C++ binding) adds barrier and register tracking and a CFG builder to find independent instruction pairs for swapping/dual issue; notes that on older SMs instructions are grouped in blocks of 7 or 3 with a control word in front (Nov 2025). — [redplait blog](http://redplait.blogspot.com/2025/11/barriers-registers-tracking-for-sass.html); [denvdis repo](https://github.com/redplait/denvdis)

### Inferences
- For kernel optimization the driver/firmware layer is irrelevant on NVIDIA today: clocks are controlled by signed GSP firmware, and the user's RTX 5060 Ti will run the proprietary driver for CUDA anyway. The useful "open" knowledge is the SASS encoding + control-code semantics (from the microbenchmark papers and maxas/CuAssembler/denvdis), which is what DeepGEMM, CuAsmRL and maxas exploited.
- One indirect benefit: NVK's compiler work exposes SM ISA details publicly (Mesa's NAK backend), which could serve as a reference for SASS semantics, but no 2025-2026 source in this run documents compute-kernel gains from it.

### Gaps
- I found no 2025-2026 source describing envytools or NVK work on GSP firmware internals, nor any kernel-performance result derived from driver RE.
- Whether Mesa NAK's ISA definitions cover Hopper/Blackwell control codes was not checked.

## Cross-cutting reusable lessons (for the Polish report)

1. The RE loop that worked in every case: build a baseline -> dump SASS (`cuobjdump -sass`, `nvdisasm`, `cuobjdump --list-text` to find library kernels) -> microbenchmark/ncu to find stalls -> hypothesize the hardware rule (bank = reg mod 4; reuse cache 8 B/slot; yield bit; 14-bit FP8 accumulation; mma.sync 2/3 of wgmma peak) -> restructure or patch -> measure. Sources: maxas, ACCU cuBLAS article, DeepGEMM, Machete.
2. Numbers worth citing: maxas +4.8% vs cuBLAS at 4096 (GM204, 2017); fast.cu 764 vs 716 TFLOPS (H100, CUDA 12.6, Nov 2024); DeepGEMM 10%+ from a 2-bit SASS patch, up to 1550 TFLOPS H800 (Apr 2025); FA3 740 TFLOPS/75% (Jul 2024); Machete +29-42% throughput on H100 (Oct 2024); llama.cpp MMQ tensor cores 1.65-1.77x (Jun 2024); CuAsmRL +9% avg from SASS reordering (Jan 2025); CUDA-L2 +11.4% vs cuBLASLt autotune (Dec 2025).
3. Hardware facts obtained only by RE: 4 register banks / reuse cache (Maxwell..Ampere), control-code field layout (Volta/Turing), FP8 tensor-core accumulation ~14 bits (Hopper), wrong WGMMA swizzle docs (Hopper), consumer Blackwell lacks TMEM/tcgen05 (community, unofficial).
4. For the user's hardware: everything Hopper/SM100-specific (WGMMA, TMA multicast, TMEM, DeepGEMM, FlashMLA) does not apply to sm_120; what applies is the Ampere-style `mma.sync` + `cp.async` + register/SMEM double buffering + L2-aware tile ordering + SASS inspection with `cuobjdump`, and the new blockscaled `mma.sync.kind::mxf4nvf4` for NVFP4.
