## Confirmed

1. **Claim:** "Volta+ SASS uses one 128-bit word per instruction: at least 91 bits instruction, at least 23 bits control information (reuse 4, wait-barrier mask 6, read barrier 3, write barrier 3, yield 1, stall 4), replacing Maxwell/Pascal's 64-bit control word per 3 instructions (3 x 21 bits)." — Source: arXiv 1804.06826 (Jia, Maggioni, Staiger, Scarpazza, submitted 2018-04-18). The abstract page does not contain the numbers; the PDF text (local pdftotext, lines 334–361, 395–412) does: "Volta uses one 128-bit word to encode each instruction together with its corresponding control information … previous architectures that use a 64-bit word to encode each instruction, and a separate 64-bit word to encode control information associated to multiple instructions"; "at least 91 bits are used to encode the instruction; at least 23 bits are used to encode control information; the remaining 14 bits appeared to be unused"; "on Pascal and Maxwell, each control word contains one zero as its most significant bit, and 3 sections of 21 bits each"; field table Width 4/6/3/3/1/4 = Reuse flags / Wait barrier mask / Read barrier index / Write barrier index / Yield flag / Stall cycles. Confirmed.

2. **Claim:** "Mesa NAK's open-source encoder places the Volta+ control fields at bits 105..109 (delay), 109 (yield), 110..113 (write barrier), 113..116 (read barrier), 116..122 (wait mask), 122..126 (reuse), and only writes yield and reuse when sm < 120, i.e. not on consumer Blackwell." — The cited gitlab URL is blocked (Anubis "Access Denied"), but the local clone of mesa main (HEAD 335d5698dca1d1b9d11ef18cf5f523cc0f7f58fb, 2026-10-17) `src/nouveau/compiler/nak/sm70_encode.rs` lines 324–333 reads exactly: `set_field(105..109, deps.delay); set_field(110..113, wr_bar or 7); set_field(113..116, rd_bar or 7); set_field(116..122, wt_bar_mask); if self.sm < 120 { set_bit(109, yld); set_field(122..126, reuse_mask); }`. Confirmed (from primary source clone; the "i.e. not on consumer Blackwell" interpretation is the note's inference, correctly labelled as such in §KQ2 Inferences).

3. **Claim:** "NVIDIA's Instruction Set Reference (CUDA Binary Utilities 13.4) lists opcode names and one-line descriptions for Turing, Ampere/Ada, Hopper and Blackwell/Rubin (CC 10.0–12.0) but no encodings; nvdisasm offers -hex, --print-life-ranges, -cfg, -json but no control-code decoding." — Fetched docs.nvidia.com page: header v13.4, `nvdisasm V13.4.0`; sections Turing (7.5), Ampere/Ada (8.0, 8.6, 8.9), Hopper (9.0), "Blackwell and Rubin" (10.0, 10.3, 10.7, 11.0, 12.0); tables are opcode + short description only; options `-hex/--print-instruction-encoding`, `-plr/--print-life-ranges` (+`-lrm`), `-cfg`, `-bbcfg`, `-json/--emit-json`; no option described for decoding control/scheduling bits. Confirmed.

4. **Claim:** "On RTX 5090 (sm_120, CUDA 13.1) ptxas rejects tcgen05.alloc, .cta_group::2 and tcgen05.mma for sm_120a; SM100a cubins contain UTCHMMA.2CTA, UTMALDG.4D.2CTA, UTCBAR.2CTA.MULTICAST while SM120a binaries contain zero UTC*/UTMA* opcodes (only HMMA.16816.F32.BF16)." — Gist fetched: RTX 5090 (GB202, CC 12.0), CUDA 13.1, driver 590.48.01, dated 2026-03-06; ptxas errors quoted verbatim for `tcgen05.alloc`, `.cta_group::2`, `tcgen05.mma` on `sm_120a`; SM100a opcode list includes UTCHMMA.2CTA, UTMALDG.4D.2CTA, UTMASTG.4D, UTMACCTL.PF, UTMACMDFLUSH, UTCATOMSWS.2CTA, UTCBAR.2CTA.MULTICAST; "There are zero UTC* or UTMA* opcodes in any SM120a binary"; only HMMA.16816.F32.BF16 listed for SM120a. Confirmed as a faithful citation (single-author gist, not independently reproduced; CUTLASS doc in claim 5 corroborates the sm_120 ≠ tcgen05 point).

5. **Claim:** "CUTLASS documents that SM120 (GeForce Blackwell) uses warp-level mma.sync.aligned.kind::f8f6f4 / mxf8f6f4 / mxf4 / mxf4nvf4 block-scaled instructions instead of SM100's tcgen05.mma, and that on GeForce there is no multicast so the cluster shape is fixed to 1x1x1." — Fetched blackwell_functionality.md: SM120 section tables list `mma.sync.aligned.kind::f8f6f4` and `kind::mxf8f6f4.block_scale` (and mxf4 variants) while the SM100 section centres on `tcgen05.mma`; verbatim: "On Geforce series graphics card, there is no multicast feature therefore the cluster shape is fixed to 1x1x1." Confirmed (the doc never states the contrast "instead of" explicitly, but the two sections make it unambiguous).

6. **Claim:** "DeepGEMM discovered by SASS diffing that a bit in FADD/FFMA controls yield, flipped it together with the reuse bit in compiled binaries (deep_gemm/jit/interleave_ffma.py) for 10%+ gains on fine-grained FP8 GEMMs; upstream later dropped it because 'NVCC 12.9 will automatically do the FFMA interleaving'." — Fork README (AlignmentResearch/DeepGEMM) fetched: "one bit in a series of FADD instructions is flipped in an interleaving pattern", authors "believe this bit controls yield" ("just a guess"), script `deep_gemm/jit/interleave_ffma.py` also flips the reuse bit "since registers cannot be reused if the warp is yielded", "improves performance (10%+ in some cases) for fine-grained scaling FP8 GEMMs". The NVCC 12.9 sentence is NOT in the fork README; it is in the upstream deepseek-ai/DeepGEMM README (fetched raw, news 2025.07.20): "As NVCC 12.9 will automatically do the FFMA interleaving, all post optimizations will be no longer supported"; requirements CUDA Toolkit 12.9+, SM90/SM100. The note cites both sources for the respective halves. Confirmed. Minor wording note: the README says the yield interpretation was a guess, and the flipped bit was observed in FADD instructions, the script patches FFMA.

7. **Claim:** "CuAssembler, the most complete community SASS assembler, learns encodings automatically (sympy linear solves over nvdisasm output) but ships prebuilt instruction repositories only for sm_60/61/70/75/80/86 and offers dsass to display scoreboard control codes that cuobjdump -sass hides." — GitHub tree `CuAsm/InsAsmRepos` lists exactly DefaultInsAsmRepos.sm_{60,61,70,75,80,86}.txt; README: supports Pascal/Volta/Turing/Ampere (SM60–SM86), Sympy 1.4+ "needed by solving the LAE, and carrying out the null space of V"; dsass: "The original dumped sass by `cuobjdump -sass *.exe` will not show scoreboard control codes". Local clone HEAD 96a9f72 dated 2023-04-20 (GitHub commit date not visible via web; gh API blocked for this repo). Confirmed. "Most complete" is an editorial judgement, not a sourced fact.

8. **Claim:** "On B200 (sm_100) tcgen05.mma FP16 dependency latency is 11.0–11.4 cycles (m64n64k16 to m256n256k16) versus 32/64/128 cycles for Hopper wgmma m64n64/128/256k16; TMEM is 256 KB per SM as 512 columns x 128 lanes of 32-bit cells; FP4 maps to OMMA and FP6 to QMMA." — arXiv 2512.02189v3 (Jarmusch & Chandrasekaran, v3 dated 2026-03-02) fetched: Table V tcgen05.mma 11.0 (m64n64k16), 11.3 (m128n128k16), 11.4 (m256n256k16); Hopper wgmma 32.0 (m64n64k16), 64.0 (m64n128k16), 128.0 (m64n256k16); "remains nearly constant across tile sizes (11.0–11.4 cycles)"; TMEM "256 KB" "Structured as a 2D array of 512 columns by 128 lanes of 32-bit cells"; Table IV: FP4 → OMMA (verified via CUTLASS disassembly), FP6 → QMMA (and FP8 → QMMA). Confirmed. Nuance: the Blackwell shapes are m128n128k16/m256n256k16, so the rows are not shape-for-shape comparable with Hopper's m64nNk16 — the note's wording "m64n64k16…m256n256k16" is accurate but readers should not read it as a like-for-like comparison.
