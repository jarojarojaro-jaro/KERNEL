## KQ1. Status per architecture: what is documented vs reverse engineered (Maxwell → Blackwell, sm_100 vs sm_120)

### Takeaway
NVIDIA still publishes only opcode names plus one-line descriptions (CUDA Binary Utilities "Instruction Set Reference", now covering Turing → Blackwell/Rubin CC 7.5–12.0), never bit encodings or scheduling semantics; every encoding table in existence (MaxAs, CuAssembler, TuringAs, nv_isa_solver, DocumentSASS, NAK, JEB) was recovered by fuzzing/diffing `nvdisasm` output or by intercepting strings inside `nvdisasm` itself. Consumer Blackwell (sm_120) is a distinct ISA subset from datacenter sm_100: it has no tcgen05/TMEM/2-CTA instructions (no `UTC*`/`UTMA*` opcodes in sm_120a cubins; `ptxas` rejects `tcgen05.*` for sm_120a) and instead gets warp-level `mma.sync` with new `kind::f8f6f4` / block-scaled `mxf4nvf4` variants that lower to `QMMA`/`OMMA`.

### Cited Findings
- Official doc coverage (CUDA Binary Utilities 13.4, 2026): Instruction Set Reference tables exist for Turing (CC 7.5), Ampere/Ada (8.0/8.6/8.9), Hopper (9.0) and "Blackwell and Rubin" (CC 10.0, 10.3, 10.7, 11.0, 12.0). Tables give opcode names + short descriptions grouped by category; no encodings; operand location types only (registers, uniform registers, predicates, constant memory, descriptors). No Maxwell/Pascal/Volta tables in the current doc — [NVIDIA CUDA Binary Utilities](https://docs.nvidia.com/cuda/cuda-binary-utilities/index.html). An older version (CUDA 11.8) still covers Kepler through Volta — [Mesa NVK external docs](https://docs.mesa3d.org/drivers/nvk/external_hardware_docs.html).
- Useful official flags: `cuobjdump -sass` (also `-elf`, `-ptx`, `-res-usage`, `-arch`); `nvdisasm --print-life-ranges` (`-plr`) with `-lrm count|narrow|wide`; `nvdisasm --print-code` (`-c`); `nvdisasm --print-instruction-encoding` (`-hex`) prints the raw encoding bytes; also `-cfg`, `-bbcfg`, `-g`, `-gi`, `-gp`, `-json`, `-raw`, `-ndf`, `-novliw`. No official option decodes the control (scheduling) bits — [NVIDIA CUDA Binary Utilities](https://docs.nvidia.com/cuda/cuda-binary-utilities/index.html).
- Maxwell/Pascal: MaxAs (Scott Gray, Perl) is the reference RE of the 64-bit-per-3-instructions control word; the repo was formally archived by Intel ("DISCONTINUATION OF PROJECT", commit 54eda7a, 2023-01-03) — [NervanaSystems/maxas README](https://github.com/NervanaSystems/maxas) and local clone.
- Volta (sm_70): Citadel's 66-page tech report (Jia, Maggioni, Staiger, Scarpazza, arXiv 1804.06826, submitted 2018-04-18) derived the new 128-bit encoding by "exhaustive instruction disassembly": "at least 91 bits are used to encode the instruction; at least 23 bits are used to encode control information; the remaining 14 bits appeared to be unused" — [arXiv 1804.06826](https://arxiv.org/abs/1804.06826) (text extracted from PDF).
- Turing (sm_75): "Turing uses the same instruction encoding as Volta, but it extends Volta's instruction set"; opcodes are 10–13 bits in the least-significant bits of the first 64-bit word; one dispatcher per processing block, no dual issue observed; Turing has 64 uniform registers (URZ + UR0–UR62) with a separate integer-only uniform datapath — [arXiv 1903.07486 (Jia et al., 2019-03-18)](https://arxiv.org/abs/1903.07486).
- Ampere (sm_80/86): "Demystifying the Nvidia Ampere Architecture through Microbenchmarking and Instruction-level Analysis" (Abdelkhalik et al., HPEC 2022, arXiv 2208.11174) measured clock cycles per PTX instruction and the SASS counterparts; microbenchmarks written in PTX — [arXiv 2208.11174](https://arxiv.org/pdf/2208.11174). Full ISA model of an Ampere core (RTX A6000) incl. issue logic, register-file cache and compiler-managed dependences: "Analyzing Modern NVIDIA GPU cores" (Huerta et al., arXiv 2503.20481, 2025-03-26), 13.98% MAPE vs. real HW — [arXiv 2503.20481](https://arxiv.org/abs/2503.20481).
- Ada (sm_89): no dedicated dissecting paper found; the only encoding-level source is Kuter Dinel's nv_isa_solver auto-generated spec for SM89 (RTX 4090) — [kuterdinel.com/nv_isa_sm89](https://kuterdinel.com/nv_isa_sm89/) via [Mesa NVK external docs](https://docs.mesa3d.org/drivers/nvk/external_hardware_docs.html).
- Hopper (sm_90/90a): nv_isa_solver publishes an auto-generated SM90a spec with 186 instruction pages (HGMMA, WARPGROUP, UTMALDG, SYNCS included), "automatically generated by fuzzing nvdisasm utility" — [kuterdinel.com/nv_isa](https://kuterdinel.com/nv_isa/); repo credits CuAssembler for the parser and Zhang et al. 2017 for the fuzzing approach, 357 stars — [kuterd/nv_isa_solver](https://github.com/kuterd/nv_isa_solver). Hopper opcode table (official names): HGMMA, IGMMA, QGMMA (FP8), BGMMA, WARPGROUP, WARPGROUPSET, UTMALDG, UTMASTG, UTMAREDG, UTMAPF, UTMACCTL, UTMACMDFLUSH, UBLKCP, UBLKPF, UBLKRED, SYNCS — [NVIDIA CUDA Binary Utilities](https://docs.nvidia.com/cuda/cuda-binary-utilities/index.html). Hopper also introduced "memory descriptors" shown as `desc[URx][URy]` in SASS, used for TMA; NVIDIA says it will not document them — [NVIDIA forum](https://forums.developer.nvidia.com/t/what-does-desc-mean-in-sass/258352). Microarchitecture: wgmma `m64nNk16` (N=16…256) FP16 SS mode m64n256k16: 128.0 cycles latency, 729.3 TFLOPS (≈95% of peak) vs mma.sync m16n8k16 24.1 cycles, 494.4 TFLOPS (62.9% avg); FP8 wgmma m64n256k32 ≈1448 TFLOPS; TMA ≈170 cycles higher latency than regular loads, >1800 GB/s; DSMEM SM-to-SM 181 cycles (cluster 2); L2 near/far hit 258/414 cycles on H800 PCIe — [arXiv 2501.12084v2 (Luo et al., 2025-09-04)](https://arxiv.org/html/2501.12084v2).
- Blackwell datacenter (sm_100/100a, B200): TMEM = 256 KB per SM organised as 512 columns × 128 lanes of 32-bit cells; `tcgen05.mma` FP16 dependency-chain latency 11.0–11.4 cycles for m64n64k16…m256n256k16 vs Hopper wgmma 32/64/128 cycles; measured B200 throughput FP16 1929.6 TFLOPS (96.5% of peak), FP8 3850.6, FP6 5134.4, FP4 7700.2, INT8 3928.5 TOPS; FP4 maps to `OMMA`, FP6 to `QMMA`; FP64 is not supported by tcgen05.mma (separate DMMA path) — [arXiv 2512.02189v3 (Jarmusch & Chandrasekaran, v3 2026-03-02)](https://arxiv.org/html/2512.02189v3). Official Blackwell opcode table: UTCHMMA, UTCIMMA, UTCOMMA, UTCQMMA ("uniform MMA" variants), LDTM/STTM (register ↔ tensor memory), UTCBAR, UTCCP (smem→TMEM async copy), UTCSHIFT, UTCATOMSWS, plus the TMA/bulk family; the table does not annotate which of CC 10.0/10.3/10.7/11.0/12.0 supports each — [NVIDIA CUDA Binary Utilities](https://docs.nvidia.com/cuda/cuda-binary-utilities/index.html). 2-SM mode appears as `cta_group::2` in PTX and `2CTA` in SASS; A is duplicated across the pair, B and D sharded; 1SM M=64 reaches ≤~50% of peak, M=128 ~100%; SMEM bandwidth 128 B/clk/SM — [SemiAnalysis, 2026-03-31](https://newsletter.semianalysis.com/p/dissecting-nvidia-blackwell-tensor).
- Blackwell consumer (sm_120, GB20x): a 2026-03-06 investigation on RTX 5090 (CUDA 13.1, driver 590.48.01) found `ptxas` rejects `tcgen05.alloc`, `.cta_group::2` and `tcgen05.mma` for `sm_120a`; SM100a cubins contain `UTCHMMA.2CTA`, `UTMALDG.4D.2CTA`, `UTMASTG.4D`, `UTMACCTL.PF`, `UTMACMDFLUSH`, `UTCATOMSWS.2CTA`, `UTCBAR.2CTA.MULTICAST`, while "there are zero UTC* or UTMA* opcodes in any SM120a binary"; the only tensor opcode seen in SM120a was `HMMA.16816.F32.BF16`; patching cubin `e_flags` 0x06006402→0x06007802 was rejected by the driver (error 500) — [gist by solatticus](https://gist.github.com/solatticus/aab6ec3a0436748b021cbbdd12e8c739). The NVVM verifier encodes targets as major*100+minor*10+suffix (SM100a=1001, SM100f=1002, SM101a=1011, SM103a=1031, SM120a=1201) and gates tcgen05 with bitmask 0xc0000c03 after subtracting 1001 — same gist.
- RTX 5080 (GB203, sm_120) vs H100: FP8/FP6 `mma.sync.aligned.kind::f8f6f4` m16n8k32 maps to `QMMA`; FP4 was expected to map to `OMMA` but produced `QMMA`; `OMMA` appeared only with block scaling (ue8m0); Table IV says "tcgen05 is yet to be supported for the arch. sm_120a"; shared memory configurable to ~99 KB/SM (vs ~227 KB/SM on GH100); L1 128 KB/SM vs 256 KB; L2 hit ≈358 vs ≈273 cycles; GB203 has 2 FP64 units/SM vs 64 — [arXiv 2507.10789v2 (Jarmusch et al., 2025-07-21)](https://arxiv.org/html/2507.10789v2).
- CUTLASS: SM100 uses `tcgen05.mma` (block-scaled kinds `mxf8f6f4`, `mxf4`, `mxf4nvf4`); SM120 uses warp-level `mma.sync.aligned.kind::f8f6f4`, `kind::mxf8f6f4.block_scale`, `kind::mxf4.block_scale`, `kind::mxf4nvf4.block_scale`; "On Geforce series graphics card, there is no multicast feature therefore the cluster shape is fixed to 1x1x1"; SM120 GEMM: "Only TN layout is supported"; NVFP4 (`nv_float4_t`) uses `ue4m3` scales with vector size 16, MXFP4 uses `ue8m0` with vector size 32 — [CUTLASS blackwell_functionality.md](https://github.com/NVIDIA/cutlass/blob/main/media/docs/cpp/blackwell_functionality.md).
- PTX target suffixes: `a` = architecture-specific (introduced with Hopper sm_90a; `sm_100a` runs only on CC 10.0), `f` = family-specific (CUDA 12.9, runs on same major CC with ≥ minor; `sm_100`/`sm_100f` generate the same cubin); architecture-specific features are "primarily related to Tensor Cores" — [NVIDIA blog, 2025-05-01](https://developer.nvidia.com/blog/nvidia-blackwell-and-nvidia-cuda-12-9-introduce-family-specific-architecture-features/). Current PTX ISA is 9.4 and introduces `sm_107a`/`sm_107f` — [PTX ISA](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html). PTX ISA 9.2 "Target ISA Notes" list tcgen05 for sm_100a/sm_101a (+family variants), sm_120 absent; LLVM notes sm_101 was renamed sm_110 in PTX 9.0 — [NVIDIA forum thread](https://forums.developer.nvidia.com/t/does-b200-5090-support-tcgen05-ld-red/363672) (fetch returned 403; content from search snippet only), [LLVM NVPTXSubtarget.h](https://www.llvm.org/doxygen/NVPTXSubtarget_8h_source.html).
- Commercial RE: JEB 5.31 (PNF Software, 2025-08-15) ships a SASS disassembler + experimental SASS→pseudo-C decompiler for sm_70 … sm_121 ("all Volta+ instructions are fixed size, 16-byte long"), tested on >100 M instructions from ~620 k kernels against cuobjdump/nvdisasm, credits DocumentSASS — [PNF blog](https://pnfsoftware.com/blog/reversing-nvidia-cuda-sass-code/).
- Academic encoding work (2026): "Automated Instruction Encoding Synthesis for Modern GPU ISA Compression" (Ma & He, ICCD 2026, arXiv 2609.18662, 2026-09-16) normalises public SASS encoding text into a spec, validates a disassembler against nvdisasm on 3.78 M instructions (Blackwell/Hopper/Ampere), code at github.com/reoLantern/nvsass-disassembler — [arXiv 2609.18662](https://arxiv.org/abs/2609.18662). NVLift (NDSS BAR 2026) lifts 47 SASS instructions (SM75) to LLVM IR — [bar2026-28.pdf](https://www.ndss-symposium.org/wp-content/uploads/bar2026-28.pdf).

### Inferences
- For the user's RTX 5060 Ti (GB206, sm_120), everything learned from Hopper wgmma/TMA or Blackwell tcgen05 kernels (DeepGEMM, FlashMLA, CUTLASS SM100 GEMMs) is not directly portable; the relevant "fast kernel" vocabulary for this GPU is Ampere/Ada-style: `ldmatrix`→`LDSM`, `cp.async`→`LDGSTS`, `mma.sync`→`HMMA.16816`/`IMMA`/`QMMA`/`OMMA`, plus block-scaled FP4 — which is exactly what llama.cpp's `mma.cuh` already emits (see KQ3).
- The sm_120 vs sm_100 gap is enforced at three levels (ptxas rejects, NVVM verifier bitmask, driver rejects re-flagged cubins), so there is no "unlock" path; consistent with TMEM being physically absent, but that is an inference by the gist author, not a measurement.
- Hopper/Blackwell encodings exist publicly only as auto-generated nvdisasm-fuzzed specs (nv_isa_solver SM90a/SM89) and inside NAK (sm_70…sm_120 subset); nobody has published a verified sm_100a/sm_120a encoding table with control bits yet (sass-king: "Full stall/yield bit placement remains open").

### Gaps
- Could not retrieve the exact PTX ISA "Target ISA Notes" tables (page is 470 k chars; forum thread 403) to quote the verbatim target list for `tcgen05.*`, `wgmma`, `setmaxnreg`, `cp.async.bulk.tensor` on sm_120; evidence is indirect (CUTLASS docs, ptxas errors in the gist, paper Table IV).
- No per-instruction encoding pages of nv_isa_solver were read (only the index), so I cannot quote bit ranges for HGMMA/UTMALDG.
- No public source found for sm_120 vs sm_100 differences in the official opcode table (NVIDIA lumps CC 10.0–12.0 together).

## KQ2. Control codes / scheduling info embedded in SASS and why they matter for performance

### Takeaway
Since Volta every instruction is a 128-bit word whose bits 105–125 carry 21 bits of compiler-computed scheduling state — stall count (4 b), yield (1 b), write barrier (3 b), read barrier (3 b), wait-barrier mask (6 b, SB0–SB5), reuse flags (4 b) — the same six fields that Maxwell/Pascal packed as 3×21 bits in a separate 64-bit control word per 3 instructions; the hardware has no scoreboard for fixed-latency ops, so these bits *are* the latency hiding, operand-reuse-cache and warp-switch policy, and Mesa's NAK now encodes them for sm_70…sm_120 using NVIDIA-provided latency tables (with the yield and reuse fields notably not emitted for sm_120).

### Cited Findings
- Maxwell/Pascal layout (MaxAs wiki): one 64-bit control word precedes each group of 3 instructions; each instruction gets 21 bits = 17 control bits + 4 reuse bits (instr 1: bits 0–16 + 17–20; instr 2: 21–37 + 38–41; instr 3: 42–58 + 59–62; bit 63 unused). Within the 17 bits: stall count bits 0–3 (0–15 clocks), yield bit 4, write barrier bits 5–7 (7 = none), read barrier bits 8–10, wait-barrier mask bits 11–16 (one bit per barrier, 6 barriers). Stall 0 = dual issue with next instruction (only legal across different pipes); stalls 12–15 require yield; BAR/BRA/CAL/RET/EXIT need ≥5; a barrier takes 1 extra clock to activate; barrier set/wait on predicated instructions is unreliable; "Yielding costs no clocks when another warp has work ready" — [maxas wiki Control-Codes](https://github.com/NervanaSystems/maxas/wiki/Control-Codes).
- Volta+ layout (Citadel): "Volta uses one 128-bit word to encode each instruction together with its corresponding control information … nvdisasm shows the 128-bit word as two 64-bit words. The first word only encodes instruction information. The second encodes both instruction and control information." Field widths: Reuse flags 4 | Wait barrier mask 6 | Read barrier index 3 | Write barrier index 3 | Yield flag 1 | Stall cycles 4. "Volta, Pascal and Maxwell have 4 register reuse caches and 4 source operand slots… Reuse mitigates register bank conflicts." Write barriers track variable-latency writes among 6 barriers; read barriers protect WAR for "unbuffered instructions that write the contents of registers to memory"; yield: "When this bit is set, the scheduler prefers to issue the next instruction from the current warp. When the bit is cleared, the scheduler prefers to switch to another warp, making all register reuse flags for the next instruction ineffective. This costs one extra cycle to switch." Kepler used 7×8-bit sections — [arXiv 1804.06826 §2.1](https://arxiv.org/abs/1804.06826) (extracted from PDF).
- Exact Volta+ bit positions as implemented by an open-source encoder (Mesa NAK `sm70_encode.rs`, `set_instr_deps`): delay (stall) bits 105..109, yield bit 109, wr_bar 110..113 (7 = none), rd_bar 113..116, wait mask 116..122, reuse mask 122..126 — and the yield bit and reuse mask are only written `if self.sm < 120` — local clone `mesa/src/nouveau/compiler/nak/sm70_encode.rs` lines 324–333 (HEAD 335d569, 2026-10-16); public source: [Mesa nak/sm70_encode.rs](https://gitlab.freedesktop.org/mesa/mesa/-/blob/main/src/nouveau/compiler/nak/sm70_encode.rs). Maxwell/Pascal in NAK `sm50.rs`: sched fields 0..4 delay, bit 4 yield, 5..8 wr_bar, 8..11 rd_bar, 11..17 wait mask, 17..21 reuse, packed at `21*instr_index` into a 64-bit word emitted "Every 3 instructions" — local `nak/sm50.rs` lines 239–246, 3406, 3426.
- CuAssembler's decoder (`CuAsm/CuControlCode.py`): stall = code & 0xf, yield = bit 4 (`isYield()` is true when the bit is **0**), write barrier = (code & 0xe0)>>5, read barrier = (code & 0x700)>>8, wait mask = (code & 0x1f800)>>11; textual form `B------:R-:W-:Y:S05` (e.g. `B0----5:R0:W5:Y:S05`); reuse field dropped from the control string on 2022-09-15 because "for some instructions (HMMA.SP) reuse may use some other bits, and for TEXS/BRA/... the reuse bits may be used for other encoding fields" — local clone `cuassembler/CuAsm/CuControlCode.py`; [cloudcores/CuAssembler](https://github.com/cloudcores/CuAssembler). CuAssembler also notes padding differs: sm_5x/6x 32 B (1+3 group), sm_7x/8x 16 B — local `CuAsm/CuSMVersion.py` lines 182–189.
- Why it matters (Maxwell SGEMM): bank = register number mod 4; each of 3 FFMA operand slots has an 8-byte reuse cache; without reuse ≈20% slowdown estimated (128 of 520 clocks); `--noreuse` cost "a couple hundred GFLOPS"; FFMA operand ordering reaches 39–47% reuse; LDS/STS/TLD/BAR/BRA dual-issue with FFMA "and don't count against the FFMA clock budget" → 512 FFMA per 520-clock loop (98.5% bound); achieved ~98% of peak on GM107, 96% on GM204, up to 25% faster than cuBLAS at small sizes, 4.8% at 4096² — [maxas wiki SGEMM](https://github.com/NervanaSystems/maxas/wiki/SGEMM).
- Volta/Turing register file: 2 banks with 64-bit-wide ports; "Any FFMA instruction that accesses the same bank with all its 3 source registers is said to have a bank conflict" (Volta, vs 4 banks on Maxwell/Pascal) — [arXiv 1804.06826 §3.5](https://arxiv.org/abs/1804.06826); Turing: 16,384 32-bit registers per processing block, 2 banks with dual 32-bit ports — [arXiv 1903.07486](https://arxiv.org/abs/1903.07486).
- Latencies these stall counts encode (Turing, dependent issue): IADD3/SHF/LOP3/SEL/MOV/FADD/FFMA/FMUL/ISETP 4 cycles; IMAD/FMNMX 5; HADD2/HMUL2/HFMA2 6; POPC/FLO/BREV/MUFU ~15; DADD/DMUL ~48; DFMA ~54; shared memory 19 cycles, L1 hit 32, L2 ~188, global with TLB miss 616 — [arXiv 1903.07486](https://arxiv.org/abs/1903.07486). Volta: "most integer and single-precision instructions have a latency of 4 cycles; most double-precision 8" (Pascal: 6) — [arXiv 1804.06826](https://arxiv.org/abs/1804.06826).
- Mechanism confirmed at the microarchitecture level: "the software-based dependence management in modern NVIDIA GPUs outperforms a hardware scoreboard mechanism in both performance and area"; model includes issue scheduler policy, register file cache, stream-buffer instruction prefetcher — [arXiv 2503.20481](https://arxiv.org/abs/2503.20481).
- NVIDIA-provided latency data in the open: NAK files `sm75_instr_latencies.rs`, `sm80_instr_latencies.rs`, `sm120_instr_latencies.rs` state "This contains the register scheduling information provided by NVIDIA"; categories: "Coupled instructions are ones with fixed latencies, they need delays but not scoreboards. Decoupled instructions … need scoreboards but not delays. There are also redirected instructions which depending on the SM can be coupled or decoupled"; `latencies/sm100/{reg,ureg,pred,upred}_{raw,war,waw}.csv` are converted by `lat_rs_gen.py` (Collabora/Red Hat 2024); sm120 file: "These latencies come from B100 (SM100) and not the consumer RTX chips (SM120). We have to add some padding to get everything passing on the RTX chips" — local clone `mesa/src/nouveau/compiler/nak/` and `latencies/`; Mesa docs: "Red Hat has NDA'd documentation on NVIDIA instruction latencies" — [Mesa NVK external docs](https://docs.mesa3d.org/drivers/nvk/external_hardware_docs.html).
- DeepGEMM's use of the yield/reuse bits (original README, Feb 2025): "By comparing the compiled SASS, we discover that one bit in a series of FADD instructions is flipped in an interleaving pattern … we identified that this bit controls yield … we also flip the reuse bit (registers cannot be reused if the warp is yielded)… This adjustment improves performance (10%+ in some cases) for fine-grained scaling FP8 GEMMs"; script `deep_gemm/jit/interleave_ffma.py` — [AlignmentResearch/DeepGEMM fork README](https://github.com/AlignmentResearch/DeepGEMM). Current upstream README (2025-07-20 news): "As NVCC 12.9 will automatically do the FFMA interleaving, all post optimizations will be no longer supported"; requires CUDA ≥12.9, SM90/SM100; env vars `DG_JIT_DUMP_SASS=1`, `DG_JIT_DUMP_ASM=1`, `DG_JIT_DUMP_PTX=1`, `DG_JIT_PTXAS_VERBOSE`, `DG_JIT_DEBUG` — local clone `deepgemm/README.md` (HEAD 1fc9c66, 2026-10-14); [deepseek-ai/DeepGEMM](https://github.com/deepseek-ai/DeepGEMM). No `interleave_ffma.py` exists in the current tree (grep of clone).
- Tooling that displays control codes today: CuAssembler `dsass` ("Format sass with control codes from input sass/cubin/exe"; `cuobjdump -sass` alone "will not show scoreboard control codes"); `denvdis` `nvd -S` shows scheduling tables, `-O` encoding field values, `-T` register tracking — local `cuassembler/README.md`; [redplait/denvdis](https://github.com/redplait/denvdis). JEB has a `.DisplaySchedulingInfo` option — [PNF blog](https://pnfsoftware.com/blog/reversing-nvidia-cuda-sass-code/). sass-king lists `gpuasm.com` for "scoreboards, stalls, and dependency arrows" — [florianmattana/sass-king](https://github.com/florianmattana/sass-king).

### Inferences
- The NAK encoder's `if self.sm < 120` guard around yield (bit 109) and reuse (122..126) strongly suggests consumer Blackwell changed or dropped those two fields (sass-king independently reports "Full stall/yield bit placement remains open" for SM120). The stall/barrier fields (105..109, 110..122) are still emitted for sm_120, so dependency barriers and stall counts are unchanged. Treat the exact sm_120 yield/reuse semantics as unknown.
- The DeepGEMM trick (post-processing yield+reuse bits of FFMA in a cubin to overlap promotion FFMAs with MMAs) is the only documented production use of control-bit patching in a modern inference kernel, and NVIDIA folded it into ptxas 12.9 — the practical lesson is that control-bit scheduling is worth >10% on MMA-bound kernels, and that the fastest way to get it is a newer ptxas rather than hand patching.
- For SASS reading on the user's hardware, the most robust decode path is: `cuobjdump -sass` → CuAssembler `dsass` for sm_8x formatting (control string semantics identical through sm_90 per CuSMVersion), with the caveat that sm_120 yield/reuse decoding may be wrong.

### Gaps
- No public source gives the sm_100/sm_120 control-bit layout explicitly; the NAK code is the only evidence, and it does not say *why* yield/reuse are skipped on sm_120.
- The DeepGEMM original README (Feb 2025) was read via a fork mirror; web.archive.org is blocked from this environment.
- CuAssembler's "HMMA.SP uses other bits for reuse" note has no bit-level documentation.

## KQ3. Assemblers, patchers, and feasibility of hand-written SASS today

### Takeaway
There is no maintained general-purpose SASS assembler beyond Ampere: MaxAs (sm_5x/6x, archived 2023), TuringAs (sm_70/75/80, last commit 2022-01), CuAssembler (prebuilt repos for sm_60/61/70/75/80/86, last commit 2023-04, Ada issue open since 2024), while the live projects are either in-place patchers (denvdis `ced`/`ina`, nvdisasm-round-trip style) or the Mesa NAK compiler (Rust encoder for sm_50–sm_120 incl. HMMA/LDSM/IMMA but not wgmma/tcgen05); production kernels (CUTLASS, ThunderKittens, llama.cpp, DeepGEMM) therefore write inline PTX and only post-process bits, and even DeepGEMM retired that for NVCC ≥12.9.

## KQ4. Tensor-core instructions at SASS level and what RE found about numerics

### Takeaway
The PTX→SASS tensor-core mapping is stable per generation (Volta `HMMA.884` ×16 per wmma 16×16×16 in STEP0–3 groups; Turing/Ampere `HMMA.1688`/`HMMA.16816` one-to-one with `mma.sync`, `IMMA` for INT8/4/1, `LDSM` for `ldmatrix`, `LDGSTS` for `cp.async`; Hopper `HGMMA`/`QGMMA`/`IGMMA`/`BGMMA` + `UTMALDG`; Blackwell `UTCHMMA/UTCQMMA/UTCOMMA/UTCIMMA` + `LDTM/STTM/UTCBAR/UTCCP` on sm_100 and warp-level `QMMA`/`OMMA` on sm_120), while numerics RE established that products are exact, accumulation is done in ≥FP32-width adders with non-IEEE alignment truncation (revised from "round-toward-zero"), and FP16-accumulate output is converted only at the end.

### Cited Findings
- Volta: wmma 16×16×16 compiles to 16 `HMMA.884.F32.F32.STEP{0,1,2,3}` instructions in groups of 4 with `.reuse.T` operand modifiers (e.g. `HMMA.884.F32.F32.STEP0 R8, R26.reuse.T, R16.reuse.T, R8;`) — [arXiv 1804.06826](https://arxiv.org/abs/1804.06826) (PDF text, lines 1966–1985).
- Turing: "NVCC compiles the same primitive invocation into only 4 HMMA instructions of a new kind" (`.1688` infix); Tensor Cores add int8/int4/int1; measured T4 matrix throughput: FP16 41,616 GFLOPS, INT8 74,934 GOPS, INT4 114,384 GOPS, INT1 552,230 GOPS (vs P4 FP16 6,571) — [arXiv 1903.07486](https://arxiv.org/abs/1903.07486).
- Ampere/Turing mapping and latencies (Sun et al., arXiv 2206.02874, TPDS; A100, RTX3070Ti, RTX2080Ti): `mma.m16n8k16` (BF16) → `HMMA.16816.FP32.BF16`, `mma.m16n8k8` → `HMMA.1688.FP32.BF16`, `mma.m8n8k4` → `HMMA.884` on Volta/Turing but on Ampere lowers to FPU (CUDA-core) code ~10× slower; legacy `wmma` m16n16k16 → two `HMMA.16816`; A100 completion latency m16n8k16 ≈24.7 cycles, m16n8k8 ≈17.7, TF32 m16n8k8 ≈25; `ldmatrix` x1/x2/x4 ≈23.1/25.1/29.3 cycles; `ld.shared.u32` 23.0 (no conflict) → 37.0 (8-way); A100 dense FP16 peak ≈1000 FMA/clk/SM (vendor 1024), sparse ≈2000; ldmatrix.x4 ≈128 B/clk/SM; RTX3070Ti ≈252 FMA/clk/SM with FP32 accumulate vs ≈507 with FP16 accumulate (consumer halving) — [arXiv 2206.02874v3](https://arxiv.org/html/2206.02874v3).
- Numerics (Sun et al.): multiplication and inner-product addition give zero error vs CPU FP32 for BF16 inputs ("high precision inside the Tensor Cores"); accumulation shows small error (1.89E-08 for BF16) → "relatively low precision"; FP16 in/out: zero error vs CPU FP16, i.e. computed in high precision and converted only at the end; TF32 and FP16 give the same error level (both 10 mantissa bits); chained FP16 GEMM overflows to inf after ≈N=10 — [arXiv 2206.02874v3](https://arxiv.org/html/2206.02874v3).
- Numerics (Fasi, Higham, Mikaitis, Pranesh, PeerJ CS 2021; V100, T4, A100): probed intermediate precision, subnormal support, rounding mode, operation order and normalisation of partial sums; concluded accumulation rounds toward zero — [PeerJ cs-330](https://peerj.com/articles/cs-330.pdf) (page fetch failed; claim from search summary). Revised 2025: an SMT formalisation of Volta/Turing/Ampere tensor cores finds they "do not, as previously reported, use round-to-zero for accumulation"; a 5-term accumulator needs 3 extra carry-out bits; the loss arises because mantissa bits discarded during significand alignment are truncated (so a small addend vanishes when the exponent gap exceeds the mantissa width) — [arXiv 2502.15999 (Valpey & Pai, NFM 2025, 2025-02-21)](https://arxiv.org/abs/2502.15999).
- Hopper: wgmma `m64nNk16` dense FP16 ≈729 TFLOPS (zero inputs) / ≈704.5 (random) on H800 PCIe; FP8 wgmma ≈1448 TFLOPS with either FP16 or FP32 accumulation (no throughput penalty for FP32 accumulate); Hopper DPX uses new `VIMNMX` SASS — [arXiv 2501.12084v2](https://arxiv.org/html/2501.12084v2). Tensor-core PTX "compiles to a set of SASS instructions (HMMA, HGMMA, QGMMA, IGMMA, or BGMMA) depending on operand precision" and "SASS opcodes can be obtained from CUTLASS binaries" — [arXiv 2512.02189](https://arxiv.org/pdf/2512.02189).
- Blackwell sm_100: `tcgen05.mma` FP16 latency 11.0–11.4 cycles (m64n64k16…m256n256k16) vs Hopper wgmma 32/64/128; FP4 → `OMMA`, FP6 → `QMMA`; TMEM 128 lanes × 512 columns × 32 bit = 256 KB/SM, optimal tile 64×64 (4 KB FP8) — [arXiv 2512.02189v3](https://arxiv.org/html/2512.02189v3). Accumulator D must live in TMEM; A in TMEM or SMEM; B in SMEM — [Modal GPU glossary](https://modal.com/gpu-glossary/device-hardware/tensor-memory). Official sm_100 SASS names: `UTCHMMA`, `UTCIMMA`, `UTCOMMA`, `UTCQMMA`, `LDTM`/`STTM`, `UTCBAR`, `UTCCP`, `UTCSHIFT`, `UTCATOMSWS` — [NVIDIA CUDA Binary Utilities](https://docs.nvidia.com/cuda/cuda-binary-utilities/index.html). Observed in SM100a cubins: `UTCHMMA.2CTA`, `UTMALDG.4D.2CTA`, `UTCBAR.2CTA.MULTICAST` — [solatticus gist](https://gist.github.com/solatticus/aab6ec3a0436748b021cbbdd12e8c739).
- Blackwell sm_120 (RTX 5080): `mma.sync.aligned.kind::f8f6f4` m16n8k32 FP8/FP6 → `QMMA`; FP4 → `QMMA` unless block-scaled (then `OMMA`); low-precision peak "over 11 TFLOP/s" in their ILP microbenchmark (ILP 6, 32 warps; per-format peaks not given); FP4 e2m1 power 16.753 W vs FP8 e4m3 46.661 W (Blackwell) / 55.823 W (Hopper) (table units ambiguous); FP8 GEMM result 0.233 TFLOP/s at 8192³ flagged as likely a benchmarking issue — [arXiv 2507.10789v2](https://arxiv.org/html/2507.10789v2).
- Blackwell MMA latency ordering by type (SemiAnalysis measurement, 2026-03-31): S8 < BF16 = E4M3 = F4 < MXF8 = MXF4; same-bit-width formats have identical throughput; micro-scaling adds "virtually no overhead" — [SemiAnalysis](https://newsletter.semianalysis.com/p/dissecting-nvidia-blackwell-tensor).

### Inferences
- For the RTX 5060 Ti, the relevant SASS tensor opcodes are `HMMA.16816.{F32,F16}.{F16,BF16}`, `HMMA.1688.F32.TF32`, `IMMA.16832.S8`, `QMMA` (FP8/FP6, sm_120 only via `kind::f8f6f4`), `OMMA` (block-scaled FP4), fed by `LDSM`/`LDGSTS`; llama.cpp's MXFP4/NVFP4 `mma.sync … m16n8k64` paths are the only Blackwell-specific instructions it will emit on this card.
- The consumer FP32-accumulate halving seen on RTX3070Ti (252 vs 507 FMA/clk/SM) is a GeForce-segmentation effect worth re-measuring on GB206; no 2025–2026 source measured it for sm_120.
- Tensor-core numerics RE is mature for Volta–Ampere but no equivalent bit-exact study exists for Hopper FP8 or Blackwell FP4/FP6 accumulation.

### Gaps
- PeerJ paper could not be fetched directly (only the search summary); exact per-architecture rounding tables not quoted.
- No source gives bit-level encodings of HGMMA/UTCHMMA (nv_isa_solver pages not read; sass-king still "open").
- No measured FP16-vs-FP32-accumulate throughput ratio for sm_120 found.

## KQ5. Open-source driver RE as a source of ISA knowledge (envytools/envydis, NVK/NAK, open-gpu-kernel-modules, open-gpu-doc)

### Takeaway
The nouveau ecosystem is now the richest *open* source of post-Volta SASS encoding knowledge: Mesa NAK contains a Rust encoder for sm_20…sm_120 with NVIDIA-supplied latency tables (under NDA to Red Hat, but the derived CSVs/Rust are public) and an nvdisasm round-trip test harness; envytools/envydis remains authoritative only for Maxwell and earlier; NVIDIA's open-gpu-doc and open-gpu-kernel-modules contribute class headers/QMD layouts but no shader ISA.

### Cited Findings
- Mesa's own inventory of sources: official open-gpu-doc (class headers; open-gpu-kernel-modules fills gaps), the CUDA 11.8 nvdisasm doc for Kepler→Volta opcodes; reverse-engineered: nv_isa_solver (Hopper, Ada), "Mel's opcode list … scraped from nvdisasm error messages" at gitlab.freedesktop.org/mhenning/re (`opclass` dir), envytools ("Maxwell and earlier"), maxas, asfermi, nv-shader-tools ("disassembling and fuzzing the hardware ISA"); encodings tested against nvdisasm via `nvdisasm_tests.rs`, behaviour via `hw_tests.rs` and `Foldable` impls in `ir.rs`; "Red Hat has NDA'd documentation on NVIDIA instruction latencies"; delays/waits background: Turing T4 paper §2.1 and "Analyzing Modern NVIDIA GPU cores" — [Mesa NVK external docs](https://docs.mesa3d.org/drivers/nvk/external_hardware_docs.html).
- NAK status: Rust back-end, default for Turing+ (RTX 20 and newer); Blackwell enabling (QMD 5.0, Faith Ekstrand/Collabora, June 2025) → Mesa 25.2 Vulkan 1.4 on RTX 50xx, passing Vulkan CTS; at launch "proper instruction scheduling was missing"; kernel-side Blackwell support arrived with nouveau in Linux 6.16 (GSP firmware) — [Phoronix (NVK Blackwell)](https://www.phoronix.com/news/NVIDIA-Blackwell-NVK-Mesa), [Phoronix (Mesa 25.2)](https://www.phoronix.com/news/Mesa-25.2-NVK-Blackwell), [Collabora](https://collabora.com/news-and-blog/news-and-events/mesa-25.2-brings-new-hardware-support-for-nouveau-users.html).
- NAK source facts (local clone 2026-10-16): architecture gates in `sm70_encode.rs` include `sm >= 73`, `sm >= 75` (HMMA/LDSM/MUFU.TANH), `sm >= 80`, `sm >= 86`, `sm >= 90` (HMMA uniform predicate), `sm >= 100` (ureg size 8 vs 6 bits; several operand encodings change at sm_100), `sm >= 120` (eight new ops asserting `e.sm >= 120`, plus the control-bit change); `ir.rs` defines `is_hopper` (90–99), `is_blackwell_a` (100–109), `is_blackwell_b` (120–129); `sm70.rs` selects `SM120Latency`/`SM80Latency`/`SM75Latency` for `needs_scoreboards`, RAW/WAR/WAW latency; `needs_yield()` is true only for `Bar`, `BSync`, `Nanosleep` — local `nak/sm70_encode.rs`, `nak/ir.rs`, `nak/sm70.rs`.
- envytools: "a disassembler and assembler for various ISAs found on nvidia GPUs" (envydis); Turing RE in envytools began 2018 — [Fedora envytools package](https://packages.fedoraproject.org/pkgs/envytools/envytools), [Phoronix 2018](https://www.phoronix.com/news/Nouveau-Starts-Envy-Turing). NVIDIA's open-gpu-doc release "primarily covers Maxwell, Pascal, Volta, and Kepler" with Turing WIP and includes shader program headers — [Phoronix (open-gpu-doc)](https://www.phoronix.com/news/NVIDIA-Open-GPU-Docs).
- NVK/nouveau status 2025: NVK enabled for Volta and older since April 2025; Blackwell and Kepler since Mesa 25.2 — [nouveau.freedesktop.org](https://nouveau.freedesktop.org/).

### Inferences
- Because NAK must produce correct, non-hanging code on real sm_120 hardware (CTS-passing), its `set_instr_deps` and `sm120_instr_latencies.rs` are currently the most trustworthy public description of how to fill stall/barrier fields on the user's GPU — more so than any SASS assembler project, all of which stop at sm_86.
- open-gpu-kernel-modules is useful for memory/QMD/launch-descriptor layouts, not for SASS; anyone RE-ing kernels should pair it with `cuobjdump -elf` to read `.nv.info` / EIATTR metadata rather than expecting ISA tables.
