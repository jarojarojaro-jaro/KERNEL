## Key question 1: Fatbinary / cubin / PTX structure (containers, ELF layout, .nv.info attributes, e_flags, sm vs compute, lazy loading)

### Takeaway
A CUDA host binary carries device code as an undocumented but well reverse-engineered three-level nesting: a 16-byte host-side wrapper struct in `.nvFatBinSegment` (magic 0x466243B1) points at a fatbin blob in `.nv_fatbin` (magic 0xBA55ED50, 16-byte header, then 64-byte entry headers, each followed by an optionally LZ4-compressed PTX text or cubin ELF payload). The cubin is a normal ELF with `e_machine = EM_CUDA (190)`, SM version encoded in `e_flags`, one `.text.<mangled_kernel>` section per kernel, and per-kernel metadata (register count, max threads, parameter layout) stored as EIATTR_* records in `.nv.info.<kernel>`.

### Cited Findings

**Host-side wrapper and ELF sections**
- The host object contains a `__fatBinC_Wrapper_t` struct with four fields `magic`, `version`, `data` (pointer to the fatbin bytes), `filename_or_fatbins`; magic is `0x466243B1`, version 1; the wrapper lives in section `.nvFatBinSegment` and its `data` field is filled by an `R_X86_64_64` relocation pointing at `.nv_fatbin + 0`; the object also gets a `__nv_module_id` section and a static constructor (blog dated 2026-07-31) — [The Software Frontier: How CUDA Binaries Actually Work](https://www.thesoftwarefrontier.com/p/how-cuda-binaries-actually-work)
- Clang's CUDA host codegen test shows the same layout: wrapper in `.nvFatBinSegment` with fixed magic 1180844977 (= 0x466243B1), blob in `.nv_fatbin`, or `__nv_relfatbin` in relocatable-device-code (`-rdc`) mode — [clang test CodeGenCUDA/device-stub.cu](https://llvm.googlesource.com/clang/+/81fb2fbc3c4aca758a04162d4e8529dbb39b9fdb/test/CodeGenCUDA/device-stub.cu)
- NVIDIA's `fatbinary_section.h` (bundled in Triton's NVIDIA backend) names the Linux sections `.nv_fatbin` (data), `.nvFatBinSegment` (control), and `__nv_relfatbin` (pre-linked relocatable fatbin); the data section is deliberately separate so it is easy to find — [search summary of fatbinary_section.h](https://generationalwealth.duckdns.org/venv/lib/python3.13/site-packages/triton/backends/nvidia/include/fatbinary_section.h) (direct fetch returned HTTP 503; content taken from the search snippet, unverified verbatim)
- Useful inspection commands: `readelf -SW libfoo.so | grep nv_fatbin` (how much of the file is device code), `readelf -x .nvFatBinSegment k.o`, `readelf -rW k.o | grep nvFatBinSegment` — [The Software Frontier](https://www.thesoftwarefrontier.com/p/how-cuda-binaries-actually-work)

**Fatbin container header (reverse-engineered, consistent across three independent parsers)**
- Outer header (16 bytes, `#[repr(C, align(8))]`): `magic: u32 = 0xBA55ED50`, `version: u16 = 1`, `header_size: u16`, `fat_size: u64` (not including the header). Entry header is asserted to be 64 bytes: `kind: u16` (1 = PTX, 2 = ELF/cubin), `version: u16 = 0x0101`, `header_size: u32`, `padded_payload_size: u32`, `unknown0`, `payload_size: u32`, `unknown1`, `unknown2`, `sm_version: u32`, `bit_width: u32`, `unknown3`, `unknown4: u64`, `unknown5: u64`, `uncompressed_payload: u64`; when `uncompressed_payload != 0` the payload is LZ4-block decompressed to exactly that size; a kind-2 payload must start with `7F 45 4C 46` — local file `cudaparsers/src/fatbin.rs` (Apache-2.0, 2023) — [vivekpanyam/cudaparsers](https://github.com/vivekpanyam/cudaparsers)
- Same layout in C with field names: `fat_elf_header {magic u32; version u16; header_size u16; size u64}` and `fat_text_header {kind u16; unknown1 u16; header_size u32; size u64; compressed_size u32; unknown2 u32 ("address size for PTX?"); minor u16; major u16; arch u32; obj_name_offset u32; obj_name_len u32; flags u64; zero u64; decompressed_size u64}`; flags: `FATBIN_FLAG_64BIT 0x1`, `FATBIN_FLAG_DEBUG 0x2`, `FATBIN_FLAG_LINUX 0x10`, `FATBIN_FLAG_COMPRESS 0x2000`; `FATBIN_TEXT_MAGIC 0xBA55ED50` — local files `fatbin-decomp/fatbin-decompress.h`, `fatbin-decompress.c` — [n-eiling/cuda-fatbin-decompression](https://github.com/n-eiling/cuda-fatbin-decompression)
- Entry field offsets as given by the 2026 blog: kind at 0, header size at 4, padded payload size at 8, compressed size at 0x10, architecture at 0x1c, flags at 0x28; next entry = current + header_size + payload_size; entry kinds include CUBIN, PTX and "kind 8" linked to LTO device links — [The Software Frontier](https://www.thesoftwarefrontier.com/p/how-cuda-binaries-actually-work)
- JEB's cubin-entry API lists the LZ4 flag as 8192 (0x2000) and a separate Zstandard flag 32768 (0x8000) — [JEB ICudaCubinEntry API doc](https://pnfsoftware.com/jeb/apidoc_md/com.pnfsoftware.jeb.core.units.code.cuda.ICudaCubinEntry.md)
- Earlier Python walker (malfet, 2020-07-08, `cubinsizes.py`): reads `.nv_fatbin` and `__nv_relfatbin` of `libtorch_cuda.so`, checks magic and version 1, treats kind 1 as PTX and kind 2 as SM cubin, sums ELF sizes per `sm_<n>` / `ptx_<n>`; does not handle compression — [gist malfet/8990c577d61c1a46fa87e7d93b8dfdf8](https://gist.github.com/malfet/8990c577d61c1a46fa87e7d93b8dfdf8)
- nvcc compresses fatbin payloads by default; `--no-compress` disables it; `--compress-mode` accepts `default|size|speed|balance|none`, and the default is currently equivalent to `speed` (NVCC 13.4 docs) — [CUDA Compiler Driver NVCC](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html)
- Extracting a raw fatbin from a host binary: `objcopy -O binary --only-section=.nv_fatbin <input> <output>`; the decompressor was validated by comparing with an `nvcc -no-compress` build; the old flag spelling was `-Xfatbin --compress-all` — local `fatbin-decomp/README.md` — [n-eiling/cuda-fatbin-decompression](https://github.com/n-eiling/cuda-fatbin-decompression)
- A hobbyist who hooked `__cudaRegisterFatBinary` (Oct–Dec 2024) saw bytes `A2 7F 45 4C 46` instead of `7F 45 4C 46` at the start of the payload; resolution: "CUDA compressed the fatBin" — [PyTorch forum: Cuda FatBinary format error](https://discuss.pytorch.org/t/cuda-fatbinary-format-error/211641)

**Cubin ELF identity and e_flags (from LLVM's ELF.h, which mirrors NVIDIA's values)**
- `EM_CUDA = 190`; `ELFOSABI_CUDA = 51`, `ELFOSABI_CUDA_V2 = 41`; `ELFABIVERSION_CUDA_V1 = 7`, `ELFABIVERSION_CUDA_V2 = 8` — [llvm/BinaryFormat/ELF.h](https://raw.githubusercontent.com/llvm/llvm-project/main/llvm/include/llvm/BinaryFormat/ELF.h)
- e_flags: `EF_CUDA_SM = 0xff` ("processor selection mask prior to Blackwell"), `EF_CUDA_SM_MASK = 0xff00` and `EF_CUDA_SM_OFFSET = 8` ("following Blackwell", i.e. the new ABI shifts the SM byte); SM values run from `EF_CUDA_SM20 = 0x14` to `EF_CUDA_SM121 = 0x79` (decimal 20..121, so sm_120 = 0x78); `EF_CUDA_TEXMODE_UNIFIED = 0x100`, `EF_CUDA_TEXMODE_INDEPENDANT = 0x200`, `EF_CUDA_64BIT_ADDRESS = 0x400`, `EF_CUDA_ACCELERATORS_V1 = 0x800` ("set when using the sm_90a processor"), `EF_CUDA_SW_FLAG_V2 = 0x1000`, `EF_CUDA_VIRTUAL_SM = 0xff0000` (virtual/compute_XX selection mask), `EF_CUDA_ACCELERATORS = 0x8` ("set when using an accelerator variant like sm_100a in the new ABI") — [llvm/BinaryFormat/ELF.h](https://raw.githubusercontent.com/llvm/llvm-project/main/llvm/include/llvm/BinaryFormat/ELF.h)
- LLVM's ELF.h contains no `R_CUDA_*` relocation enums and no CUDA-specific `SHT_*` section types — [llvm/BinaryFormat/ELF.h](https://raw.githubusercontent.com/llvm/llvm-project/main/llvm/include/llvm/BinaryFormat/ELF.h)
- JEB's loader identifies cubins as ELF with `EM_CUDA (190)`; relocations are not supported/applied; `ET_REL` relocatable cubins are not processed — [PNF Software blog, 2025-08-15](https://pnfsoftware.com/blog/reversing-nvidia-cuda-sass-code/)
- NVIDIA's definition: "A CUDA binary (also referred to as cubin) file is an ELF-formatted file which consists of CUDA executable code sections as well as other sections containing symbols, relocators, debug info, etc." (CUDA Binary Utilities 13.4) — [CUDA Binary Utilities](https://docs.nvidia.com/cuda/cuda-binary-utilities/index.html)

**.nv.info / EIATTR_* metadata**
- Per-kernel info lives in sections named `.nv.info.<kernel>`; each item is `format: u8` + `attribute: u8` + value, with formats `EIFMT_NVAL = 0x01` (no value, u16 pad), `EIFMT_BVAL` (byte), `EIFMT_HVAL` (u16), `EIFMT_SVAL` (u16 size + payload) — local `cudaparsers/src/cubin.rs` — [vivekpanyam/cudaparsers](https://github.com/vivekpanyam/cudaparsers)
- Attribute enumeration (ordered, starting at `EIATTR_ERROR = 0x00`): PAD, IMAGE_SLOT, JUMPTABLE_RELOCS, CTAIDZ_USED, MAX_THREADS, IMAGE_OFFSET, IMAGE_SIZE, TEXTURE_NORMALIZED, SAMPLER_INIT, PARAM_CBANK, SMEM_PARAM_OFFSETS, CBANK_PARAM_OFFSETS, SYNC_STACK, TEXID_SAMPID_MAP, EXTERNS, REQNTID, FRAME_SIZE, MIN_STACK_SIZE, SAMPLER_FORCE_UNNORMALIZED, BINDLESS_IMAGE_OFFSETS, BINDLESS_TEXTURE_BANK, BINDLESS_SURFACE_BANK, KPARAM_INFO, SMEM_PARAM_SIZE, CBANK_PARAM_SIZE, QUERY_NUMATTRIB, MAXREG_COUNT, EXIT_INSTR_OFFSETS, S2RCTAID_INSTR_OFFSETS, CRS_STACK_SIZE, NEED_CNP_WRAPPER, NEED_CNP_PATCH, EXPLICIT_CACHING, ISTYPEP_USED, MAX_STACK_SIZE, SUQ_USED, LD_CACHEMOD_INSTR_OFFSETS, LOAD_CACHE_REQUEST, ATOM_SYS_INSTR_OFFSETS, COOP_GROUP_INSTR_OFFSETS, COOP_GROUP_MAX_REGIDS, SW1850030_WAR, WMMA_USED, HAS_PRE_V10_OBJECT, ATOMF16_EMUL_INSTR_OFFSETS, ATOM16_EMUL_INSTR_REG_MAP, REGCOUNT, SW2393858_WAR, INT_WARP_WIDE_INSTR_OFFSETS, SHARED_SCRATCH, STATISTICS, INDIRECT_BRANCH_TARGETS, SW2861232_WAR, SW_WAR, CUDA_API_VERSION, NUM_MBARRIERS, MBARRIER_INSTR_OFFSETS, COROUTINE_RESUME_ID_OFFSETS, SAM_REGION_STACK_SIZE, PER_REG_TARGET_PERF_STATS, CTA_PER_CLUSTER, EXPLICIT_CLUSTER, MAX_CLUSTER_RANK, INSTR_REG_MAP — local `cudaparsers/src/cubin.rs` (enum validated against cuobjdump on "thousands of cubin files") — [vivekpanyam/cudaparsers](https://github.com/vivekpanyam/cudaparsers)
- `EIATTR_KPARAM_INFO` is a 12-byte SVAL: `index: u32`, `ordinal: u16`, `offset: u16`, then a packed u32 with `log_alignment` (bits 0-7), `space` (bits 8-11), `cbank` (bits 12-16), `is_cbank` flag (bit 17 == 0), `size_bytes` (bits 18-31). `EIATTR_EXTERNS` is a 4-byte symbol index resolved through the ELF symtab — local `cudaparsers/src/cubin.rs` — [vivekpanyam/cudaparsers](https://github.com/vivekpanyam/cudaparsers)
- The nvcc-generated host stub's `__cudaSetupArgSimple` offsets (0, 4, 8, 16 for saxpy) match the cubin's `EIATTR_KPARAM_INFO` — [The Software Frontier](https://www.thesoftwarefrontier.com/p/how-cuda-binaries-actually-work)
- Kernel arguments are read from constant bank 0 at an architecture-dependent base: 0x160 for sm_70–sm_89, 0x210 for sm_90, 0x380 for sm_100–sm_12x; JEB's memory model places kernel code in the first 256 MB, constant banks from 0x10000000, shared/local memory at 0x30000000 — [PNF Software blog](https://pnfsoftware.com/blog/reversing-nvidia-cuda-sass-code/)

**SASS encoding basics (needed to read the .text sections)**
- All Volta+ SASS instructions are fixed-size, 16 bytes; destination operands come first; any instruction can be predicated (`@!P0 IMAD R0, R1, R2, R3`); registers: R0–R255, P0–P7, SR0–SR255, and from sm_75 uniform registers UR/UP — [PNF Software blog](https://pnfsoftware.com/blog/reversing-nvidia-cuda-sass-code/)
- nvdisasm JSON output: each instruction is 16 bytes, so the n-th instruction address is `start + n*16`; empty `"opcode": ""` objects mark gaps; `other-attributes` flags control-flow / subroutine-call instructions; sample output for an SM 9.0 target shows `LDC`, `S2R`, `HGMMA`, `EXIT`, `STS.128`, `RET.REL.NODEC` (schema version 13.4.0) — [CUDA Binary Utilities 13.4](https://docs.nvidia.com/cuda/cuda-binary-utilities/index.html)

**sm_XX vs compute_XX, a/f suffixes, JIT and lazy loading**
- `-arch` sets the virtual (compute_XX) target for PTX; `-code` selects real (sm_XX) targets; `-gencode` generalises both; passing a real arch to `-arch` implies its closest virtual arch; the default `-arch` in NVCC 13.4 is `sm_75`; `--cubin`, `--fatbin`, `--ptx` produce device-only outputs; `--fatbin` can combine multiple PTX and cubin images — [NVCC 13.4 docs](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html)
- Suffix semantics (NVCC 13.4): PTX for `sm_XYa` can only be compiled to `sm_XYa`; `sm_XYf` (family-specific) compiles to later GPUs in the same family (Z >= Y) in plain/f/a forms; plain `sm_XY` PTX compiles to any `sm_MN`, `sm_MNa`, `sm_MNf` with MN >= XY; code built for sm_80 runs on other CC 8.x GPUs (sm_86, sm_89) — [NVCC 13.4 docs (offset 100000)](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html)
- Supported real/virtual targets in NVCC 13.4: 75, 80, 86, 87, 88, 89, 90, 90a, 100/100f/100a, 103/103f/103a, 107/107f/107a (listed as Rubin), 110/110f/110a, 120/120f/120a, 121/121f/121a — [NVCC 13.4 docs](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html)
- At launch the driver reads the fatbin index and picks an exact-architecture cubin, then a compatible one, then PTX JIT-compiled at load time — [The Software Frontier](https://www.thesoftwarefrontier.com/p/how-cuda-binaries-actually-work)
- Lazy loading: introduced CUDA 11.7 (off by default), default on Linux in 12.2, default on all platforms in 12.3; requires driver >= 515; modules load on first use, kernels can be forced with `cuModuleGetFunction()` / `cudaFuncGetAttributes()`; modules with managed variables still load eagerly; `cuModuleGetLoadingMode` reports the mode; implications: possible deadlocks with cross-kernel sync, VRAM allocation failures at late load, and module loading landing inside benchmark windows (use a warm-up) — [CUDA Programming Guide: Lazy Loading](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/lazy-loading.html)
- `CUDA_MODULE_LOADING` = `DEFAULT|LAZY|EAGER` (DEFAULT equals LAZY); `CUDA_MODULE_DATA_LOADING` same values, inherits from `CUDA_MODULE_LOADING` when unset — [CUDA Programming Guide: Environment Variables](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/environment-variables.html)

### Inferences
- For the RTX 5060 Ti the relevant fatbin entries are `sm_version = 120` cubins (kind 2) and `compute_120`/`compute_120a` PTX (kind 1); because sm_120a code cannot be forward-compiled, a library that ships only `sm_120a` is tied to consumer Blackwell, while `sm_120f`/`compute_120` entries are the portable ones.
- Because the SM byte moved from `e_flags & 0xff` to `(e_flags >> 8) & 0xff` in the "new ABI" (Blackwell-era), any home-grown cubin parser must check `ELFABIVERSION` (7 vs 8) / OSABI (51 vs 41) before decoding the SM number; parsers written for Ampere/Hopper may misreport Blackwell cubins.
- The three independent parsers agree on the 16-byte fatbin header and the 64-byte entry header, so this part of the format can be treated as stable since at least CUDA 11.x (2020 gist) through 2026 (blog); the `flags` word (0x2000 = LZ4, 0x8000 = Zstd per JEB) is where new nvcc `--compress-mode` variants will show up.
- `EIATTR_REGCOUNT`, `EIATTR_MAX_THREADS`, `EIATTR_REQNTID`, `EIATTR_CTA_PER_CLUSTER`, `EIATTR_PARAM_CBANK` and `EIATTR_KPARAM_INFO` are the ones that matter for performance study: they give register pressure (occupancy), launch-bounds hints, cluster shape and the argument layout needed to re-launch a stolen kernel by hand.

### Gaps
- No NVIDIA primary source documents the fatbin header or EIATTR records; all layouts above are reverse-engineered (cudaparsers, n-eiling, malfet, 2026 blog, JEB) and NVIDIA's own `fatbinary_section.h` could not be fetched verbatim (HTTP 503).
- The exact byte sizes/encodings of `EIATTR_REGCOUNT`, `EIATTR_MAX_THREADS`, `EIATTR_PARAM_CBANK` values were not confirmed beyond "SVAL with u16 size" (cudaparsers stores them as raw `Vec<u32>`); confirm with `cuobjdump -elf` on a real cubin.
- Meaning of the Zstd flag (0x8000) and of NVCC `--compress-mode size` were not tied to a specific compressor by any primary source.
- The `.nv.rel.action`, `.nv.shared.<kernel>`, `.nv.constant0.<kernel>` section semantics were not covered by any fetched source (only section-name conventions are implied by cudaparsers' `.nv.info.` prefix filter); verify with `readelf -S` on a cubin.

## Key question 2: Official NVIDIA tools (cuobjdump, nvdisasm, cu++filt, nvcc, ptxas, nvprune, fatbinary, compute-sanitizer) and SM support per CUDA version

### Takeaway
`cuobjdump` is the Swiss-army knife for host binaries (list/extract per-arch cubins and PTX, SASS, resource usage); `nvdisasm` works only on cubins but gives CFGs, register liveness, line info and JSON; CUDA 13.x (from 13.0) only compiles for compute capability >= 7.5, and CUDA 13.4 explicitly supports sm_120/sm_120a/sm_120f for consumer Blackwell.

### Cited Findings

**cuobjdump (CUDA Binary Utilities v13.4)**

- `-arch` values accepted by cuobjdump 13.4: sm_75, sm_80, sm_86, sm_87, sm_88, sm_89, sm_90, sm_90a, sm_100, sm_100a, sm_100f, sm_103, sm_103a, sm_103f, sm_107, sm_107a, sm_107f, sm_110, sm_110a, sm_110f, sm_120, sm_120a, sm_120f, sm_121, sm_121a, sm_121f — [CUDA Binary Utilities 13.4](https://docs.nvidia.com/cuda/cuda-binary-utilities/index.html)

- `-b` accepted values: SM75, SM80, SM86, SM87, SM88, SM89, SM90, SM90a, SM100, SM100a, SM103, SM103a, SM107, SM107a, SM107f, SM110, SM110a, SM120, SM120a, SM121, SM121a — [CUDA Binary Utilities 13.4](https://docs.nvidia.com/cuda/cuda-binary-utilities/index.html)
- nvdisasm needs complete relocation info for control-flow analysis; if missing use `-ndf`, or rebuild with `ptxas`/`nvlink` using `-preserve-relocs` — [CUDA Binary Utilities 13.4](https://docs.nvidia.com/cuda/cuda-binary-utilities/index.html)
- The doc page carries "Last updated on Oct 12, 2026" and sample output reports `nvdisasm V13.4.0` — [CUDA Binary Utilities 13.4 (offset 100000)](https://docs.nvidia.com/cuda/cuda-binary-utilities/index.html)
- Architecture families listed by the doc: Turing CC 7.5; Ampere and Ada 8.0, 8.6, 8.9; Hopper 9.0; "Blackwell and Rubin" 10.0, 10.3, 10.7, 11.0, 12.0 — [CUDA Binary Utilities 13.4](https://docs.nvidia.com/cuda/cuda-binary-utilities/index.html)

**cu++filt and nvprune**

- nvcc options relevant to RE: `-G` (device debug), `-lineinfo` (line info for device code), `--keep` and `--keep-dir` (keep intermediates), `-Xptxas` (pass to ptxas), `--resource-usage`/`-res-usage`, `--no-compress`, `--compress-mode default|size|speed|balance|none`; tools referenced: ptxas, nvlink, nvprune, tileiras, and the `fatbinary` tool (named in the `--concat` description) — [NVCC 13.4 docs](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html)
- `nvcc --keep` leaves the host stub file (`saxpy.cudafe1.stub.c`) which shows the static constructor `__sti____cudaRegisterAll` → `__cudaRegisterBinary` → `__cudaRegisterEntry(host_fn_ptr, "_Z5saxpyifPKfPf")` and the device stub `__cudaLaunchPrologue` / `__cudaSetupArgSimple` / `__cudaLaunch` — [The Software Frontier](https://www.thesoftwarefrontier.com/p/how-cuda-binaries-actually-work)
- Nsight Compute: SASS is always embedded in the report; CUDA-C source correlation needs `-lineinfo` at compile time and `--import-source yes` at collection; if the SASS view shows no source "your binary does not contain the necessary lineinfo information", check with cuobjdump — [VI-HPS Nsight Compute slides](https://www.vi-hps.org/cms/upload/material/tw41/Nsight_Compute.pdf); [OLCF Nsight Compute webinar 2020](https://www.olcf.ornl.gov/wp-content/uploads/2020/02/OLCF-Webinar-Nsight-Compute.pdf); [NVIDIA forum: Cannot see source of some kernels](https://forums.developer.nvidia.com/t/cannot-see-source-of-some-kernels/195130)

**Which CUDA versions compile for which SM (incl. sm_120)**
- CUDA 13.0 removed offline compilation and library support for compute capabilities 5.x, 6.x, 7.0, 7.2 (Maxwell, Pascal, Volta); Turing (7.5) is the lowest target; driver branch 580 (released with 13.0) is the final/LTS branch for pre-7.5 GPUs, supported until mid-2028; apps built with CUDA 12.9 or earlier keep running — [NVIDIA blog 2025-08-04: Navigating GPU architecture support](https://developer.nvidia.com/blog/navigating-gpu-architecture-support-a-guide-for-nvidia-cuda-developers/)
- `nvcc --list-gpu-arch` on CUDA 12.9 lists compute_50 through compute_121, including compute_100, compute_103, compute_120, compute_121 (sm_110 absent in 12.9) — [NVIDIA blog 2025-08-04](https://developer.nvidia.com/blog/navigating-gpu-architecture-support-a-guide-for-nvidia-cuda-developers/)
- Blackwell device code first shipped in CUDA Toolkit 12.8 (third-party guide; treat as secondary) — [bestllmfor.com Blackwell sm120 build guide](https://bestllmfor.com/guides/llama-cpp-cuda-blackwell-sm120-build/)
- PyTorch 2.7.0 wheels built with CUDA 12.8 added Blackwell; "all of our binaries using CUDA >= 12.8 support the Blackwell architecture"; a cu128 nightly reported `['sm_100', 'sm_120', 'compute_120']` in `torch.cuda.get_arch_list()` — [PyTorch forum: Pytorch support for sm120](https://discuss.pytorch.org/t/pytorch-support-for-sm120/216099)

### Inferences
- For the user's RTX 5060 Ti, the minimum practical toolchain is CUDA 12.8 (first Blackwell support); CUDA 13.4 is the current reference and still lists sm_120 in both cuobjdump `-arch` and nvdisasm `-b`, so `nvdisasm -b SM120` can disassemble raw instruction blobs carved out of memory.
- `cuobjdump -xelf` + `nvdisasm -cfg/-plr/-json` is the official "pipeline": extract the sm_120 slice from a `.so`, then analyse per kernel; `-plr` (register life ranges) is the closest official equivalent to a register-pressure view when the source is not available.
- `nvprune -arch sm_120 libcublas_static.a` is a cheap way to isolate exactly the Blackwell cubins of a static NVIDIA library before extraction.

### Gaps
- The CUDA 13.4 Binary Utilities page was read in two slices; the instruction-set reference tables (Turing/Ampere/Ada/Hopper/Blackwell instruction lists) fell between slices and were not captured; they exist in the same document (table of contents of the 12.6 PDF confirms per-arch instruction sections).
- `compute-sanitizer` and the standalone `fatbinary` tool's CLI were not researched (no source fetched).
- Per-version tables (12.8 vs 12.9 vs 13.0–13.4) of exactly when sm_110/sm_121/sm_107 were added could not be pinned to a primary source; only the 12.9 `--list-gpu-arch` output and the 13.4 lists are confirmed.
- `-poolmgr` (asked in the task) does not exist in the 13.4 nvdisasm option list.

## Key question 3: Extracting kernels from third-party binaries (cuBLAS/cuBLASLt/cuDNN, PyTorch wheels, TensorRT engines, llama.cpp CUDA, vLLM); listing kernels; finding the one that ran; picking the SM slice

### Takeaway
Any ELF `.so` with a `.nv_fatbin` section (cuBLAS, cuDNN, `libtorch_cuda.so`, llama.cpp's `libggml-cuda.so`, vLLM's `_C` extension) can be enumerated with `cuobjdump -lelf/-lptx` and sliced per architecture with `cuobjdump -xelf`; the kernel that actually ran is identified by name from `nsys` (`cuda_gpu_kern_sum:mangled`) or `ncu --print-kernel-base=mangled`, then located in the SASS dump; TensorRT plan files are the one container with no public layout.

### Cited Findings
- cuobjdump "takes host binaries as input" including shared libraries; `cuobjdump -lelf libfoo.so` lists architectures and cubin count, `-xelf <partial-name|all>` extracts; `-all` dumps all fatbin sections, not just the executable fatbin — [CUDA Binary Utilities 13.4](https://docs.nvidia.com/cuda/cuda-binary-utilities/index.html); [The Software Frontier](https://www.thesoftwarefrontier.com/p/how-cuda-binaries-actually-work)
- malfet's `cubinsizes.py` was written precisely to enumerate per-arch cubin sizes inside PyTorch's `libtorch_cuda.so` by walking `.nv_fatbin` and `__nv_relfatbin` — [gist malfet](https://gist.github.com/malfet/8990c577d61c1a46fa87e7d93b8dfdf8)
- cuBLAS: "*gemm API functions map to myriad different kernels. The mapping depends on CUDA version, GPU architecture, and arguments passed (matrix sizes, shapes, transpose modes)... internal implementation details that NVIDIA does not publish... subject to frequent change, without notice"; profiler output shows sm90 XMMA and cutlass kernel names — [NVIDIA forum: Using gcgemm from CuBLAS](https://forums.developer.nvidia.com/t/using-gcgemm-from-cublas/116703)
- cuBLAS 13.4 docs have a "3.1.3 cuBLASLt Logging" section and logger APIs `cublasLoggerConfigure()`, `cublasSetLoggerCallback()`, `cublasLtLoggerSetLevel()`, `cublasLtLoggerSetMask()`, `cublasLtLoggerSetFile()` — [cuBLAS docs v13.4](https://docs.nvidia.com/cuda/cublas/index.html) (the env-var section `CUBLASLT_LOG_LEVEL` etc. was not reached in the fetched slices)
- Nsight Systems: `cuda_gpu_kern_sum` report accepts a suffix: `:base` summarises over the kernel base name (not the templated name), `:mangled` over the raw mangled name; mangled names require capture with a recent nsys, re-export is not enough — [Nsight Systems Post-Collection Analysis Guide](https://docs.nvidia.com/nsight-systems/AnalysisGuide/index.html); [NVIDIA forum: Mangled kernel names in raw file](https://forums.developer.nvidia.com/t/mangled-kernel-names-in-raw-file/257510)
- Nsight Compute: `--print-kernel-base mangled|demangled|function` controls display; `--kernel-name-base` controls the matched name during collection; `ncu -i <REPORT> --page raw --print-kernel-base=mangled` prints an existing report with mangled names — [NVIDIA forum: Mangled kernel name in nsight compute metrics output](https://forums.developer.nvidia.com/t/mangled-kernel-name-in-nsight-compute-metrics-output/240198)
- llama.cpp's `ggml/src/ggml-cuda/CMakeLists.txt` appends `120a-real` to `CMAKE_CUDA_ARCHITECTURES` when the toolkit supports it and rewrites plain `12X` to `12Xa` because "the Blackwell FP4 tensor core instructions are not forwards compatible and therefore need 12Xa"; `120f-virtual` would in principle work but a CMake regex conflicted with the `f` suffix (needs CMake >= 3.31.8 or >= 4.0.2) — [llama.cpp ggml-cuda CMakeLists mirror](https://git.mitjafelicijan.com/r/llmnpc/blob/llama.cpp/ggml/src/ggml-cuda/CMakeLists.txt)
- Known llama.cpp build failure (Feb 2026): `-DCMAKE_CUDA_ARCHITECTURES=120` on CUDA 13.1 fails in ptxas for MXFP4 template instances (block-scale MMA rejected on sm_120) — [llama.cpp issue #19662](https://github.com/ggml-org/llama.cpp/issues/19662)
- Prebuilt llama.cpp binaries may lack suitable PTX and then "silently offload zero layers to the GPU"; recommendation: build from source with 12.8+ toolkit and 570+ driver — [bestllmfor.com guide](https://bestllmfor.com/guides/llama-cpp-cuda-blackwell-sm120-build/)
- PyTorch cu128 arch lists seen in the wild: `['sm_70','sm_75','sm_80','sm_86','sm_90','sm_100','sm_120']`; one user reported some kernels (embedding) still not compiled for sm_120 in a nightly (single report) — [PyTorch forum: sm120](https://discuss.pytorch.org/t/pytorch-support-for-sm120/216099)
- TensorRT: a plan is "an optimized inference engine in a serialized format"; "an engine contains the optimized network, kernel selections, and memory management strategy"; plans are tied to the hardware and software versions used to build them; forum users report "the PLAN file can't be decoded explicitly"; NVIDIA's `trt-engine-explorer` (trex) inspects engine graphs via JSON export (since TensorRT 8.2) — [TensorRT glossary](https://docs.nvidia.com/deeplearning/tensorrt/latest/reference/glossary.html); [NVIDIA forum: How to read the plan file](https://forums.developer.nvidia.com/t/how-to-read-the-plan-file/62157); [trt-engine-explorer](https://github.com/NVIDIA/TensorRT/blob/147005ffe1dc447bec8af9601539a9d464ca77fd/tools/experimental/trt-engine-explorer)
- NVBit 1.7: dynamic binary instrumentation of SASS "when first loaded", no recompilation, works on pre-compiled applications from any compiler; supports SM >= 3.5 and <= 12.1, requires CUDA >= 12.0, Linux x86_64/aarch64, GCC >= 8.5; licensed under the CUDA Toolkit EULA, research prototype — [NVlabs/NVBit README](https://raw.githubusercontent.com/NVlabs/NVBit/master/README.md)

### Inferences
- Workflow for "which cuBLAS kernel did llama.cpp/PyTorch run on my 5060 Ti": `nsys profile` → `nsys stats --report cuda_gpu_kern_sum:mangled` → take the mangled name → `cuobjdump -sass -arch sm_120 -fun <mangled> libcublasLt.so` (or extract with `-xelf` then `nvdisasm -cfg -plr`). The `-fun` filter avoids dumping tens of thousands of kernels.
- Because llama.cpp compiles `120a-real`, its `libggml-cuda.so` contains an `sm_120a` cubin with `EF_CUDA_ACCELERATORS` set and the `.nv.info` will show the Blackwell-specific instruction use; the same library will not run its FP4 paths on a future sm_121/sm_13x GPU unless rebuilt.
- NVIDIA libraries (cuBLASLt, cuDNN) carry many architecture slices; `nvprune -arch sm_120` on the static archive or `cuobjdump -xelf` with a name containing `sm_120` is the fastest way to isolate the relevant 5-10 % of the fatbin.
- TensorRT engines are effectively opaque; the practical route to their kernels is runtime capture (key question 4), not static parsing.

### Gaps
- No primary source for how vLLM packages its CUDA kernels (likely `_C.abi3.so`/`_moe_C` extensions built like any torch extension) — not researched; assume the generic `.nv_fatbin` route.
- cuBLAS/cuBLASLt logging env vars (`CUBLASLT_LOG_LEVEL`, `CUBLASLT_LOG_MASK`, `CUBLAS_LOGINFO_DBG`) were not confirmed from the fetched doc slices; the logging section exists (3.1.3) but its text was not retrieved. Whether the log prints the selected kernel name is unverified.
- Whether cuDNN 9.x still ships uncompressed per-arch cubins or uses a different internal packaging (runtime-fused kernels via NVRTC) was not researched.
- TensorRT plan internals: no source describes whether cubins are stored verbatim, compressed or encrypted inside the plan.

## Key question 4: Runtime dumping (hooking cuModuleLoadData / cuLibraryLoadData / __cudaRegisterFatBinary via LD_PRELOAD or Frida; JIT cache; host stubs)

### Takeaway
Runtime capture is a two-hook problem: hook the runtime's `__cudaRegisterFatBinary(void* wrapper)` (read `wrapper->data`, which is a fatbin that is usually LZ4-compressed, so decompress before expecting `7F 45 4C 46`) and the driver's `cuModuleLoadData`/`cuModuleLoadDataEx`/`cuLibraryLoadData` (whose `image` may be a cubin, fatbin or PTX text); `__cudaRegisterFunction`/`__cudaRegisterEntry` give the host-pointer → mangled-kernel-name map; PTX JIT results land in `~/.nv/ComputeCache` (default 1 GiB, max 4 GiB).

### Cited Findings
- Clang's design: a module constructor wraps the GPU binary in a struct, calls `__cudaRegisterFatBinary`, stores the handle, then a helper calls `__cudaRegisterFunction` once per kernel and `__cudaRegisterVar` per device variable; a destructor calls `__cudaUnregisterFatBinary`; the review note states the fatbin format is undocumented — [LLVM review D8463](https://reviews.llvm.org/D8463?id=24973); [clang CGCUDANV.cpp](https://llvm.googlesource.com/clang/+/refs/heads/release_50/lib/CodeGen/CGCUDANV.cpp)
- Flang's CUDA runtime shows the full sequence: `__cudaRegisterFatBinary` → `__cudaRegisterFatBinaryEnd(handle)`, and `__cudaRegisterFunction` / `__cudaRegisterVar` for functions and variables — [flang runtime/CUDA/registration.cpp](https://llvm.googlesource.com/llvm-project/+/a78861fc55d18046989ff4d624a037e9181da170/flang/runtime/CUDA/registration.cpp)
- In nvcc 2026-era stubs the names are `__cudaRegisterBinary` and `__cudaRegisterEntry(host_fn_ptr cast to kernel signature, "_Z5saxpyifPKfPf")`, called from the static constructor `__sti____cudaRegisterAll` before `main` — [The Software Frontier](https://www.thesoftwarefrontier.com/p/how-cuda-binaries-actually-work)
- A hobbyist LD_PRELOAD hook on `__cudaRegisterFatBinary` cast the argument to `__fatBinC_Wrapper_t` and read `bin->data`; the payload did not start with an ELF header because "CUDA compressed the fatBin" — [PyTorch forum: Cuda FatBinary format error](https://discuss.pytorch.org/t/cuda-fatbinary-format-error/211641)
- A "cudahook" project uses LD_PRELOAD + `dlsym` to hook CUDA runtime functions including `__cudaRegisterFatBinary`; the target must be dynamically linked to the CUDA runtime (static `cudart` defeats it) — [juniorprincewang: CUDA API Remoting](http://juniorprincewang.github.io/2018/05/14/CUDA-API-Remoting/)
- PTX-EMU hooks `__cudaRegisterFatBinary` to extract PTX at runtime — [deepwiki PTX-EMU: Fat Binary Registration and PTX Extraction](https://deepwiki.com/gty111/PTX-EMU/3.1.1-fat-binary-registration-and-ptx-extraction) (page returned HTTP 429 on direct fetch; claim from search snippet)
- `cuModuleLoadData(module, image)`: the pointer "may be obtained by mapping a cubin or PTX file, passing a cubin or PTX file as a NULL-terminated text string"; `cuLinkComplete` "returns the cubin image for the linked device code, which can be used with cuModuleLoadData" (owned by the link state until `cuLinkDestroy`) — [CUDA Driver API: Module Management (13.4.2)](https://docs.nvidia.com/cuda/archive/13.4.2/cuda-driver-api/cuda_driver_api/group__CUDA__MODULE.html)
- `cuLibraryLoadData`: "The code may be a cubin or fatbin as output by nvcc, or a NULL-terminated PTX"; a fatbin may contain relocatable code for separate compilation — [cuda-python driver.library_load_data](https://nvidia.github.io/cuda-python/pr-preview/pr-3095/cuda-bindings/latest/module/generated/driver_v2/cuda.bindings._v2.driver.library_load_data.html)
- ZLUDA's `zluda_dump` is a library injected into a CUDA application that records, for every launched GPU function, the PTX source, the launch configuration and argument dumps before/after execution; `ZLUDA_DUMP_KERNEL=<name>` filters by kernel, `ZLUDA_DUMP_DIR` sets output; a `replay.py` re-executes dumped kernels — [ZLUDA mirror docs](https://git.uoc.run.place/Applied-Software/ZLUDA/compare/v4..master)
- DocumentSASS obtains the SASS instruction and latency tables by running `nvdisasm` on cubins for each architecture under an LD_PRELOAD `intercept.so` that man-in-the-middles `memcpy`, then `strings` + `funnel.py`; the strings are generated dynamically per input architecture, so plain `strings nvdisasm` is not enough; tested with CUDA 11.6; last push 2025-07-18 — local `docsass/README.md` — [0xD0GF00D/DocumentSASS](https://github.com/0xD0GF00D/DocumentSASS)
- JIT cache env vars: `CUDA_CACHE_DISABLE` (1 disables PTX JIT and binary finalization caching, default 0); `CUDA_CACHE_PATH` (default Linux `~/.nv/ComputeCache`, Windows `%APPDATA%\NVIDIA\ComputeCache`); `CUDA_CACHE_MAXSIZE` (default 1073741824 = 1 GiB desktop/server, 268435456 = 256 MiB embedded, maximum 4294967296 = 4 GiB; larger binaries are not cached, old entries evicted); `CUDA_FORCE_PTX_JIT=1` forces PTX JIT instead of embedded cubin (overrides `CUDA_FORCE_JIT`); `CUDA_DISABLE_PTX_JIT=1` requires embedded cubin; `CUDA_LAUNCH_BLOCKING=1` serialises launches — [CUDA Programming Guide: Environment Variables](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/environment-variables.html)
- Lazy loading means a hook on `cuModuleGetFunction`/`cuKernelGetFunction` sees kernels only on first use; `cuModuleLoad()` does not guarantee immediate loading; `CUDA_MODULE_LOADING=EAGER` restores old behaviour — [CUDA Programming Guide: Lazy Loading](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/lazy-loading.html)
- NVBit injects at the moment a GPU function is first loaded and can inspect/modify SASS, so it doubles as a "see every kernel actually loaded" tool (SM 3.5–12.1, CUDA >= 12.0) — [NVlabs/NVBit README](https://raw.githubusercontent.com/NVlabs/NVBit/master/README.md)

### Inferences
- Minimal LD_PRELOAD dumper design (not found ready-made, must be written): export `__cudaRegisterFatBinary(void* w)` → `dlsym(RTLD_NEXT, ...)`; read `((uint64_t*)w)[1]`-style `data` pointer at offset 8 (fields: u32 magic 0x466243B1, u32 version, void* data, void* filename_or_fatbins); check `*(u32*)data == 0xBA55ED50`; size = `header_size + fat_size`; write the blob; then run `cuobjdump -lelf/-xelf` on the dumped file (cuobjdump accepts "external fatbins"), or decompress with the n-eiling tool when flag 0x2000 is set. Also export `__cudaRegisterFunction(handle, hostFun, deviceFun, deviceName, ...)` to log the host-pointer → kernel-name map.
- For the driver side (NVRTC/Triton/PyTorch-inductor/TensorRT-style JIT), hook `cuModuleLoadData`, `cuModuleLoadDataEx`, `cuModuleLoadFatBinary`, `cuLibraryLoadData` in `libcuda.so.1` (Frida `Interceptor.attach(Module.findExportByName('libcuda.so.1','cuModuleLoadData'))` or an LD_PRELOAD shim); dispatch on the first 4 bytes: `7F 45 4C 46` → cubin, `50 ED 55 BA` (LE of 0xBA55ED50) → fatbin, ASCII `//` or `.version` → PTX. Because lazy loading is now default, a hook on `cuModuleGetFunction`/`cuKernelGetFunction` is what tells you which kernels were actually used.
- Since `CUDA_FORCE_PTX_JIT=1` forces PTX JIT and `CUDA_CACHE_PATH` is user-controlled, the JIT cache directory is a passive way to collect finalized cubins for every PTX-only kernel an app runs (e.g. a PyTorch wheel with `compute_120` PTX but no `sm_120` cubin). The cache file format itself was not documented by any source.
- Statically linked `cudart` (the nvcc default) means the `__cudaRegister*` symbols are internal to the executable; in that case the driver-level `cuModuleLoad*`/`cuLibraryLoadData` hooks in `libcuda.so.1` are the reliable ones (the runtime always ends up calling the driver).

### Gaps
- No maintained open-source "dump every cubin an app loads" tool was found; cudahook (2018) and the PyTorch-forum snippet are the closest; NVBit and zluda_dump are adjacent (instrumentation / PTX+args respectively).
- Exact exported symbol names for runtime registration in CUDA 13.x (`__cudaRegisterFatBinary` vs the `__cudaRegisterBinary`/`__cudaRegisterEntry` seen in the 2026 stub) were not reconciled: the stub may call wrappers in `cudart` that in turn call the classic names; verify with `nm -D libcudart.so.13`.
- Frida-specific CUDA scripts: none found; the approach is standard `Interceptor.attach` on `libcuda.so.1` exports (inference, unverified).
- The on-disk format of `~/.nv/ComputeCache` entries was not found in any source.

## Key question 5: Generic RE tools (Ghidra, Binary Ninja, IDA, radare2/rizin, objdump) and Compiler Explorer

### Takeaway
As of October 2026 the only mature generic-RE-tool SASS disassembler is commercial (JEB 5.31, Aug 2025, sm_70–sm_121 incl. Blackwell, with an experimental decompiler); Ghidra has only a 2020 Kepler sm_30 SLEIGH spec and an unrelated Falcon microcontroller module; no Binary Ninja, IDA, radare2/rizin or binutils SASS module was found. The practical open path is `cuobjdump`/`nvdisasm` output plus community encoding databases (DocumentSASS, EoSS, CuAssembler), and Compiler Explorer for side-by-side CUDA → PTX → SASS with GPU execution.

### Cited Findings
- JEB 5.31 (post 2025-08-15, updated 2025-08-18, author Nicolas Falliere): generic SASS disassembler + experimental pseudo-C decompiler for Volta → Blackwell (sm_70–sm_121); pre-Volta unsupported; validated against cuobjdump/nvdisasm on >100 million unique instructions across ~620,000 kernels; options DisplayImplicitDescriptors (`desc[UR4]`), DisplayRegisterNumbers, DisplayHiddenAttributes, DisplaySchedulingInfo; decompiler caveats: partial IR (only 4-operand FMNMX; ELECT/VOTE untranslated), BRX jump tables not processed, non-inlined device subroutines handled poorly, unrolled loops unreadable; cubin extraction from host files is best-effort "since Nvidia does not officially document the fatbin format"; credits DocumentSass — [PNF Software blog](https://pnfsoftware.com/blog/reversing-nvidia-cuda-sass-code/)
- Ghidra: a SLEIGH spec `CUDA.slaspec` for NVIDIA Kepler sm_30 cubins (Habr article 2020-07-01, author Danil6969, repo github.com/Danil6969/Ghidra-Nvidia-GPU); 64-bit (8-byte) fixed instructions; only sm_30; loader details not described — [Habr: Ghidra spec for Nvidia Kepler](https://habr.com/ru/post/509156/)
- Ghidra: `marysaka/ghidra_falcon` supports NVIDIA Falcon microcontrollers (not SASS), v1.1 Sep 2024, "pretty immature" — [marysaka/ghidra_falcon](https://github.com/marysaka/ghidra_falcon)
- `sass-king`: documentation-focused reverse engineering of SASS for Blackwell GPUs whose README lists a Ghidra plugin as a future plan — [imtaqin.id article on sass-king](https://imtaqin.id/sass-king-reverse-engineers-nvidia-sass-for-blackwell-gpus) (article returned HTTP 404 on fetch; claim from search snippet only, unverified)
- Binary Ninja: no SASS architecture plugin found; the related academic tool NVLift (NDSS 2026 BAR workshop) lifts SASS to LLVM IR for Turing (SM75) with 47 supported instructions, not a Binary Ninja plugin — [NDSS BAR 2026 program](https://www.ndss-symposium.org/ndss-program/bar-2026/)
- IDA Pro / radare2 / rizin: no cubin loader or SASS processor module surfaced in any search; Hex-Rays' supported-processor list does not include CUDA — [Hex-Rays supported processors 9.1](https://docs.hex-rays.com/9.1/user-guide/disassembler/supported-processors)
- `decuda` (G8x/G9x cubin disassembler) is archived/read-only — [laanwj/decuda wiki](https://github.com/laanwj/decuda/wiki/)
- DocumentSASS: "an extensive description of SASS instructions as well as latencies was contained in two specific strings in nvdisasm", extracted via memcpy interception; lists prior RE assemblers MaxAs, AsFermi, CuAssembler, TuringAs, KeplerAs, Decuda; 212 stars, last push 2025-07-18 — [0xD0GF00D/DocumentSASS](https://github.com/0xD0GF00D/DocumentSASS)
- EoSS: "Exploring SASS - A Systematic Framework to Explore NVIDIA's ISA" (Avalos, Payer, Rogers; ASPLOS 2027): extracts instruction specifications "from data embedded in NVIDIA tooling", generates valid encodings and executes them on real hardware via binary patching; releases validated instruction sets for seven architectures Volta → Blackwell with 443 to 1,239 executable instruction classes per generation; no repo URL on the page — [Purdue EoSS page](https://engineering.purdue.edu/tgrogers/publication/avalos-asplos-2027/)
- CuAssembler ("An unofficial cuda assembler, for all generations of SASS, hopefully") reads SASS and writes machine code back into cubins; README text says it currently only supports the Turing instruction set — [cloudcores/CuAssembler](https://github.com/cloudcores/CuAssembler); mirror [bogan-FMA/CuAssembler](https://github.com/bogan-FMA/CuAssembler)
- Modal GPU glossary: SASS instructions are listed in the CUDA Binary Utilities docs "but their semantics are not defined"; the mapping from assembler text to binary encoding "is entirely undocumented, but it has been reverse-engineered in certain cases" — [Modal GPU Glossary: Streaming Assembler](https://modal.com/gpu-glossary/device-software/streaming-assembler)
- Compiler Explorer (godbolt.org): NVIDIA blog 2025-06-18 (Jake Hemstad) — select from multiple CUDA compiler versions, source lines colour-coded to PTX and SASS side by side, flags such as `-use_fast_math` and `--resource-usage`, and since 2022 execution of CUDA code on NVIDIA GPUs in the browser; suited to "small CUDA programs" — [NVIDIA blog: Compiler Explorer, the kernel playground](https://developer.nvidia.com/blog/compiler-explorer-the-kernel-playground-for-cuda-developers)
- A local Compiler Explorer integration (Wafer) states that for SASS output "nvdisasm must be available (included with CUDA Toolkit)" — [docs.wafer.ai compiler-explorer](https://docs.wafer.ai/compiler-explorer/viewing-output)

### Inferences
- For a Blackwell-only hobbyist, the realistic free stack in 2026 is: `cuobjdump -sass`/`nvdisasm -cfg -plr -hex` for reading, DocumentSASS/EoSS-style tables for operand/latency semantics, and Nsight Compute's Source page (needs `-lineinfo` + `--import-source yes`) for executed-instruction and stall correlation. A Ghidra-based workflow would require writing a new SLEIGH spec for 128-bit Volta+ encodings; nothing public covers sm_80+ in Ghidra.
- JEB is the only tool that will show a cubin as "code + CFG + decompiled pseudo-C" for sm_120, and its known arg-base offsets (0x380 in c[0x0] for sm_100–12x) are directly useful when reading `nvdisasm` output by hand: loads `c[0x0][0x380+...]` are kernel parameters on Blackwell.
- Compiler Explorer is the fastest way to learn "what SASS does nvcc emit for construct X on sm_120" without local toolchain churn; it is not an RE tool for third-party binaries.
- `objdump`/`readelf` are still useful on cubins for section/symbol listing (`readelf -S`, `nm | cu++filt`) because a cubin is standard ELF, but they cannot disassemble `.text.*` (no EM_CUDA backend in binutils).
