# Verification of rea.md (NVIDIA track, dimension: applying REA to NVIDIA kernel work)

Verified 2026-10-17. Method: each cited URL fetched (WebFetch) or checked against the local read-only clone of morluto/rea at commit `060eb43b` (2026-10-17); independent checks via treeless `git clone` of ghidra (master) and llvm-project (main), raw.githubusercontent.com, GitHub commit pages, frida.re and docs.nvidia.com. Note: the per-turn WebSearch budget was exhausted before this verification started, so "independent" evidence below comes from a second primary source fetched directly, not from web search.

## Confirmed

1. **Claim:** REA's own ELF front-end rejects cubins: open_binary accepts only e_machine 3/62/8/20/40/183/243 (EM_CUDA=190 -> 'unsupported ELF architecture'), and the pwntools bridge raises 'Initial layout profile requires x86-64 ELF objects.'
   - Local clone `src/domain/elfFixedHeader.ts` lines 73–85: `case 3`, `62`, `8`, `20`, `40`, `183`, `243` only; `src/domain/binaryTarget.ts` line 210: `if (architecture === null) return err("unsupported ELF architecture");`. `bridge/pwntools/layout_impl.py` line 124: `"Initial layout profile requires x86-64 ELF objects."` (also lines 120 and 172 variants). Raw GitHub copy of layout_impl.py contains the same three messages. EM_CUDA = 190 "NVIDIA CUDA architecture" confirmed at https://au.sco.com/developers/gabi/latest/ch4.eheader.html.

2. **Claim:** Ghidra master ships 39 processor modules and none is NVIDIA/PTX/SASS/AMDGPU, so no REA Ghidra language override can decode SASS.
   - GitHub tree page lists 39 entries; independent treeless clone of ghidra master: `git ls-tree HEAD Ghidra/Processors/` = 39 dirs (6502 … x86), exactly the list in the note; no NV/PTX/SASS/CUDA/AMD/GCN/RDNA entry.

3. **Claim:** LLVM's NVPTX target directory has only MCTargetDesc and TargetInfo (no Disassembler, no AsmParser), so llvm-objdump cannot disassemble PTX/SASS; NVIDIA states nvdisasm 'only accepts cubin files' while cuobjdump accepts cubins and host binaries (-lelf, -xelf all, -sass, -arch sm_120).
   - GitHub page and independent treeless clone of llvm-project main: `llvm/lib/Target/NVPTX/` subdirs = `MCTargetDesc`, `TargetInfo` only (AMDGPU by contrast has AsmParser, Disassembler, MCA, MCTargetDesc, TargetInfo, Utils). CUDA Binary Utilities v13.4: "nvdisasm only accepts cubin files"; "cuobjdump accepts both cubin files and host binaries"; options `-lelf`, `-xelf` (with `all`), `-sass`, `-arch` with `sm_120`, `sm_120a`, `sm_120f`, `sm_121` (also `sm_121a`, `sm_121f`) present; `-fun`, `-res-usage`, nvdisasm `-cfg -bbcfg -plr -json -b -g -gi` all present.

4. **Claim:** REA's objdump integration maps to a fixed set: -f, -h, -t, -r, -W(-WK/-WN), -d, -D, -i; there is no -s/-j section dump and no -T, so fatbin bytes cannot be extracted through REA, only located.
   - Local clone `src/objdump/ObjdumpCommand.ts` lines 12–20: `architectures`→`-i`, `file_headers`→`-f`, `section_headers`→`-h`, `symbols`→`-t`, `relocations`→`-r`, `dwarf`→`-W` + `-WK`/`-WN`, `disassemble`→`-d`, `disassemble_all`→`-D`; the mapping is `satisfies Record<typeof input.operation, ...>` (closed set). No `-s`, `-j`, `-T`, `-x` anywhere under `src/objdump/`. Raw GitHub copy agrees.

5. **Claim:** CUDA fatbins are embedded as a wrapper struct {magic 0x466243b1, version 1, gpu_binary, unused} in .nvFatBinSegment pointing at .nv_fatbin, registered by __cudaRegisterFatBinary then __cudaRegisterFunction per kernel — the host-side anchors a Ghidra-via-REA investigation can follow.
   - CGCUDANV.cpp (llvm.googlesource.com, main): `constexpr unsigned CudaFatMagic = 0x466243b1;`, struct comment `// struct { int magic, int version, void * gpu_binary, void * dont_care };`, sections `.nv_fatbin`, `__nv_relfatbin`, `.nvFatBinSegment` ("NVIDIA's cuobjdump looks for fatbins in this section"), calls `__cudaRegisterFatBinary(&FatbinWrapper)`, `__cudaRegisterFunction`, `__cudaRegisterFatBinaryEnd` (only with `CUDA_USES_FATBIN_REGISTER_END`), `__cudaUnregisterFatBinary`. (Minor: the fourth field is named `dont_care` in Clang, "unused" in the claim — same meaning.)

6. **Claim:** REA starts GDB from REA_GDB_COMMAND (default 'gdb') with --nx --quiet --interpreter=mi3 (MI2 fallback) and disables auto-loading; cuda-gdb 13.4 is GDB 16.3-based and documented to work with GDB/MI (-i=mi), so driving cuda-gdb via REA is plausible but untested.
   - Local clone `src/gdb/GdbSessionManager.ts` line 532 `this.#command = this.#environment.REA_GDB_COMMAND ?? "gdb"`, line 678 `arguments: ["--nx", "--quiet", `--interpreter=${miVersion}`]`, line 644–652 mi3 then mi2 retry, line 811 `"-gdb-set auto-load off"`; docs/reverse-engineering-tools.md says the same. CUDA-GDB v13.4 docs: Emacs "with the GDB/MI interface … via `M-x gdb`" with `(setq gud-gdb-command-name "cuda-gdb -i=mi")`; 13.2 release note "Moved from GDB 14.2 to 16.3" (no later base change listed in 13.3/13.4). The "untested" qualifier is the note's own and is honest.

7. **Claim:** Frida 17.0.0 (2025-05-17) removed static Module.getExportByName/findExportByName; hooks must use Process.getModuleByName('libcuda.so.1').getExportByName('cuModuleLoadData'); REA pins frida 17.23.2 as an optional dependency and bounds message capture to 16 MiB.
   - frida.re 17.0.0 post dated 17 May 2025: "The following static Module methods are now gone:" `Module.findBaseAddress()`, `Module.getBaseAddress()`, `Module.findExportByName()`, `Module.getExportByName()`; replacement `Process.getModuleByName('libc.so').getExportByName('open')`; `Module.getGlobalExportByName`. Independent: frida.re/docs/javascript-api confirms `Process.getModuleByName`, instance `Module.getExportByName`, static `Module.getGlobalExportByName`. Local clone package.json line 397 `"frida": "17.23.2"` under optionalDependencies; `src/frida/FridaInstrumentationManager.ts` line 41 `MAX_SESSION_CAPTURE_BYTES = 16 * 1024 * 1024`; docs/frida-instrumentation.md "Message capture is bounded to 16 MiB".

8. **Claim:** llama.cpp (master 2026-10-17) selects the MMVQ kernel mul_mat_vec_q for quantized matmuls when ggml_cuda_should_use_mmvq returns true — for GGML_TYPE_Q4_K on GGML_CUDA_CC_BLACKWELL that is ne11 <= 5 ('tuned on RTX 5090'), MMVQ_MAX_BATCH_SIZE is 8, and the Q4_K dot is vec_dot_q4_K_q8_1.
   - raw mmvq.cu (master): `if (GGML_CUDA_CC_IS_NVIDIA(cc) && cc == GGML_CUDA_CC_BLACKWELL) { switch (type) { // tuned on RTX 5090 case GGML_TYPE_Q2_K: case GGML_TYPE_Q3_K: case GGML_TYPE_Q4_K: return ne11 <= 5; …`; `get_vec_dot_q_cuda`: `case GGML_TYPE_Q4_K: return vec_dot_q4_K_q8_1;`; mmvq.cuh: `#define MMVQ_MAX_BATCH_SIZE 8`; ggml-cuda.cu `ggml_cuda_mul_mat`: `if (ggml_cuda_should_use_mmvq(src0->type, cc, ne11)) { ggml_cuda_mul_mat_vec_q(...); return; }`. GitHub commits page: master head is `2744e48d` "CUDA: faster MMVQ for low-bit types (#30517)" dated 2026-10-17, matching the note's stated commit. (Exact line number "2000" in ggml-cuda.cu not re-verified.)

## Refuted with corrections

- **Claim (extra, note line 50):** "Numba, for example, shells out to `nvdisasm` with `-gi`/`-cfg` because 'nvdisasm only accepts input from a file'" cited to the decoder-genetics.wustl.edu numba `codegen.py` mirror.
  - **Correction:** the cited page exists and contains the comment "# nvdisasm only accepts input from a file, so we need to write out to a", but its only invocation is `subprocess.run(['nvdisasm', fname], ...)` — no `-gi` and no `-cfg` flag appear in that file. The flag claim is not supported by the cited source (newer upstream numba/numba-cuda versions do add such flags, but that is not what was cited). Also the cited path (`python3.1/site-packages`) is a third-party conda mirror, not numba upstream; cite github.com/numba/numba instead.
