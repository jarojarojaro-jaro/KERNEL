## KQ1. Key papers and their methods — the most useful numbers for kernel writers

### Takeaway
The microbenchmarking literature forms a direct lineage: Wong et al. (ISPASS 2010, GT200) → Citadel's Volta (2018) and Turing (2019) tech reports (introduced SASS-level control-code decoding and a custom assembler) → Ampere (2022: Abdelkhalik et al., Sun et al.) → Hopper (2024–2025: Luo et al. "Benchmarking and Dissecting" and "Dissecting ... Multiple Level Analysis") → Blackwell (2025–2026: Jarmusch et al. RTX 5080 vs H100, then B200; SemiAnalysis B200, Chips and Cheese RTX PRO 6000/B200). The numbers that matter most for a kernel writer are: ~30 cycle L1/shared hit, ~200–360 cycle L2 hit (and up to 2× more for the "far" L2 partition on A100/H100/B200), ~550–880 cycle DRAM, 4-cycle dependent FFMA/IADD3 latency, 128 B/clk/SM shared memory bandwidth, `wgmma` needing N ≥ 64 to reach peak (32–128 cycle latency), and `tcgen05.mma` issuing in ~11 cycles on B200.

### Cited Findings

**Foundational / lineage**
- Wong, Papadopoulou, Sadooghi-Alvandi, Moshovos, "Demystifying GPU microarchitecture through microbenchmarking", ISPASS 2010, pp. 235–246, University of Toronto; measured CUDA-visible characteristics of the GT200 (GTX280), reporting "undisclosed properties of both the processing elements and the memory hierarchy"; later papers cite it as the first to introduce microbenchmarks for latency/throughput of memories and instructions — [hgpu.org listing](https://hgpu.org/?p=2165); [PDF mirror](https://bilbo.iut-bm.univ-fcomte.fr/and/gitweb/these_gilles.git/blob/HEAD:/DOCS/gpuarch-ispass2010.pdf)
- Mei & Chu, "Dissecting GPU Memory Hierarchy through Microbenchmarking" (arXiv 1509.02308, 2015) introduced the fine-grained pointer-chase ("P-chase") method reused by every later paper — [arXiv 1509.02308](https://arxiv.org/abs/1509.02308)

**Citadel Volta report (Jia, Maggioni, Staiger, Scarpazza; arXiv 1804.06826, submitted 2018-04-18, 66 pages, copyright Citadel Enterprise Americas; GPUs: V100 PCIe, P100, P4, M60, K80)** — [arXiv abs](https://arxiv.org/abs/1804.06826), [PDF](https://arxiv.org/pdf/1804.06826)
- Instruction encoding: "Volta uses one 128-bit word to encode each instruction together with its corresponding control information" (pre-Volta: 64-bit instructions + a separate 64-bit control word per bundle of 3 (Pascal/Maxwell) or 7 (Kepler) instructions); "at least 91 bits are used to encode the instruction; at least 23 bits are used to encode control information; the remaining 14 bits appeared to be unused" — [PDF §2](https://arxiv.org/pdf/1804.06826)
- Control section is 21 bits: Reuse flags (4 b), Wait barrier mask (6 b), Read barrier index (3 b), Write barrier index (3 b), Yield flag (1 b), Stall cycles (4 b, 0–15 cycles). Six dependency barriers track variable-latency instructions (memory); read barriers protect against WAR hazards; yield bit cleared = scheduler prefers to switch warps and "making all register reuse flags for the next instruction ineffective. This costs one extra cycle"; no dual-issue observed on Volta (one dispatcher per processing block) — [PDF §2.1](https://arxiv.org/pdf/1804.06826)
- Register file: Volta has 2 banks, 64-bit wide (bank = register index mod 2) vs 4 × 32-bit banks earlier; an FFMA conflicts only if all three 32-bit source registers are in the same bank; `.reuse` caches (4 slots) mitigate conflicts — [PDF §3.5](https://arxiv.org/pdf/1804.06826)
- Memory hierarchy table (clock cycles, V100 / P100 / P4 / M60 / K80): L1 data hit latency 28 / 82 / 82 / 82 / 35; L2 hit ≈193 / 234 / 216 / 207 / 200; L1 data line 32 B, L2 line 64 B on Volta; shared memory no-conflict latency 19 / 24 / 23 / 23 / 26 cycles, 32 banks × 4 B; shared bandwidth measured 12,080 GiB/s of 13,800 theoretical on V100; L1 load throughput 108.3 B/cycle/SM measured vs 256 theoretical on V100; global memory first-touch 1029 cycles (L2 miss + TLB miss), 375 cycles L2 miss with TLB hit; L1 TLB 2 MiB pages / 32 MiB coverage, L2 TLB 32 MiB entries / ~8192 MiB coverage (V100); constant caches: L1 2 KiB (~27 cycles), L1.5 ≥64 KiB (~89 cycles), L2 (~245 cycles); L0 instruction cache ~12 KiB, L1 instruction cache 128 KiB — [PDF §3, Table 3.1](https://arxiv.org/pdf/1804.06826)
- Instruction latencies (V100, cycles): IADD3/SHF/LOP3/SEL/MOV/FADD/FFMA/FMUL/ISETP/FSET/FSETP = 4; IMAD/FMNMX/DSET/DSETP = 5; HADD2/HMUL2/HFMA2 = 6; DADD/DMUL/DFMA = 8; POPC = 10; FLO/BREV/MUFU = 14. Pascal: most = 6, IMUL/IMAD ≈ 86 (emulated). Shared-memory atomics on V100: 6 cycles uncontended, 66 with 32-thread contention; global atomics 36 → 76 — [PDF §4.1–4.2, Tables 4.1–4.2](https://arxiv.org/pdf/1804.06826)
- Method for fixed-latency instructions: "We decrease A's stall cycles in its control word, till A's result consumed by B is incorrect. The last stall value producing correct results is A's latency"; variable-latency: bracket with `CS2R` (read of `SR_CLOCKLO`) and subtract the known latency of the consumer — [PDF §4.1](https://arxiv.org/pdf/1804.06826)
- Volta `mma_sync` (wmma 16×16×16) compiles to 4 sets × 4 `HMMA.884.F32.F32.STEP0..3` instructions; the report maps every C-matrix element to the thread that holds it — [PDF §4.3, Listing 4.1](https://arxiv.org/pdf/1804.06826)
- Companion Turing paper: Jia, Maggioni, Smith, Scarpazza, "Dissecting the NVidia Turing T4 GPU via Microbenchmarking", arXiv 1903.07486 (2019-03-18): instruction encoding "matches Volta's, with additional instructions"; TU104 has the same memory-hierarchy depth as GV100; clock throttling under power/thermal limits affects compute-intensive workloads — [arXiv 1903.07486](https://arxiv.org/abs/1903.07486)

**Ampere (2022)**
- Abdelkhalik et al., "Demystifying the Nvidia Ampere Architecture through Microbenchmarking and Instruction-level Analysis" (arXiv 2208.11174, New Mexico State Univ.): per-instruction clock-cycle latency for PTX instructions and their SASS counterparts, tensor cores via the WMMA API across data types and shapes — [arXiv 2208.11174](https://arxiv.org/abs/2208.11174)
- Sun, Li, Geng, Stuijk, Corporaal, "Dissecting Tensor Cores via Microbenchmarks: Latency, Throughput and Numeric Behaviors" (arXiv 2206.02874 v3, 2022-11-24; TPDS 2022; GPUs: A100, RTX 3070 Ti, RTX 2080 Ti): A100 `mma.sync` FP16→FP32 m16n8k16 completion latency 24.7 cycles, peak 1004.2 FMA/clk/SM (peak theoretical 1024) at 8 warps, ILP=2; m16n8k8 17.7 cycles; TF32 m16n8k8 25 cycles, 492.4 FMA/clk/SM (peak 512); INT8 m16n8k32 1986.5 (peak 2048); sparse `mma.sp` doubles throughput but "does not reduce latency"; `ldmatrix` x1/x2/x4 latency 23.1/25.1/29.3 cycles, ~128 B/clk/SM peak; `ld.shared.u32` 23.0 cycles no conflict, 25.0 (2-way), 29.0 (4-way), 37.0 (8-way) ≈ 2 cycles per extra way; on Ampere each `mma` compiles to a single `HMMA.16816.F32.BF16`/`HMMA.1688.FP32.BF16`, `wmma.m16n16k16` → two `HMMA.16816`; `mma.m8n8k4` compiles to FPU instructions ~10× slower; RTX 3070 Ti halves throughput with FP32 accumulate (252.7 vs 509.4 FMA/clk/SM) unlike A100 — [arXiv 2206.02874 html](https://arxiv.org/html/2206.02874v3)

**Hopper (2024–2025)**

- Luo et al., "Dissecting the NVIDIA Hopper Architecture through Microbenchmarking and Multiple Level Analysis" (arXiv 2501.12084 v2, 2025; H800 PCIe 114 SMs, A100, RTX 4090): fine-grained P-chase separates L2 near/far partitions — A100/H800: near hit 208.0/258.0, far hit 356.6/414.1, near miss 474.9/555.5, far miss 622.7/743.7 cycles; L2 throughput 1708 (4090) / 2007.9 (A100) / 3942.4 (H800) B/clk; shared 126.5/126.2/127.9 B/clk/SM; `wgmma` N-sweep (FP16 dense, SS): N=256 128 cyc / 728.5 TFLOPS, N=128 64 / 728.5, N=64 32 / 719.6, N=32 24 / 477.3, N=16 20 / 287.0, N=8 18 / 158.2 → "recommends N ≥ 64"; FP8→FP16 m64n256k32 128 cycles, 1448.4 TFLOPS (peak 1513); random-input FP16 drops clock from 1620 MHz to 1275 MHz and ≈595 TFLOPS; TMA adds ≈170 cycles latency (issue + mbarrier init/arrive/wait) but global→shared >1800 GB/s and a CUTLASS GEMM (128×256×64 tile, 2 stages) reaches ≈600 TFLOPS with TMA vs ≈450 without; DSM local access 33 cycles vs 29 direct, cluster-2 SM-to-SM ≈181 cycles, cluster 2–16 184–213 cycles, via global memory 1110 cycles; DSM ring 3.28 TB/s at cluster 2; DPX 16-bit ops up to 13× faster than software; methodology: P-chase random 64 B chunks averaged over >1 M accesses, 32 B stride with K-means clustering for fine-grained, `mov.u32 %0, %%smid` to identify SMs, throughput computed as ops/time "not cycle counts, because clock frequency varies" — [arXiv 2501.12084 html](https://arxiv.org/html/2501.12084v2)

### Inferences
- For an RTX 5060 Ti (GB206) owner the closest measured per-SM numbers are the RTX 5080 (GB203) and RTX PRO 6000 (GB202) data: 128 KB unified L1/shared, ≈99 KB usable shared per block, ≈358-cycle / ≈130 ns L2 hit, 4-cycle FP32 dependent latency, 128 B/clk/SM shared bandwidth, 1 cycle `%clock64` overhead. Chip-level numbers (L2 size, bandwidth, SM count) must be re-measured because GB206 is a different die.
- The 2 cycles/extra-way shared-memory conflict cost (Sun et al., A100) and ~128 B/clk/SM peak are the practical targets for `ldmatrix`-based tiling on any post-Volta part; consumer Blackwell keeps the same 128 B/clk figure (Chips and Cheese).
- Tensor-core latency trends: `mma.sync` ≈24 cycles (Ampere/Hopper), `wgmma` 32–128 cycles scaling linearly with N, `tcgen05.mma` ≈11 cycles issue latency — so Hopper/B200 kernels need deep async pipelines, while sm_120 kernels remain `mma.sync` register-fed and look more like Ampere kernels (see KQ5).
- Several papers (Hopper 2402.13499/2501.12084, Blackwell 2507.10789) report that `mma.sync` reaches only ~63 % of peak on Hopper while `wgmma` reaches ~96 %: on datacenter parts the instruction choice, not just tiling, determines peak.

### Gaps
- No paper measures the RTX 5060 Ti / GB206 directly; GB206 SM count (36?), L2 size and bandwidth remain unverified here.
- The Ampere paper (2208.11174) full tables were not read; only its scope is cited.
- Chips and Cheese RTX 4090 article gives charts, not numeric L1/shared latency, so absolute ns values for Ada L1 are missing.
- The B200 paper's TMEM latency and L1/L2/HBM latency are "not reported"; the Chips and Cheese B200 piece gives no far-partition L2 or HBM figures.

## KQ2. Techniques: timing, pointer chasing, dependency chains, SASS-level control, sweeps, pitfalls

### Takeaway
Every modern dissection uses the same toolkit: `clock()`/`%clock64` (SM-local cycle counter, 1–2 cycle read overhead) or `%globaltimer` (ns wall clock) read via inline PTX, random-stride pointer chasing for the memory hierarchy, dependency chains through an accumulator for latency and independent instruction streams (ILP × warps sweeps) for throughput, `%smid` to locate SMs, and SASS inspection with `cuobjdump`/`nvdisasm` to confirm that ptxas did not optimize the benchmark away. For true instruction-level control (stall counts, barriers, reuse) the Citadel reports used a custom assembler; today that role is played by community assemblers (CuAssembler, maxas lineage) because NVIDIA documents neither SASS encoding nor control bits. The three recurring pitfalls are clock variation under power limits, compiler reordering/elimination, and cold-cache/TLB warm-up.

### Cited Findings
- Citadel Volta: fixed-latency instruction latency measured by lowering the control-word stall count until the dependent result is wrong; variable-latency measured by creating artificial read/write barrier dependencies and bracketing with `CS2R` reads — [arXiv 1804.06826 PDF §4.1](https://arxiv.org/pdf/1804.06826)
- Citadel Volta instruction-cache discovery: "By charting the average inverse throughput experienced by instructions, we reveal the instruction cache hierarchy ... Each plateau in the inverse throughput reveals a cache level" using long sequences of independent FFMA — [arXiv 1804.06826 PDF Fig. 3.3](https://arxiv.org/pdf/1804.06826)
- Hopper (2501.12084): latency via P-chase with random strides in 64-byte chunks averaged over >1 M accesses; fine-grained P-chase with 32-byte stride and K-means clustering of latency groups (near/far L2); throughput with 1024-thread blocks (L1/shared), 2× SMs blocks (L2), 4× SMs with float4 (global); SM identity via `mov.u32 %0, %%smid`; throughput computed from wall time, not cycles, "because clock frequency varies"; power/frequency monitored with external tools — [arXiv 2501.12084](https://arxiv.org/html/2501.12084v2)
- Hopper (2402.13499): tensor-core tests in PTX, each instruction executed 1024× per kernel; DSM latency with `clock()` plus `%smid` to confirm blocks landed on different SMs — [arXiv 2402.13499](https://arxiv.org/html/2402.13499)
- Blackwell RTX 5080 paper: "Microbenchmarks are written in PTX and CUDA, with PTX kernels in separate files. The authors checked the generated SASS to confirm no optimization occurred"; timing with `%clock64`; ALU tests averaged over 1024 runs; pointer-chase swept 1–32 warps with strides 1 and 4, median over 1024 repeats; `%clock64` overhead 1 cycle (GB203) / 2 cycles (GH100); some first-run warm-up results excluded — [arXiv 2507.10789](https://arxiv.org/html/2507.10789v2)
- B200 paper: dependency chains through the accumulator for latency, independent MMAs to saturate the pipeline for throughput, PTX→SASS validation using CUTLASS binaries for opcode names, NVML power sampling at 10 ms, Nsight Compute scheduler-stall and tensor-utilization counters; warm-up 100 then 1000 timed iterations (Sec. IV) vs 10 + 100 (Sec. VII) — [arXiv 2512.02189](https://arxiv.org/html/2512.02189v3)
- Sun et al. (tensor cores): completion latency measured with ILP=1 and one warp per SM; throughput as FMA/clk/SM = workload ÷ latency; sweeps across ILP and warps/SM; GPU timer in the listing and `clock64()` in the appendix; throughput drop at 5–6 warps attributed to sub-core scheduling — [arXiv 2206.02874](https://arxiv.org/html/2206.02874v3)
- Power as a confound: on H800 PCIe (350 W limit) zero-initialized inputs keep power <200 W while random inputs hit 350 W "quickly", dropping clocks from 1620 MHz to 1275 MHz and dense FP16 wgmma from ≈729 to ≈595 TFLOPS — [arXiv 2501.12084](https://arxiv.org/html/2501.12084v2); Chips and Cheese on RDNA3: lowering fabric clock with few outstanding requests skews latency, "latency testing is hard" — [chipsandcheese.com](https://chipsandcheese.com/p/latency-testing-is-hard-rdna-3-power-saving)
- Nsight Compute locks SM clocks by default (`--clock-control` default `boost`; values `base`, `boost`, `force-boost`, `none`, `reset`), which changes measured durations; to compare with Nsight Systems, lock clocks externally with `nvidia-smi` and use `--clock-control none` — [ncu Profiling Guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html); [ncu CLI](https://docs.nvidia.com/nsight-compute/NsightComputeCli/index.html)
- Per-SM L2 latency differs by up to 52 % on L40 and also on RTX 5090, so single-SM pointer-chase numbers depend on which SM the block landed on (`%smid`) — [arXiv 2606.22588](https://arxiv.org/abs/2606.22588)
- SASS control codes (community): CuAssembler tutorial states "no official (at least no comprehensive) doc is provided on SASS, just simple opcodes list"; support claims differ between forks ("currently only supports Turing" vs "Pascal/Volta/Turing/Ampere SM60/61/70/75/80/86") — [CuAssembler Tutorial](https://github.com/cloudcores/CuAssembler/blob/master/Tutorial.md); [fork](https://github.com/2015xli/cuassembler); maxas (Maxwell) automated stall counts "to satisfy the pipeline depth of the particular instructions" — [maxas wiki](https://github.com/NervanaSystems/maxas/wiki/Introduction)
- SAGE paper summarises the control fields as reuse (4 b), wait barrier mask (6 b), read barrier (3 b), write barrier (3 b), yield (1 b), stall cycles (4 b) — [arXiv 2209.03125](https://arxiv.org/pdf/2209.03125); a 2025-06-14 hobbyist post reports ptxas default control bits `0x003fde` (reuse 0, wait mask 3, read/write barrier 7 = unset, yield 0, stall "F") — author's own guess, bit positions unverified — [handmade.network](https://handmade.network/p/691/ampitup/blog/p/9032-some_other_useful_stuff_and_some_guesses_on_what_the_default_control_bits_are_and_why)
- Official binary tools: `cuobjdump -sass` / `-ptx` / `-elf` / `-res-usage` / `-lelf` / `-xelf all`; `nvdisasm -hex` (`--print-instruction-encoding`), `-plr` (`--print-life-ranges`), `-cfg`/`-bbcfg` (DOT control-flow graph), `-g`/`-gi`/`-gp` (line info), `-raw`, `-json`, `-ndf` (no dataflow); the manual does not document control bits ("layout-id: Undocumented enum") — [CUDA Binary Utilities](https://docs.nvidia.com/cuda/cuda-binary-utilities/index.html)
- Ncu metric naming for self-built microbenchmarks: `unit__(subunit?)_(pipestage?)_quantity_(qualifiers?)` with roll-ups `.sum/.avg/.min/.max` and `.pct_of_peak_sustained_active/elapsed`; units `sm`, `smsp`, `l1tex`, `lts`, `ltc`, `dram`; metrics containing `sass_` are software-patched SASS metrics — [ncu Profiling Guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html)

### Inferences
- A reproducible microbenchmark recipe for the user's RTX 5060 Ti: (1) `nvidia-smi -lgc <base>` or `ncu --clock-control base`; (2) write the kernel body in PTX (`asm volatile`) with `mov.u64 %0, %%clock64;` brackets and `mov.u32 %0, %%smid;`; (3) run `cuobjdump -sass` and confirm the loop contains exactly the instruction under test; (4) warm up (first-touch includes TLB miss: 1029 vs 375 cycles on V100); (5) sweep ILP × warps; (6) report cycles for latency but bytes/s for bandwidth.
- Because NVIDIA never documented control codes, the "ground truth" on control-bit semantics for post-Ampere SASS (Hopper/Blackwell) is still the 2018 Citadel layout plus community inference; nobody has published a Blackwell control-bit decode in the sources found.

### Gaps
- No source found that confirms a maintained CuAssembler-like assembler for sm_90/sm_100/sm_120; CuAssembler's own README claims differ between forks.
- `%globaltimer` resolution/overhead was not quantified in any fetched paper (only `%clock64`).
- The exact warm-up protocols differ across papers (100–1024 iterations) with no study of how many are needed.

## KQ3. Profilers as RE tools: Nsight Compute, CUPTI, Nsight Systems, cuda-gdb, NVBit, compute-sanitizer — and what they reveal about kernels you did not compile

### Takeaway
Nsight Compute works on any cubin (including cuBLAS/cuDNN/llama.cpp fat binaries) and its Source page shows SASS with per-instruction warp-stall sampling, executed-instruction counts, L1/L2 sector counts and register dependencies even without `-lineinfo` (only the CUDA-C correlation needs line info). NVBit goes further: it rewrites SASS at load time to count, trace or patch instructions of precompiled libraries; cuda-gdb steps SASS and reads `$R<n>`/`$P<n>`/`$UR<n>`; CUPTI exposes the same PC-sampling data programmatically; compute-sanitizer is a correctness tool, not a profiler.

### Cited Findings

**Nsight Compute (ncu)**
- Warp sampling: "At a fixed cycle interval, each SM's sampler selects a random active warp and records its program counter and scheduler state"; interval is the device minimum — "as low as 32 cycles on small devices, and up to 2048 cycles on larger chips"; metrics `smsp__pcsamp_sample_count`, `smsp__pcsamp_interval_cycles`, `smsp__pcsamp_warps_issue_stalled_<reason>` (per-warp `smsp__warpidsamp_...`, `_not_issued` variants); samples "correlate with executed instructions but have no time resolution"; stall samples are attributed to the consumer instruction, with "Attributed Stalls" mapping to the producer — [ncu Profiling Guide §2.4–2.5](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html)
- Stall reasons (exact names): `barrier`, `branch_resolving`, `dispatch_stall`, `drain`, `imc_miss`, `lg_throttle`, `long_scoreboard` (L1TEX dependency), `math_pipe_throttle`, `membar`, `mio_throttle` (MIO queue full), `misc`, `no_instructions` (fetch / i-cache miss), `not_selected`, `selected`, `short_scoreboard` (MIO dependency, e.g. shared memory), `sleeping`, `tex_throttle`, `wait` (fixed-latency dependency), `warpgroup_arrive` (`WARPGROUP.ARRIVES`/`WAIT`); `selected`/`not_selected` are scheduler states not stalls; "Only focus on stalls if the schedulers fail to issue every cycle" — [ncu Profiling Guide §2.4.7–2.4.10](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html)
- Source page: views switch between SASS, PTX and Source (CUDA-C, Fortran, Python) plus side-by-side; "available options depend on the source information embedded into the executable"; the high-level view requires `-lineinfo`/`--generate-line-info`; columns include "Warp Stall Sampling (All Samples)", "Warp Stall Sampling (Not-issued Samples)" (CC ≥ 7.0), "Instructions Executed", "Thread Instructions Executed", "Predicated-On Thread Instructions Executed", "Divergent Branches", "Live Registers", "Attributed Stalls", "L1 Wavefronts Shared / Shared Ideal", "L2 Theoretical Sectors Global" plus "Excessive" variants (achieved − ideal), L2 explicit evict-policy hit/miss; the SASS view draws register dependencies (write/read triangles, colored by dependency length); heatmap + "Navigate By" minimap — [Nsight Compute User Guide, Source Page](https://docs.nvidia.com/nsight-compute/NsightCompute/index.html)
- NVIDIA forum guidance: library code mixed into a kernel is folded into kernel-level totals; the Source page with `-lineinfo` isolates your own code; the "Sampling Data" column shows stall reasons per line — [NVIDIA forum](https://forums.developer.nvidia.com/t/very-strange-sampling-data-in-nsight-compute/271386)
- CLI flags (exact): `--set basic|full` (`--list-sets`), `--section <id>|regex:` (`--list-sections`), `--metrics` with `regex:`, `group:`, `breakdown:`, `pmsampling:` prefixes, `--clock-control base|boost|force-boost|none|reset` (default `boost`), `--cache-control all|none` (default `all` = flush caches between replay passes), `--replay-mode kernel|application|range|app-range`, `--import-source on|off`, `-k`/`--kernel-name <name>|regex:`, `-s`/`--launch-skip`, `-c`/`--launch-count`, `--target-processes application-only|all`, `--page details|raw|source|session`, `--print-source sass|ptx|tileir|cuda|cuda,sass|...`, `-o`/`--export` with `%h %p %i` macros, `--query-metrics` + `--query-metrics-mode base|suffix|all`, `--kernel-name-base function|demangled|mangled`, `--print-summary none|per-gpu|per-kernel|per-nvtx`. Example: `ncu --set full --clock-control base --cache-control all --replay-mode kernel -k regex:gemm -s 1 -c 2 --page source --print-source sass -o gemm_report ./app` — [ncu CLI docs](https://docs.nvidia.com/nsight-compute/NsightComputeCli/index.html)
- Replay: kernel replay saves/restores all accessible memory between passes; application replay re-runs the process per pass (matching kernels via `--app-replay-match grid`); for cache-sensitive workloads use `--replay-mode application --cache-control none`; range replay via `--nvtx --nvtx-include` or `cu(da)ProfilerStart/Stop`; instruction-level source metrics need no profiling permissions via CLI but are unavailable under graph profiling — [ncu Profiling Guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html)
- Sections: `SpeedOfLight_RooflineChart` (hierarchical Double/Half/Single/Tensor variants), `MemoryWorkloadAnalysis_Chart`/`_Tables` (limiters: Mem Busy, Max Bandwidth, Mem Pipes Busy), `WarpStateStats`, `SourceCounters`; example metric names `l1tex__data_bank_conflicts_pipe_lsu.sum`, `sm__inst_executed`, `sm__throughput` — [ncu Profiling Guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html)
- ncu's own "Compute Triage Guide" exists as a separate doc — [docs.nvidia.com](https://docs.nvidia.com/nsight-compute/ComputeTriage/index.html)
- The B200 dissection used Nsight Compute scheduler-stall and tensor-utilization counters and reported L2 hit rates 68–84 % from ncu — [arXiv 2512.02189](https://arxiv.org/html/2512.02189v3)

**CUPTI**
- CUPTI PC Sampling API (CUPTI 13.x docs): functions to enable/disable, start/stop, flush (`cuptiPCSamplingGetData`), configure attributes, enumerate stall reasons, `cuptiGetCubinCrc`, `cuptiGetSassToSourceCorrelation`, enum `CUpti_PCSamplingCollectionMode`; older activity API used `CUpti_ActivityPCSamplingStallReason` and `cuptiActivityConfigurePCSampling` (CUDA 9/10 docs); NVIDIA's `pc_sampling_continuous` sample "will work on devices with compute capability 7.0 and higher" — [CUPTI PC Sampling API](https://docs.nvidia.com/cupti/api/group__CUPTI__PCSAMPLING__API.html); [sample mirror (third-party)](https://huggingface.co/MNghia/soft_gripper_envs/blob/main/samples/pc_sampling_continuous/pc_sampling_continuous.cpp)

**cuda-gdb**
- Supports SASS-level debugging "including instruction stepping, disassembly display, and register contents"; does not support PTX-level debugging — [NVIDIA forum (staff)](https://forums.developer.nvidia.com/t/does-cuda-gdb-support-ptx-level-debugging/26463)
- Disassembly is obtained indirectly through `cuobjdump` (must be on `$PATH`), so raw instruction bytes are not captured; `set cuda disassemble_from device_memory` disassembles what is actually resident on the device (can differ from the cubin loaded at launch) — [NVIDIA forum](https://forums.developer.nvidia.com/t/cuda-gdb-can-not-see-the-hex-of-sass-code/329735)
- Exact syntax: `x/4i $pc-32`, `disass $pc,+16`, `disas $errorpc,+16` (markers `=>` current PC, `*>` exception PC); `info registers $R0 $R1 $R2 $R3`; predicates `$P0`–`$P6` in `info registers system`; uniform registers `$UR0`, `$UR1`; `print *(@global unsigned long long *)d_global`; `p *$_cuda_const_bank(0x0,0xc)`; focus `cuda device 0 sm 1 warp 2 lane 3`, `cuda block 1 thread 3`, `cuda kernel 0`; `info cuda sms|warps|lanes|kernels|contexts`; `set cuda break_on_launch application` (breaks on the first instruction of every kernel, i.e. works for library kernels); `autostep LOCATION for LENGTH [lines|instructions]`; single-stepping is warp-level (`set cuda step_divergent_lanes`); optimized `-lineinfo` builds step "somewhat erratic[ally]"; convenience variables `$laneid`, `$warpid`, `$smid` — [cuda-gdb docs](https://docs.nvidia.com/cuda/cuda-gdb/index.html)

**NVBit**
- NVBit 1.7 (README, 2026): "research prototype of a dynamic binary instrumentation library"; inspects SASS of each `__global__`/`__device__` function when first loaded and injects calls to arbitrary device functions before/after any SASS instruction; can remove instructions (no correctness guarantee); requirements: SM compute capability ">= 3.5 && <= 12.1" (so RTX 5060 Ti sm_120 is in range), x86_64/aarch64 Linux, GCC ≥ 8.5, CUDA ≥ 12.0, nvcc ≥ 10.2 for tools; released only as a binary artifact on GitHub Releases under the CUDA Toolkit EULA; "does not require application source code ... regardless of which compiler" — [NVBit README](https://github.com/NVlabs/NVBit/blob/master/README.md) (local copy at the scratchpad path above)
- MICRO 2019 paper (Villa, Stephenson, Nellans, Keckler): dynamic recompilation at the SASS level producing ABI-compliant instrumented code; capabilities: basic-block instrumentation, multiple injections at the same location, inspection of all ISA-visible state, dynamic selection of instrumented/uninstrumented code, permanent modification of register state, source correlation, instruction removal; works on precompiled CUDA, OpenACC, OpenCL, CUDA-Fortran — [research.nvidia.com](https://research.nvidia.com/publication/2019-10_nvbit-dynamic-binary-instrumentation-framework-nvidia-gpus); predecessor SASSI (compile-time, deprecated: "please use NVBit!") — [NVlabs/SASSI](https://github.com/NVlabs/SASSI)

**compute-sanitizer**
- Four tools: memcheck (out-of-bounds/misaligned access, hardware exceptions), racecheck (shared-memory hazards), initcheck (uninitialized global reads), synccheck (invalid synchronization primitive usage); part of the CUDA toolkit — [Compute Sanitizer docs (12.0)](https://docs.nvidia.com/cuda/archive/12.0.0/compute-sanitizer/index.html)

**Tensor-core numerics via instruction-level probing** (also an RE-by-profiler technique, see KQ4) — [arXiv 2511.10909](https://arxiv.org/html/2511.10909v3)

### Inferences
- For llama.cpp's CUDA kernels (built with nvcc, usually without `-lineinfo`) `ncu --set full --page source --print-source sass` still yields per-SASS-instruction stall reasons, executed counts and L2 sector excess; adding `-lineinfo` to llama.cpp's build adds the CUDA-C correlation at no runtime cost. For cuBLAS/cuDNN kernels only the SASS view exists, but that is enough to see e.g. `HMMA`/`QMMA`/`OMMA`, `LDGSTS`, `UTMALDG`, `SYNCS` patterns and where warps stall.
- `set cuda break_on_launch application` + `x/Ni $pc` + `info registers $R…` in cuda-gdb is the way to single-step a cuBLAS kernel and watch register contents without any symbols; NVBit is the way to count or trace instructions across a whole llama.cpp run with no rebuild.
- The toolchain matrix: ncu (static + sampled counters, no code change), CUPTI (same data, programmatic), NVBit (dynamic SASS rewriting), cuda-gdb (interactive SASS stepping), compute-sanitizer (correctness only). None of them decodes control bits; for that one needs `nvdisasm -hex` plus the Citadel field layout.

### Gaps
- The list of NVBit example tools (instr_count, mem_trace, opcode_hist, mov_replace etc.) lives in the release tarball, not in the GitHub repo, so it could not be confirmed from the README; NVBit's overhead numbers were not on the publication page.
- Nsight Systems' GPU-metrics sampling and its relevance to RE were not researched (out of scope of fetched docs).
- Whether ncu's "Source Counters" rules (uncoalesced access, bank-conflict detection) fire on third-party kernels was not stated explicitly in the docs retrieved; the metrics they rely on are SASS-patched (`sass_`), which suggests they do, but this is inference.
- `set cuda disassemble_from` full option list and `@shared`/`@local` syntax were not in the fetched cuda-gdb pages.

## KQ4. Tensor-core and memory-subsystem RE results: HMMA numerics, async copy pipelines, L2 persistence, memory compression, what remains unknown

### Takeaway
Numerics have been fully reverse-engineered to bit accuracy: Fasi et al. (2021) → Valpey et al. (2025, correcting the "round-to-zero" claim to truncation with a 5-term accumulator) → MMA-Sim (MICRO 2026) which shows Hopper/Ada FP8 MMA keeps only F=13 fraction bits in the fused sum while Blackwell (B200 and RTX PRO 6000) keeps F=25, and FP32 outputs are RZ while FP16 outputs are RNE. Data-movement pipelines are characterised (TMA ≈170 cycles extra latency but ~1800 GB/s, `LDGSTS` better below ~12 KiB in flight, L2 persistence set-aside up to 3/4 of L2). Unknowns remain: TMEM latency, dual-die effects, memory-compression behaviour, and Blackwell control-code semantics.

### Cited Findings
- Fasi, Higham, Mikaitis, Pranesh, "Numerical behavior of NVIDIA tensor cores" (PeerJ CS 2021; V100, T4, A100): first RE of intermediate precision, subnormal support, rounding mode and operation order — [PeerJ](https://peerj.com/articles/cs-330.pdf)
- Valpey et al., "An SMT Formalization of Mixed-Precision Matrix Multiplication" (arXiv 2502.15999, Univ. of Rochester, 2025; Volta/Turing/Ampere): "Nvidia's machines do not, as previously reported, use round-to-zero for accumulation, and their 5-term accumulator requires 3 extra carry-out bits for full accuracy"; the actual behaviour is truncation — [arXiv 2502.15999](https://arxiv.org/html/2502.15999v1)
- MMA-Sim (Xie, Xu, Wang, Yang, Yang — Microsoft; arXiv 2511.10909 v3 2026-09-28, MICRO 2026; code `github.com/microsoft/MMA-Sim`): ten architectures — V100, T4, A100, RTX 4090, H100, B200, RTX PRO 6000 (RTX Blackwell), MI100, MI250X, MI300X; "closed-loop feature probing" with >1 M randomized differential tests (10–20 h before GPU acceleration, ~1 h after); findings: Volta FP16 F=23 fraction bits with RZ-FP32 output; Turing/Ampere F=24; Hopper/Blackwell F=25 for non-FP8; FP8 inputs F=13 on Ada and Hopper but F=25 on Blackwell and RTX Blackwell; FP32 outputs rounded RZ, FP16 outputs RNE; four precision bottlenecks (input FTZ of FP16 subnormals on CDNA2, "small F for FP8" on Ada/Hopper, "RZ-E8M13 output rounding for FP8" on Ada/Hopper, RNE-FP16 output) and one asymmetry (CDNA3 violates Φ(−A,B,−C) = −Φ(A,B,C)); developers had already raised software accumulation precision to offset Hopper FP8 — [arXiv 2511.10909](https://arxiv.org/html/2511.10909v3)
- Sun et al. 2022 (A100): BF16/FP16/TF32 MMA produce zero error vs CPU when inputs are exactly representable; FP16-with-FP16-accumulate computes at higher precision and rounds only the final result; FP16 chains overflow to inf at N ≥ 10; permuted shared layout + `ldmatrix` cut a 2048² BF16 GEMM from 913,363 to 303,227 cycles, `cp.async` pipeline alone to 451,560 — [arXiv 2206.02874](https://arxiv.org/html/2206.02874v3)
- Async copy / TMA (H800, 2025): TMA ≈170 cycles extra latency (issue + mbarrier), >1800 GB/s global→shared, 1D tensor maps capped at 256 elements per box dim (2 KB for int64), larger x-dim boxes faster; CUTLASS GEMM ≈600 vs ≈450 TFLOPS with/without TMA — [arXiv 2501.12084](https://arxiv.org/html/2501.12084v2); AsyncPipe +39.5 % at 8×8 blocks but −1.8 % at 32×32 on H800 — [arXiv 2402.13499](https://arxiv.org/html/2402.13499)
- Async copy / TMA (B200, 2026): `LDGSTS` saturates ≈6.6 TB/s at 32 KiB in flight, ≈600 ns baseline latency doubling after 8 KiB in flight (MIO throttle); TMA keeps scaling to 128 KiB in flight; TMA multicast reduces L2 traffic toward 1/cluster_size through the "L2 Request Coalescer (LRC)"; implicit multicast fades beyond 64 bytes in flight; MLA kernels use async copy for paged loads while MHA uses TMA — [SemiAnalysis](https://newsletter.semianalysis.com/i/191922559/async-copy-vs-tma-comparison)
- Distributed shared memory: 180–213 cycles SM-to-SM (cluster 2–16), 6.13× faster than via global memory, local DSM throughput 205 GB/s vs 225 theoretical, broadcast patterns degrade with cluster size — [arXiv 2501.12084](https://arxiv.org/html/2501.12084v2)
- L2 persistence (official): a portion of L2 can be set aside for persisting accesses (guide sizes up to 3/4 of L2 capped by the device maximum), `accessPolicyWindow` is per stream with an example `hitRatio` 0.6; MIG disables the set-aside; under MPS the size cannot be changed with `cudaDeviceSetLimit` — [CUDA Programming Guide §L2 Cache Control](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/l2-cache-control.html); Ampere GTC 2020 slides: resetting persistence does not evict data, only resets status — [GTC S21819](https://developer.download.nvidia.com/video/gputechconf/gtc/2020/presentations/s21819-optimizing-applications-for-nvidia-ampere-gpu-architecture.pdf); hobbyist H100 test reserved 31.25 MB of 50 MB — [veitner.bearblog.dev](https://veitner.bearblog.dev/gpu-l2-cache-persistence/)
- ncu exposes L2 evict-policy hit/miss metrics ("L2 Explicit Evict Policy Metrics" for `evict_first`/`evict_last`) on the Source page — [Nsight Compute User Guide](https://docs.nvidia.com/nsight-compute/NsightCompute/index.html)
- B200 TMEM: 256 KB/SM, 16 TB/s read bandwidth, optimal 64×64 tile; "The paper describes a pointer-chase comparison against shared memory but reports no TMEM vs. SMEM latency numbers" — [arXiv 2512.02189](https://arxiv.org/html/2512.02189v3)
- Blackwell SASS opcode list in NVIDIA's own docs (CC 10.0/10.3/10.7/11.0/12.0): `OMMA` (FP4), `QMMA` (FP8), `HMMA`, `DMMA`, `IMMA`; tensor-core ops `UTCHMMA`, `UTCIMMA`, `UTCOMMA`, `UTCQMMA`, `UTCCP`, `UTCSHIFT`; TMEM `LDT`/`LDTM`, `STT`/`STTM`; bulk/TMA `UBLKCP`, `UTMALDG`, `UTMASTG`, `UTMAREDG`; `LDGSTS`, `SYNCS`/`SYNCSU`/`USYNCS`, `DECOMPRESS`, `SPARSIFY` — [CUDA Binary Utilities](https://docs.nvidia.com/cuda/cuda-binary-utilities/index.html)

### Inferences
- For FP8 inference kernels (relevant to llama.cpp quantized paths), Hopper/Ada tensor cores effectively accumulate in ~14-bit precision per fused sum; the standard workaround (promote partial sums to FP32 registers every k-chunk, as DeepSeek-style kernels do) is unnecessary on Blackwell including the user's sm_120 card, which keeps F=25.
- The Blackwell opcode list shows that consumer CC 12.0 shares the documented opcode namespace with 10.x, but the sm_120 gist (KQ5) found zero `UTC*`/`UTMA*` opcodes in sm_120a binaries, so the table is a union over the family, not a per-CC capability list.

### Gaps
- No microbenchmark of NVIDIA's compressible memory / "compute data compression" (Ampere+) was found; only the `DECOMPRESS` SASS opcode and the B200 nvCOMP-based decompression-engine numbers exist.
- TMEM access latency, cross-die (NV-HBI) latency and far-partition L2 latency on B200 are unreported in every fetched source.
- MMA-Sim's workaround sections (scaling inputs, "MMA without CC", changing instructions) were truncated in the fetch and not captured.

## KQ5. Consumer vs datacenter differences discovered via microbenchmarks (RTX 4090 vs H100; RTX 50xx / sm_120 vs B200)

### Takeaway
Consumer Blackwell (sm_120: RTX 5060 Ti/5080/5090, RTX PRO 6000) is "architecturally closer to Hopper than to datacenter Blackwell": it has no TMEM and no `tcgen05`, no `wgmma`, 128 KB unified L1/shared (99 KB per block) instead of 228–256 KB, 48 instead of 64 resident warps per SM, far fewer FP64 units, but it does get 5th-gen tensor cores with FP4/FP6/FP8 via register-fed `mma.sync` block-scaled instructions (`kind::mxf4nvf4`, m16n8k64), TMA, thread-block clusters and the higher FP8 accumulation precision.

### Cited Findings
- Official CC 12.0 vs 10.0 (Blackwell Tuning Guide): max concurrent warps/SM "64 for compute capability 10.0 and 48 for compute capability 12.0"; shared memory per SM 228 KB (10.0) vs 128 KB (12.0); max shared per block 227 KB (10.0) vs 99 KB (12.0); register file 64K 32-bit registers per SM, 255 registers/thread, 32 blocks/SM for both; thread-block clusters "supported by Blackwell GPUs as well" (portable max 8, B200 non-portable 16 via `cudaFuncAttributeNonPortableClusterSizeAllowed`); GB200 L2 126 MB; B200 HBM3/3e up to 180 GB — [Blackwell Tuning Guide](https://docs.nvidia.com/cuda/blackwell-tuning-guide/index.html)
- RTX 5080 (GB203) vs H100 PCIe measured (2025-07): L1 128 KB vs 256 KB; L2 65 MB/1 partition vs 50 MB/2 partitions; L2 hit ≈358 vs ≈273 cycles; FP64 chain 63.57 vs 8.04 cycles (2 vs 64 FP64 units/SM); GB203 supports FP4/FP6 tensor formats that GH100 lacks; "`tcgen05` is not yet implemented for sm_120a"; sustained tensor ILP limit 6 at 25 warps (GB203) vs 5 at 29 warps (GH100); FP8 (e4m3) tensor power 46.7 W (Blackwell test) vs 55.8 W (Hopper) — [arXiv 2507.10789](https://arxiv.org/html/2507.10789v2)
- sm_120 vs sm_100 binary investigation (gist, 2026-03-06, CUDA 13.1): "SM100 has a dedicated tensor memory (TMEM) subsystem with its own instruction family" (`UTCHMMA.2CTA`, `UTMALDG.4D.2CTA`); "SM120 uses the older HMMA instruction family" (`HMMA.16816.F32.BF16`, "the same register-to-register MMA approach" since Volta); "There are zero UTC* or UTMA* opcodes in any SM120a binary"; "NVIDIA's own assembler (ptxas, CUDA 13.1) explicitly rejects tcgen05 instructions for SM120"; an SM100a cubin with ELF headers patched to SM120a is rejected by the driver; conclusion that FlashAttention-4 cannot run on SM120 — the hardware claim ("not a software lock, not a fuse bit") is the author's inference from toolchain and binary evidence, not a silicon measurement — [gist solatticus](https://gist.github.com/solatticus/aab6ec3a0436748b021cbbdd12e8c739)
- Colfax, "CUTLASS Tutorial: NVFP4 Blockscaled GEMM on NVIDIA RTX PRO Blackwell GPUs (SM12x)", 2026-06-20, RTX PRO 6000 Server Edition, CUDA 13.2: "SM12x has no tcgen05 instruction and no TMEM. ### Inferences
- For the user's RTX 5060 Ti: kernels should be written Ampere/Ada-style (register-fed `mma.sync` + `ldmatrix` + `cp.async`/TMA pipelines, ≤99 KB shared per block, ≤48 warps/SM), while the new block-scaled `mma.sync.kind::mxf4nvf4` / `mxf8f6f4` instructions give the FP4/FP8 throughput. Hopper `wgmma` kernels and datacenter-Blackwell `tcgen05` kernels (FlashAttention-3/4 paths) will not run; CUTLASS ≥ 3.9 sm120 examples and Colfax's SM12x tutorial are the reference kernels to reverse-engineer.
- The 48-warp (vs 64) limit and 128 KB L1/shared mean occupancy sweeps on sm_120 saturate earlier; the RTX 5080 paper's tensor ILP sweep (ILP=6 at 25 warps) suggests ~6 independent `mma.sync` chains per warp is the sweet spot.
- Several "consumer vs datacenter" claims (no TMEM on GB202) rest on toolchain/binary evidence; the hardware-level truth is undocumented by NVIDIA, which is exactly what microbenchmarks like 2507.10789 are for.

### Gaps
- No direct RTX 5060 Ti (GB206) measurement of L2 size/bandwidth, SM count or FP8/FP4 tensor rates was found; NVIDIA spec sheets were not consulted here.
- The PTX ISA "Target ISA Notes" for `wgmma` (expected `sm_90a` only) and for `mma ... kind::mxf8f6f4` on `sm_120a` were not fetched directly (the PTX ISA page exceeded fetch limits); the Colfax article and CCCL docs are the closest confirmations.
- Whether sm_120 supports `cp.async.bulk` DSMEM, TMA multicast across clusters, or 2-CTA MMA was not addressed by any fetched source.
- The RTX 5080 paper's FP8 GEMM table has unit errors; no reliable measured FP8/FP4 TFLOPS for RTX 50-series was found other than Colfax's "~60 % of 2000 TFLOP/s" on RTX PRO 6000.
