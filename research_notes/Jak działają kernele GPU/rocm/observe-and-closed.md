## KQ1. Runtime logging and tracing: AMD_LOG_LEVEL/AMD_LOG_MASK, HIP_*, ROC_*/GPU_* (CLR) and HSA_* (ROCR) env vars; rocprofv3 / rocprof-sys; amdgpu ftrace; umr; rocgdb; sysfs/debugfs; amd-smi

### Takeaway
Every CLR knob is a single macro table (`rocclr/utils/flags.hpp`, `RUNTIME_FLAGS(debug,release,release_on_stg)`), every ROCR knob is parsed in one constructor (`core/util/flag.h`, `Flag::Refresh()`), and the override `HSA_OVERRIDE_GFX_VERSION` is parsed in ROCT (`libhsakmt/src/topology.c`), so the "authoritative list" is three files. Observability is layered: `AMD_LOG_LEVEL=4..5` + `AMD_LOG_MASK` bits show AQL packets/HWq addresses/code-object loads in user space; `rocprofv3 --hip-trace --hsa-trace --kernel-trace` gives timestamped API/dispatch records; `amdgpu:*` ftrace tracepoints (`amdgpu_cs_ioctl`, `amdgpu_sched_run_job`, `amdgpu_userq_*`) and `/sys/kernel/debug/kfd/{mqds,hqds,rls}` show the kernel side; `umr --waves`/`-O halt_waves`/`-RS <ring>` reads SQ wave state and rings directly from the hardware.

## KQ3. How the ecosystem is built and versioned: TheRock, release cadence, driver/firmware/ROCr/LLVM coupling, gfx target lists, HSA_OVERRIDE_GFX_VERSION, COV5/COV6

### Takeaway
TheRock is the CMake super-project that builds ROCm from two monorepos (`rocm-systems`, `rocm-libraries`) plus `llvm-project`, with per-GPU-family targets (`-DTHEROCK_AMDGPU_FAMILIES=gfx110X-all`) and a packaging step that splits arch-neutral host code from per-ISA "kpack" device wheels (`rocm-sdk-device-gfx1100`). ### Inferences
- Why `HSA_OVERRIDE_GFX_VERSION=11.0.0` works for a gfx1101/1102 card (e.g. 7700/7800 XT) but 11.0.0 on an RDNA2 card does not: the override only changes which `IsaRegistry` entry the agent claims and therefore which code objects the loader accepts; the hardware still executes gfx11xx-encoded instructions. gfx1101/1102 share the GFX11.0 ISA encoding, so gfx1100 binaries run; a gfx1030 device given 11.0.0 would load gfx1100 code and then fault/hang (wrong encodings, VOPD, s_delay_alu). The override cannot create missing hardware features and also bypasses `xnack`/`sramecc` sanity (both "unsupported" for gfx11).
- For an RX 7900 XTX (gfx1100) the override is never needed; it matters only for unlisted DIDs (`"HSA_OVERRIDE_GFX_VERSION may be needed"` assert) or to make libraries that only ship `gfx1100` Tensile/MIOpen kernel DBs work on gfx1101/1102.
- COV coupling: a COV6 code object (needed for `gfx11-generic` binaries) is rejected by a ROCR that lacks the generic-version table (pre-6.x); conversely COV5 objects load on any ROCR ≥ 6. The numeric field that ROCR checks is `EI_ABIVERSION` + the generic version in `e_flags`; libraries (hipBLASLt/MIOpen `.co`/`.kdb`) ship COV5 per-ISA, so mixing a newer rocBLAS with an older ROCR surfaces as `HSA_STATUS_ERROR_INCOMPATIBLE_ARGUMENTS` on `hsa_executable_load_agent_code_object`, not at install time.
- Release cadence 2024-2026: minor every ~4 months (6.1→6.2→6.3→6.4), then 7.0 (2025-09) and an accelerated "7.2.x → 7.14 → 10.0/10.1" sequence in 2026 that matches TheRock/rockrel nightly→rc→stable channels; the numbering jump (7.14 → 10.0) is a scheme change, not 3 major releases.

### Gaps
- No primary statement found on *which* ROCm versions require amdgpu-dkms vs the in-tree upstream kernel driver; the official matrix only lists AMD's packaged `amdgpu` driver versions (30.x/31.x), and treats the inbox driver implicitly.
- Default `-mcode-object-version` as actually configured in the ROCm fork of clang (vs upstream "5") was not verified in the ROCm llvm-project source this round.
- Exact Tensile/hipBLASLt kernel-DB naming per ISA inside `.kpack` was not inspected.

## KQ4. Vulkan compute as the second open stack: RADV pipeline, llama.cpp Vulkan shaders, RADV_DEBUG/ACO_DEBUG, differences vs HSA/AQL, AMDVLK/PAL, what RADV/ACO teach about RDNA3

### Takeaway
On the same gfx1100 silicon, llama.cpp's Vulkan backend compiles GLSL to SPIR-V with `glslc` at build time (`-fshader-stage=compute --target-env=vulkan1.2|1.3`, coopmat variants, `VK_KHR_cooperative_matrix`), RADV turns SPIR-V → NIR → ACO → ISA and records PM4 into IBs that the kernel's `amdgpu_cs` ioctl (hence `amdgpu_cs_ioctl`/`amdgpu_sched_run_job` tracepoints) submits to the GFX/ACE ring via kernel queues — whereas HIP/ROCR writes AQL packets to a user-mode KFD queue with no per-dispatch ioctl. ACO's pass list ("Insert wait states", "Resolve hazards and insert NOPs", "Insert delay_alu and form clauses", "VOPD Scheduling" for GFX11+) is the most readable open encoding of RDNA3's hazard/latency rules.

### Cited Findings

### Inferences
- Dispatch-path difference on the 7900 XTX today: HIP → ROCR AQL queue (user-mode ring + doorbell, HQD via KFD/HWS-MES, CWSR preemption) vs Vulkan/RADV → `vkQueueSubmit` → `DRM_IOCTL_AMDGPU_CS` → drm_sched → kernel GFX/compute ring → `INDIRECT_BUFFER` into the app's PM4 IB. Consequences: Vulkan has per-submit kernel overhead and is visible in ftrace; HIP has none but is invisible to ftrace; Vulkan compute shares the graphics CP/ME pipe (unless an ACE compute queue is picked, `GGML_VK_ALLOW_GRAPHICS_QUEUE` controls this), HIP always uses MEC compute pipes. With DRM user queues (6.16+, `amdgpu.user_queue=1`) RADV can move to the same doorbell model, converging the two.
- Memory model difference: HIP uses KFD SVM/GPUVM with fine/coarse-grained pools and `hipMallocManaged`; RADV uses GEM BOs (`amdgpu_bo_create` tracepoint, `bo_history.log`), explicit `VkDeviceMemory` heaps — llama.cpp's `GGML_VK_PREFER_HOST_MEMORY`/`DISABLE_HOST_VISIBLE_VIDMEM` toggle the 256 MiB-style host-visible VRAM heap (ReBAR) rather than page-migration.
- What RADV/ACO teach about RDNA3 that ROCm's LLVM also knows but documents less readably: VOPD dual-issue only in wave32 (ACO "VOPD Scheduling"), `s_delay_alu` as a software-visible dependency hint (GFX11+), hazards "not handled by the hardware" needing NOPs, memory clauses (`s_clause`), attribute ring replacing the parameter cache. For kernel optimisation, reading `aco_insert_NOPs.cpp` / `aco_insert_waitcnt.cpp` / `aco_form_hard_clauses.cpp` (files inferred from pass names) is the quickest route to the exact GFX11 hazard table.
- `RADV_DEBUG=cs,asm,shaderstats` on a llama.cpp Vulkan run prints the RDNA3 disassembly and VGPR/SGPR/occupancy stats of every ggml shader, a free counterpart to `GPU_DUMP_CODE_OBJECT`+`llvm-objdump` on the HIP side; `MESA_VK_TRACE=rgp` produces RGP captures loadable in Radeon GPU Profiler (closed, Windows/Linux binary).

### Gaps
- I did not read the ACO source files themselves (only the README), so the specific GFX11 hazard list (e.g. VALU→SGPR→VMEM, trans-op forwarding) is not quoted here; belongs partly to the ISA RE track.
- Whether llama.cpp's Vulkan dispatches use the ACE compute queue by default on RADV (vs graphics queue) was not verified beyond the `GGML_VK_ALLOW_GRAPHICS_QUEUE` env var name.
- Benchmarks HIP vs Vulkan on gfx1100 for Qwen3-27B were out of scope.

## KQ5. Debugging the stack when it breaks on gfx1100: failure modes and how to diagnose each

### Takeaway
On RDNA3 the characteristic failures are (a) queue creation failing in ROCR because MES/KFD cannot map an HQD ("HSA exception: Queue create failed at hsaKmtCreateQueue" with dmesg "MES failed to response msg=14"), (b) `gfx_0.0.0`/compute ring timeouts leading to soft→mode1 reset with "VRAM is lost", (c) GPU page faults from a shader (`[gfxhub0] no-retry page fault ... client TCP/SQC`), and (d) code-object/ISA mismatches surfacing as `HSA_STATUS_ERROR_INVALID_ISA` (unknown node id) or `HSA_STATUS_ERROR_INCOMPATIBLE_ARGUMENTS` (loader). The diagnostic ladder is dmesg → `AMD_LOG_LEVEL=4` → `AMD_SERIALIZE_KERNEL=3 AMD_SERIALIZE_COPY=3` under rocgdb → umr waves/rings (with `amdgpu.gpu_recovery=0`) → firmware/driver version alignment.

### Cited Findings
- Queue creation failure (gfx1102, Debian 2024-03): rocRAND test fails with "HSA exception: Queue create failed at hsaKmtCreateQueue"; dmesg repeats "MES failed to response msg=14" and "failed to reg_write_reg_wait"; author suspected outdated firmware, Feb-2024 linux-firmware did not fix it — [debian-ai list](https://lists.debian.org/debian-ai/2024/03/msg00097.html)
- RX 7900 XTX ring timeout → reset: freedesktop issue shows a `gfx_0.0.0` ring timeout triggering a GPU reset, MES failing to remove a hardware queue, GFX block declared hung; Firefox report shows the reset escalating from soft to full mode1 reset with "VRAM is lost" afterwards; a ROCm issue on a 7900 XT shows a generic 'unknown error' from a simple kernel with a GFXHUB page fault from the CPC client — [drm/amd #3056](https://gitlab.freedesktop.org/drm/amd/-/issues/3056), [drm/amd #2421](https://gitlab.freedesktop.org/drm/amd/-/issues/2421), [ROCm #2642](https://github.com/RadeonOpenCompute/ROCm/issues/2642)
- ROCR error sites: `amd_gpu_agent.cpp` throws `HSA_STATUS_ERROR_INVALID_ISA` ("Agent creation failed. The GPU node has an unrecognized id.") when the (possibly overridden) gfx triple is not in `IsaRegistry`; `amd_aql_queue.cpp` throws `HSA_STATUS_ERROR_OUT_OF_RESOURCES` ("Queue event creation failed.") and in two more places during queue setup; the loader returns `HSA_STATUS_ERROR_INCOMPATIBLE_ARGUMENTS` when the code object ISA is not supported by the agent — [amd_gpu_agent.cpp L147](https://github.com/ROCm/ROCR-Runtime/blob/master/runtime/hsa-runtime/core/runtime/amd_gpu_agent.cpp), [amd_aql_queue.cpp L239-306](https://github.com/ROCm/ROCR-Runtime/blob/master/runtime/hsa-runtime/core/runtime/amd_aql_queue.cpp), [executable.cpp L1284-1295](https://github.com/ROCm/ROCR-Runtime/blob/master/runtime/hsa-runtime/loader/executable.cpp)
- `HSA_ENABLE_VM_FAULT_MESSAGE` and `HSA_ENABLE_QUEUE_FAULT_MESSAGE` default on (set to "0" to silence); ROCR prints these from the async-event thread — [flag.h L81-85](https://github.com/ROCm/ROCR-Runtime/blob/master/runtime/hsa-runtime/core/util/flag.h)
- HIP docs: VM faults inside kernels come from out-of-bounds loops, invalid kernel arguments (null/unregistered/bad pointers), synchronization issues, compiler bugs, runtime bugs; use `AMD_SERIALIZE_KERNEL=3` + `AMD_SERIALIZE_COPY=3` so the backtrace includes the launching code; `HSA_ENABLE_SDMA=0` to isolate copy-engine problems; `HSA_ENABLE_INTERRUPT=0` for interrupt storms — [HIP debugging docs](https://rocm.docs.amd.com/projects/HIP/en/latest/how-to/debugging.html)
- Kernel: `vmid` 0 in a page-fault line ⇒ kernel driver or firmware, non-zero ⇒ user process (pasid maps to PID); client id names the block (TCP/SQC/SQG = shader, CPC/CPF/CPG = command processor, SDMA) — [amdgpu debugging](https://docs.kernel.org/gpu/amdgpu/debugging.html)
- Kernel knobs: `amdgpu.gpu_recovery=0` keeps the hung state for umr; `vm_fault_stop=2` stops the memory controller on first fault; `lockup_timeout` per-queue; `debug_mask=0x4` forces full reset; `halt_if_hws_hang=1` halts instead of resetting when HWS (MES) hangs — [module params](https://docs.kernel.org/gpu/amdgpu/module-parameters.html)
- KFD debugfs for queue problems: `/sys/kernel/debug/kfd/mqds` (all memory queue descriptors), `hqds` (hardware queue descriptors as programmed), `rls` (runlist handed to HWS), `hang_hws` (write-only: provoke a HWS hang for testing) — [kfd_debugfs.c](https://github.com/torvalds/linux/blob/master/drivers/gpu/drm/amd/amdkfd/kfd_debugfs.c)
- MES/firmware mismatch class of bug: "the kernel sends a command to the GPU's micro-engine scheduler (MES) that the installed firmware does not support" (GC 11.0.4, fixed by MES fw 0x52) — [Ubuntu discourse](https://discourse.ubuntu.com/t/boot-hang-on-amd-ryzen-systems-with-phoenix2-hawk-point-2-graphics-on-24-04/79862)
- `amd-smi firmware --ucode-list` / `amd-smi firmware -f` prints loaded firmware versions; `amd-smi reset` warns that a GPU reset "can also terminate any process holding an open /dev/kfd handle" — [AMD SMI CLI](https://rocm.docs.amd.com/projects/amdsmi/en/latest/how-to/using-AMD-SMI-CLI-tool.html)

### Inferences
- Diagnostic ladder for a headless 7900 XTX:
  1. `dmesg -w | grep -E 'amdgpu|kfd|MES|ring|fault'` — identifies the class: `MES failed to response` (firmware/driver mismatch or MES hang → align kernel + linux-firmware first, then `halt_if_hws_hang=1` + umr), `ring gfx_0.0.0 timeout` (hang → `gpu_recovery=0`, umr waves), `no-retry page fault ... pasid N ... client TCP` (shader bug → ROCR prints the VM fault message; rerun with `AMD_SERIALIZE_KERNEL=3` under `rocgdb` to get the launching HIP call).
  2. `rocminfo` / `amd-smi static` — confirms the agent exists; "unrecognized id" ⇒ `HSA_OVERRIDE_GFX_VERSION` or newer ROCT; nothing ⇒ `/dev/kfd` permissions (render/video groups) or KFD not loaded.
  3. `AMD_LOG_LEVEL=4 AMD_LOG_MASK=0x1|0x8|0x4000` — shows whether the code object loads (COV/ISA mismatch ⇒ `INCOMPATIBLE_ARGUMENTS` right after `hsa_executable_load_agent_code_object`) and the exact AQL packet that never completes.
  4. `cat /sys/kernel/debug/kfd/hqds` + `umr --user-queue kfd,comm=<proc>,queue=N --waves uq -O bits,halt_waves` — distinguishes "queue never mapped" (HWS/MES problem) from "waves stuck" (infinite loop / s_waitcnt deadlock / LDS hang).
- `GPU_MAX_HW_QUEUES=4` default and KFD `max_num_of_queues_per_device=4096`: a llama.cpp process will not exhaust queues, but many `hipStream`s in vLLM-class engines plus other processes can hit MES oversubscription, which is where time-slicing/preemption bugs in MES firmware appear (the Debian gfx1102 case is a queue *creation* failure, i.e. before any dispatch).
- Because ROCm user space is coupled to the driver by the "one year" rule but the driver is coupled to firmware by exact MES opcode tables, the most common hobbyist breakage on RDNA3 is kernel/firmware skew (Ubuntu HWE kernel vs distro linux-firmware), not ROCm version skew.

### Gaps
- No single authoritative AMD doc enumerating gfx1100 failure modes exists; the list is assembled from issue trackers and docs. Frequencies are not quantified.
- `AMD_LOG_LEVEL` output examples were not captured live (no GPU in this sandbox), so the exact line formats beyond the format strings quoted from `rocvirtual.cpp` are not shown.
- "MES failed to response msg=14" opcode meaning (which MES API call 14 is) was not resolved; it lives in the kernel header `mes_v11_api_def.h`, not read here.
