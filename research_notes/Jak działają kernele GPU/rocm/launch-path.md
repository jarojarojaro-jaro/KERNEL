## KQ1. Layers and repos: what runs where, from libamdhip64.so down to /dev/kfd and firmware

### Takeaway
A HIP launch passes through four user-space libraries and one kernel driver before any firmware sees it: `libamdhip64.so` (HIP API + ROCclr, one binary built from `ROCm/clr`), `libhsa-runtime64.so` (ROCr, `ROCm/ROCR-Runtime`), `libhsakmt.so` (the thunk, ioctl wrapper for `/dev/kfd`, now in the same repo), `libamd_comgr.so` (code-object manager, dlopen'ed by ROCclr for compilation/metadata), then `amdgpu.ko` with its `amdkfd` component, then CP/MES firmware. ROCclr and ROCr both run in the calling thread (direct dispatch) and the GPU is driven through memory-mapped user-mode queues, not per-launch ioctls.

### Inferences
- The ".so" names are standard ROCm packaging (`libamdhip64.so` from `clr/hipamd`, `libhsa-runtime64.so` from `ROCR-Runtime`, `libhsakmt.so` from `libhsakmt`, `libamd_comgr.so` from `llvm-project/amd/comgr`); the source tree confirms the module boundaries (HIP API → ROCclr `amd::`/`roc::` namespaces → `Hsa::` wrappers → `hsaKmt*` → ioctl), but I did not re-verify the CMake target names in this pass.
- Because of direct dispatch, the hot launch path has **no thread hand-off and no syscall**: it is a chain of C++ calls ending in an atomic increment of `write_dispatch_id`, a 64-byte store into a user-mapped ring, and one 64-bit MMIO store to the doorbell page. Everything the kernel driver does (queue creation, MQD, MES ADD_QUEUE) is amortized at stream/queue creation.

## KQ2. The AQL dispatch: queue creation, packet fields, barriers, streams→queues, signals, kernargs, loader

### Takeaway
A HIP stream is an `amd::HostQueue` whose `roc::VirtualGPU` owns (or shares, via `Device::acquireQueue`'s per-priority pool capped by `GPU_MAX_HW_QUEUES`=4) one HSA user-mode queue of `ROC_AQL_QUEUE_SIZE`=16384 64-byte AQL packets. `submitKernelInternal` fills an `hsa_kernel_dispatch_packet_t` (`kernel_object` = GPU address of the kernel descriptor, `kernarg_address` from a 4 MiB kernarg pool, grid/workgroup sizes, LDS, scratch), `dispatchGenericAqlPacket` reserves a slot with `hsa_queue_add_write_index_screlease`, writes the packet, commits the header with a release store and rings the doorbell with `hsa_signal_store_screlease(doorbell_signal, index)` — which ROCr implements as a single 64-bit store to an uncached MMIO page.

### Inferences
- "How many hardware queues does my 7900 XTX stream get?" — per process and per priority class, at most `GPU_MAX_HW_QUEUES` (4) ROCclr-created HSA queues, each a 16384-packet (1 MiB) ring; a 5th normal-priority stream shares the least-loaded existing queue. These are *user queues* that MES then time-slices onto the 32 compute HQDs of gfx11 (see KQ3), so raising `GPU_MAX_HW_QUEUES` costs scratch memory per queue (scratch is sized per queue in `GpuAgent::QueueCreate`) and more MES oversubscription rather than more parallel hardware.
- Because the default header carries the barrier bit, kernels on one HIP stream execute strictly one after another even though the AQL queue is `HSA_QUEUE_TYPE_MULTI`; `hipExtLaunchKernel(..., hipExtAnyOrderLaunch)` is the knob that lets the CP overlap consecutive dispatches on the same queue.
- The completion signal is *not* attached to each kernel packet in the fast path; stream synchronisation uses barrier packets with signals (`Barriers()`), so the CP's "decrement completion signal" write happens per barrier/marker, not per kernel — this is what makes HIP's per-launch cost mostly a CPU-side packet build plus one MMIO store.

### Gaps
- I did not find a documented per-ASIC value of `HSA_AGENT_INFO_QUEUE_MAX_SIZE` (`maxAqlSize_`) for gfx1100; read it with `hsa_agent_get_info` or `rocminfo` ("Max Queue Size").
- Whether the kernarg pool for gfx1100 ends up in device (VRAM, HDP-flushed) or host fine-grain memory depends on `kernel_arg_impl_` selection logic in `rocsettings.cpp:233-255` that I did not fully trace per ASIC; `AMD_LOG_LEVEL=4` prints `KernargSegmentByteSize` and the chosen implementation.

## KQ3. Kernel driver side: AMDKFD_IOC_CREATE_QUEUE, MQD, HWS runlists vs MES on RDNA3, CWSR, VMIDs/page tables, doorbells

### Takeaway
On gfx11 the KFD does not program the compute pipe itself: `create_queue_cpsch` allocates a doorbell, fills an in-memory MQD (`struct v11_compute_mqd`, the `cp_hqd_*` register image) and sends `MES_SCH_API_ADD_QUEUE` to the MES firmware with the process' page-table base, PASID, MQD address, write-pointer address, doorbell offset and quanta; MES then maps the queue onto one of the 4 pipes × 8 HQDs of the single MEC, preempting (CWSR) and re-mapping as queues are oversubscribed. Pre-MES ASICs (gfx9/CDNA) use the HWS runlist path (`pm_send_runlist` with PM4 `IT_MAP_PROCESS`/`IT_MAP_QUEUES`/`IT_RUN_LIST` to the HIQ).

### Inferences
- On the RX 7900 XTX (gfx1100) the realistic queue budget is: ≤ 4 HIP streams' worth of distinct AQL queues per priority per process (ROCclr), ≤ 1024 queues per process (KFD), and 32 compute HQDs on the chip shared by *all* processes and by the kernel's own compute rings; MES time-slices (`gang_quantum` ≈ 1 ms, `process_quantum` ≈ 10 ms as set by KFD) when more user queues than HQDs are active. For llama.cpp (one process, a handful of streams) nothing is oversubscribed, so the queue stays "mapped & connected" and a doorbell write goes straight to the Queue Manager.
- Because HWS/MES preemption uses CWSR (trap handler `cwsr_trap_gfx11_hex` saved with the queue's `ctx_save_restore` area allocated by the thunk), a long-running kernel on one process can be context-switched mid-wave; that is also why the trap handler/TBA/TMA addresses are part of `ADD_QUEUE`.

### Gaps
- `KFD_MES_PROCESS_QUANTUM` / `KFD_MES_GANG_QUANTUM` numeric values are only given by the source comments ("Equivalent to 10ms"/"1ms"); I did not open the header where they are defined.
- The MES firmware source itself is not public (Phoronix reported it was "under legal review" when the spec was released); the spec is explicitly "not meant to serve as a programming guide".
- Exact CWSR save-area size per queue on gfx1100 (`ctx_save_restore_size`) depends on `wave_num`/`CNTL_STACK_BYTES_PER_WAVE(gfxv)` constants in `queues.c` that I did not extract.

## KQ4. Hardware front end: CP reads AQL, ACE/ADC dispatches workgroups via SPI, initial wave state, s_endpgm and completion; the PM4 path used by Mesa/RADV as the second open implementation

### Takeaway
After the doorbell, the CP's MEC firmware (CPC) fetches the AQL packet from the user ring, resolves `kernel_object` to the kernel descriptor, programs the compute dispatch registers from `compute_pgm_rsrc1/2/3`, and hands the grid to the dispatcher (ADC/ACE), which cuts it into workgroups for the SPI; the SPI allocates VGPR/SGPR/LDS/wave slots on a WGP/CU, initialises up to 16 user SGPRs (set by CP) plus system SGPRs/VGPRs (set by ADC/SPI) and launches waves. The graphics path (Mesa RADV/radeonsi) does the same thing explicitly with PM4: `SET_SH_REG COMPUTE_PGM_LO/RSRC1/RSRC2/RSRC3`, user data in `COMPUTE_USER_DATA_*`, then `PKT3_DISPATCH_DIRECT dim_x dim_y dim_z dispatch_initiator`.

### Cited Findings
- HIP docs: "The ACEs break down kernels into workgroups for distribution to shader processor input (SPI) blocks"; "Multiple ACEs enable concurrent kernel execution, with each ACE capable of dispatching one kernel at a time"; "ACEs process commands from different queues asynchronously"; "The workgroup manager, also called the shader processor input (SPI), bridges the command processor and compute units"; "Workgroup-to-CU mapping is non-deterministic and based on available resources"; wave scheduling: "The fetch arbiter selects one warp per cycle to fetch instructions from memory, prioritizing the oldest warps". — [ROCm HIP hardware implementation](https://rocm.docs.amd.com/projects/HIP/en/latest/understand/hardware_implementation.html)
- rocprofiler-compute (RDNA): the SPI "accepts dispatched work from the command processor and schedules wavefronts onto Workgroup processors (WGPs)"; metrics `SPI Busy`, `Compute Wave Dispatches`, `Wave Dispatch Rate` (waves/cycle; >1 means dispatch across multiple shader engines). — [rocprofiler-compute RDNA SPI](https://rocm.docs.amd.com/projects/rocprofiler-compute/en/latest/conceptual/rdna/spi.html)
- MI300/MI200 performance counters name the CP sub-blocks and their counters: fetcher (`CPF_CPF_STAT_IDLE/STALL`, `CPF_CPF_TCIU_STALL`) and packet processor (`CPC_ME1_BUSY_FOR_PACKET_DECODE`, `CPC_UTCL1_STALL_ON_TRANSLATION`). — [ROCm MI300/MI200 performance counters](https://rocm.docs.amd.com/en/latest/reference/gpu-arch/mi300-mi200-performance-counters.html)
- LLVM initial kernel execution state: "This section defines the register state that will be set up by the packet processor prior to the start of execution of every wavefront. This is limited by the constraints of the hardware controllers of CP/ADC/SPI."; "The initial SGPRs comprise up to 16 User SGPRs that are set by CP and apply to all wavefronts of the grid ... These are then immediately followed by the System SGPRs that are set up by ADC/SPI and can have different values for each wavefront". SGPR order (each gated by an `enable_sgpr_*` bit in the kernel descriptor, dense from SGPR0): Private Segment Buffer (4), Dispatch Ptr (2, "64-bit address of AQL dispatch packet"), Queue Ptr (2, "64-bit address of amd_queue_t"), Kernarg Segment Ptr (2), Dispatch Id (2), Flat Scratch Init (2), Private Segment Size (1), Work-Group Id X/Y/Z (1 each), Work-Group Info (1), Scratch Wavefront Offset (1, "set by SPI in a per wavefront basis"). VGPRs: Work-Item Id X, Y, Z (1 each) or, on gfx90a+/gfx11+, packed `0:9 Work-Item Id X, 10:19 Y, 20:29 Z` in VGPR0. The dispatch sequence (steps 7-10): "CP executes micro-code and is responsible for detecting and setting up the GPU to execute the wavefronts of a kernel dispatch"; "CP ensures that when the a wavefront starts executing the kernel machine code, the scalar general purpose registers (SGPR) and vector general purpose registers (VGPR) are set up as required by the machine code. The required setup is defined in the kernel descriptor"; "When the kernel dispatch has completed execution, CP signals the completion signal specified in the kernel dispatch packet if not 0." — [LLVM AMDGPUUsage, Initial Kernel Execution State](https://llvm.org/docs/AMDGPUUsage.html#initial-kernel-execution-state)
- Completion/interrupt plumbing on the host side: `amd_signal_t` carries `event_mailbox_ptr` and `event_id` (KQ2), the CP end-of-pipe interrupt is `SOC15_INTSRC_CP_END_OF_PIPE` handled by `kfd_signal_event_interrupt(pasid, context_id0, 32)` (KQ2). — [kfd_int_process_v11.c v6.17](https://raw.githubusercontent.com/torvalds/linux/v6.17/drivers/gpu/drm/amd/amdkfd/kfd_int_process_v11.c)
- Second implementation — RADV compute dispatch (`src/amd/vulkan/radv_cmd_buffer.c:15449-15545`, `radv_emit_dispatch_packets`): direct path emits `PKT3(PKT3_DISPATCH_DIRECT, 3, predicating) | PKT3_SHADER_TYPE_S(1)` followed by `params->dim[0], dim[1], dim[2], params->dispatch_initiator`; indirect path `PKT3(PKT3_DISPATCH_INDIRECT, 1, predicating)` with the grid size optionally loaded into a user SGPR (`AC_UD_CS_GRID_SIZE`, `pdev->load_grid_size_from_user_sgpr`). `dispatch_initiator` bits used: `S_00B800_CS_W32_EN(1)` (wave32), `S_00B800_ORDER_MODE(1)`, `S_00B800_FORCE_START_AT_000(1)` (lines 15289-15339). Shader registers for compute are `R_00B830_COMPUTE_PGM_LO`, `R_00B848_COMPUTE_PGM_RSRC1`, `R_00B84C_COMPUTE_PGM_RSRC2`, `R_00B8A0_COMPUTE_PGM_RSRC3` (`src/amd/vulkan/radv_shader.c:2203-2206`), versus `SPI_SHADER_PGM_LO_VS/PS` for graphics stages. — [Mesa radv_cmd_buffer.c](https://gitlab.freedesktop.org/mesa/mesa/-/blob/main/src/amd/vulkan/radv_cmd_buffer.c); [Mesa radv_shader.c](https://gitlab.freedesktop.org/mesa/mesa/-/blob/main/src/amd/vulkan/radv_shader.c)
- The LLVM kernel descriptor contains the images of the same registers (`compute_pgm_rsrc1`, `compute_pgm_rsrc2`, `compute_pgm_rsrc3` with per-generation tables "compute_pgm_rsrc1 for GFX6-GFX12", "compute_pgm_rsrc3 for GFX10-GFX11"), plus `kernel_code_entry_byte_offset` and the `enable_sgpr_*`/`enable_vgpr_workitem_id` bits (`compute_pgm_rsrc2.user_sgpr.user_sgpr_count`). — [LLVM AMDGPUUsage, Kernel Descriptor](https://llvm.org/docs/AMDGPUUsage.html#kernel-descriptor)

### Inferences
- The AQL path and the PM4 path converge on the same hardware registers: what RADV writes with `SET_SH_REG` (PGM_LO = code address, RSRC1/2/3 = VGPR/SGPR counts, LDS, scratch, user-SGPR count, workgroup-ID enables) the MEC firmware derives from the kernel descriptor pointed to by `kernel_object`, and what RADV passes in `DISPATCH_DIRECT` (dim x/y/z, dispatch initiator) comes from `grid_size_*`/`workgroup_size_*` of the packet. Reading `radv_emit_dispatch_packets` + the LLVM `compute_pgm_rsrc*` tables is therefore the best open "source" for what the CP firmware does per AQL dispatch.
- `s_endpgm` by the last wave of the last workgroup is what lets the CP retire the dispatch; the release fence encoded in the packet header (L2 writeback for system scope) is executed by the CP at that point, before it decrements `completion_signal.value` and, if the signal is an interrupt signal, writes `event_id` to `event_mailbox_ptr` and raises the end-of-pipe interrupt that the KFD turns into a wake-up for `AMDKFD_IOC_WAIT_EVENTS`. (Mechanism inferred from `amd_signal_t` fields + KFD interrupt handler; the firmware itself is closed.)

### Gaps
- No public document states how the MEC firmware walks `kernel_object` → kernel descriptor → `COMPUTE_PGM_*` registers; this is inferred from the kernel-descriptor ABI + the Mesa PM4 sequence.
- radeonsi `si_compute.c` (the OpenGL compute dispatch) could not be fetched (GitLab raw/API and cgit returned 404/HTML through the proxy); RADV was used instead.
- Per-wave launch latency of the SPI and the ADC/ACE workgroup dispatch rate on RDNA3 are microarchitecture measurements and belong to the microbenchmark track.

## KQ5. Launch latency on AMD: what is measured, what dominates, and the knobs

### Takeaway
I found no trustworthy, primary, recent (2024-2026) empty-kernel launch-latency number for RDNA3 or MI300X under plain HIP; the available figures are either framework-level (Triton: 100-300 µs per launch, dominated by Python/Triton, not HIP), vendor/startup claims (≈4.5 µs per launch on MI300X, unverified), or older cross-GPU surveys (clpeak: 3-100 µs, 2010-2022). What the source code shows is that the HIP fast path is CPU-bound packet construction + one MMIO store; the knobs that change it are `AMD_DIRECT_DISPATCH`, `HIP_FORCE_DEV_KERNARG`, `hipExtAnyOrderLaunch`, HIP graphs (flat batch submit), and the serialisation/profiling flags that add signals and fences.

### Cited Findings
- Triton attention kernels on MI300X vs H100 (arXiv, Nov 2025): "Triton kernel launch software overhead of roughly 100 to 300 µs without graphs, which dominates kernel time for sequences under about 1000 tokens"; even with cached checks "the launch overhead stays around 80 µs"; the graph trade-off is that "the arguments to all kernels in this graph are frozen". — [arXiv 2511.11581](https://arxiv.org/pdf/2511.11581) (numbers relayed through search snippets; the paper's §7.2 is the primary location)
- Secondary blog summarising that study: HIP graphs "cut MI300-family latency roughly 2x on short sequences; CUDA graphs cut H100 latency only about 6%". Unverified against the paper. — [Spheron blog](https://www.spheron.network/blog/triton-on-amd-rocm-vs-nvidia-cuda-same-kernel-different-perf/)
- Startup claim (Kog AI, via news sites): standard MI300X stacks pay "~4.5 μs launch overhead" per kernel per token. Vendor-linked, no methodology. — [creeta.com](https://news.creeta.com/en/kog-ai-mi300x-monokernel-tutorial-2026/)
- IWOCL 2023 (GROMACS, Alekseenko/Páll): slide 3 "Kernels get faster, latency stays the same" with a clpeak-based scatter of kernel launch latency ≈3-100 µs across GPUs 2010-2022; on NVIDIA V100 the launch sequence for one reduce kernel took "CUDA: 10.3 µs" vs "oneAPI: 44.1 µs" (runtime overhead, not AMD hardware). — [IWOCL 2023 slides](https://www.iwocl.org/wp-content/uploads/iwocl-2023-Andrey-Alekseenko-2519.pdf)
- Historical: LLVM review D86376 (2020) "[HIP] Improve kernel launching latency" measured `__hipPushConfigure/__hipPopConfigure` overhead at "about 60 us" and "typical kernel launching latency is about 500us" on that era's stack — obsolete, pre-direct-dispatch. — [llvm.org D86376](https://lists.llvm.org/pipermail/cfe-commits/Week-of-Mon-20200824/335286.html)

### Inferences
- What dominates per launch on this stack, from the code path: (1) HIP API bookkeeping (`HIP_INIT_API`, stream/device lookup, `ihipLaunchKernel_validate`), (2) `NDRangeKernelCommand` allocation and `amd::Command::enqueue` locking (`vdev()->execution()` scoped lock), (3) `submitKernelInternal`: hidden-arg patching, kernarg pool alloc + `nontemporalMemcpy` (+ HDP flush or read-back on large-BAR device kernargs), (4) `dispatchGenericAqlPacket`: atomic wptr increment, 64-byte store, release store, MMIO doorbell. Everything else (CP fetch/decode, ADC/SPI) is GPU-side and overlaps with the CPU for back-to-back launches. Serialisation (`HIP_LAUNCH_BLOCKING`), profiling (`HIP_FORCE_QUEUE_PROFILING`, rocprof) and `hipEvent` stop events add barrier packets with interrupt signals and system-scope L2 flushes — those are the expensive parts, not the dispatch itself.
- For llama.cpp on gfx1100 the practical levers are: keep `AMD_DIRECT_DISPATCH` on (default), keep `HIP_FORCE_DEV_KERNARG=1`, avoid `hipDeviceSynchronize`/events in the decode loop, use the ggml HIP graph path (`GGML_HIP_GRAPHS`, which maps onto `dispatchAqlPacketBatchFlat`) so N kernels become one wptr bump + one doorbell, and only raise `GPU_MAX_HW_QUEUES` if more than 4 concurrently active streams are really needed.
- Measuring it properly on the 7900 XTX: time N back-to-back empty `hipLaunchKernel`s with `std::chrono` around the loop (CPU enqueue cost) and `hipEventRecord` pairs / `rocprofv3 --kernel-trace` (GPU-side gaps between consecutive dispatches); run with `AMD_LOG_LEVEL=4 AMD_LOG_MASK=0x...` once to confirm which kernarg implementation and queue is used, and with `HSA_ENABLE_INTERRUPT=0` to see the polling-vs-interrupt effect on `hipStreamSynchronize` wake-up.

### Gaps
- No primary 2024-2026 measurement of empty-kernel launch latency on RDNA3 (gfx1100) or MI300X under plain HIP was found; the Chips and Cheese MI300X article contains no dispatch-latency numbers (checked). This needs to be measured locally (recipe above) — treat the 4.5 µs (MI300X, vendor claim) and 100-300 µs (Triton framework overhead) figures as non-comparable anchors only.
- The ROCm 4.5 release-note statement about "Direct Dispatch" reducing dispatch variance (and `AMD_DIRECT_DISPATCH=0` to disable) surfaced only in search snippets; the exact release-notes URL was not captured.
- No quantified effect of `hipExtAnyOrderLaunch` or `HSA_ENABLE_INTERRUPT=0` on RDNA3 was found in any source.
