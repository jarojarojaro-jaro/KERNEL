## Refuted with corrections

7. **Claim:** "amdgpu ftrace tracepoints amdgpu_cs_ioctl and amdgpu_sched_run_job print timeline, fence context:seqno, ring_name and num_ibs and fire only on the DRM CS (Mesa/RADV) path; KFD/HSA dispatches are user-mode ring+doorbell writes visible instead via /sys/kernel/debug/kfd/{mqds,hqds,rls,hang_hws} and umr --user-queue kfd,comm=...,queue=N --waves uq -O bits,halt_waves"
   - Confirmed parts: amdgpu_trace.h L168-214 — both events `TP_printk("timeline=%s, fence=%llu:%llu, ring_name=%s, num_ibs=%u", …)` with `job->base.s_fence->finished.context/seqno`, `to_amdgpu_ring(job->base.sched)->name`, `job->num_ibs`; kfd_debugfs.c L109-117 `mqds`/`hqds`/`rls` 0444, `hang_hws`/`mem_limit` 0200; umr wave_status docs show `umr --user-queue kfd,comm=ollama,queue=2 --waves uq -O full_shader,halt_waves` and `-O bits`/`-O halt_waves`. HSA/AQL dispatches indeed never pass through `amdgpu_cs_ioctl` (only call site: `amdgpu_cs.c` L1374 in the CS ioctl).
   - **Refuted part: "fire only on the DRM CS (Mesa/RADV) path".** `trace_amdgpu_sched_run_job` is called from `amdgpu_job_run()` (amdgpu_job.c L449), the drm_sched run callback for *every* amdgpu job on any ring, not only CS jobs. Kernel-internal jobs also go through it: GPUVM page-table updates via SDMA (`amdgpu_vm_sdma.c` L123 `amdgpu_job_submit(p->job)` from `amdgpu_vm_sdma_commit`; `vm->update_funcs = &amdgpu_vm_sdma_funcs` is the default in amdgpu_vm.c L2634/2739), which KFD memory mapping triggers (`amdgpu_amdkfd_gpuvm.c` L1308 `amdgpu_vm_bo_update`), and TTM buffer moves/evictions (`amdgpu_ttm.c` L181 `amdgpu_job_submit`). So on a ROCm-only workload `amdgpu_sched_run_job` still fires on `sdma0`-class rings for hipMalloc/mapping/eviction traffic. **Correction:** `amdgpu_cs_ioctl` is CS-only; `amdgpu_sched_run_job` fires for every drm_sched job (CS IBs, VM PTE updates, TTM copies, kernel test IBs) — only per-*dispatch* AQL traffic is invisible to ftrace.
