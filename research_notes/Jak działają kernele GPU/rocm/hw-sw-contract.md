## KQ1. The AMDGPU kernel ABI: kernel descriptor, initial wave state, kernarg layout / hidden args, LDS granularity and occupancy arithmetic

### Takeaway
On gfx1100 the entire launch contract is a 64-byte **kernel descriptor** (`GROUP_SEGMENT_FIXED_SIZE`, `PRIVATE_SEGMENT_FIXED_SIZE`, `KERNARG_SIZE`, entry offset, `COMPUTE_PGM_RSRC1/2/3` and the `ENABLE_SGPR_*` bits) that CP copies into hardware registers, plus a dense set of **user SGPRs** (kernarg pointer, dispatch pointer, ...) and **system SGPRs** (workgroup IDs) and a single **packed VGPR0** holding x/y/z work-item IDs. Occupancy on RDNA3 is VGPR-bound (1536 VGPRs/SIMD lane, allocation granule 24 for wave32 / 12 for wave64, max 16 waves/SIMD) and LDS-bound (128 KiB per WGP, 64 KiB max per workgroup, allocated in 512-byte blocks); SGPRs never limit it because gfx10+ always allocates 128 SGPRs per wave.

### Cited Findings

**Kernel descriptor (64 bytes, 64-byte aligned, consumed by CP firmware)**
- "CP microcode requires the Kernel descriptor to be allocated on 64-byte alignment." Layout (bits): `31:0 GROUP_SEGMENT_FIXED_SIZE` (fixed LDS bytes per work-group, excludes dynamic LDS), `63:32 PRIVATE_SEGMENT_FIXED_SIZE` (scratch bytes per work-item), `95:64 KERNARG_SIZE`, `191:128 KERNEL_CODE_ENTRY_BYTE_OFFSET` (signed offset from descriptor to entry, "must be 256 byte aligned"), `383:352 COMPUTE_PGM_RSRC3`, `415:384 COMPUTE_PGM_RSRC1`, `447:416 COMPUTE_PGM_RSRC2`, bits 448-454 `ENABLE_SGPR_PRIVATE_SEGMENT_BUFFER / DISPATCH_PTR / QUEUE_PTR / KERNARG_SEGMENT_PTR / DISPATCH_ID / FLAT_SCRATCH_INIT / PRIVATE_SEGMENT_SIZE`, bit 458 `ENABLE_WAVEFRONT_SIZE32` ("GFX10-GFX11: If 0 execute in wavefront size 64 mode. If 1 execute in native wavefront size 32 mode"), bit 459 `USES_DYNAMIC_STACK` (code object v5+), bits 470:464 `KERNARG_PRELOAD_SPEC_LENGTH` and 479:471 `KERNARG_PRELOAD_SPEC_OFFSET` (GFX90A/GFX942 only, "Reserved, must be 0" elsewhere). — [LLVM AMDGPUUsage, "Kernel Descriptor"](https://llvm.org/docs/AMDGPUUsage.html#kernel-descriptor) (raw: `llvmdocs/AMDGPUUsage.rst` lines 6181-6420)
- On targets with *Architected flat scratch* (gfx1100, gfx942, gfx1201) `ENABLE_SGPR_PRIVATE_SEGMENT_BUFFER` and `ENABLE_SGPR_FLAT_SCRATCH_INIT` are "not supported and must be 0". — [AMDGPUUsage, Kernel Descriptor table](https://llvm.org/docs/AMDGPUUsage.html#kernel-descriptor)
- "The total number of SGPR user data registers requested must not exceed 16 and match value in `compute_pgm_rsrc2.user_sgpr.user_sgpr_count`." — [AMDGPUUsage](https://llvm.org/docs/AMDGPUUsage.html#kernel-descriptor)

**compute_pgm_rsrc1 (GFX6-GFX12)**
- `5:0 GRANULATED_WORKITEM_VGPR_COUNT`: "GFX10-GFX12 (wavefront size 64): max(0, ceil(vgprs_used / 4) - 1); GFX10-GFX12 (wavefront size 32): max(0, ceil(vgprs_used / 8) - 1)", where "vgprs_used is defined as the highest VGPR number explicitly referenced plus one". Used by CP for `COMPUTE_PGM_RSRC1.VGPRS`. — [AMDGPUUsage, compute_pgm_rsrc1 table](https://llvm.org/docs/AMDGPUUsage.html#code-object-v3-kernel-descriptor)
- `9:6 GRANULATED_WAVEFRONT_SGPR_COUNT`: "GFX10-GFX12: Reserved, must be 0. (128 SGPRs always allocated.)" — [AMDGPUUsage](https://llvm.org/docs/AMDGPUUsage.html#code-object-v3-kernel-descriptor)
- Other rsrc1 fields: `PRIORITY` (must be 0, CP fills), `FLOAT_ROUND_MODE_32`, `FLOAT_ROUND_MODE_16_64`, `FLOAT_DENORM_MODE_32`, `FLOAT_DENORM_MODE_16_64` (→ `COMPUTE_PGM_RSRC1.FLOAT_MODE`), plus GFX10+ `MEM_ORDERED`, `WGP_MODE`, `FWD_PROGRESS` ("If 1 execute SIMD wavefronts to ensure wavefronts will make some forward progress", → `COMPUTE_PGM_RSRC1.FWD_PROGRESS`). — [AMDGPUUsage](https://llvm.org/docs/AMDGPUUsage.html#code-object-v3-kernel-descriptor)

**compute_pgm_rsrc2 (GFX6-GFX12)**
- bit 0 `ENABLE_PRIVATE_SEGMENT`: with *Architected flat scratch* "enable the setup of the FLAT_SCRATCH register pair"; → `COMPUTE_PGM_RSRC2.SCRATCH_EN`. bits 5:1 `USER_SGPR_COUNT` (→ `COMPUTE_PGM_RSRC2.USER_SGPR`). bit 6 `ENABLE_TRAP_HANDLER` "GFX6-GFX11 Must be 0 ... set by the CP if the runtime has installed a trap handler" (on GFX12 this bit becomes `ENABLE_DYNAMIC_VGPR`). bits 7/8/9 `ENABLE_SGPR_WORKGROUP_ID_X/Y/Z` (→ `TGID_X_EN/TGID_Y_EN/TGID_Z_EN`), bit 10 `ENABLE_SGPR_WORKGROUP_INFO` (→ `TGID_SIZE_EN`), bits 12:11 `ENABLE_VGPR_WORKITEM_ID` (→ `TIDIG_CMP_CNT`; 0 = X only, 1 = X,Y, 2 = X,Y,Z), bits 13/14 exception enables (must be 0), bits 23:15 `GRANULATED_LDS_SIZE` "Must be 0. CP uses the rounded value from the dispatch packet, not this value, as the dispatch may contain dynamically allocated group segment memory ... Granularity: GFX7-GFX12 roundup(lds-size / (128 * 4))", bits 24-30 IEEE exception enables (→ `COMPUTE_PGM_RSRC2.EXCP_EN`). — [AMDGPUUsage, compute_pgm_rsrc2 table](https://llvm.org/docs/AMDGPUUsage.html#code-object-v3-kernel-descriptor)

**compute_pgm_rsrc3 (GFX10-GFX11)**
- `3:0 SHARED_VGPR_COUNT` (subvector mode; "For wavefront size 32 shared_vgpr_count must be 0"), `9:4 INST_PREF_SIZE` ("GFX11: Number of instruction bytes to prefetch, starting at the kernel's entry point instruction, before wavefront starts execution. The value is 0..63 with a granularity of 128 bytes"), bit 10 `TRAP_ON_START`, bit 11 `TRAP_ON_END` (both "Must be 0", CP fills), bit 31 `IMAGE_OP`. — [AMDGPUUsage, compute_pgm_rsrc3 for GFX10-GFX11](https://llvm.org/docs/AMDGPUUsage.html#code-object-v3-kernel-descriptor)

**Initial register state at wave launch**
- "The register numbers used for enabled registers are dense starting at SGPR0: the first enabled register is SGPR0, the next enabled register is SGPR1 etc.; disabled registers do not have an SGPR number." "The initial SGPRs comprise up to 16 User SGPRs that are set by CP and apply to all wavefronts of the grid ... immediately followed by the System SGPRs that are set up by ADC/SPI and can have different values for each wavefront." — [AMDGPUUsage, Initial Kernel Execution State](https://llvm.org/docs/AMDGPUUsage.html#initial-kernel-execution-state)
- SGPR set-up order: Private Segment Buffer (4, not on architected-scratch targets), Dispatch Ptr (2, "64-bit address of AQL dispatch packet"), Queue Ptr (2, "64-bit address of amd_queue_t"), Kernarg Segment Ptr (2, "directly copied from the kernarg_address in the kernel dispatch packet"), Dispatch Id (2), Flat Scratch Init (2, not on architected scratch), Private Segment Size (1), Preloaded Kernargs (gfx90a/gfx942), then system SGPRs: Work-Group Id X (1), Y (1), Z (1), Work-Group Info (1: `{first_wavefront, 14'b0000, ordered_append_term[10:0], threadgroup_size_in_wavefronts[5:0]}`), Scratch Wavefront Offset (1). — [AMDGPUUsage, SGPR Register Set Up Order table](https://llvm.org/docs/AMDGPUUsage.html#initial-kernel-execution-state)
- gfx1100 Target Properties: "cumode, wavefrontsize64 (features); Architected flat scratch; Packed work-item IDs"; product list includes "Radeon RX 7900 XTX". gfx942 is also "Architected flat scratch". — [AMDGPUUsage, Processors table](https://llvm.org/docs/AMDGPUUsage.html#processors) (raw lines 569-575, 490)
- Packed work-item ID method (gfx1100): "the initial value of VGPR0 register is used for all work-item IDs": bits `0:9` Work-Item Id X ("Always initialized"), `10:19` Y ("Initialized if enable_vgpr_workitem_id > 0, otherwise set to 0"), `20:29` Z (if `> 1`), `30:31` reserved. — [AMDGPUUsage, Register Layout for Packed Work-Item ID Method](https://llvm.org/docs/AMDGPUUsage.html#initial-kernel-execution-state)
- Hardware responsibility split: "SGPRs before the Work-Group Ids are set by CP using the 16 User Data registers. Work-group Id registers X, Y, Z are set by ADC ... Scratch Wavefront Offset is set by SPI in a per wavefront basis ... The VGPRs are set by SPI which only supports specifying either (X), (X, Y) or (X, Y, Z)." — [AMDGPUUsage](https://llvm.org/docs/AMDGPUUsage.html#initial-kernel-execution-state)
- Architected flat scratch (gfx1100): "If ENABLE_PRIVATE_SEGMENT is enabled ... then the FLAT_SCRATCH register pair will be initialized to the 64-bit address of the base of scratch backing memory being managed by SPI for the queue executing the kernel dispatch plus the value of the wave's Scratch Wavefront Offset"; "a Private Segment Buffer is not supported. Instead the flat SCRATCH instructions are used." — [AMDGPUUsage, Kernel Prolog / Flat Scratch](https://llvm.org/docs/AMDGPUUsage.html#flat-scratch)
- Prolog: on GFX9+ "The M0 register is not used for range checking LDS accesses and so does not need to be initialized"; if the kernel calls functions it sets SGPR32 as stack pointer; frame pointer is SGPR33 ("always set to 0 in the kernel prolog"). — [AMDGPUUsage, Kernel Prolog](https://llvm.org/docs/AMDGPUUsage.html#kernel-prolog)
- Private (scratch) address mapping: `wavefront-scratch-base + (private-address * wavefront-size * 4) + (wavefront-lane-id * 4)` (dword interleaving per lane); NULL for LDS is `0xFFFFFFFF`, for private `0x00000000`; GFX9-GFX11 expose aperture bases as inline constant registers `SRC_SHARED_BASE/LIMIT` and `SRC_PRIVATE_BASE/LIMIT`, apertures are 2^32 bytes. — [AMDGPUUsage, Memory Spaces](https://llvm.org/docs/AMDGPUUsage.html#memory-spaces)

**Kernarg segment and hidden arguments (code object V5)**
- Kernarg memory "must be at least 16-byte aligned"; "For AMDGPU the kernel execution directly accesses the kernel argument memory in the same way constant memory is accessed." "On dGPU the kernarg backing memory is accessed as MTYPE UC (uncached) to avoid needing to invalidate the L2 cache"; "CP invalidates the L0 and L1 caches at the start of each kernel dispatch." — [AMDGPUUsage, Kernel Dispatch; Memory Model GFX10-GFX11](https://llvm.org/docs/AMDGPUUsage.html#kernel-dispatch)
- V5 `.value_kind` hidden args: `hidden_block_count_x/y/z` ("The grid dispatch work-group count ... This count only includes the non-partial work-group count. This is not the same as the value in the AQL dispatch packet, which has the grid size in work-items"), `hidden_group_size_x/y/z` ("the same value as the AQL dispatch packet work-group size"), `hidden_remainder_x/y/z` (size of the partial work-group, 0 if none), `hidden_grid_dims` (1..3), `hidden_heap_v1` (device malloc heap), `hidden_dynamic_lds_size` ("Size of the dynamically allocated LDS memory"), `hidden_private_base` / `hidden_shared_base` ("Only used by GFX8"), `hidden_queue_ptr` ("only required for pre-GFX9 devices for the trap handler ABI"); earlier kinds `hidden_global_offset_x/y/z`, `hidden_printf_buffer`, `hidden_hostcall_buffer`, `hidden_default_queue`, `hidden_completion_action`, `hidden_multigrid_sync_arg`. — [AMDGPUUsage, Code Object V5 Metadata](https://llvm.org/docs/AMDGPUUsage.html#code-object-v5-metadata)
- CLR fills them in `VirtualGPU::...` (`clr/rocclr/device/rocm/rocvirtual.cpp` lines ~4062-4115): `HiddenBlockCountX → global[0] / local[0]`, `HiddenGroupSizeX → local[0]`, `HiddenRemainderX → uint16_t(global[0] % local[0])`, `HiddenGridDims → sizes.dimensions()`, `HiddenPrivateBase → amd_queue_t::private_segment_aperture_base_hi`, `HiddenSharedBase → group_segment_aperture_base_hi`, `HiddenQueuePtr → gpu_queue_`, `HiddenDynamicLdsSize → sharedMemBytes`; then `argSize = std::min(gpuKernel.KernargSegmentByteSize(), signature.paramsSize())`. — [ROCm/clr rocvirtual.cpp](https://github.com/ROCm/clr/blob/develop/rocclr/device/rocm/rocvirtual.cpp)
- Kernarg placement: CLR flag `HIP_FORCE_DEV_KERNARG` default `true` ("Forces kernel arguments to be stored in device memory to reduce latency. Can improve performance by 2-3 µs for some kernels"). — [clr/rocclr/utils/flags.hpp](https://github.com/ROCm/clr/blob/develop/rocclr/utils/flags.hpp) line 228; [HIP env var docs](https://rocm.docs.amd.com/projects/HIP/en/latest/reference/env_variables.html)
- Preloaded kernargs (gfx90a/gfx942 only): "If the kernarg_preload_spec_length is non-zero, the CP firmware will append an additional 256 bytes to the kernel_code_entry_byte_offset" (prologue for incompatible firmware); hidden args can be preloaded with attributes `inreg` + `amdgpu-hidden-argument`. — [AMDGPUUsage, Preloaded Kernel Arguments](https://llvm.org/docs/AMDGPUUsage.html#preloaded-kernel-arguments)

### Inferences
- Worked occupancy arithmetic for gfx1100 (derived from the cited granule/total values): wave32 → 1536 VGPRs per SIMD lane, granule 24, cap 16 waves/SIMD: ≤96 VGPRs → 16 waves; 120 → 12; 168 → 9; 192 → 8; 256 → 6. wave64 (`-mwavefrontsize64`) → 768 effective, granule 12: ≤48 → 16; 96 → 8; 256 → 3. 768 KiB VGPR file per CU = 4 SIMD × 192 KiB = 4 × 1536 regs × 32 lanes × 4 B, consistent with `Feature1536VGPRs`.
- Because gfx10+ always allocates 128 SGPRs/wave (rsrc1 field reserved), the SGPR term in CLR's formula is never the binding limit on RDNA3; `.sgpr_count` matters only for correctness of the descriptor.
- LDS: the rsrc2 granularity for GFX7-GFX12 is 128 dwords = 512 B per allocation block, so a kernel declaring e.g. 33 KiB of LDS reserves 33 KiB rounded to 512 B; in WGP mode two workgroups of 64 KiB fit in the 128 KiB pool, in CU mode each CU sees 64 KiB.
- In HIP, dynamic LDS is passed via `hidden_dynamic_lds_size` and added by CP to the dispatch packet's `group_segment_size`; the descriptor's `GRANULATED_LDS_SIZE` is ignored ("Must be 0"). Max dynamic LDS per kernel reported by `hipFuncGetAttributes` is computed in CLR as `availableLDSSize_ - localMemSize_` (`rockernel.cpp`: `maxDynamicSharedSizeBytes_`).
- Typical SGPR picture for a HIP kernel on gfx1100 (inference from the dense-order rule and COV5 hidden args): user SGPRs usually hold kernarg_segment_ptr (and dispatch_ptr only when the compiler cannot prove `amdgpu-no-dispatch-ptr`, since blockDim/gridDim now come from hidden kernargs), immediately followed by system SGPR workgroup_id_x (y/z only if enabled); VGPR0 = packed tid (x in bits 9:0).

### Gaps
- `getMaxWavesPerEU` per GPUKind lives in LLVM's TargetParser, not in `AMDGPUBaseInfo.cpp`; I did not fetch it. The "16 waves/SIMD on gfx10+" figure is taken from CLR (`MaxWavesPerSimd = 16` for versionMajor >= 10) rather than from LLVM directly.
- I could not open the file where `FeatureISAVersion11_0_0` is defined (feature lists moved out of `AMDGPU.td`; `GCNProcessors.td` line 234 only references it), so the gfx1100 feature list (incl. `Feature1536VGPRs`, `FeatureAddressableLocalMemorySize65536`) is confirmed only via Phoronix's quote of the LLVM commit and the LLVM comment "gfx10/11/12: 64 KiB addressable, 128 KiB physical block".
- The exact numeric value of `Isa::ldsAlignment()` CLR uses for gfx11 is in a per-ISA table I did not extract; LLVM's 512 B (128 dwords) is the authoritative hardware granularity.

## KQ2. Code object metadata (msgpack `.note`): field meaning, V5 vs V6, and how ROCr/CLR use it at launch

### Takeaway
The msgpack note (`amdhsa.kernels[]`) is what the *runtime* reads (descriptor is what the *hardware* reads): CLR parses `.kernarg_segment_size`, `.group_segment_fixed_size`, `.private_segment_fixed_size`, `.vgpr_count`, `.sgpr_count`, `.wavefront_size`, `.max_flat_workgroup_size`, `.workgroup_processor_mode`, `.uniform_work_group_size` and the `.args[].value_kind` list to build the AQL packet, the kernarg buffer and occupancy answers. V5 added the block-count/group-size/remainder/grid-dims/dynamic-LDS hidden args and `.uses_dynamic_stack`; V6 only adds `.cluster_dims`.

### Cited Findings
- V3+ kernel metadata (required unless noted): `.kernarg_segment_size` ("size in bytes of the kernarg segment"), `.group_segment_fixed_size`, `.private_segment_fixed_size`, `.kernarg_segment_align`, `.wavefront_size` ("Must be a power of 2"), `.sgpr_count`, `.vgpr_count` ("Number of vector registers required by each work-item for GFX6-GFX9. A register is required if it is used explicitly, or if a higher numbered register is used explicitly"), `.agpr_count` ("GFX90A, GFX908"), `.max_flat_workgroup_size` ("Must be >=1 and consistent with ReqdWorkGroupSize"), optional `.reqd_workgroup_size`, `.workgroup_size_hint`, `.sgpr_spill_count`, `.vgpr_spill_count`, `.kind`. — [AMDGPUUsage, Code Object V3 Kernel Metadata](https://llvm.org/docs/AMDGPUUsage.html#code-object-v3-metadata) (raw lines 5432-5548)
- V5 changes: `amdhsa.version` = `[1, 2]`; kernel additions `.uses_dynamic_stack` (boolean) and `.workgroup_processor_mode` (boolean, "(GFX10+) Controls ENABLE_WGP_MODE"); attribute `.uniform_work_group_size` (integer; "Metadata is only emitted when value is 1"); new `.value_kind`s listed in KQ1. — [AMDGPUUsage, Code Object V5 Metadata](https://llvm.org/docs/AMDGPUUsage.html#code-object-v5-metadata)
- V6: "Code object V6 metadata is the same as V5 with the changes": `.cluster_dims` (sequence of 3 integers, "The dimension of the cluster"). — [AMDGPUUsage, Code Object V6 Metadata](https://llvm.org/docs/AMDGPUUsage.html#code-object-v6-metadata)
- CLR parsing: `devkernel.cpp` reads metadata through comgr (`prog().getKernelMetadata(name(), &kernelMetaNode)`), with cases such as `KernelField::...` → `kernel->SetWGPMode(buf == "true" || buf == "1")` (comment: "The compiler currently serializes this boolean field as '0'/'1' instead of 'false'/'true'") and `KernelField::UniformWrokGroupSize → setUniformWorkGroupSize(buf == "1")`. — [ROCm/clr devkernel.cpp](https://github.com/ROCm/clr/blob/develop/rocclr/device/devkernel.cpp) (~lines 560-600)
- CLR per-kernel workgroup info (`rocclr/device/rocm/rockernel.cpp` ~lines 95-140): `privateMemSize_ = workitemPrivateSegmentByteSize_`, `localMemSize_ = usedLDSSize_ = workgroupGroupSegmentByteSize_`, `preferredSizeMultiple_ = wavefront_size`, `usedStackSize_ = kernelHasDynamicCallStack_`, `maxDynamicSharedSizeBytes_ = availableLDSSize_ - localMemSize_`; wavefront size comes from the code object and "might be different than what HSA reports. For example on Navi GPUs someone using -mwavefrontsize64", falling back to `HSA_AGENT_INFO_WAVEFRONT_SIZE`. A `RuntimeHandle {kernelCodeHandle_, WorkitemPrivateSegmentByteSize(), WorkgroupGroupSegmentByteSize()}` is written into the code object's runtime-handle variable (used for device-side enqueue). — [ROCm/clr rockernel.cpp](https://github.com/ROCm/clr/blob/develop/rocclr/device/rocm/rockernel.cpp)
- AQL dispatch: "6. A kernel dispatch packet includes information about the actual dispatch, such as grid and work-group size, together with information from the code object about the kernel, such as segment sizes. The HSA compatible runtime queries on the kernel symbol can be used to obtain the code object values which are recorded in the code object metadata." ### Inferences
- `.vgpr_count`/`.sgpr_count` in metadata are what `hipFuncGetAttributes().numRegs` and the occupancy API see; the hardware instead sees the granulated rsrc1 fields. Both are produced by the same backend, so they agree, but tools that patch binaries must update both.
- The `private_segment_size` in the AQL packet (from `.private_segment_fixed_size`, plus dynamic stack) drives ROCr's scratch allocation, which on first use allocates per-queue scratch for all "device slots" (waves the whole GPU can hold); large scratch kernels (spills, `alloca`, recursion) trigger the "use-once" path and serialization, a classic hidden performance cliff.

## KQ3. The AMDGPU memory model on GFX11 (and GFX942 contrast): scopes, waitcnts, cache invalidates, MTYPE, fine- vs coarse-grained memory, atomics and XNACK

### Takeaway
GFX11 has per-CU vector L0, per-shader-array L1 (gl1), device L2 and MALL; the compiler implements C++ scopes with `s_waitcnt vmcnt/vscnt/lgkmcnt` plus `buffer_gl0_inv` (workgroup scope in WGP mode) and `buffer_gl1_inv; buffer_gl0_inv` (agent/system acquire), while release at agent/system scope is just a full `s_waitcnt` (L2 is the coherence point, no writeback needed on dGPU). Coherence with the CPU is a *page-table MTYPE* property: fine-grained = uncached/bypass-L2 and slow, coarse-grained = cached and fast; and on gfx11 dGPU any FP32 atomic (and most integer atomics) to fine-grained memory is silently a NOP because Infinity Fabric lacks those atomics.

### Cited Findings

**Hardware/cache topology as the memory model sees it (GFX10-GFX11)**
- "Each WGP has multiple compute units (CU) ... In CU wavefront execution mode the wavefronts may be executed by different SIMDs in the same CU. In WGP wavefront execution mode the wavefronts may be executed by different SIMDs in different CUs in the same WGP." "Each WGP has a single LDS memory shared by the wavefronts of the work-groups executing on it." "All LDS operations of a WGP are performed as wavefront wide operations in a global order and involve no caching." — [AMDGPUUsage, Memory Model GFX10-GFX11](https://llvm.org/docs/AMDGPUUsage.html#memory-model-gfx10-gfx11)
- "The vector memory operations access a vector L0 cache. There is a single L0 cache per CU ... a `buffer_gl0_inv` is required for coherence between wavefronts executing in the same work-group as they may be executing on SIMDs of different CUs that access different L0s." "The scalar memory operations access a scalar L0 cache shared by all wavefronts on a WGP. The scalar and vector L0 caches are not coherent." "The vector and scalar memory L0 caches use an L1 cache shared by all WGPs on the same SA ... a `buffer_gl1_inv` is required for coherence between wavefronts executing in different work-groups." "The L1 caches use an L2 cache shared by all SAs on the same agent." "On GFX10.3 and GFX11 a memory attached last level (MALL) cache exists for GPU memory. The MALL cache is fully coherent with GPU memory and has no impact on system coherence." — [AMDGPUUsage, Memory Model GFX10-GFX11](https://llvm.org/docs/AMDGPUUsage.html#memory-model-gfx10-gfx11)
- Counters: "vmcnt reports completion of load, atomic with return and sample instructions in order, and the vscnt reports the completion of store and atomic without return in order"; "A `s_waitcnt lgkmcnt(0)` is required to ensure synchronization between LDS operations and vector memory operations between wavefronts of a work-group, but not between operations performed by the same wavefront"; "A `s_waitcnt vmcnt(0) & vscnt(0)` is required to ensure synchronization between vector memory operations of different wavefronts." — [AMDGPUUsage](https://llvm.org/docs/AMDGPUUsage.html#memory-model-gfx10-gfx11)
- Scalar cache rule: "Scalar memory operations are only used to access memory that is proven to not change during the execution of the kernel dispatch ... The scalar and vector caches are invalidated between kernel dispatches by CP"; SGPR spills via scalar stores require `s_dcache_wb` before `s_endpgm`. — [AMDGPUUsage](https://llvm.org/docs/AMDGPUUsage.html#memory-model-gfx10-gfx11)
- MTYPE: kernarg memory "MTYPE UC (uncached)" on dGPU, "MTYPE CC (cache coherent)" on APU; scratch "MTYPE NC (non-coherent) ... there is never a need to invalidate these entries from the L0 or L1 caches"; global segment V# "MTYPE set to support memory coherence that matches the runtime (such as CC for APU and NC for dGPU)". — [AMDGPUUsage](https://llvm.org/docs/AMDGPUUsage.html#memory-model-gfx10-gfx11)
- WGP vs CU mode: "In WGP wavefront execution mode ... explicit management of the per CU L0 caches is required for work-group synchronization ... In CU wavefront execution mode ... all global memory access by the work-group access the same L0 ... and so do not require explicit management of the caches for work-group synchronization." CLR flag `GPU_ENABLE_WGP_MODE` default `true` ("Enables WGP Mode in HW if available"); LLVM feature `cumode` (`-mcumode`). — [AMDGPUUsage](https://llvm.org/docs/AMDGPUUsage.html#memory-model-gfx10-gfx11); [clr flags.hpp](https://github.com/ROCm/clr/blob/develop/rocclr/utils/flags.hpp)

**Code sequences (GFX10-GFX11 table)**
- Non-atomic volatile load: `buffer/global/flat_load glc=1 dlc=1` + `s_waitcnt vmcnt(0)`; nontemporal: `slc=1 dlc=1`. Monotonic atomic load at agent/system scope: `glc=1 dlc=1` ("If GFX11, omit dlc=1"); at workgroup scope `glc=1` ("If CU wavefront execution mode, omit glc=1"). — [AMDGPUUsage, AMDHSA Memory Model Code Sequences GFX10-GFX11](https://llvm.org/docs/AMDGPUUsage.html#memory-model-gfx10-gfx11)
- Acquire load, workgroup scope, global: `buffer/global_load glc=1` → `s_waitcnt vmcnt(0)` → `buffer_gl0_inv` (all three "omit" in CU mode). Acquire load, agent/system scope, global: `buffer/global_load glc=1 dlc=1` ("If GFX11, omit dlc=1") → `s_waitcnt vmcnt(0)` ("Ensures the load has completed before invalidating the caches") → `buffer_gl1_inv; buffer_gl0_inv` ("Ensures that following loads will not see stale global data"). — [AMDGPUUsage](https://llvm.org/docs/AMDGPUUsage.html#memory-model-gfx10-gfx11)
- Release fence, agent/system scope: `s_waitcnt lgkmcnt(0) & vmcnt(0) & vscnt(0)` ("s_waitcnt vmcnt(0) must happen after any preceding global/generic load/load atomic/atomicrmw-with-return-value. s_waitcnt vscnt(0) must happen after any preceding global/generic store/store atomic/atomicrmw-no-return-value"); acq_rel atomicrmw at agent/system scope starts with the same full `s_waitcnt`. No L2 writeback instruction appears in the GFX10-GFX11 release sequences. — [AMDGPUUsage](https://llvm.org/docs/AMDGPUUsage.html#memory-model-gfx10-gfx11)

**Fine- vs coarse-grained memory (HIP runtime)**
- "Coarse-grained coherence: The memory is considered up-to-date only after synchronization performed using hipDeviceSynchronize, hipStreamSynchronize, or any blocking operation that acts on the null stream ... Fine-grained coherence: The memory is coherent even while being modified ... To achieve fine-grained coherence, many AMD GPUs use a limited cache policy, such as leaving these allocations uncached by the GPU or making them read-only." — [HIP docs, Coherence control](https://rocm.docs.amd.com/projects/HIP/en/latest/how-to/hip_runtime_api/memory_management/coherence_control.html) (`hip/docs/how-to/hip_runtime_api/memory_management/coherence_control.rst`)
- Table: `hipHostMalloc` + `hipHostMallocDefault` → fine-grained; `hipHostMallocNonCoherent` → coarse-grained; `hipExtMallocWithFlags` + `hipDeviceMallocDefault` → coarse-grained; `hipDeviceMallocFinegrained` → fine-grained; `hipMallocManaged` → fine-grained (coarse after `hipMemAdvise(..., hipMemAdviseSetCoarseGrain)`); `malloc` → fine-grained. Footnote: with none of `hipHostMallocCoherent/NonCoherent/Mapped` set, `HIP_HOST_COHERENT` (default 0) decides, and "If neither these flags nor the HIP_HOST_COHERENT environment variable is set, or set as 0, the host memory allocation is coarse-grained"; "When hipHostMallocMapped flag is set, the allocated host memory is fine-grained and the hipHostMallocNonCoherent flag is ignored." — [HIP Coherence control](https://rocm.docs.amd.com/projects/HIP/en/latest/how-to/hip_runtime_api/memory_management/coherence_control.html)
- Performance: "Coarse-grained: ... Utilizes the full L2 cache, providing high bandwidth ... Fine-grained: Recommended for atomic flags, signals, and small synchronization variables. Typically bypasses the L2 cache or employs heavy coherency protocols to ensure immediate visibility, resulting in lower bandwidth." — [HIP Coherence control, Performance implications](https://rocm.docs.amd.com/projects/HIP/en/latest/how-to/hip_runtime_api/memory_management/coherence_control.html)
- CLR flag translation in `hipExtMallocWithFlags` (`clr/hipamd/src/hip_memory.cpp` ~lines 820-835): `hipDeviceMallocFinegrained → CL_MEM_SVM_ATOMICS`; `hipDeviceMallocUncached → ROCCLR_MEM_HSA_UNCACHED`; `hipDeviceMallocContiguous → ROCCLR_MEM_HSA_CONTIGUOUS | ROCCLR_MEM_HSA_UNCACHED`; `hipMallocSignalMemory → CL_MEM_SVM_ATOMICS | CL_MEM_SVM_FINE_GRAIN_BUFFER | ROCCLR_MEM_HSA_SIGNAL_MEMORY` (size must be exactly 8 bytes). — [ROCm/clr hip_memory.cpp](https://github.com/ROCm/clr/blob/develop/hipamd/src/hip_memory.cpp)

**Atomics and the fine-grained NOP trap**
- "Coarse-grained ... can be used for device-scope synchronization during the execution of a single GPU kernel"; system-scope atomics on it are downgraded to device scope; coarse-grained is cacheable so atomics execute in L2. "Fine-grained device memory is marked uncacheable through the page tables, so atomics that hit it are forwarded to Infinity Fabric." — [ROCm, AMD GPU atomics operation support (ROCm 10.1.0)](https://rocm.docs.amd.com/en/latest/reference/gpu-atomics-operation.html)
- gfx11: "L2 cache supports FP32 atomic add, min and max"; "The Infinity Fabric does not support FP32 atomic add, min and max atomics"; float atomics to uncached memory "cannot be forwarded to the Infinity Fabric, so they will NOP and give incorrect result". Table rows: gfx11 dGPU, device DRAM, coarse-grained, device scope: all integer atomics "Native"; gfx11 dGPU, fine-grained (migratable and pinned host DRAM), device scope: 32-bit Add/Sub/Min/Max/Inc/Dec "NOP" and 64-bit Add/Min/Max "NOP"; gfx11 APU same rows "Native". "Any atomic not supported by the PCIe bus will be a NOP and give incorrect result." — [ROCm atomics support page](https://rocm.docs.amd.com/en/latest/reference/gpu-atomics-operation.html)
- gfx12: "L2 cache and Infinity Fabric both also support FP32 atomic add, min and max, and packed-FP16 atomic add, and packed-BF16 atomic add"; fine-grained system memory is cacheable; system-scope atomics bypass L2 ("Scope Downgrade" rows); MI300X fine-grained system rows "Scope Downgrade", MI300A "Native". — [ROCm atomics support page](https://rocm.docs.amd.com/en/latest/reference/gpu-atomics-operation.html)
- HIP hardware feature table (RDNA3 column): FP32 atomic add in global and shared memory ✅, FP64 atomic add ✅ (RDNA1/CDNA1 ❌), bfloat16 ✅, FP8 ❌ (CDNA3 ✅), tensor-float32 ❌ (CDNA3 ✅). — [HIP docs, Hardware features](https://rocm.docs.amd.com/projects/HIP/en/latest/reference/hardware_features.html)
- LLVM metadata that replaced the old `-munsafe-fp-atomics` story: `!amdgpu.no.fine.grained.memory` ("the atomic does not access fine-grained allocated memory"), `!amdgpu.no.remote.memory` / `!amdgpu.no.remote.memory.access`, `!amdgpu.ignore.denormal.mode` (formerly `amdgpu.ignore.denormal.mode`, now `atomic.ignore.denormal.mode`); example `atomicrmw fadd ptr addrspace(1) %ptr, float %value seq_cst, align 4, !atomic.ignore.denormal.mode !0, !amdgpu.no.fine.grained.memory !0, !amdgpu.no.remote.memory.access !0`. — [AMDGPUUsage, LLVM IR Metadata](https://llvm.org/docs/AMDGPUUsage.html#llvm-ir-metadata) (raw lines 2510-2590)
- HIP `__constant__`: "Variables in that address space are routed through the constant cache, but that address space has a limited logical size ... the access has to be uniform within a warp, otherwise the accesses are serialized." — [HIP C++ language extensions](https://rocm.docs.amd.com/projects/HIP/en/latest/how-to/hip_cpp_language_extensions.html)

**XNACK / page faults / managed memory**
- LLVM `xnack` target feature: "If not specified for code object V4 or above, generate code that can be loaded and executed in a process with either setting of XNACK replay. XNACK replay can be used for demand paging and page migration. If enabled in the device, then if a page fault occurs the code may execute incorrectly unless generated with XNACK replay enabled ... code generated with XNACK replay enabled ... on a device that does not have XNACK replay enabled will execute correctly but may be less performant." — [AMDGPUUsage, Target Features](https://llvm.org/docs/AMDGPUUsage.html#target-features)
- HIP unified memory: "it is essential to set the environment variable HSA_XNACK=1 and use a GPU kernel mode driver that supports HMM. Without this configuration, access-driven memory migration will be disabled". Support table: `hipMallocManaged()/__managed__` ✅ on CDNA4/CDNA3/CDNA2/CDNA1/RDNA1/GCN5; system allocator (`new`/`malloc`) ✅ only on CDNA4/CDNA3/CDNA2 ("Works only with HSA_XNACK=1 and kernels with HMM support. - UTPX README: without XNACK "the GPU device cannot handle pagefaults and ROCm degrades the allocation to host-resident memory where all access from the device must cross the host-device interconnect (e.g., PCIe)". — [UoB-HPC/utpx](https://github.com/UoB-HPC/utpx)
- Cache measurements (RDNA3, Navi31): L1 "doubles capacity to 256 KB", L2 "6 MB, compared to 4 MB on RDNA 2", scalar cache load-to-use 15.4 ns; Infinity Cache latency 161 ns (scalar) / 199 ns (vector) when the fabric clock idles down, 128.4 ns / 150.3 ns at a forced high power state; "caches on the shader clock domain do not see a notable latency difference" (L0/L1/L2/scalar). — [Chips and Cheese, Microbenchmarking AMD's RDNA 3](https://chipsandcheese.com/p/microbenchmarking-amds-rdna-3-graphics-architecture); [Chips and Cheese, Latency testing is hard: RDNA 3 power saving](https://chipsandcheese.com/p/latency-testing-is-hard-rdna-3-power-saving)

### Inferences
- On gfx11 dGPU, release at agent scope is "cheap" (just drain counters) because L2 is the device coherence point and GPU memory lives behind L2/MALL; the cost sits on the acquire side (`buffer_gl1_inv; buffer_gl0_inv`) and on system-scope traffic to fine-grained pages, which bypass L2 entirely. That is why `__threadfence()` + atomics in fine-grained host memory are slow and why `hipHostMalloc` default (fine-grained) buffers must not be used as compute buffers.
- The practical rule for llama.cpp-style code on the 7900 XTX: keep weights/activations in `hipMalloc` (coarse-grained, cached in L2, atomics native); use `hipHostMallocNonCoherent` or `hipMemAdviseSetCoarseGrain` for large pinned staging buffers; reserve fine-grained memory for 8-byte flags/signals; never do `atomicAdd(float*)` into host-visible fine-grained memory (silent NOP on gfx11 per the ROCm table).
- RDNA3 has no XNACK listed in the HIP managed-memory table at all (table stops at RDNA1 ✅ for `hipMallocManaged`, ❌ for system allocator); together with LLVM's note that gfx11 has no `xnack` entry in its Target Properties, `hipMallocManaged` on the 7900 XTX falls back to host-resident or eagerly placed memory rather than fault-driven migration (inferred from the support table and the UTPX note; not directly stated for gfx1100).
- `hipDeviceMallocUncached` maps to `ROCCLR_MEM_HSA_UNCACHED`, i.e. an MTYPE UC page mapping; this mirrors how the kernarg segment is mapped (MTYPE UC on dGPU) and trades L2 caching for coherence without invalidates.

### Gaps
- No AMD document quantifying the bandwidth penalty of fine-grained vs coarse-grained on RDNA3 was found (only the qualitative "lower bandwidth" statement); the MI200-era "AMD lab notes" blog on this was not retrieved. Needs a microbenchmark on the user's card.
- The atomics page does not mention `-munsafe-fp-atomics` or `hipDeviceMallocUncached`; the semantics of the deprecated clang flag versus the new `!amdgpu.no.fine.grained.memory` metadata are only inferred from the LLVM metadata section.
- `HSA_XNACK` behaviour on gfx1100 specifically (whether KFD exposes XNACK at all on RDNA3) was not verified from a primary source.

## KQ4. HIP runtime features that decide performance: streams → hardware queues, events/signals, hipGraph, hipExtLaunchKernel flags, cooperative launch, occupancy API, dynamic LDS, memory pools, ReBAR, clocks/power

### Takeaway
CLR multiplexes all HIP streams onto a small pool of HSA/AQL hardware queues (`GPU_MAX_HW_QUEUES` default 4 per priority level, cooperative queue separate), kernargs go to device memory by default, `hipExtLaunchKernel` adds `hipExtAnyOrderLaunch` and per-launch events, and hipGraph is supported but library "graph-safety" is uneven (CK, MIOpen, rocThrust, rocWMMA not graph-safe). Occupancy answers are computed by CLR from comgr ISA metadata exactly as in KQ1. Clocks/power are set with `amd-smi set --perf-level/--power-cap/--clk-limit` and Infinity-Fabric power saving is known to distort latency measurements on RDNA3.

- `amd-smi` CLI (requires sudo for set/reset): `amd-smi set --gpu 0 --perf-level HIGH` (values `AUTO, LOW, HIGH, MANUAL, STABLE_STD, STABLE_PEAK, STABLE_MIN_MCLK, STABLE_MIN_SCLK, DETERMINISM`); `amd-smi set --gpu 0 --power-cap 450` (`-o, --power-cap WATTS`, range reported per card); `amd-smi set --gpu 0 --clk-limit sclk max 2100` ("For mclk and fclk ONLY, a max value is rounded down to the nearest selectable DPM level; sclk is honored exactly"); `amd-smi set --gpu 0 --clk-level sclk 0 1` (levels from `amd-smi static --clock`); `amd-smi metric --gpu 0 --power --clock --temperature`; `amd-smi reset --gpureset --gpu all` ("Any process with an open /dev/kfd handle will be terminated when a GPU reset occurs"). — [AMD SMI CLI docs](https://rocm.docs.amd.com/projects/amdsmi/en/latest/how-to/using-AMD-SMI-CLI-tool.html)
- `amdsmi_set_power_cap` takes microwatts and "cap must be between the minimum and maximum power cap values set by the system"; not available inside a VM guest. — [amdsmi Power Control API](https://rocm.docs.amd.com/projects/amdsmi/en/latest/doxygen/docBin/html/group__PowerCont.html)
- 7900 XTX power-cap reports (search snippets, pages themselves blocked by Anubis): a user reported "The default limit is 291w, whereas the TDP of the card should be 355w" and an I/O error writing 355 W; another reported "Manually increasing the power cap to 350 Watt brings measurable performance improvements"; an Arch thread found caps adjustable only up to the card default (350000000 µW). — [drm/amd issue #2356](https://gitlab.freedesktop.org/drm/amd/-/issues/2356); [drm/amd issue #2400](https://gitlab.freedesktop.org/drm/amd/-/issues/2400); [bbs.archlinux.org thread](https://bbs.archlinux.org/viewtopic.php?id=282180)
- Infinity Fabric power management on the 7900 XTX changes measured Infinity Cache latency from 161 ns to 128.4 ns depending on power state (see KQ3). — [Chips and Cheese](https://chipsandcheese.com/p/latency-testing-is-hard-rdna-3-power-saving)

### Inferences
- With default `GPU_MAX_HW_QUEUES=4`, more than four concurrently active normal-priority streams share AQL queues; kernels from different streams on one AQL queue are still independent for CP but lose the ability to be dispatched out of order relative to barrier packets, so "N streams for concurrency" tricks from CUDA stop helping beyond ~4 on ROCm unless the variable is raised (the HIP docs' "recommended maximum 4" suggests hardware/firmware pipe limits on consumer parts).
- `hipExtAnyOrderLaunch` tells CLR it may skip the implicit barrier bit between consecutive dispatches on the same queue; it is the only per-launch flag that changes CP scheduling on AMD (no CUDA-style launch attributes/cluster dims on gfx11).
- Event timing (`hipEventElapsedTime`, or `startEvent/stopEvent` of `hipExtLaunchKernel`) forces profiled dispatches (`profileNDRange`), which on ROCm means CP timestamps on the AQL packet and can serialize a batch; use `GPU_FORCE_QUEUE_PROFILING` consciously.
- For benchmarks on the 7900 XTX: pin `--perf-level` (or `STABLE_PEAK`/`DETERMINISM` if exposed) and watch the power cap, because the default Linux cap may sit below the Windows TBP and the fabric clock down-shifts at low queue depth (both affect memory-bound llama.cpp decode).

### Gaps
- No primary source for the number of hardware compute pipes/queues KFD exposes on gfx1100 (MEC pipes × queues) was retrieved; only CLR's software pool size (4 per priority) is confirmed.
- Resizable BAR: no ROCm documentation on large-BAR requirements or measured `hipMemcpy` effects for the 7900 XTX surfaced in search; only gaming "Smart Access Memory" reviews. Flagged as unverified.
- hipGraph concrete limitations vs CUDA graphs (unsupported node types, capture restrictions, conditional nodes) are not enumerated in HIP docs; only library-level graph safety is documented.
- Memory pools (`hipMallocAsync`/`hipMemPool*`) and `hipOccupancyMaxActiveBlocksPerMultiprocessor` public wrappers were seen in `hip_platform.cpp` (lines 548-646) but their flag handling was not read in detail.

## KQ5. What a CUDA programmer must know on HIP/RDNA3, and what gfx1100 lacks vs gfx942 and gfx1201

### Takeaway
HIP on gfx1100 compiles straight to ISA (no PTX layer), defaults to wave32 but can be built wave64, exposes `warpSize` as a runtime value (and `__AMDGCN_WAVEFRONT_SIZE` at compile time), reinterprets `__launch_bounds__`'s second argument as *min waves per SIMD*, has no `--maxrregcount`, and runs a WGP/CU-mode hardware model where workgroup-scope coherence needs explicit `buffer_gl0_inv`. Versus gfx942 it lacks MFMA/AGPRs, kernarg preload, FP8/TF32 and XNACK-driven managed memory; versus gfx1201 it lacks FP32 atomics over Infinity Fabric, packed FP16/BF16 atomics, dynamic VGPRs, and the new WMMA/FP8 paths.

### Cited Findings
- "Code should not assume a warp size of 32 or 64, as AMD GPU architectures have different warp sizes. The warpSize built-in should be used in device code, while the host can query it during runtime via the device properties"; lane-mask bit-shifts must use a 64-bit-capable type (`lane_mask_t`) on wave64. — [HIP porting guide, warpSize](https://rocm.docs.amd.com/projects/HIP/en/latest/how-to/hip_porting_guide.html)
- `__launch_bounds__` conversion: "MIN_BLOCKS_PER_MULTIPROCESSOR in CUDA must be converted to MIN_WARPS_PER_EXECUTION_UNIT in HIP"; CU mode (CDNA): `MIN_WARPS_PER_EXECUTION_UNIT = (MIN_BLOCKS_PER_MULTIPROCESSOR * MAX_THREADS_PER_BLOCK) / (warpSize * 2)`; WGP mode (RDNA): `/ (warpSize * 4)`. "Unlike nvcc, amdclang++ does not support the --maxregcount option." — [HIP porting guide](https://rocm.docs.amd.com/projects/HIP/en/latest/how-to/hip_porting_guide.html)
- `MIN_WARPS_PER_EXECUTION_UNIT` defaults to 1; "On AMD GPUs a Compute Unit consists of 4 Execution Units, also known as SIMDs, each with their own register file"; `hipDeviceProp_t::executionUnitsPerMultiprocessor` exists. — [HIP C++ language extensions](https://rocm.docs.amd.com/projects/HIP/en/latest/how-to/hip_cpp_language_extensions.html)
- Wave size selection: LLVM feature `wavefrontsize64` ("-m[no-]wavefrontsize64 Control the wavefront size used when generating code for kernels. When disabled native wavefront size 32 is used"); the descriptor bit `ENABLE_WAVEFRONT_SIZE32` records it; CLR takes the kernel's wavefront size from the code object ("on Navi GPUs someone using -mwavefrontsize64"). — [AMDGPUUsage, Target Features](https://llvm.org/docs/AMDGPUUsage.html#target-features); [clr rockernel.cpp](https://github.com/ROCm/clr/blob/develop/rocclr/device/rocm/rockernel.cpp)
- Compilation model: "the kernel execution directly accesses the kernel argument memory in the same way constant memory is accessed"; `amdhsa` code objects contain the final ISA with descriptor + metadata (no intermediate re-JIT); `.amdhsa_kernel` assembler directives (`.amdhsa_next_free_vgpr`, `.amdhsa_next_free_sgpr`, `.amdhsa_reserve_*`) are how hand-written assembly produces the descriptor. — [AMDGPUUsage, Kernel Dispatch / Assembler](https://llvm.org/docs/AMDGPUUsage.html#kernel-dispatch)
- gfx942-only ABI features: kernarg preload (`KERNARG_PRELOAD_SPEC_LENGTH/OFFSET`, "GFX90A, GFX942"), unified VGPR/AGPR file (`ACCUM_OFFSET` in rsrc3, "vgprs_used 0..512", granule 8), `sramecc` property; `.agpr_count` metadata only for "GFX90A, GFX908". — [AMDGPUUsage](https://llvm.org/docs/AMDGPUUsage.html#code-object-v3-kernel-descriptor)
- gfx12 (gfx1201)-only ABI features: `ENABLE_DYNAMIC_VGPR` in rsrc2 bit 6 ("each wave allocates one VGPR chunk at launch and can request for additional space to use during execution in SQ"), separate `compute_pgm_rsrc3 for GFX12` table, CWSR trap handler scratch reservation for dynamic VGPRs in the prolog; gfx1201 is "amdgpu12.01" in the generic-target table. — [AMDGPUUsage](https://llvm.org/docs/AMDGPUUsage.html#code-object-v3-kernel-descriptor)
- Feature table deltas (HIP docs): FP8 types and TF32 only on CDNA3; bfloat16 on RDNA3/CDNA; FP32/FP64 atomic add on RDNA2+/CDNA2+. — [HIP Hardware features](https://rocm.docs.amd.com/projects/HIP/en/latest/reference/hardware_features.html)
- Atomics delta: gfx12 adds FP32 add/min/max and packed FP16/BF16 add in both L2 and Infinity Fabric; gfx11 has them in L2 only (see KQ3). — [ROCm atomics support page](https://rocm.docs.amd.com/en/latest/reference/gpu-atomics-operation.html)
- Managed/system-allocator memory needs CDNA2+ with `HSA_XNACK=1`; RDNA columns show only `hipMallocManaged` support. — [HIP Unified memory](https://rocm.docs.amd.com/projects/HIP/en/latest/how-to/hip_runtime_api/memory_management/unified_memory.html)
- Cache topology differences: gfx942 "L1 Vector Cache 32 KiB", "L2 4 MiB per XCD", "L3 256 MiB", LDS 64 KiB; gfx1100 "L0 Vector 32 KiB", "Graphics L1 256 KiB", "L2 6 MiB", "Infinity Cache 96 MiB", LDS 128 KiB; gfx1201 "Graphics L1 N/A", "L2 8 MiB", "Infinity Cache 64 MiB". — [ROCm GPU specs](https://rocm.docs.amd.com/en/latest/reference/gpu-arch-specs.html)
- GFX11 instruction prefetch is tunable from the descriptor (`INST_PREF_SIZE`, 0..63 × 128 B) — no CUDA analogue. — [AMDGPUUsage, compute_pgm_rsrc3 GFX10-GFX11](https://llvm.org/docs/AMDGPUUsage.html#code-object-v3-kernel-descriptor)

### Inferences
- "No constant cache banks": on AMD, `__constant__` and kernargs are served by the scalar (K$) L0 cache and the compiler uses `s_load` only when uniformity is provable; divergent `__constant__` reads become vector loads through L0/L1/L2 ("the accesses are serialized" in the HIP doc). There is no CUDA-style 64 KiB constant bank with broadcast hardware; the scalar cache is 16 KiB per WGP on gfx1100 (ROCm spec table).
- Because CLR reads `.workgroup_processor_mode` from metadata and doubles SIMD count in the occupancy math, `-mcumode` changes both the memory-model sequences (no `buffer_gl0_inv` at workgroup scope) and the reported occupancy; kernels that assume "a block fits on one CU and L0 is shared" are correct only in CU mode.
- The RDNA4 (gfx1201) removal of the Graphics L1 means the gfx11 `buffer_gl1_inv` step is irrelevant there; the GFX12 memory model table in AMDGPUUsage is separate (not read in detail here).
- hipify pitfalls that follow directly from the cited contract: 32-bit lane masks (`__ballot` returns 64-bit on wave64), `__launch_bounds__` second argument semantics, `warpSize` not being `constexpr`, missing `--maxrregcount`, no XNACK/managed-memory migration on RDNA, and silent NOP atomics on fine-grained memory.

### Gaps
- The gfx1100 vs gfx942 differences in *instructions* (MFMA vs WMMA, no async LDS DMA on gfx11, `buffer_load ... lds`) are deliberately left to the ISA track; I did not verify async-LDS-DMA absence on gfx11 from a primary source here.
- `__AMDGCN_WAVEFRONT_SIZE` macro deprecation status and `__hip_warpSize` handling in HIP 7 headers were not checked in source (only the docs' guidance to use `warpSize`).
- The "GFX12 Memory Model" section (raw lines 15633-17766) was not read; statements about gfx1201 coherence are inferred from the atomics page and specs table only.
