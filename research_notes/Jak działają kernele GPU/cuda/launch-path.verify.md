# Verification: CUDA stack internals (NVIDIA) — "From cudaLaunchKernel to the SM"

Verified 2026-10-17 against the cloned sources already in the scratchpad (Mesa `335d5698dca1d1b9d11ef18cf5f523cc0f7f58fb`, OGKM `ca2d03e6fafd4d4b56b383497d931c25b283bfcf` / 615.78.08), the RTAS 2023/2024 PDFs (downloaded to `/tmp/claude-0/-home-user-KERNEL/2fec5121-746d-5a8c-9207-83ad66dddd8f/scratchpad/stack_cuda/verify/pdf/` and text-extracted with pdftotext), and the cited web pages. Independent web searches found no contradicting or newer primary evidence for any claim (no B200/CUDA 13 null-kernel measurement exists in the literature found; no public source gives a different default TSG timeslice).

Result: 8/8 load-bearing claims confirmed, 0 refuted, 0 unverifiable. Extra spot-checks: 2 confirmed, 1 unverifiable (already flagged as such in the note).

## Confirmed

1. **Claim:** "A compute launch is a QMD descriptor scheduled by two compute-class methods, SEND_PCAS_A(qmd_addr >> 8) followed by SEND_SIGNALING_PCAS2_B(PCAS_ACTION_INVALIDATE_COPY_SCHEDULE) on Ampere+ (SEND_SIGNALING_PCAS_B{invalidate,schedule} up to Turing); NVK uploads the root descriptor table as a constant buffer and the QMD with 0x100 alignment before emitting them, and patches the QMD in place for indirect dispatch."
   **Evidence:** `src/nouveau/vulkan/nvk_cmd_dispatch.c` lines 341-352: `P_NVA0C0_SEND_PCAS_A(p, qmd_addr >> 8);` then `if (nvk_cmd_buffer_compute_cls(cmd) <= TURING_COMPUTE_A) P_IMMD(p, NVA0C0, SEND_SIGNALING_PCAS_B, {.invalidate = INVALIDATE_TRUE, .schedule = SCHEDULE_TRUE}) else P_IMMD(p, NVC6C0, SEND_SIGNALING_PCAS2_B, PCAS_ACTION_INVALIDATE_COPY_SCHEDULE)`. Root descriptor upload: lines 170-187 `nvk_cmd_buffer_upload_alloc(cmd, root_size, min_cbuf_alignment, ...)`, bound as `NVK_CBUF_TYPE_ROOT_DESC` cbuf (line 208-212). QMD allocation: line 237 `nvk_cmd_buffer_alloc_qmd(cmd, qmd_size_B, 0x100, ...)`. Indirect: `nvk_CmdDispatchIndirect2KHR` (line 456) uses `LINE_LENGTH_IN`/`LAUNCH_DMA` (lines 441-447) at `nak_get_qmd_dispatch_size_layout()` offsets (line 511). Independent: Mesa MR !198 "nvk: add compute support for ampere" describes the PCAS2_B change.

2. **Claim:** "QMD size is 64 dwords (256 B) for QMD v0.6–v3.0 (Kepler through Ada) and 96 dwords (384 B) for v4.0 (Hopper) and v5.0 (Blackwell); NAK fills PROGRAM_ADDRESS, CTA_THREAD_DIMENSION0-2, grid size, REGISTER_COUNT, SHARED_MEMORY_SIZE, BARRIER_COUNT, SLM size, constant buffers and cache-invalidate bits, and on v5 sets QMD_TYPE=0x2 and QMD_GROUP_ID=0x1f."
   **Evidence:** `src/nouveau/compiler/nak/qmd.rs`: `qmd: [u32; 64]` at lines 387 (v0.6), 454 (v1.7), 511 (v2.1), 669 (v2.2), 704 (v3.0); `qmd: [u32; 96]` at lines 760 (v4.0, `qmd_init!(bv, clcbc0, QMDV04_00, 4, 0)`) and 808 (v5.0); lines 816-817 `set_field!(bv, clcdc0, QMDV05_00, QMD_TYPE, 0x2); set_field!(..., QMD_GROUP_ID, 0x1f);`. `nak_qmd_size_B` (line 886) selects by class: BLACKWELL_COMPUTE_A -> v5, HOPPER_COMPUTE_A -> v4, AMPERE_COMPUTE_A (covers Ada) -> v3.0, etc. Setters present: BARRIER_COUNT (92), CTA_RASTER_* / GRID_* alias (99-127, 744-746, 801-803), CTA_THREAD_DIMENSION0-2 (132-134), INVALIDATE_* (139-164), SHADER_LOCAL_MEMORY_LOW/HIGH (361-371), CONSTANT_BUFFER (254-283), PROGRAM_ADDRESS (315), REGISTER_COUNT (403...), SHARED_MEMORY_SIZE (431...).

5. **Claim:** "With the open kernel modules (615.78.08, Turing+ only; Blackwell is open-modules-only), channel creation is forwarded to GSP firmware ('RPC to allocate the channel on GSPFW/host' when IS_GSP_CLIENT) and nvidia.ko speaks to GSP through 226 RPC message types (e.g. ALLOC_CHANNEL_DMA=6, GSP_RM_CONTROL=76, GSP_RM_ALLOC=103); the user-space driver components (libcuda etc.) are identical for both kernel flavours and remain closed."
   **Evidence:** `kernel-open/Kbuild:109 -DNV_VERSION_STRING="615.78.08"`; README line 183 "can be used on any Turing or later GPU". `kernel_channel.c` lines 975-981: `// RPC to allocate the channel on GSPFW/host.` ... `if (IS_GSP_CLIENT(pGpu) || bFullSriov) ... _kchannelSendChannelAllocRpc(...)`. `rpc_global_enums.h`: 226 `X(RM|GSP, ...)` entries; `X(RM, ALLOC_CHANNEL_DMA, 6)`, `X(GSP, GSP_RM_CONTROL, 76)`, `X(GSP, GSP_RM_ALLOC, 103)`. 6. **Claim:** "The hardware compute scheduling pipeline is Host Interface (PBDMAs pulling an indirect buffer of pushbuffer segments 'without system call or driver overheads') -> Compute Front End -> Task Management Unit/SKED (priority-level linked lists selected by the TMD/QMD GROUP_ID field) -> Work Distribution Unit/CWD (hardware-limited task slots, priority-sorted task table, load balancer dispatching CTAs to TPCs, skipping TPCs masked by the 'SM mask' which actually acts as a TPC mask, and evicting lower-priority TMDs); by default only eight compute channels exist per context (through CUDA 12.2, changeable via CUDA_DEVICE_MAX_CONNECTIONS) and TSGs are round-robin time-sliced (~2 ms slices measured on GTX 1060)."
   **Evidence (RTAS 2023 PDF text):** "or more Pushbuffer Direct Memory Access units (PBDMAs)", "the GPU without system call or driver overheads", "The Compute Front End relays TMD pointers from ... the Host Interface to ... the Task Management Unit", footnote 16 "More recently called the 'Scheduler Unit' or 'SKED' in patents ... Grid Management Unit (GMU)", "the TMU reads the TMD's GROUP_ID field", "The number of task slots is hardware [limited]", "Priority-Sorted Task Table", "The Load Balancer dispatches thread blocks from the TMD at the head", "When all WDU task slots are occupied ... the lower-priority TMD will be evicted", Fig. 4 "An 'SM mask' acting as a TPC mask on the Telsa P100 GPU", "GPUs from Kepler through at least Ampere". **Citation note:** the channel-count and timeslice parts are NOT in rtas23.pdf; they come from RTAS 2024 (rtas24.pdf, which the note itself cites correctly): line 334 "By default, through at least CUDA 12.2 on x86_64, only eight [channels]", footnote 11 "Via the environment variable CUDA_DEVICE_MAX_CONNECTIONS", "the GPU globally round-robin timeslices across", "approximately 20 timeslices per 80 ms. The slice lengths are largely consistent, at about 2 ms each" (GTX 1060 3GB). Independent: CUDA env-var docs "1 to 32 connections, default is 8 (assumes no MPS)". The report writer should attach the RTAS 2024 URL to the second half of this claim.

7. **Claim:** "RM's hardware default TSG timeslice is NV_RAMRL_ENTRY_TSG_TIMESLICE_TIMEOUT_128 << NV_RAMRL_ENTRY_TSG_TIMESLICE_SCALE_3 = 0x80 << 3 = 1024 µs ('Returns the default timeslice (in us) for a channelgroup as defined by hardware'), adjustable per channel group via NVA06C_CTRL_CMD_SET_TIMESLICE {timesliceUs}, with NVA06C_CTRL_CMD_SET_INTERLEAVE_LEVEL (LOW/MEDIUM/HIGH), PREEMPT and MAKE_REALTIME controls."
   **Evidence:** `kernel_fifo_gv100.c` lines 43-51: comment "Returns the default timeslice (in us) for a channelgroup as defined by hardware." and `return NV_RAMRL_ENTRY_TSG_TIMESLICE_TIMEOUT_128 << NV_RAMRL_ENTRY_TSG_TIMESLICE_SCALE_3;`; `dev_ram.h` lines 64-65 `SCALE_3 0x00000003`, `TIMEOUT_128 0x00000080` (0x80<<3 = 1024). `ctrla06c.h`: `NVA06C_CTRL_CMD_SET_TIMESLICE (0xa06c0103)` with `NvU64 timesliceUs`, `SET_INTERLEAVE_LEVEL (0xa06c0107)` with `LOW 0/MEDIUM 1/HIGH 2`, `CMD_PREEMPT (0xa06c0105)` (`MAX_MANUAL_TIMEOUT_US 1000000`), `MAKE_REALTIME (0xa06c0110)`. Web search found no public source contradicting 1024 µs (Tegra docs recommend 1.5-2 ms caps; NVML vGPU docs say "default" without a number).

8. **Claim:** "Measured null-kernel launch overhead with CUDA 12.6 / driver 560.35.03 is 2260.5 ns on A100, 2374.6 ns on H100 and 2771.6 ns on GH200 (kernel durations 1440/1235/1171 ns); on V100/CUDA 10.1 per-kernel cost was 9.6 µs with sync per launch, 3.8 µs with overlapped stream launches and 3.4 µs inside a CUDA graph (2.9 µs pure execution), with ~400 µs to instantiate the graph; device-side graph launch is more than 2x lower latency than host launch."
   **Evidence:** arXiv 2504.11750 ("Characterizing and Optimizing LLM Inference Workloads on CPU-GPU Coupled Architectures", Apr 2025): "CUDA 12.6 and NVIDIA driver 560.35.03"; Table V "CudaLaunchAPI with nullKernel launch overhead and nullKernel duration": AMD+A100 2260.5 / 1440.0 ns, Intel+H100 2374.6 / 1235.2 ns, GH200 2771.6 / 1171.2 ns (minor: the A100/H100 rows are host-platform-labelled "AMD+A100"/"Intel+H100"). NVIDIA blog "Getting Started with CUDA Graphs" (V100, CUDA 10.1): 2.9 µs, 9.6 µs, 3.8 µs, 3.4 µs, ~400 µs instantiate. Device graph launch blog: "the device-side launch latency better than 2x lower than that of the host launch" (CUDA 12.0). Web search found no newer B200/CUDA 13 null-kernel measurement.
