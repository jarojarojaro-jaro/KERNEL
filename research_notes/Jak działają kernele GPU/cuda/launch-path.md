## Q1. Layers and binaries: libcudart vs libcuda vs nvidia.ko/nvidia-uvm.ko vs GSP firmware; module loading, lazy loading, primary context

### Takeaway
The runtime (`libcudart`, toolkit) is a thin convenience layer that owns nothing on the GPU: it retains the per-device *primary context* and loads fat binaries into the driver (`libcuda.so`, installed with the driver), which owns contexts, modules (→ GPU code + constant banks in VRAM), streams (→ hardware channels), and user-mode command submission. `nvidia.ko` (Resource Manager, RM) exposes an object/ioctl API (`NV_ESC_RM_ALLOC/CONTROL/FREE/MAP_MEMORY`) and, on Turing+ with the open modules, forwards most "physical" GPU programming to the **GSP firmware** via RPC; `nvidia-uvm.ko` owns the unified-memory VA space and page faults. Since CUDA 12.2/12.3, kernels are loaded **lazily** at first `CUfunction` use unless `CUDA_MODULE_LOADING=EAGER`.

### Cited Findings
- "The driver and runtime APIs are very similar and can for the most part be used interchangeably"; runtime provides "implicit primary context initialization and management"; "Primary contexts are created as needed, one per device per process"; "The driver API is also language-independent as it only deals with cubin objects" — [CUDA Runtime API: Driver vs Runtime](https://docs.nvidia.com/cuda/cuda-runtime-api/driver-vs-runtime-api.html)
- "The primary context is unique per device and shared with the CUDA runtime API"; `cuDevicePrimaryCtxRetain`: "Unlike cuCtxCreate() the newly retained context is not pushed onto the stack"; "The context is automatically reset once the last reference to it is released"; `cuDevicePrimaryCtxSetFlags`: `CU_CTX_SCHED_SPIN` ("actively spin"), `CU_CTX_SCHED_YIELD`, `CU_CTX_SCHED_BLOCKING_SYNC` ("block the CPU thread on a synchronization primitive"), `CU_CTX_SCHED_AUTO` (default) "uses a heuristic based on the number of active CUDA contexts in the process" — yields if contexts > logical processors, else spins — [CUDA Driver API: Primary Context](https://docs.nvidia.com/cuda/cuda-driver-api/group__CUDA__PRIMARY__CTX.html)
- `cuModuleLoad` "Takes a filename fname and loads the corresponding module module into the current context"; "The CUDA driver API does not attempt to lazily allocate the resources needed by a module" (memory for functions/data must be allocatable or the call fails); accepted inputs: cubin, fatbin, PTX ("either as output by nvcc or handwritten"), Tile IR; `cuModuleGetLoadingMode` returns `CU_MODULE_EAGER_LOADING`/`CU_MODULE_LAZY_LOADING`, "Module loading mode is controlled by CUDA_MODULE_LOADING env variable"; in LAZY mode "the function retrieved may be partially loaded", `cuFuncLoad` forces it — [CUDA Driver API: Module Management](https://docs.nvidia.com/cuda/cuda-driver-api/group__CUDA__MODULE.html)
- Lazy loading: "As of CUDA 12.3, lazy loading is enabled by default on all platforms" (introduced opt-in in 11.7, default on Linux in 12.2); requires driver ≥ 515 and runtime ≥ 11.7; "cuModuleLoad() does not guarantee that a module will be loaded immediately"; explicit triggers are `cuModuleGetFunction()` and `cudaFuncGetAttributes()`; "Lazy loading does not affect modules containing managed variables, which will still be loaded eagerly"; deadlock caveat: "A deadlock can occur if cross-kernel synchronization is required, but kernel execution has been serialized"; memory caveat: "If an application allocates the entire VRAM on startup, CUDA can fail to allocate memory for modules at runtime"; benchmarking: "Lazy loading may skew performance measurements by moving CUDA module initialization into the measured execution window" — [CUDA Programming Guide 4.8 Lazy Loading](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/lazy-loading.html)
- Env vars (verbatim): `CUDA_MODULE_LOADING` — DEFAULT ("equivalent to LAZY"), LAZY ("loading of specific kernels is delayed until a CUDA function handle, CUfunc, is extracted"), EAGER ("Fully loads CUDA modules and kernels at program initialization"); `CUDA_MODULE_DATA_LOADING` (same values, for module data); `CUDA_FORCE_PTX_JIT=1` "Forces PTX JIT compilation" (ignores embedded CUBIN); `CUDA_DISABLE_PTX_JIT=1`; `CUDA_CACHE_PATH` default `~/.nv/ComputeCache`; `CUDA_CACHE_MAXSIZE` default 1 GiB desktop (256 MiB embedded, max 4 GiB); `CUDA_LAUNCH_BLOCKING=1` "Disables asynchronous execution" — [CUDA Programming Guide 5.2 Environment Variables](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/environment-variables.html)
- Kernel parameters "are passed to the device through constant memory and have been limited to 4,096 bytes"; "Beginning with CUDA 12.1, you can now pass up to 32,764 bytes as kernel parameters on NVIDIA Volta and above" — [NVIDIA blog, CUDA 12.1 large kernel parameters](https://developer.nvidia.com/blog/cuda-12-1-supports-large-kernel-parameters)

### Inferences
- `cudaLaunchKernel` → (cudart, statically linked by default) → `cuLaunchKernel`/`cuLaunchKernelEx` in `libcuda.so` → libcuda writes the QMD + pushbuffer methods in user space and rings the doorbell; the kernel driver is not on the per-launch path (see Q2/Q3). The exact cudart→libcuda entry (whether it uses the public `cuLaunchKernelEx` or an internal export) is not documented; the public contract is only "interchangeable APIs sharing the primary context".
- "Load" of a module in the driver = allocate VRAM for code/data, apply relocations/patch addresses (the QMD needs a GPU VA for `PROGRAM_ADDRESS`, constant banks for params), JIT PTX→SASS if no matching SASS (cached in `~/.nv/ComputeCache`), and upload. The driver docs only state the observable rules (resources allocated eagerly per module, lazy per-function); the internal loader is closed.

### Gaps
- No public source describes libcuda's internal module loader (ELF relocation, constant-bank layout for params beyond "bank 0 / constant memory", JIT invocation). Binary-format track covers the cubin side.
- The cudart→libcuda mapping (one-to-one `cudaLaunchKernel`→`cuLaunchKernelEx`?) is not verifiable from docs; only black-box tracing (e.g., `LD_DEBUG`, `ltrace`, CUPTI driver-API callbacks) would show it.

## Q2. User-mode command submission: GPFIFO channels, pushbuffers, USERD and doorbells, Host semaphores, and the QMD (what libcuda builds; what NVK builds in the open)

### Takeaway
A CUDA stream maps to an RM *channel* (`*_CHANNEL_GPFIFO_*` class, e.g. `HOPPER_CHANNEL_GPFIFO_A` 0xC86F, `BLACKWELL_CHANNEL_GPFIFO_A/B` 0xC96F/0xCA6F) with a ring of 8-byte **GP entries** pointing at **pushbuffer** segments of method words, a user-mapped **USERD** page (`GPPut` at 0x8C), and a **doorbell** (`NVC361_NOTIFY_CHANNEL_PENDING` at 0x90 in the mapped `VOLTA_USERMODE_A` region, written with a per-channel *work submit token*). A compute launch is a 256-byte (Kepler–Ada, QMD v0.6–v3.0) or 384-byte (Hopper v4.0, Blackwell v5.0) **QMD** in GPU memory, scheduled by two compute-class methods: `SEND_PCAS_A(qmd_addr>>8)` + `SEND_SIGNALING_PCAS2_B(INVALIDATE_COPY_SCHEDULE)`. NVK (`nvk_cmd_dispatch.c` + `nak/qmd.rs`) is a complete open implementation of this path.

### Inferences
- The whole "launch" in the open stack is: (1) write QMD (256/384 B) to GPU-visible memory, (2) append ~4 dwords of methods (`SEND_PCAS_A`, `SEND_SIGNALING_PCAS2_B`) to the pushbuffer, (3) append a GP entry, (4) write `GPPut` in USERD, (5) write the work-submit token to the doorbell. libcuda has every ingredient to do (1)–(5) without a syscall: client-provided USERD (`hUserdMemory/userdOffset`, `NVOS04_FLAGS_MAP_CHANNEL`), `GET_WORK_SUBMIT_TOKEN`, and the mappable `VOLTA_USERMODE_A` region. Nouveau instead performs (3)–(5) in the kernel per `DRM_NOUVEAU_EXEC` — so NVK is the open reference for the *content* of a launch, not for its *user-mode doorbell path*.
- QMD `RELEASE_SEMAPHORE0..2` (v5) / `RELEASE0_*` (v2/v3) let the compute front end write a payload when the grid completes without any extra pushbuffer methods; combined with Host `SEM_EXECUTE ACQUIRE` this is the natural implementation of stream ordering, events and `cudaStreamWaitEvent` (unverified for libcuda, but it is exactly what the fields are for; `ACQUIRE_SWITCH_TSG` lets Host switch channels while an acquire is pending).
- `DEPENDENT_QMD*`, `DEPENDENCE_COUNTER`, `HW_ONLY_SKED_NEXT_QMD_POINTER`, `QMD_GROUP_ID` and the latch fields are hardware hooks for graph-style chaining (a QMD completing can `INVALIDATE_COPY_SCHEDULE` or `DECREMENT_DEPENDENCE` on a successor) — plausible substrate of CUDA Graphs / device graph launch / PDL; NVK already uses `set_dependent_qmd` for its own purposes.
- `SASS_VERSION` in the QMD (NAK writes 0x30 on Kepler) tells the SM which ISA revision the code at `PROGRAM_ADDRESS` uses; `REGISTER_COUNT` (8 bits) and `SHARED_MEMORY_SIZE` are what the CWD uses for occupancy — the same numbers `cuobjdump`/`nvdisasm` report for a kernel.

### Gaps
- `SEND_PCAS_A/SEND_SIGNALING_PCAS2_B` ("PCAS" = ?) semantics are only visible as enum names (`PCAS_ACTION_INVALIDATE_COPY_SCHEDULE`); no NVIDIA prose. The exact meaning of `QMD_TYPE=0x2`/`QMD_GROUP_ID=0x1f` chosen by NAK is undocumented.
- Whether libcuda actually uses QMD release semaphores vs. Host `SEM_EXECUTE` for stream completion is not verifiable without tracing pushbuffers (a GPU memory dump under `nvdebug` or `envytools` tracing on the proprietary driver would answer it).

## Q3. Hardware front end: Host/PBDMA, runlists & time-slicing, Compute Front End, SKED/TMU, CWD/WDU, SM dispatch, completion tracking; what GSP-RM and the kernel driver do

### Takeaway
Per-launch, the kernel driver does nothing: Host (PFIFO) round-robins **runlists** of TSGs/channels (default TSG timeslice encoded as `TIMEOUT_128 << SCALE_3` = 1024 µs in RM; ~2 ms measured on Pascal), a PBDMA pulls GP entries/methods of the active channel, the Compute Front End hands the QMD pointer to the **SKED/TMU** (priority-ordered linked lists keyed by `QMD_GROUP_ID`), which feeds the **CWD/WDU** (limited task slots, priority-sorted task table, load balancer dispatching CTAs to TPCs honouring `SM_DISABLE_MASK`/`TPC_DISABLE_MASK`); completion is reported by semaphore releases and `CWD_REFERENCE_COUNT`. GSP-RM (RISC-V firmware) now owns channel/runlist/context-switch programming; `nvidia.ko` talks to it through ~226 RPC message types.

### Cited Findings
- Default TSG timeslice in RM: `kfifoChannelGroupGetDefaultTimeslice_GV100()` "Returns the default timeslice (in us) for a channelgroup as defined by hardware" → `NV_RAMRL_ENTRY_TSG_TIMESLICE_TIMEOUT_128 << NV_RAMRL_ENTRY_TSG_TIMESLICE_SCALE_3` with `TIMEOUT_128 = 0x80`, `SCALE_3 = 3` (`src/common/inc/swref/published/volta/gv100/dev_ram.h:64-65`) — i.e. 0x80<<3 = **1024 µs** — [OGKM kernel_fifo_gv100.c](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/main/src/nvidia/src/kernel/gpu/fifo/arch/volta/kernel_fifo_gv100.c)
- Scheduling pipeline (Bakita & Anderson, RTAS 2023, "accurate for NVIDIA from Kepler through at least Ampere"): "The GPU's Host Interface bridges the gap from CPU to GPU for the TMD. ### Inferences
- The RM default of 1024 µs vs. Bakita's measured ~2 ms per TSG slice on a GTX 1060 (proprietary driver, 2024 paper) are not necessarily contradictory (different GPU/driver, and RM can set `timesliceUs` per TSG via `NVA06C_CTRL_CMD_SET_TIMESLICE`); treat "≈1–2 ms" as the order of magnitude of compute time-slicing between contexts.
- Stream priorities map onto `QMD_GROUP_ID` (TMU priority lists) plus possibly TSG interleave level (`NVA06C_CTRL_CMD_SET_INTERLEAVE_LEVEL LOW/MEDIUM/HIGH`); the CUDA API exposes only a small integer range (two levels observed by Olmedo on Maxwell–Turing). The CWD's eviction rule explains why a high-priority stream can preempt dispatch of new CTAs but not running CTAs.
- The QMD v5 latch/`PRE_EXIT`/`HOLD_CTA_LAUNCH_UNTIL_PARENT_LATCH_ACQUIRE` fields are the hardware side of PDL (`cudaTriggerProgrammaticLaunchCompletion`/`cudaGridDependencySynchronize`), which is why PDL needs sm_90+.
- GSP-RM moved the *physical* RM (channel RAMFC setup, runlist submission, context-switch programming, clocks, interrupts) into firmware; `nvidia.ko` became a "kernel client" that marshals the same object API over RPC. Consequence: the open modules are open but the scheduler policy still lives in a closed blob.

### Gaps
- No public documentation of SKED/CWD task-slot counts, the CTA-to-SM assignment heuristic on Ada/Blackwell (Olmedo covers Maxwell–Turing), or how `OCCUPANCY_*` QMD fields influence the load balancer.
- GSP firmware internals (RISC-V code) are a blob; only the RPC surface and the nouveau-extracted firmware layout (`nouveau_firmware_layout.ods`) are public.

## Q4. Launch latency: numbers over the years, graphs vs streams, device launch, PDL, and knobs

### Takeaway
Null-kernel launch cost has moved from ~5 µs (Kepler–Volta era, Linux) to ~2.3–2.8 µs per launch on A100/H100/GH200 with CUDA 12.6/driver 560 (2025 measurement); CUDA Graphs cut per-kernel overhead from 3.8 µs (overlapped streams) to 3.4 µs on V100/CUDA 10.1, with ~400 µs instantiate cost; device-side graph launch is ">2x lower" latency than host launch; remaining gaps are "GPU-side activities associated with each kernel launch" (front-end QMD processing, CTA ramp-up/drain), which is what PDL overlaps.

### Cited Findings
- V100 / CUDA 10.1 (NVIDIA blog, 2019): empty-ish kernel "2.9μs" execution; "9.6μs per kernel (including overheads)" when synchronizing after each launch; "3.8μs (vs 2.9μs kernel execution time)" when launches overlap; graph of 20 kernels: "3.4μs"; "the time to create and instantiate the graph is relatively large at around 400μs"; "the first graph launch is around 33% slower that all subsequent launches" — [NVIDIA blog: Getting Started with CUDA Graphs](https://developer.nvidia.com/blog/cuda-graphs/)
- A100/H100/GH200, CUDA 12.6, driver 560.35.03 (arXiv 2504.11750, Apr 2025, "CudaLaunchAPI with nullKernel launch overhead and nullKernel duration"): launch overhead **2260.5 ns (AMD+A100), 2374.6 ns (Intel+H100), 2771.6 ns (GH200)**; nullKernel duration 1440.0 / 1235.2 / 1171.2 ns — [arXiv 2504.11750](https://arxiv.org/html/2504.11750)
- Device graph launch (CUDA 12.0): "the device-side launch latency better than 2x lower than that of the host launch"; "device launch latency stays almost constant regardless of how much parallelism is in the graph"; modes: fire-and-forget and tail launch — [NVIDIA blog: Device Graph Launch](https://developer.nvidia.com/blog/enabling-dynamic-control-flow-in-cuda-graphs-with-device-graph-launch/)
- llama.cpp + CUDA Graphs (NVIDIA blog 2024, profiled on A100, Llama 7B Q4): "The gaps seen between kernels within token evaluation are due to launch overheads"; "The highest achieved speedup is 1.2x for the smallest Llama 7B model on the fastest NVIDIA H100 GPUs"; after graphs, remaining overheads "are due to GPU-side activities associated with each kernel launch"; `cudaGraphExecUpdate` "is used to update the previously instantiated executable graph with much lower overhead" — [NVIDIA blog: Optimizing llama.cpp with CUDA Graphs](https://developer.nvidia.com/blog/optimizing-llama-cpp-ai-inference-with-cuda-graphs/)
- Spin/yield/blocking knobs: `CU_CTX_SCHED_SPIN / YIELD / BLOCKING_SYNC / AUTO` (runtime: `cudaDeviceScheduleSpin/Yield/BlockingSync/Auto` via `cudaSetDeviceFlags`); AUTO: yield "If the number of CUDA contexts ... exceeds the number of logical processors", otherwise spin — [CUDA Driver API: Primary Context](https://docs.nvidia.com/cuda/cuda-driver-api/group__CUDA__PRIMARY__CTX.html)
- Queue knobs: `CUDA_DEVICE_MAX_CONNECTIONS` 1–32 (default 8), `CUDA_DEVICE_MAX_COPY_CONNECTIONS`, `CUDA_LAUNCH_BLOCKING`; streams sharing one of the 8 channels create false dependencies (see Q3, RTAS 2024) — [CUDA env vars](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/environment-variables.html)
- Parameter path: kernel params go through constant memory; ≤4,096 B historically, 32,764 B since CUDA 12.1 on Volta+ — [NVIDIA blog](https://developer.nvidia.com/blog/cuda-12-1-supports-large-kernel-parameters)
- PDL overlap requires cc 9.0+ (Hopper, Blackwell); see Q3 — [CUDA PG 4.5](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/programmatic-dependent-launch.html)

### Inferences
- Where the ~2.5 µs go (from Q2/Q3 mechanics): CPU side — argument marshalling into a constant bank, QMD write, pushbuffer/GP entry write, USERD `GPPut` + doorbell MMIO (PCIe posted write); GPU side — PBDMA GP-entry fetch over PCIe (host memory), method decode, Compute FE → SKED → CWD task-slot insert, CTA ramp, and the completion semaphore release + CPU-visible write-back. CUDA Graphs remove the per-launch CPU work and let the driver batch QMDs/pushbuffer segments; device launch removes the PCIe round trip; PDL hides CTA ramp/drain. Note NVIDIA's own statement that after graphs the residual gaps are GPU-side.
- For the user's RTX 5060 Ti (PCIe 5.0 x8 on Blackwell GB206), expect per-launch floors in the ~2–3 µs class on Linux; this is an inference from the data-center numbers above, not a measurement.

### Gaps
- No peer-reviewed per-generation table (Kepler→Blackwell) of empty-kernel launch latency; a forum thread (Robert Crovella / njuffa, developer forums "Too much time for kernel launch latency", t/233645) reportedly states the floor fell from ~5 µs to ~2.5–3 µs with PCIe 5 hardware, but the page returned HTTP 403 through the proxy and could not be verified.
- No public measurement of GPU-side QMD→first-CTA latency in isolation (would need `nvdebug`/`gpu-microbench` style instrumentation or `%globaltimer` sampling in the first warp).

## Q5. What the open sources actually revealed (OGKM, open-gpu-doc, nouveau/envytools, NVK) and what remains closed

### Takeaway
Open today: the entire kernel-side RM object/ioctl API and class/control headers (OGKM), hardware register manuals for Host/PBDMA/runlists (open-gpu-doc), QMD field layouts for every generation Kepler→Blackwell (open-gpu-doc → Mesa), a working user-space compute dispatcher and QMD filler (NVK/NAK), the DRM submission uAPI (nouveau), and reverse-engineered scheduler behaviour (UNC papers, nvdebug). Closed: `libcuda.so` (module loader, PTX JIT, how QMDs/pushbuffers are built, graph compilation, lazy loading), GSP firmware internals, SKED/CWD microarchitecture beyond patents, and SASS encodings.

### Cited Findings
- OGKM content: kernel modules `nvidia.ko`, `nvidia-modeset.ko`, `nvidia-uvm.ko` sources; class headers (`src/common/sdk/nvidia/inc/class/`, 150+ `clc*.h` files incl. `clc9c0.h/clcbc0.h/clcdc0.h` compute and `clc86f.h/clc96f.h/clca6f.h` GPFIFO), control headers (`ctrl0080`, `ctrl2080`, `ctrla06c/f`, `ctrlc36f`, `ctrlc56f`), alloc params, RPC enums/structures (`src/nvidia/generated/g_rpc-structures.h`, `g_rpc-message-header.h`), MIG manager, fifo HALs per arch (`src/nvidia/src/kernel/gpu/fifo/arch/{turing,ampere,hopper,blackwell}`) — [OGKM tree](https://github.com/NVIDIA/open-gpu-kernel-modules)
- Not in OGKM: QMD headers (`*qmd.h`) — they come from `open-gpu-doc/classes/compute/` (RTAS 2023 footnote: "classes/compute/clc0c0qmd.h in open-gpu-doc"; Mesa's `update-from-open-gpu-doc.py`) — [RTAS 2023](https://www.cs.unc.edu/~jbakita/rtas23.pdf), [Mesa update script](https://gitlab.freedesktop.org/mesa/mesa/-/blob/main/src/nouveau/headers/update-from-open-gpu-doc.py)
- open-gpu-doc manuals (register-level prose): `manuals/<arch>/<chip>/dev_pbdma.ref.txt`, `dev_runlist.ref.txt`, `dev_fifo.ref.opensource`, `dev_ram.ref` (GP entry and RAMUSERD formats) — [open-gpu-doc manuals](https://nvidia.github.io/open-gpu-doc/manuals/ampere/ga100/dev_pbdma.ref.txt)
- Nouveau/NVK: Mesa `src/nouveau/{vulkan,compiler/nak,headers,winsys,mme,nil}`; NVK's `nv_push_*` generated method helpers (`nv_push_clc6c0.h` etc.) built from the same class headers by `class_parser.py`; NVK has a `cubin` directory (`src/nouveau/cubin`) — [Mesa src/nouveau](https://gitlab.freedesktop.org/mesa/mesa/-/tree/main/src/nouveau)
- Nouveau on Turing+ consumes NVIDIA's GSP firmware extracted from OGKM ("These files are used by the Nouveau device driver to load and communicate with the GSP firmware") — [OGKM README](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/main/README.md)
- envytools: FIFO/PFIFO docs are complete for pre-GF100 and partial for GF100+ (the GF100+ PFIFO page is mostly "write me"); the DMA-pusher and intro pages remain the best prose on method encoding — [envytools FIFO index](https://envytools.readthedocs.io/en/latest/hw/fifo/index.html)
- User-space driver components are identical across kernel flavours and are not part of the open release — [NVIDIA README kernel_open](https://us.download.nvidia.com/XFree86/Linux-x86_64/615.78.08/README/kernel_open.html); libsmctrl needed "an undocumented CUDA callback API" to reach the QMD before launch — [RTAS 2023](https://www.cs.unc.edu/~jbakita/rtas23.pdf)

### Inferences
- Practical reverse-engineering recipe for the user's RTX 5060 Ti (GB206, sm_120, `BLACKWELL_COMPUTE_B` class 0xCEC0 / QMD v5): (a) read `clcdc0qmd.h`/`clcec0qmd.h` and `nak/qmd.rs` for the descriptor; (b) read `clc86f.h`/`clca6f.h` for GPFIFO/semaphore methods; (c) use NVK (`NVK_DEBUG=push` / `nv_push_dump`) on nouveau to see real pushbuffers; (d) for the proprietary stack, intercept at the `cuLaunchKernelEx` boundary (CUPTI/`LD_PRELOAD`) or `strace` the `NV_ESC_RM_*` ioctls to see channel/USERD setup — the per-launch doorbell writes will not appear in `strace` because they are MMIO.
- Everything an optimiser needs to *reason* about launch cost (QMD size, constant-bank params, 8 channels, time-slices, CWD priority rules) is public; what is not public is the policy inside libcuda (when it batches, how it allocates channels to streams, how graphs are lowered).

### Gaps
- No open implementation exists of user-mode doorbell submission against `nvidia.ko` (NVK targets nouveau's DRM uAPI; an "nvkmd" backend for the NVIDIA RM is not in the Mesa tree as of this commit — only `nvkmd/nouveau`).
- SASS instruction encodings and `libcuda`'s PTX JIT remain closed (covered by the parallel SASS/binary-format tracks).
