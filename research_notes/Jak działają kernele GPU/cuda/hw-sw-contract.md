## KQ1. PTX ISA as the real public ISA: versions and what it exposes per generation; sm_120 vs sm_100

### Takeaway
PTX is the only ISA NVIDIA documents and guarantees (a "stable ISA that spans multiple GPU generations", translated by `ptxas`/driver to SASS). Since PTX 8.0/Hopper the interesting datapath features are *architecture-specific* (`sm_90a`, `sm_100a`, `sm_120a`) and since PTX 8.8 *family-specific* (`sm_100f`, `sm_120f`); the consumer Blackwell `sm_120` family gets TMA/mbarrier/clusters, `setmaxnreg`, `ldmatrix/stmatrix` b8 shapes, block-scaled `mma.sync` with FP4/FP6/FP8 — but **no `wgmma` (Hopper-only `sm_90a`), no `tcgen05`/TMEM (sm_100a/103a/110a and their families only), and only 100 KB shared memory per SM** vs 228 KB on `sm_100a`.

### Inferences
- For the user's RTX 5060 Ti the "Hopper/Blackwell-datacenter playbook" (warp-specialized producer/consumer with `wgmma` or `tcgen05` + TMEM, 2-SM `cta_group::2`, 228 KB smem) does **not** apply. The sm_120 playbook is Ampere-style `mma.sync` (now with FP8/FP6/FP4 block-scaled kinds), TMA (`cp.async.bulk.tensor`, but multicast is not recommended), mbarrier pipelines, clusters/DSMEM, `setmaxnreg`, `ldmatrix/stmatrix` with b8 shapes, 99 KB dynamic smem per block, 256-bit `ld.v8.b32`.
- Because PTX 8.7 is the first with `sm_120`, any toolchain that must emit native sm_120 code needs CUDA ≥ 12.8 (and `sm_120f` needs CUDA ≥ 12.9); PTX for `compute_90`/`compute_100` JIT-compiles forward onto sm_120 only if it uses no `a`-features (nvcc refuses `sm_90a` PTX on other targets by construction).
- The `a`/`f` split means the "contract" is now per-feature, not per-generation: e.g. `redux.sync.f32` is sm_100a/f only; a kernel author must consult Table 72/73 or the per-instruction Target ISA Notes, which is why CUTLASS has dozens of `CUTE_ARCH_*_ENABLED` macros rather than `__CUDA_ARCH__ >= X` checks.

### Gaps
- No official statement from NVIDIA on *why* sm_120 lacks `tcgen05`/TMEM other than the compute-capability tables; the whitepaper (Jan 2025) predates the RTX 5060 Ti (GB206) and contains no GB206/5060 Ti table (grep for "5060"/"GB206" in the extracted text returned nothing).
- The exact `tensormap.replace .swizzle_atomicity` restrictions "on sm_120a" are referenced by a cross-link whose target section I did not isolate in the text dump.

## KQ2. PTX vs SASS: what ptxas does and does not guarantee; inline PTX as the "assembly" of CUTLASS/FA3/DeepGEMM

### Takeaway
PTX is a virtual ISA with unlimited virtual registers and no scheduling or instruction-selection guarantees; `ptxas` ("the ptxas optimizing backend compiler") allocates physical registers, selects SASS opcodes and schedules. Production libraries therefore write performance-critical sequences as `asm volatile` **PTX** strings (CUTLASS/CuTe atoms, DeepGEMM, FA3) and let ptxas lower them; SASS is not a supported programming target (SASS RE is covered by another track).

### Cited Findings
- "High level language compilers for languages such as CUDA and C/C++ generate PTX instructions, which are optimized for and translated to native target-architecture instructions." "The ptxas optimizing backend compiler optimizes and assembles PTX source files, producing corresponding binary object files." — [PTX ISA §1.2, §2](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#introduction) (local lines 779–790, 1078)
- "Since PTX supports virtual registers, it is quite common for a compiler frontend to generate a large number of register names. … `.reg .b32 %r<100>;`" — [PTX ISA §5.4.6 Parameterized Variable Names](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#parameterized-variable-names)
- "In PTX, predicate registers are virtual and have .pred as the type specifier." Instructions have "an optional guard predicate … @{!}p". — [PTX ISA §9.3 Predicated Execution](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#predicated-execution)
- Performance-only directives/pragmas exist precisely because scheduling/regalloc is ptxas's: PTX 9.0 adds "pragma enable_smem_spilling", "pragma frequency … execution frequency of a basic block", "performance-tuning directives .abi_preserve and .abi_preserve_control"; PTX 9.3 adds "mma_throughput pragma"; PTX 8.3 "pragma used_bytes_mask … mask for used bytes for a load operation". CUDA 13.0 release notes: "Registers can spill to shared memory when opted in via enable_smem_spilling." — [PTX ISA §13.2/13.5/13.11](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#release-notes), [CUDA 13.0 Release Notes](https://docs.nvidia.com/cuda/archive/13.0.0/cuda-toolkit-release-notes/index.html)
- The Programming Guide says the Tensor Core feature set is exposed *only* through inline PTX: "The Tensor Core feature set is available within the CUDA compilation toolchain through inline PTX. It is strongly recommended that applications use this feature set through CUDA-X libraries such as cuDNN, cuBLAS, and cuFFT … or through CUTLASS". ## KQ3. Memory consistency model: scopes, orders, proxies, formal model, practical implications

### Takeaway
PTX's model (formalized in Lustig/Sahasrabuddhe/Giroux, ASPLOS 2019) is a scoped, weakly-ordered, non-DRF model: every *strong* op carries a scope (`.cta/.cluster/.gpu/.sys`; warp is **not** a scope) and a semantics (`.weak/.relaxed/.acquire/.release/.acq_rel/.sc`), synchronization is defined by release→acquire *patterns* plus barriers, and memory accessed through different *proxies* (generic vs async/TMA vs tensormap vs readonly) needs a proxy fence (`fence.proxy.async`). CUDA's `__syncthreads()` is `bar.sync` (CTA-scope sync), `__threadfence()` is a GPU-scope fence, and CUDA C++ atomics compile to the documented PTX ABI.

### Cited Findings
- Scopes (PTX §8.5): ".cta — The set of all threads executing in the same CTA"; ".cluster"; ".gpu — … all threads in the current program executing on the same compute device … This also includes other kernel grids invoked by the host program on the same compute device"; ".sys — … all compute devices, and all threads constituting the host program itself." "Note that the warp is not a scope; the CTA is the smallest collection of threads that qualifies as a scope in the memory consistency model." — [PTX ISA §8.5 Scope](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#scope)
- Proxies (§8.6): "A memory proxy, or a proxy is an abstract label applied to a method of memory access. … A proxy fence is required to synchronize memory operations across different proxies." Non-generic proxies: "textures and surface accesses, accesses to the same location via the same proxy using distinct virtual memory addresses, async-proxy and tensormap-proxy accesses by .async.bulk operations, fabric-proxy accesses by fabric operations, readonly-proxy accesses by ld.proxy::readonly operations." §8.6.1: strong modifications via generic/async/tensormap/fabric proxies "eventually become observable by strong accesses to the same location performed via a different proxy … if modification and access are: system-scope … or gpu-scope if the different proxies involved are … async-proxy, generic-proxy." — [PTX ISA §8.6 Proxies](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#proxies)
- Async proxy for TMA (§9.7.10.28.2): "The cp{.reduce}.async.bulk operations are performed in the asynchronous proxy (or async proxy). Accessing the same memory location across multiple proxies needs a cross-proxy fence. For the async proxy, fence.proxy.async should be used to synchronize memory between generic proxy and the async proxy. The completion of a cp{.reduce}.async.bulk operation is followed by an implicit generic-async proxy fence. So the result of the asynchronous operation is made visible to the generic proxy as soon as its completion is observed." — [PTX ISA §9.7.10.28.2 Async Proxy](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#async-proxy)
- Fence flavours (§9.7.15.4 `membar/fence`): ".sem = { .sc, .acq_rel, .acquire, .release }"; "fence.acq_rel is a light-weight fence that is sufficient for memory synchronization in most programs"; "fence.sc is a slower fence that can restore sequential consistency when used in sufficient places, at the cost of performance"; "If the optional .sem qualifier is absent, .acq_rel" is assumed; `.op_restrict = { .mbarrier_init }` and `.sync_restrict::shared::cta/::cluster` restrict the class of ops ordered (must use `.cluster` scope); proxy fences are "bi-directional": `fence.proxy.async::generic.acquire.sync_restrict::shared::cluster.cluster`. Target notes: "fence requires sm_70 or higher … fence.proxy requires sm_70 … .cluster scope qualifier requires sm_90 … fence.proxy.async requires sm_90 or higher." — [PTX ISA §9.7.15.4](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#parallel-synchronization-and-communication-instructions-membar-fence)
- Morally strong (§8.7): two ops are morally strong if "related in program order … or each operation is strong and specifies a scope that includes the thread executing the other operation", "Both operations are performed via the same proxy", and "If both are memory operations, then they overlap completely." Data race = conflicting ops "not related in causality order and … not morally strong." Mixed-size races void the axioms. — [PTX ISA §8.7](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#morally-strong-operations)
- Release/acquire patterns (§8.8): release pattern = `st.release`/`atom.release`/`mbarrier.arrive.release`, or `fence.release; st.relaxed`, or "a release or acquire-release memory fence followed in program order by an asynchronous operation that performs a strong write" (e.g. `fence.release; cp.async.bulk.global.shared.relaxed.sys.b128`), or `st.async.release.sys`. Acquire pattern = `ld.acquire`/`atom.acquire`/`mbarrier.test_wait.acquire`, or `ld.relaxed; fence.acquire`, or "first observing completion of an asynchronous operation … followed by an acquire memory fence": `cp.async.bulk…relaxed.sys… [dst],[M]; mbarrier.try_wait.relaxed p,[barrier]; @p fence.acquire;`. "red.add [M], 1; fence.acquire; is not an acquire pattern." — [PTX ISA §8.8](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#release-and-acquire-patterns)
- Synchronizes-with (§8.9.4): "A bar{.cta}.sync or bar{.cta}.red or bar{.cta}.arrive operation synchronizes with a bar{.cta}.sync or bar{.cta}.red operation executed on the same barrier. A barrier.cluster.arrive operation synchronizes with a barrier.cluster.wait operation." API synchronization: "Completion of a task enqueued in a CUDA stream synchronizes with the start of the following task in the same stream"; "Start of a CUDA kernel synchronizes with start of all threads in the kernel. End of all threads in a kernel synchronize with end of the kernel"; graph node completion synchronizes with dependents; **"the tensormap-proxy … is not acquired from generic-proxy at CUDA Kernel start and must therefore be acquired explicitly using fence.proxy.tensormap::generic.acquire when needed."** — [PTX ISA §8.9.4 Memory synchronization](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#memory-synchronization)
- Async ops are outside program order (§8.9.1.1): "Some PTX instructions (all variants of cp.async, cp.async.bulk, cp.reduce.async.bulk, wgmma.mma_async) perform operations that are asynchronous to the thread … ordered after prior instructions in the same thread (except in the case of wgmma.mma_async), but they are not part of the program order". "The implicit mbarrier complete-tx operation that is part of all variants of cp.async.bulk … is ordered only with respect to the memory operations performed by the same asynchronous instruction, and in particular it does not transitively establish ordering with respect to prior instructions from the issuing thread." — [PTX ISA §8.9.1.1](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#asynchronous-operations)
- Litmus "MP with red" (§8.11.1): with `st.release.gpu [flag]` in T1 and `red.sys.add [flag]; fence.acquire.gpu; ld.weak [x]` in T2, "It is possible to observe the outcome where R2 reads the value 0 from x and flag has the final value of 2 … Using the atom instruction instead of red forbids this outcome." — [PTX ISA §8.11](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#special-cases)
- The formal model: Lustig, Sahasrabuddhe, Giroux, "A Formal Analysis of the NVIDIA PTX Memory Consistency Model", ASPLOS 2019 (DOI 10.1145/3297858.3304043). Abstract: "the PTX memory model is weakly ordered but provides scoped synchronization primitives … unlike some competing GPU memory models, PTX does not require data race freedom … we adapt the English language specification from the public PTX documentation into a formal axiomatic model … derive … an OpenCL-like scoped C++ model and develop a mapping … onto PTX … use the Alloy relational modeling tool to empirically test the correctness of the mapping … compile the model and mapping into Coq and build a full machine-checked proof that the mapping is sound". PDF: https://d1qx31qr3h6wln.cloudfront.net/publications/ASPLOS_2019_PTXMemoryModel.pdf — [NVIDIA Research page](https://research.nvidia.com/publication/2019-04_formal-analysis-nvidia-ptx-memory-consistency-model)
- Official C++→PTX atomics ABI (Hopper Tuning Guide, "PTX Writer's Guide to Interoperability → Atomics ABI"): seq_cst fence `fence.sc.<scope>`; seq_cst load `fence.sc.<scope>; ld.relaxed.<scope>`; seq_cst store `fence.sc.<scope>; st.relaxed.<scope>`; seq_cst RMW `fence.sc.<scope>; atom.acquire.<scope>.<op>`; release store `st.release.<scope>` or `fence.release.<scope>; st.relaxed.<scope>`; acquire load `ld.acquire.<scope>` or `ld.relaxed.<scope>; fence.acquire.<scope>`; acq_rel RMW `atom.acq_rel.<scope>.<op>`; relaxed `ld/st/atom.relaxed.<scope>`. "Memory order parameters are monotonic, so strengthening one is valid"; mappings "may be mixed within one binary." — [Hopper Tuning Guide: Atomics ABI](https://docs.nvidia.com/cuda/archive/13.0.0/hopper-tuning-guide/ptx-writers-guide-to-interoperability/atomic-abi.html)
- CUDA C++ view: "The CUDA programming model assumes a weakly ordered memory model." `__threadfence_block()`: "All writes to all memory made by the calling thread before the call … are observed by all threads in the calling thread's block as occurring before all writes … after the call"; `__threadfence()`: "No writes to all memory made by the calling thread after the call to __threadfence() are observed by any thread in the device as occurring before any write to all memory made by the calling thread before the call"; `__threadfence_system()` extends to "host threads, and all threads in peer devices." `__syncthreads_count/and/or` "evaluate the predicate for all non-exited threads in the block." — [CUDA Programming Guide §5.4 C/C++ Language Extensions](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/cpp-language-extensions.html)
- CUDA C++ thread scopes: `cuda::thread_scope_system/device/block/thread`; "the cost to synchronize threads grows as threads are further apart"; a `thread_scope_system` atomic on managed memory is atomic only if `concurrentManagedAccess` is 1, on mapped memory only if `hostNativeAtomicSupported` is 1 (or naturally aligned 1/2/4/8/16-byte load/store); `thread_scope_device` is restricted to "the same memory synchronization domain". — [CUDA Programming Guide §5.7 CUDA C++ Memory Model](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/cuda-cpp-memory-model.html)
- Forward progress (Execution Model appendix): "If the host implementation provides concurrent forward progress [intro.progress.7], then CUDA C++ provides parallel forward progress [intro.progress.9] for device threads" (i.e. a not-yet-started block is not guaranteed to ever start while others spin). "A simple but not sufficient method to test a program for CUDA API Forward Progress conformance is to run them with following environment variables set: CUDA_DEVICE_MAX_CONNECTIONS=1 CUDA_LAUNCH_BLOCKING=1, and then check that the program still terminates." — [CUDA Programming Guide §5.8 CUDA C++ Execution Model](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/cuda-cpp-execution-model.html)
- TMEM has its own sub-model: PTX §9.7.18.6 "Memory Consistency Model for 5th generation of TensorCore operations" (tcgen05.fence::before_thread_sync / ::after_thread_sync); sm_100-only, listed for completeness. — [PTX ISA §9.7.18.6](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#tensorcore-5th-generation-instructions-memory-consistency-model)
- CUTLASS implements the generic↔async proxy protocol in `include/cutlass/arch/barrier.h` (`mbarrier.arrive.expect_tx`, `mbarrier.try_wait`), `include/cute/arch/cluster_sm90.hpp` (`fence.proxy.async`, `elect.sync`) — the canonical "producer issues TMA with `mbarrier::complete_tx::bytes`, consumer `try_wait` then reads smem; smem written by generic stores must be `fence.proxy.async`-published before a TMA store reads it." — [cutlass/include/cutlass/arch/barrier.h](https://github.com/NVIDIA/cutlass/blob/main/include/cutlass/arch/barrier.h)

### Inferences
- `__syncthreads()` = `bar.sync 0` gives CTA-scope synchronization *for the generic proxy only*: it does not order TMA/`cp.async.bulk` traffic (async proxy) — you need the mbarrier completion (`try_wait`) for TMA loads and `fence.proxy.async.shared::cta` before a TMA store (`cp.async.bulk.tensor.global.shared::cta`) reads data written with ordinary `st.shared`. This is the single most common correctness bug class in hand-written Hopper/Blackwell kernels.
- `__threadfence()` is needed only when threads in *different* CTAs communicate through global memory with relaxed/volatile accesses (classic "last block" reductions, flags); within a CTA `bar.sync` already forms a release/acquire pair. Prefer `cuda::atomic_ref<T, cuda::thread_scope_device>` so the compiler emits the ABI sequences above instead of `volatile` + `__threadfence`.
- Because warp is not a scope, intra-warp communication through shared memory still needs `__syncwarp()` (which is a `bar.warp.sync`, i.e. CTA-level semantic restricted to the mask) — relying on lockstep is undefined under independent thread scheduling.

- The exact PTX lowering of `__syncthreads()`/`__syncwarp()` (`bar.sync` / `bar.warp.sync`) was not re-verified from compiler output in this track (it is standard, but the SASS/PTX RE track should confirm).

## KQ4. Runtime/driver features that affect performance and how they work

### Takeaway
Streams map onto a small pool of hardware work queues ("connections", default 8, max 32 — `CUDA_DEVICE_MAX_CONNECTIONS`), so >8 streams can serialize falsely; CUDA Graphs move per-kernel launch setup into a one-time instantiation; PDL (`griddepcontrol`) lets a dependent kernel's prologue overlap the previous kernel's tail; occupancy is computed by an open-source header (`cuda_occupancy.h`) from cubin attributes (regs/thread rounded to 256-register warp granularity across 4 SM sub-partitions, smem rounded to 128 B, block/warp caps per CC); >48 KB dynamic smem needs `cudaFuncSetAttribute(…MaxDynamicSharedMemorySize)`; L2 set-aside/access-policy windows, `cudaMallocAsync` pools with release threshold, and managed memory page-fault migration (4 KiB x86 pages, software coherence on a discrete RTX card) are the other knobs; clocks must be locked for repeatable benchmarks but GeForce `nvidia-smi -lgc` support is limited.

### Cited Findings
**Streams, hardware queues, events**
- "CUDA_DEVICE_MAX_CONNECTIONS — The environment variable controls the number of concurrent compute and copy engine connections (work queues), setting both to the specified value. If independent GPU tasks, namely kernels or copy operations launched from different CUDA streams, map to the same work queue, a false dependency is created which can lead to GPU work serialization … it is recommended that the work queue count … be greater than or equal to the number of active CUDA streams per context. Possible Values: 1 to 32 connections, default is 8 (assumes no MPS)". `CUDA_DEVICE_MAX_COPY_CONNECTIONS` (CC ≥ 8.0) overrides the copy part, same 1–32/default 8. — [CUDA Programming Guide §5.2.3.2](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/environment-variables.html)

**CUDA Graphs**
- "when you place a kernel into a stream, the host driver performs a sequence of operations in preparation for the execution of the kernel on the GPU. These operations … are an overhead cost which must be paid for each kernel that is issued. … By creating a CUDA graph that encompasses a workflow that will be launched many times, these overhead costs can be paid once for the entire graph during instantiation, and the graph itself can then be launched repeatedly with very little overhead." "Work submission using graphs is separated into three distinct stages: definition, instantiation, and execution. Instantiation takes a snapshot of the graph template, validates it, and performs much of the setup and initialization of work with the aim of minimizing what needs to be done at launch." — [CUDA Programming Guide §4.2 CUDA Graphs](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cuda-graphs.html)
- Updates: "Major changes to graph structure (such as topology or node types) require re-instantiation because topology-related optimizations must be re-applied"; `cudaGraphExecUpdate()` needs a "topologically identical" graph with consistently ordered sink nodes; individual node update "eliminates the overhead of instantiation"; `cudaGraphNodeSetEnabled()` toggles kernel/memset/memcpy nodes; "A cudaGraphExec_t cannot run concurrently with itself. A launch of a cudaGraphExec_t will be ordered after previous launches of the same executable graph"; "cudaGraph_t objects are not thread-safe"; device graphs launch via `cudaGraphLaunch()` from device code; conditional nodes exist (node parameters of conditionals cannot be updated). — [same](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cuda-graphs.html)
- Memory model hook: "Start of a CUDA graph synchronizes with start of all source nodes … Completion of a graph node synchronizes with start of all nodes with a direct dependency." — [PTX ISA §8.9.4](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#memory-synchronization)

**Programmatic Dependent Launch**
- "allows for a dependent secondary kernel to launch before the primary kernel it depends on in the same CUDA stream has finished executing. Available starting with devices of compute capability 9.0". Primary calls `cudaTriggerProgrammaticLaunchCompletion()`; secondary calls `cudaGridDependencySynchronize()` and is launched with `cudaLaunchKernelEx` + `cudaLaunchAttributeProgrammaticStreamSerialization` (`programmaticStreamSerializationAllowed = 1`). "The CUDA driver can launch the secondary kernel when all primary thread blocks have launched and executed cudaTriggerProgrammaticLaunchCompletion. If the primary kernel doesn't execute the trigger, it implicitly occurs after all thread blocks in the primary kernel exit. In either case, the secondary thread blocks might launch before data written by the primary kernel is visible. As such … it must always use cudaGridDependencySynchronize". "this behavior is opportunistic and not guaranteed to lead to concurrent kernel execution. Reliance on concurrent execution in this manner is unsafe and can lead to deadlock." Graph form: edge `from_port = cudaGraphKernelNodePortProgrammatic` (or `…PortLaunchCompletion`), `cudaLaunchAttributeProgrammaticEvent` with `triggerAtBlockStart`. — [CUDA Programming Guide §4.5 PDL](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/programmatic-dependent-launch.html)

- Shared memory limit (`cudaOccMaxBlocksPerSMSmemLimit`): `staticSmemSize = sharedSizeBytes + reservedSharedMemPerBlock`; `smemAllocatedPerCTA = roundUp(static + dynamic, 128)` (`cudaOccSMemAllocationGranularity` = 128 B for CC 8–12, 256 B for 3–7); `maxBlocks = sharedMemPerMultiprocessor / smemAllocatedPerCTA` where the SM's smem is the carveout preference (`cudaOccSMemPreferenceVoltaPlus`: `carveoutConfig` percent of `sharedMemPerMultiprocessor`, or derived from `cacheConfig` PREFER_L1/SHARED/EQUAL, then aligned up via `cudaOccAlignUpShmemSizeVoltaPlus` to the legal config sizes). **L2 set-aside / access policy**
- "Devices of compute capability 8.0 and above have the capability to influence persistence of data in the L2 cache"; `cudaDeviceSetLimit(cudaLimitPersistingL2CacheSize, min(prop.l2CacheSize*0.75, prop.persistingL2CacheMaxSize))`; per-stream/per-graph-node `accessPolicyWindow {base_ptr, num_bytes (< accessPolicyMaxWindowSize), hitRatio, hitProp=cudaAccessPropertyPersisting, missProp=cudaAccessPropertyStreaming}`; "With a hitRatio of 0.5, the hardware will select, at random, 16KB of the 32KB window"; `cudaAccessPropertyNormal` resets; disabled under MIG; under MPS only via `CUDA_DEVICE_DEFAULT_PERSISTING_L2_CACHE_PERCENTAGE_LIMIT`. — [CUDA Programming Guide §4.14 L2 Cache Control](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/l2-cache-control.html)

**Stream-ordered allocator**
- "When set up with an appropriate release threshold, the caching behavior allows the allocator to avoid expensive calls into the OS"; "The release threshold is the amount of memory in bytes a pool should hold onto before trying to release memory back to the OS. When more than the release threshold bytes of memory are held by the memory pool, the allocator will try to release memory back to the OS on the next call to stream, event or device synchronize. Setting the release threshold to UINT64_MAX will prevent the driver from attempting to shrink the pool after every synchronization." (`cudaMemPoolSetAttribute(memPool, cudaMemPoolAttrReleaseThreshold, &setVal)`); reuse policies `cudaMemPoolReuseFollowEventDependencies/AllowOpportunistic/AllowInternalDependencies`; CUDA 13.0: "cuMemCreate and cudaMallocAsync now accept host locations via CU_MEM_LOCATION_TYPE_HOST". — [CUDA Programming Guide §4.3](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/stream-ordered-memory-allocation.html), [CUDA 13.0 RN](https://docs.nvidia.com/cuda/archive/13.0.0/cuda-toolkit-release-notes/index.html)

**Unified memory / page migration**
- Support classes: "Full support for explicit managed memory allocations / all allocations with software coherence / all allocations with hardware coherence / Limited unified memory support". "Linux HMM requires Linux kernel version 6.1.24+, 6.2.11+ or 6.3+, devices with compute capability 7.5 or higher and a CUDA driver version 535+ installed with Open Kernel Modules." "Systems with separate page tables for CPUs and GPUs are referred to as software-coherent" (a discrete RTX card on x86 is this class). "Currently, all x86_64 CPUs use a default physical page size of 4KiB." "memory migration is generally more expensive with larger page sizes … because we typically migrate full memory pages." "accesses from a software coherent GPU will have more page faults and memory migration"; "by default accessing software coherent memory requires a fault and migration of data"; "On software-coherent systems, atomic accesses to unified memory may incur page faults which can lead to significant latencies." Hints: `cudaMemPrefetchAsync`, `cudaMemAdvise(…, cudaMemAdviseSetPreferredLocation/SetAccessedBy/SetReadMostly)`; CUDA 13.0 adds `cuMemDiscardBatchAsync`, `cuMemDiscardAndPrefetchBatchAsync`. — [CUDA Programming Guide §4.1 Unified Memory](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/unified-memory.html)

**Clocks and power**

- RTX 5060 Ti TGP 180 W (vendor/OEM pages; the official whitepaper has no 5060 Ti table). — [Corsair explainer](https://www.corsair.com/br/zh/explorer/gamer/gaming-pcs/rtx-5060-and-5060-ti-everything-you-need-to-know/) — secondary source; verify on the card with `nvidia-smi -q -d POWER` ("Min Power Limit"/"Max Power Limit").

### Inferences
- For llama.cpp-style inference (many small kernels per token) on the 5060 Ti the three runtime levers with the largest expected effect are (1) CUDA Graphs (llama.cpp already captures per-token graphs; the PG rationale is exactly the "short kernel, launch overhead dominates" case), (2) keeping streams ≤ 8 or raising `CUDA_DEVICE_MAX_CONNECTIONS`, and (3) locked clocks when benchmarking kernels (`sudo nvidia-smi -pm 1; nvidia-smi -lgc <base>,<base>`), accepting that GeForce may ignore locks above boost.
- Occupancy on sm_120 is capped at 48 warps/SM and 24 blocks/SM with 100 KB smem; a 256-thread block using > 50 KB smem already limits the SM to 1 block (8 warps = 17 % occupancy) — the occupancy header's `roundUp(regs*32, 256)` and `roundUp(smem, 128)` are the exact formulas to reproduce `cudaOccupancyMaxActiveBlocksPerMultiprocessor` offline from `cuobjdump --dump-resource-usage` numbers.
- Managed memory on a discrete x86 card is page-fault/migration based (software coherent); for a 16 GB card running a 27B-parameter model, `cudaMallocManaged` oversubscription will thrash at 4 KiB granularity — explicit `cudaMalloc` + host pinned staging (what ggml-cuda does) is the right contract.

### Gaps
- NVIDIA does not document the exact mapping stream→work queue (round-robin, hashing) nor the number of hardware queues on GB206; only the env var and the "false dependency" warning are official.
- Per-kernel launch overhead numbers (µs) are not given in the current Programming Guide; NVIDIA blog numbers were not fetched in this track.
- Minimum `nvidia-smi -pl` and supported `-lgc` range for the RTX 5060 Ti are not published; must be read from the device.

## KQ5. Where this is documented; what CUDA 13 changed; the compute-capability 12.0 entry

### Takeaway

### Inferences
- The 128 KB unified L1/smem per SM in the whitepaper and the 100 KB max smem config in the PG are consistent: sm_120 keeps the GA10x/AD10x cache structure (128 KB, max 100 KB smem), which is why the PTX static-smem cap for `sm_120a` is 100 KB while `sm_100a` gets 228 KB of a 256 KB cache.
- For reproducible builds targeting the user's two cards, the minimal toolchain is CUDA ≥ 12.8 (sm_120a) and preferably 13.x (sm_120f, PTX 9.x); llama.cpp's CMake `CMAKE_CUDA_ARCHITECTURES=120` (or `120a`) must be set explicitly because `-arch=all-major` would otherwise JIT from older PTX.
