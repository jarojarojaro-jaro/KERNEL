## KQ1. libcuda.so / libcudart internals: what is observable, interception projects, ZLUDA, cuda-gdb

### Takeaway
The closed user-space driver (`libcuda.so`) is observable at three layers: (1) the ioctl boundary to `/dev/nvidiactl`, `/dev/nvidia0` and `/dev/nvidia-uvm`, whose escape numbers and parameter structs are now public in NVIDIA's open kernel modules; (2) the exported driver API plus an undocumented "export table" (`cuGetExportTable`, GUID-keyed function tables) that cudart/cuBLAS use and that ZLUDA has reverse engineered function-by-function; (3) the loaded SASS, which NVBit (NVIDIA research) and cuda-gdb expose at run time. ZLUDA is the most complete public re-implementation of the driver API (in Rust, PTX -> LLVM -> AMDGPU ELF -> `hipModuleLoadData`), and its `zluda_trace` tool is the best available logger of what a CUDA application actually asks the driver to do, including the undocumented calls.

### Inferences
- The ioctl layer is fully nameable now (open kernel modules), so an `strace -e ioctl` of a CUDA program can be decoded entirely from `nv_escape.h` + `nvos.h` + `uvm_ioctl.h`; what remains closed is the RM *control command* semantics (`NV_ESC_RM_CONTROL` cmd IDs, in `ctrl*.h` headers of the same repo) and the pushbuffer/channel contents libcuda writes to the GPU, which is where kernel launch really happens (not through ioctls per launch).
- ZLUDA's table of GUID tables plus the `INTEGRITY_CHECK` hash is the strongest public evidence that cudart <-> libcuda is a private protocol: cudart does not just call documented `cu*` functions, it obtains module handles from fatbins via `get_module_from_cubin*` and runs an anti-tamper check. Any CUDA re-implementation (or interposer that replaces libcuda) must reproduce these.
- For performance work the practical consequence is: interposing `cuLaunchKernel`/`cuLaunchKernelEx` (LD_PRELOAD or `LD_AUDIT`) captures every launch configuration (grid, block, smem, attributes) even from closed libraries; `zluda_trace` is a ready-made tool for this and also dumps the exact PTX/cubin each library loads.

### Gaps
- The two NVIDIA-forum threads on `cuGetExportTable` return HTTP 403 through the proxy; their content is known only from search snippets.
- No public document describes the full set of export-table GUIDs beyond what ZLUDA implements; ZLUDA's comments themselves say some entries are unknown (`get_unknown_buffer1/2`, `device_get_something`).
- cuda-gdb documentation does not state Blackwell `sm_120`-specific support in the sections read; it says debugging supports "all CUDA-capable GPUs supported by the current CUDA release".

## KQ2. ptxas as a black box: documented options, inferred behaviour, known bad-code cases and workarounds

### Takeaway
ptxas is documented only through its command-line options; its scheduler, register allocator and control-code (stall/yield/reuse) decisions are opaque and change between CUDA versions (the driver even carries its own newer ptxas for JIT). The best-documented workaround cases are DeepGEMM's binary patching of FFMA yield/reuse bits (10%+ on FP8 GEMM, made unnecessary by NVCC 12.9), `setmaxnreg`-based warp-specialised register budgets (CUTLASS/FA3), and `__launch_bounds__`/`-maxrregcount` register caps whose main side-effect is spilling.

### Cited Findings

**Documented surface (nvcc docs, read 2026-10-17; CUDA 13.x)**

**DeepGEMM FFMA interleaving (the canonical "fix ptxas output after the fact" case)**
- Old README (commit 340d9880, 2025-04): "We observe a performance improvement in the CUTLASS FP8 kernel between NVCC 12.2 and 12.3. By comparing the compiled SASS, we discover that one bit in a series of `FADD` instructions is flipped in an interleaving pattern. After referencing some open-source CUDA assembler implementations, we identified that this bit controls `yield` ... (just a guess ...). ... we develop a similar script to modify the `FFMA` instructions in the compiled binary. Besides simply modifying the `yield` bit, we also flip the `reuse` bit (registers cannot be reused if the warp is yielded). This adjustment improves performance (10%+ in some cases) for fine-grained scaling FP8 GEMMs by creating more opportunities to overlap MMA instructions with promotion `FFMA` instructions." - The script `deep_gemm/jit/interleave_ffma.py` (same commit): runs `cuobjdump -sass <so>`, collects runs of >= 16 consecutive FFMA lines per `Function :`, reads the 128-bit encoding from the `/* 0x... */` comments, tests the reuse flag as `(high_hex & 0x0800000000000000) != 0`, and for alternating instructions does `high_hex ^= 0x0800200000000000` (clears reuse, sets yield), then patches the `.so` in place through `mmap` after locating the byte pattern — [interleave_ffma.py @ 340d988](https://raw.githubusercontent.com/deepseek-ai/DeepGEMM/340d9880f4a418d943d34260d20a79f41f4c0526/deep_gemm/jit/interleave_ffma.py)

**setmaxnreg (register re-budgeting between warpgroups)**
- PTX ISA 9.4: "Operand imm-reg-count ... must be in the range 24 to 256 (both inclusive) and must be a multiple of 8"; "The same setmaxnreg instruction must be executed by all warps in a warpgroup"; "setmaxnreg.inc instruction blocks the execution until enough registers are available in the CTA's register pool"; "requires that the kernel has been launched with a valid value of maximum number of per-thread registers specified via the appropriate ... compile-time option or the appropriate performance tuning directive. - CCCL lists `setmaxnreg.inc.sync.aligned.u32 // PTX ISA 80, SM_90a, SM_100a` — [CCCL ptx docs](https://nvidia.github.io/cccl/unstable/libcudacxx/ptx/instructions/setmaxnreg.html)
- FlashAttention-3 SM90 backward: `LoadRegisterRequirement = NumMmaWarpGroups == 2 ? 24 : 32; MmaRegisterRequirement = NumMmaWarpGroups == 2 ? 240 : 160` — [flash_bwd_kernel_sm90.h](https://huggingface.co/kernels-community/vllm-flash-attn3/blob/refs%2Fpr%2F6/flash-attn/flash_bwd_kernel_sm90.h)

### Inferences
- The only robust knobs on ptxas are: `-O{0..3}`, `-maxrregcount` / `__launch_bounds__` / `.maxnreg`, `-dlcm/-dscm` cache defaults, `--Ofast-compile`, and (indirectly) source structure and inline PTX. Everything else (scheduling, control codes, dual-issue pairing, bank-conflict-aware register assignment) is decided internally and must be *measured* via `cuobjdump -sass` + profiler per toolkit version.
- The DeepGEMM episode shows the two-level nature of the problem: PTX is only a contract; the bits that decide warp-scheduler behaviour (`yield`, `reuse`, stall counts) are chosen by ptxas, and when ptxas's heuristic is wrong the fix is either a newer ptxas (12.9) or binary patching. For the user's RTX 5060 Ti this means: always record `nvcc --version` / driver version next to any benchmark.
- `setmaxnreg` interacts with ptxas: the compile-time cap (`-maxrregcount`/`__launch_bounds__`) is what makes the hardware register pool reallocatable; without it the instruction "may have no effect". This is why CUTLASS Hopper kernels combine `__launch_bounds__` with explicit producer/consumer budgets.

### Gaps
- No primary source documents ptxas's internal pass list, control-code heuristics or dual-issue policy; all such knowledge is derived from SASS diffs (covered by the SASS track).
- I could not obtain the DeepGEMM PR #112 discussion itself (GitHub page summary does not mention FFMA); the "NVCC 12.9 does it automatically" claim rests on the DeepGEMM README.
- No systematic, citable study of ptxas version-to-version performance regressions was found beyond anecdotal forum posts.

## KQ3. cuBLAS / cuBLASLt / cuDNN / TensorRT internals: heuristics, kernel naming, logging, what profiling revealed

### Takeaway
cuBLASLt exposes its heuristic model almost completely through public attributes (tile ID, stages, split-K count, reduction scheme, CTA swizzling, inner shape, cluster shape, workspace limit) and a documented logging facility (`CUBLASLT_LOG_LEVEL=5`, `CUBLASLT_LOG_MASK`), while the shape -> kernel mapping itself and the kernel names are explicitly undocumented. cuDNN's graph API uses NVRTC-style runtime fusion engines flagged by `CUDNN_BEHAVIOR_NOTE_RUNTIME_COMPILATION`, with logging via `CUDNN_LOGLEVEL_DBG`/`CUDNN_LOGDEST_DBG`; TensorRT picks "tactics" by on-device timing and stores them in a serialisable timing cache. Profiling cuBLAS kernels has shown they are built from CUTLASS-style async pipelines (`LDGSTS`, `HMMA.16816.F32`, `DEPBAR`).

### Cited Findings

**cuBLASLt logging and heuristics (cuBLAS docs for CUDA 13.x, fetched 2026-10-17)**

- `CUDNN_LOGLEVEL_DBG` 0..3 (0 nothing, 1 errors, 2 + warnings, 3 + info after each public API call; out-of-range clipped); `CUDNN_LOGDEST_DBG` = `NULL` (off), `stdout`, `stderr` or filename (existing file overwritten); "these environmental variables are only checked once at the initialization"; legacy `CUDNN_LOGERR_DBG`/`CUDNN_LOGWARN_DBG`/`CUDNN_LOGINFO_DBG` deprecated in v9; API override via `cudnnSetCallback()`; `cudnnGetLastErrorString()` since 9.0; log entries include parameter values, device pointers, PID, TID, handle, stream, timestamps — [cuDNN troubleshooting](https://docs.nvidia.com/deeplearning/cudnn/latest/reference/troubleshooting.html)

- "The default behavior of TensorRT's optimizer is to choose the algorithms that globally minimize the execution time of the engine. ### Inferences
- Decoding a cuBLAS kernel name such as `sm90_xmma_gemm_f16f16_f16f32_f32_tn_n_tilesize128x128x64_warpgroupsize1x1x1_execute_segment_k_off_kernel__5x_cublas` is *inference only* (no NVIDIA source): `sm90` = target arch; `xmma` = NVIDIA's internal tensor-core GEMM framework (the name also appears in TensorRT kernels); `f16f16_f16f32_f32` = A/B types, C/compute types, output; `tn_n` = transpose modes (A^T, B) and layout; `tilesize128x128x64` = CTA tile M x N x K, i.e. what `CUBLASLT_ALGO_CONFIG_TILE_ID` selects; `warpgroupsize1x1x1` = warpgroup arrangement / cluster-like shape (`CUBLASLT_ALGO_CONFIG_CLUSTER_SHAPE_ID`); `execute_segment_k_off` = segment-K/split-K variant disabled (`SPLITK_NUM = 1`); `__5x_cublas` = internal build tag. The reliable way to recover the same information is `CUBLASLT_LOG_LEVEL=5` (prints the chosen algo's attributes) or `cublasLtMatmulAlgoGetHeuristic` + `cublasLtMatmulAlgoConfigGetAttribute`.
- For a llama.cpp user: ggml-cuda only falls into cuBLAS for some shapes (its own MMQ/MMVQ kernels otherwise); the cuBLASLt log level 2/5 is the cheapest way to see which GEMMs were delegated and with what tile/split-K, before deciding whether a custom kernel can beat them.

- Whether cuDNN's runtime fusion engines use NVRTC specifically is not stated in the docs read; the docs only say kernels are generated "at runtime" (`CUDNN_BEHAVIOR_NOTE_RUNTIME_COMPILATION`).
- No source maps `cublasLtMatmulTile_t` enum values to the `tilesize...` substrings in kernel names; treat the decoding above as inference.
- No public blog that systematically profiles cuBLAS split-K / swizzle / L2 choices was found; the ACCU article is the closest primary material.

## KQ4. Simulators and models built from reverse engineering: GPGPU-Sim, Accel-Sim (NVBit SASS traces), what they encode and how accurate they are

### Takeaway
Accel-Sim turns NVBit SASS traces of real binaries (including closed libraries) into cycle-level simulation on a GPGPU-Sim 4 core model; its configs encode explicit assumptions about scheduler policy (`lrr` loose round-robin, 4 schedulers per SM, 1 issue per warp per cycle), cache geometry/latency (L1 39-41 cycles, smem 29, L2 ROP 187-237) and functional-unit latencies (SFU 23, tensor 12, GMMA up to 128 cycles), validated against hardware counters (ISCA 2020: cycle error reduced by 79 percentage points over 1,945 kernels). Tested configs exist up to H100/H200 but not for Ada or Blackwell GeForce.

### Cited Findings
- Accel-Sim paper (ISCA 2020, Khairy, Shen, Rogers): "three new mechanisms ... decreases cycle error 79 percentage points, over a wide range of 80 workloads, consisting of 1,945 kernel instances"; trace generation "built using the NVBit binary instrumentation tool, produces machine ISA instruction traces from any CUDA binary, which covers closed-source libraries like cuDNN"; trace-driven SASS "increases the accuracy of the simulator over executing the virtual ISA" (PTX) — [khairy.isca2020.pdf](https://engineering.purdue.edu/tgrogers/papers/khairy.isca2020.pdf); mirror abstract adds memory-counter error reduced "by as much as 66x" and execution-time error "by 2.5x" (third-party mirror, unverified) — [academia.edu mirror](https://www.academia.edu/104596309/Accel_Sim_An_Extensible_Simulation_Framework_for_Validated_GPU_Modeling)
- Tracer usage: `./install_nvbit.sh && ./make`; `LD_PRELOAD=./tracer_tool/tracer_tool.so ./app`; `./tracer_tool/traces-processing/post-traces-processing ./traces/kernelslist` -> `.traceg` + `kernelslist.g`; env `DYNAMIC_KERNEL_RANGE="5-8@kernel_a.*,kernel_b.*"`, `ACTIVE_FROM_START=0` (with `cudaProfilerStart/Stop`), `TRACE_LINEINFO=1` (needs `-lineinfo`). - The tracer also records `cluster_id_x/y/z`, `cluster_cta_id_*`, `cluster_rank`, `sm_id` per thread block (Hopper clusters) — local `accelsim/util/tracer_nvbit/tracer_tool/tracer_tool.cu` lines 1173-1362
- Tested configs (accel-sim @ d930ad6d, 2026-08-26): `SM3_KEPLER_TITAN, SM6_TITANX, SM75_RTX2060, SM75_RTX2060_S, SM7_GV100, SM7_QV100, SM7_TITANV, SM80_A100, SM86_RTX3070, SM90_H100, SM90_H200` — local `accelsim/gpu-simulator/configs/tested-cfgs/`

- NVBit internals (MICRO 2019): instrumentation works by replacing an instruction with a jump to a per-instruction trampoline that (1) saves "only the minimum amount of general purpose registers" plus condition codes/predicates, (2) passes arguments, (3) calls the user device function, (4) restores, (5) executes the "relocated" original instruction (fixing relative branch offsets), (6) jumps back; a HAL knows encodings ("Kepler, Maxwell, and Pascal have 64-bit-wide encodings, while Volta has 128-bit-wide encodings") and ABI save/restore sets (incl. "convergence barrier state in Volta"); overhead on TITAN V: full instruction-count instrumentation "36.4x slower than native", sampling "2.3x", worst case "112x" — [NVBit paper](https://github.com/NVlabs/NVBit/releases/download/v1.0/MICRO_19_NVBit.pdf)

### Inferences
- The Accel-Sim config files are, in effect, a public, machine-readable statement of what the community believes about NVIDIA's microarchitecture (scheduler = loose round-robin per sub-core, single issue per warp, L1 ~40 cycles, smem ~29, L2 ~190-240 cycles, tensor 12 cycles, GMMA 128). They are calibrated to counters, not derived from documentation, so they are useful priors but not ground truth; the microbenchmark track measures the same quantities directly.
- There is no tested config for Ada (`sm_89`) or Blackwell GeForce (`sm_120`), and NVBit 1.7 supports CC <= 12.1; so for the RTX 5060 Ti traces can be collected but a validated simulator model would have to be derived from the H100/RTX3070 configs by the user.
- MGPUSim (AMD) is out of this track's NVIDIA scope and was not researched here.

## KQ5. Undocumented / semi-documented features and their performance use: L2 persistence, shared-memory carveout, setmaxnreg, Hopper/Blackwell cluster features, green contexts, what sm_120 lacks

### Takeaway
Most "secret" features are in fact documented in the CUDA Programming Guide and PTX ISA but scattered: L2 set-aside (CC 8.0+), opt-in shared memory up to 227 KB (Hopper) but only 99 KB on CC 12.x, cluster launch control (CC 10.0 work stealing), green contexts (SM partitioning, 8-SM granularity on CC 9.0), `setmaxnreg`. The programming guide lists Thread Block Clusters / DSMEM / TMA as supported on CC 12.x, but CUTLASS states GeForce Blackwell has no multicast so clusters are fixed to 1x1x1, and PTX restricts `tcgen05`/Tensor Memory and 2-SM MMA to `sm_100a/sm_103a/sm_110a` families; `sm_120a` gets block-scaled `mma.sync` (mxf4/nvf4/f8f6f4) instead.

### Cited Findings

**L2 persistence (CUDA Programming Guide v13.4.2, §4.14 L2 Cache Control)**
- "Devices of compute capability 8.0 and above have the capability to influence persistence of data in the L2 cache"; runtime API since CUDA 11.0, `cuda::annotated_ptr` since 11.5; set-aside: `size_t size = min(int(prop.l2CacheSize * 0.75), prop.persistingL2CacheMaxSize); cudaDeviceSetLimit(cudaLimitPersistingL2CacheSize, size);`; window: `stream_attribute.accessPolicyWindow.base_ptr`, `.num_bytes` ("Must be less than cudaDeviceProp::accessPolicyMaxWindowSize"), `.hitRatio = 0.6`, `.hitProp = cudaAccessPropertyPersisting`, `.missProp = cudaAccessPropertyStreaming`; applied with `cudaStreamSetAttribute(stream, cudaStreamAttributeAccessPolicyWindow, &stream_attribute)`; reset with `num_bytes = 0` and `cudaCtxResetPersistingL2Cache()`; "When the GPU is configured in Multi-Instance GPU (MIG) mode, the L2 cache set-aside functionality is disabled"; under MPS only via `CUDA_DEVICE_DEFAULT_PERSISTING_L2_CACHE_PERCENTAGE_LIMIT` — [L2 Cache Control](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/l2-cache-control.html)

**Compute-capability limits (Programming Guide §5.1.3, Tables 29/30, columns 7.5 | 8.0 | 8.6 | 8.7 | 8.9 | 9.0 | 10.0 | 10.3 | 10.7 | 11.0 | 12.x)**
- Max shared memory per SM: `64 KB | 164 KB | 100 KB | 164 KB | 100 KB | 228 KB | 228 KB | 228 KB | 328 KB | 228 KB | 100 KB`; per thread block (opt-in): `64 | 163 | 99 | 163 | 99 | 227 | 227 | 227 | 327 | 227 | 99 KB`; resident blocks/SM: `16 | 32 | 16 | 16 | 24 | 32 | 32 | 32 | 16 | 24 | 24`; resident warps/SM: `32 | 64 | 48 | 48 | 48 | 64 | 64 | 64 | 32 | 48 | 48`; resident threads/SM: `1024 | 2048 | 1536 | 1536 | 1536 | 2048 | 2048 | 2048 | 1024 | 1536 | 1536`; registers: 64 K per SM and per block, 255 per thread on all — [Compute Capabilities](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/compute-capabilities.html)
- Feature table (columns 7.x | 8.x | 9.0 | 10.x | 11.0 | 12.x): "Hardware-accelerated memcpy_async": No | Yes x5; "L2 Cache Residency Management": No | Yes x5; "Distributed Shared Memory": No, No | Yes x4; "Thread Block Cluster": No, No | Yes x4; "Tensor Memory Accelerator (TMA) unit": No, No | Yes x4 (i.e. listed as *Yes* for 12.x) — [Compute Capabilities](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/compute-capabilities.html)

**What sm_120 (RTX 50 / RTX 5060 Ti) has and lacks**
- CUTLASS "Blackwell SM120 GEMMs": "The NVIDIA RTX 5000 Series GPUs introduce support for new narrow precision (4bit and 6bit) block-scaled and non-block-scaled tensor cores. The PTX ISA has extended the `mma` instructions"; instructions: `mma.sync.aligned.kind::f8f6f4` ("1x Ada Fp8 Tensor Core (2x for FP32 accumulator)"), `mma.sync.aligned.kind::mxf8f6f4.block_scale`, `mma.sync.aligned.kind::mxf4.block_scale` ("2x Ada Fp8 ... (4x for FP32 accumulator)"), `mma.sync.aligned.kind::mxf4nvf4.block_scale.scale_vec::[2X|4X]`; "## Cluster Size: On Geforce series graphics card, there is no multicast feature therefore the cluster shape is fixed to 1x1x1"; pingpong (two groups of 4 MMA warps) vs cooperative (8 MMA warps); `KernelScheduleAuto` -> `KernelTmaWarpSpecializedCooperative`; tile shapes e.g. `128x128x128`, `256x128x128`, `128x128x256` with `KernelTmaWarpSpecializedMxf8f6f4Sm120` / `...PingpongMxf8f6f4Sm120`; examples in `examples/79_blackwell_geforce_gemm/` — [CUTLASS blackwell_functionality.md](https://github.com/NVIDIA/cutlass/blob/main/media/docs/cpp/blackwell_functionality.md)
- Third-party mirror of CUTLASS constants: `sm100_smem_capacity_bytes = 232448; // 227 KB` and `sm120_smem_capacity_bytes = 101376; // 99 KB` (consistent with the CC table above) — [mintlify CUTLASS overview](https://www.mintlify.com/NVIDIA/cutlass/architectures/overview)
- PTX ISA 9.4: `tcgen05.*` (Tensor Memory, 5th-gen tensor core incl. `cta_group::2` 2-SM MMA) "Supported on following architectures: sm_100a, sm_101a (Renamed to sm_110a ...)" and family variants `sm_100f`, `sm_110f` — no `sm_120`; `mma` "`.e3m2`, `.e2m3` and `.e2m1` alternate floating point type mma operation requires sm_120a and are supported on sm_120f or higher in the same family from PTX ISA version 8.8"; "Support for `.kind`, `.block_scale`, `.scale_vec_size` qualifier requires sm_120a"; `.m16n8k32` f16/e4m3/e5m2 mma "requires sm_120"; `cp.async.bulk` `.multicast::cluster{::16b}` "advised to be used with .target sm_90a or sm_100f or sm_100a or sm_103f or sm_103a or sm_107a or sm_107f or sm_110f or sm_110a" (sm_120 absent) — [PTX ISA 9.4](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html)
- CUTLASS 3.9 "added support for Blackwell SM120 kernels for GeForce GPUs"; "Kernels compiled with sm_100a (datacenter) are not compatible with RTX 50 series GPUs (SM120)" — [CUTLASS v3.9.0 release notes](https://newreleases.io/project/github/NVIDIA/cutlass/release/v3.9.0)

**Cluster launch control (work stealing)**
- "Cluster Launch Control is a feature introduced in the NVIDIA Blackwell GPU architecture (compute capability 10.0) ... allowing them to cancel thread blocks or thread block clusters. This mechanism enables work stealing"; code: `cg::invoke_one(cg::coalesced_threads(), [&](){ ptx::clusterlaunchcontrol_try_cancel(&result, &bar); }); ptx::mbarrier_arrive_expect_tx(ptx::sem_relaxed, ptx::scope_cta, ptx::space_shared, &bar, sizeof(uint4));` — [Cluster Launch Control](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cluster-launch-control.html)
- PTX: `clusterlaunchcontrol.try_cancel.async{.space}.completion_mechanism{.multicast::cluster::all}.b128 [addr], [mbar];` with `.mbarrier::complete_tx::bytes`, `.shared::cta`; "On success, the opaque response contains the ctaid of the first CTA of the canceled cluster" — [PTX ISA 9.4 §9.7.15.18](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html)

**Green contexts (SM partitioning)**
- Runtime API (CUDA 13): `cudaDeviceGetDevResource(dev, &res, cudaDevResourceTypeSm)`; `cudaDevSmResource` fields `smCount`, `minSmPartitionSize`, `smCoscheduledAlignment` ("number of SMs in the resource guaranteed to be co-scheduled on the same GPU processing cluster, which is relevant for thread block clusters"), `flags` (`cudaDevSmResourceGroupBackfill`, `cudaDevSmResourceGroupLocalityDomainId`); `cudaDevSmResourceSplit` with `cudaDevSmResourceGroupParams { smCount, coscheduledSmCount, preferredCoscheduledSmCount, flags }`; `cudaError_t cudaDevSmResourceSplitByCount(cudaDevResource* result, unsigned int* nbGroups, const cudaDevResource* input, cudaDevResource* remaining, unsigned int useFlags, unsigned int minCount)`; `cudaDevResourceGenerateDesc`; `cudaGreenCtxCreate(&ctx, desc, device, 0)`; `cudaExecutionCtxStreamCreate(&strm, ctx, cudaStreamDefault, 0)`; on CC 9.0 "the minimum number of SMs per partition is 8 and the SM count has to be a multiple of 8, if useFlags is zero" (GH200 example: 6 groups of 11 requested -> "6 groups of 16 SMs", `CU_DEV_SM_RESOURCE_SPLIT_IGNORE_SM_COSCHEDULING` relaxes it) — [Green Contexts](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/green-contexts.html)

**setmaxnreg** — see KQ2 (PTX ISA 9.4 text, FA3 budgets 24/240 and 32/160).

**ptxas/NVBit coverage for the user's card**
- NVBit: CC "<= 12.1" supported; nvcc real targets include `sm_120`, `sm_120f`, `sm_120a`, `sm_121*` — [NVBit README](https://github.com/NVlabs/NVBit), [nvcc docs](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html)

### Inferences
- "What sm_120 lacks" (combining the sources above): no Tensor Memory / `tcgen05` / 2-SM UMMA (sm_100a-only); no TMA multicast -> clusters are effectively useless (CUTLASS fixes 1x1x1) even though the CC table says clusters/DSMEM/TMA exist; 99 KB opt-in shared memory per block (vs 227 KB on 9.0/10.0) and 100 KB per SM; 48 resident warps (vs 64 on 9.0/10.0). What it *has*: Ada-like `mma.sync` with new FP4/FP6/FP8 block-scaled kinds at 2-4x Ada FP8 rate for mxf4/nvf4, plain TMA (`cp.async.bulk.tensor` without multicast), `setmaxnreg` is not listed for sm_120 in CCCL (only SM_90a/SM_100a), so Hopper-style warp-specialised register rebudgeting likely does not apply — flagged as inference.
- Practical consequence for llama.cpp/vLLM on the 5060 Ti: the fastest available tensor-core path is `mma.sync.kind::mxf4nvf4.block_scale` (NVFP4) and `kind::f8f6f4`; kernels must be compiled with `-arch=sm_120a` (or `sm_120f`), and Hopper/Blackwell-datacenter kernels (wgmma, tcgen05) will not JIT to it.
- The CC-table "Yes" for clusters on 12.x versus CUTLASS's "no multicast" are not contradictory: cluster launch and DSMEM may exist while the TMA multicast path (the main reason GEMMs use clusters) does not; verify on hardware with `cudaOccupancyMaxActiveClusters` and a `cp.async.bulk.tensor ... .multicast::cluster` test.

### Gaps
- The CUDA Programming Guide section on shared-memory carveout (`cudaFuncAttributePreferredSharedMemoryCarveout`, `cudaFuncAttributeMaxDynamicSharedMemorySize`) was not fetched; only the capacity numbers from the CC table are cited.
- No NVIDIA document explicitly enumerates sm_120 omissions (multicast, DSMEM performance, TMEM); the picture is assembled from CUTLASS docs + PTX target notes + the CC table.
- Driver-API names for green contexts (`cuGreenCtxCreate`, `cuDevSmResourceSplitByCount`) were not on the page read (CUDA 13 guide shows the runtime-API variants only).
