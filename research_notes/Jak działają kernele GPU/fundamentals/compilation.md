## KQ1. NVIDIA: the nvcc compilation trajectory, -gencode, PTX JIT, NVRTC / libNVVM / nvJitLink, what cicc vs ptxas do

### Takeaway
nvcc is a driver that runs, per virtual architecture, `cicc` (closed-source, LLVM/NVVM-based C++ front end + optimizer that emits PTX) and `ptxas` (closed-source PTX -> SASS/cubin back end doing register allocation, scheduling and control codes), then `fatbinary` to pack cubin+PTX, `cudafe++` to produce the host-side C++ with kernel stubs, and the host compiler plus `nvlink` for device linking. Every command can be printed with `nvcc -dryrun` and every intermediate kept with `--keep`; PTX is a stable virtual ISA that the driver's `libnvidia-ptxjitcompiler` JIT-compiles when no matching cubin is embedded, with a persistent on-disk cache controlled by `CUDA_CACHE_*`.

### Cited Findings

**The driver and its phases (official docs, CUDA 13.4)**
- NVCC docs: device code is preprocessed and compiled "to CUBIN and/or PTX (or cuda_tile intermediate code), then placed in a fatbinary. Host code is preprocessed again and synthesized to embed the fatbinary and convert CUDA extensions to standard C++", then the host compiler builds the host object; linking adds CUDA runtime libraries. Tools named: `ptxas`, `nvlink`, `nvprune`, `fatbinary`, `tileiras` (cuda_tile assembler). — [CUDA Compiler Driver NVCC v13.4](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html)
- Phase outputs: `--cuda` produces `x.cu.cpp.ii`, `--ptx` produces `.ptx`, `--cubin` produces `.cubin`, `--fatbin` produces `.fatbin`, `-dlink` produces `a_dlink.o`. `--keep` (`-keep`) keeps intermediate files, `--keep-dir` chooses the directory, `--save-temps` is an alias of `--keep`; `-dryrun` lists sub-commands without running them; `--verbose`/`-v` lists them while running. NVIDIA warns the internal steps are "for debugging only" and should not go into build scripts. — [NVCC v13.4](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html)
- The CUDA front end "replaces the body of each `__global__` function with CUDA runtime calls that launch the kernel" (the "stub" functions); `-static-global-template-stub` (default true) gives these stubs static linkage in whole-program mode. — [NVCC v13.4](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html)
- Default `-arch` in 13.4 is `sm_75`. `-arch=sm_NN` is shorthand for `--gpu-architecture=compute_NN --gpu-code=sm_NN,compute_NN` (for `sm_90a` the expansion is `sm_90a,compute_90,compute_90a`). `-arch=native` compiles for the GPUs visible at build time with no PTX; `-arch=all` embeds binaries for all supported `sm_*` plus PTX for the highest major virtual arch; `all-major` embeds `sm_*0` binaries plus the earliest supported. — [NVCC v13.4](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html)
- `--generate-code arch=A,code=C` (`-gencode`) equals `-arch=A -code=C` and can be repeated for several virtual architectures; documented forms include `--generate-code arch=compute_80,code=sm_80`, `arch=compute_80,code=[sm_80,sm_86]`, `arch=compute_80,code=compute_80`; shorthand `--gpu-code=compute_80,sm_80,sm_86`. Virtual architectures (`compute_XX`) are PTX intermediates, real ones (`sm_XX`) are binary load images; "If no matching binary exists, the runtime JIT-compiles the PTX". — [NVCC v13.4](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html)
- Blackwell targets listed in 13.4: virtual `compute_100`, `compute_100f`, `compute_100a`, `compute_103(/f/a)`, `compute_110(/f/a)`, `compute_120(/f/a)`, `compute_121(/f/a)`; real `sm_100 ... sm_121, sm_121f, sm_121a`. Rules implied by the PTX text: PTX for `sm_XYa` can only be compiled to `sm_XYa`; `sm_XYf` PTX can be compiled to `sm_XZ`, `sm_XZf`, `sm_XZa` with Z >= Y in the same family. `--apply-controls` (ACF) is Blackwell-and-later only. — [NVCC v13.4](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html)
- Separate compilation: `--device-c` (= `--relocatable-device-code=true --compile`, defines `__CUDACC_RDC__`), `--device-link` emits a host object with embedded executable device code that goes to the host linker; `nvlink` is the device linker; `-r` does a relocatable link; `-dlto` (`--dlink-time-opt`) must be given at both compile and link time; `-dlto -arch=sm_NN` adds an `lto_NN` target while `-arch=lto_NN` adds only that. Default is whole-program mode. — [NVCC v13.4](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html)
- Options relevant to kernel tuning: `--generate-line-info`/`-lineinfo` ("Generate line-number information for device code", recommended for profiling instead of `-G`), `--maxrregcount`, `-O`/`--optimize` sets the HOST optimization level only, ptxas has its own `--opt-level N` (`-O`, default 3) passed via `-Xptxas`. — [NVCC v13.4](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html)
- Documented ptxas options (via `-Xptxas`): `--opt-level N` (default 3), `--maxrregcount`, `--verbose`/`-v` ("prints code generation statistics"), `--warn-on-spills`, `--allow-expensive-optimizations` (enabled for O2 and above), `--def-load-cache`/`-dlcm` (default cache modifier on global/generic loads), `--fmad`, `--split-compile` (max concurrent threads for optimizations; 0 = CPU count), `--compile-as-tools-patch`, `--preserve-relocs`. — [NVCC v13.4](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html)

**What the internal tools actually look like (a real `nvcc --dryrun` log, CUDA 9.2; tool names unchanged in 13.x per the CuAssembler tutorial)**
- Environment set by nvcc: `_SPACE_`, `_CUDART_=cudart`, `_TARGET_SIZE_=64`, `_HERE_`/`_THERE_=/usr/local/cuda/bin`, `TOP=/usr/local/cuda/bin/..`, `NVVMIR_LIBRARY_DIR=/usr/local/cuda/bin/../nvvm/libdevice`, `LIBRARIES`, `PATH`, `LD_LIBRARY_PATH`, `INCLUDES`, `CUDAFE_FLAGS`, `PTXAS_FLAGS`. — [dryrun.txt (samestep.com)](https://samestep.com/blog/parallelizing-nvcc/assets/dryrun.txt)
- Sequence per virtual arch: (1) `gcc -D__CUDA_ARCH__=700 -E ... hello.cu > hello.compute_70.cpp1.ii`; (2) `cicc --c++14 --gnu_version=70301 --allow_managed -arch compute_70 -m64 -ftz=0 -prec_div=1 -prec_sqrt=1 -fmad=1 ... --gen_module_id_file --module_id_file_name ... --gen_device_file_name ... -o hello.compute_70.ptx`; (3) `ptxas -arch=sm_70 -m64 hello.compute_70.ptx -o hello.compute_70.cubin`; then (4) `fatbinary --create=hello.fatbin -64 --image=profile=sm_70@compute_70,file=... --embedded-fatbin=hello.fatbin.c --cuda`; (5) host preprocessing `gcc -E -x c++ -D__CUDACC__ -D__NVCC__ ... > hello.cpp4.ii`; (6) `cudafe++ --c++14 --gnu_version=70301 --allow_managed --m64 --parse_templates --gen_c_file_name hello.compute_70.cudafe1.cpp --stub_file_name ... --module_id_file_name ... hello.cpp4.ii`; (7) `gcc -D__CUDA_ARCH__=700 -c ... -o hello.o hello.compute_70.cudafe1.cpp`; (8) `nvlink --arch=sm_70 --register-link-binaries=... -cpu-arch=X86_64 -report-arch hello.o -o hello_dlink.compute_70.cubin` (with `-lcudadevrt`); (9) second `fatbinary ... -link ... --embedded-fatbin=hello_dlink.fatbin.c`; (10) `gcc -c -x c++ -DFATBINFILE=... -DREGISTERLINKBINARYFILE=... /usr/local/cuda/bin/crt/link.stub -o hello_dlink.o`; (11) `g++ -m64 -o hello -Wl,--start-group hello_dlink.o hello.o -lcudadevrt -lcudart_static -lrt -lpthread -ldl -Wl,--end-group`. — [dryrun.txt](https://samestep.com/blog/parallelizing-nvcc/assets/dryrun.txt)
- The blog analysis of that log: nvcc "performs several splitting, compilation, preprocessing, and merging steps for each CUDA source file"; each architecture gets its own `cicc` and `ptxas` (the most expensive steps) and nvcc runs them sequentially; `*.module_id` is produced by the first `cicc` (`--gen_module_id_file`) and consumed by later `cicc`/`cudafe++` calls; CUDA 11.3 added `-t` for built-in parallelism. — [Parallelizing nvcc (2021-02-20)](https://samestep.com/blog/parallelizing-nvcc/)
- CuAssembler tutorial: with `--keep`/`--dryrun` the visible sequence is `cicc` -> `.ptx`, `ptxas` -> `sm_75.cubin`, `fatbinary` -> embedded `.fatbin.c`, `cudafe++` -> `cudafe1.cpp` and `cudafe1.stub.c`, `nvlink` -> `_dlink.sm_75.cubin`, `gcc`/`g++` for host; you can "delete all the steps before this one (include this `ptxas` step), rename your hacked cubin to `cudatest.sm_75.cubin`, and run the rest of those building steps" because "`ptxas` just accepts one file at a time". — [CuAssembler Tutorial](https://github.com/cloudcores/CuAssembler/blob/master/Tutorial.md)
- Search results also show `cudafe++` reading `.cpp4.ii` and writing `.cudafe1.cpp` with `--stub_file_name`, and `cicc` writing `.cudafe1.c`/`.cudafe1.stub.c` via `--gen_c_file_name`/`--stub_file_name`; older CUDA 8 used a standalone `cudafe` with `--nv_arch`. — [JetBrains CPP-24859 log](https://youtrack.jetbrains.com/issue/CPP-24859/Use-of-undeclared-identifier-cudaConfigureCall-in-Clion-2021.1); [Zhihu NVCC process](https://zhuanlan.zhihu.com/p/33342065)

**The host stub / registration (clang's CUDA codegen replicates nvcc's crt contract)**
- `clang/lib/CodeGen/CGCUDANV.cpp` (llvm-project main): fatbin wrapper magic `CudaFatMagic = 0x466243b1` and `HIPFatMagic = 0x48495046 /* "HIPF" */`; sections `.nv_fatbin` / `.nvFatBinSegment` (CUDA) and `.hip_fatbin` / `.hipFatBinSegment` (HIP); globals `__cuda_gpubin_handle` / `__hip_gpubin_handle`; runtime calls `__cudaRegisterFatBinaryEnd`, `__cudaRegisterLinkedBinary` (RDC) plus the `__cudaRegister*`/`__hipRegister*` family built from the names at those lines. — repo path `llvm-project/clang/lib/CodeGen/CGCUDANV.cpp` lines 40-41, 903-1089 (commit 1614ccf5e6)
- Clang HIP docs describe the same contract for HIP: per TU a constructor `__hip_module_ctor` (`.hip.fatbin_reg`) in `@llvm.global_ctors` calls `__hipRegisterFatBinary` with a wrapper whose fields are `magic`, `version`, `image`, `reserved` placed in `.hipFatBinSegment`, stores the handle, calls `__hip_register_globals` to register kernels/variables, registers an `atexit` destructor `__hip_module_dtor` calling `__hipUnregisterFatBinary`. — [Clang HIPSupport](https://clang.llvm.org/docs/HIPSupport.html)
- clang can also compile CUDA directly: `clang++ axpy.cu -o axpy --offload-arch=sm_XX -L<cuda>/lib64 -lcudart_static -ldl -lrt -pthread`; "merged parsing"; for each GPU arch the device side is compiled to PTX, then `ptxas` generates SASS, `fatbin` combines SASS (and PTX if `--cuda-include-ptx=all|sm_*`) and the host side embeds it in an ELF section; `-ffp-contract` default `fast`, `-fcuda-flush-denormals-to-zero` default off, `-fcuda-approx-transcendentals` default off. — [Compiling CUDA with clang](https://llvm.org/docs/CompileCudaWithLLVM.html)

**PTX as a virtual ISA and the driver JIT**
- PTX ISA 9.4: PTX is "a low-level parallel thread execution virtual machine and instruction set architecture (ISA)" with the goal to "Provide a stable ISA that spans multiple GPU generations"; "The ptxas optimizing backend compiler optimizes and assembles PTX source modules"; "Each PTX module must begin with a `.version` directive specifying the PTX language version"; registers: "The number of registers is limited, and will vary from platform to platform. When the limit is exceeded, register variables will be spilled to memory"; declaration shorthand `.reg .b32 %r<100>;` declares `%r0..%r99`. State spaces `.reg`, `.sreg`, `.const`, `.global`, `.local`, `.param`, `.shared` (per-cluster), `.tex`. Tuning directives exist (`.maxnreg`, `.maxntid`, `.reqntid`, `.minnctapersm`, `.maxnctapersm` deprecated, `.noreturn`, `.pragma "nounroll"`). — [PTX ISA 9.4](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html)
- Triton's mapping of CUDA -> PTX ISA versions (code, not NVIDIA docs): CUDA 12.x -> PTX 8.x (`80+minor` below 12.6, `80+minor-1` from 12.6), CUDA 11.x -> 7.x, 10.x -> 6.x; the NVPTX backend is capped at `+ptx94` in current Triton. — `triton/third_party/nvidia/backend/compiler.py` lines 55-69, 101
- JIT environment variables (CUDA Programming Guide v13.4.2): `CUDA_CACHE_DISABLE=1` "Disables PTX JIT and binary finalization caching"; `CUDA_CACHE_PATH` default Linux `~/.nv/ComputeCache`, Windows `%APPDATA%\NVIDIA\ComputeCache`; `CUDA_CACHE_MAXSIZE` default `1073741824` (1 GiB) on desktop/server, `268435456` (256 MiB) on embedded, maximum `4294967296` (4 GiB); `CUDA_FORCE_PTX_JIT=1` "Forces PTX JIT compilation" (ignores embedded CUBIN; overrides `CUDA_FORCE_JIT`); `CUDA_DISABLE_PTX_JIT=1` disables JIT of embedded PTX; `CUDA_MODULE_LOADING` `DEFAULT`=`LAZY` (kernel loading delayed until a `CUfunc` handle is extracted) vs `EAGER`; `CUDA_MODULE_DATA_LOADING` likewise. — [CUDA env vars v13.4.2](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/environment-variables.html)
- NVIDIA driver README: `libnvidia-ptxjitcompiler.so.<ver>` "is a JIT compiler which compiles PTX into GPU machine code and is used by the CUDA driver"; `libcuda.so` "provides runtime support for CUDA"; `libnvidia-opencl.so` is "the NVIDIA Vendor ICD" (registered via `/etc/OpenCL/vendors/nvidia.icd`); `libnvidia-glvkspirv.so`, `libnvidia-glcore.so`, `libnvidia-compiler.so` are listed only as internal libraries. (README of driver 450.57; the component split is older but still the public description.) — [NVIDIA driver README 450.57 installed components](https://download.nvidia.com/XFree86/Linux-x86_64/450.57/README/installedcomponents.html)
- CUDA Compatibility: minor-version compatibility (since CUDA 11) lets apps built within the same major CUDA family run on a sufficiently new driver; forward compatibility uses the `cuda-compat-<major>-<minor>` package (page dated 2026-09-09). — [CUDA Compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/index.html)

**NVRTC, libNVVM, nvJitLink (runtime paths that bypass nvcc)**
- NVRTC 13.4 takes CUDA C++ source strings and produces PTX, cubin, cuda_tile IR, LTO IR or OptiX IR; API `nvrtcCreateProgram` -> `nvrtcCompileProgram` -> `nvrtcGetPTX`/`nvrtcGetCUBIN`/`nvrtcGetLTOIR` (+ `nvrtcGetProgramLog`, `nvrtcDestroyProgram`); `-arch` default `compute_75`, "No cubin is available if the value specified to `-arch` is a virtual architecture"; `-dlto` implies `-rdc=true` and produces only LTO IR; `-default-device`, `--std` (default c++17), `-lineinfo`, `-G` (turns off optimizations unless `--dopt`), `-maxrregcount=<N>`; NVRTC "does not depend on other CUDA Toolkit libraries or headers, and it can run without a GPU", bundling headers + CCCL in `libnvrtc-builtins` (`nvrtcInstallBundledHeaders` since 13.3); NVRTC has no linker, relocatable output is linked with nvJitLink or `cuLinkAddData`. — [NVRTC 13.4](https://docs.nvidia.com/cuda/nvrtc/index.html)
- libNVVM 13.4 (API v4.0) compiles NVVM IR (LLVM bitcode) to PTX: `nvvmCreateProgram`, `nvvmAddModuleToProgram`, `nvvmLazyAddModuleToProgram`, `nvvmCompileProgram`, `nvvmGetCompiledResult`; options `-arch=compute_XX` (default compute_75, up to `compute_121f`), `-opt=0|3` (default 3), `-ftz=0|1`, `-prec-sqrt=0|1`, `-prec-div=0|1`, `-fma=0|1`, `-g` (requires `-opt=0`), `-gen-lto`. The NVVM IR accepted is "the LLVM 7.0.1 bitcode representation" for the legacy dialect. — [libNVVM API 13.4](https://docs.nvidia.com/cuda/libnvvm-api/index.html)
- NVVM IR Specification 13.4: NVVM IR version 2.0; "The LLVM 7 dialect is based on LLVM 7.0.1. The modern dialect is based on LLVM 22.1.0 and supports only compute_100 and later"; address spaces 0 generic, 1 global, 3 shared, 4 constant, 5 local; kernel properties through `nvvm.annotations` (`kernel`, `maxntid{x,y,z}`, `reqntid{x,y,z}`, `minctasm`, `maxnreg`, `cluster_dim_{x,y,z}`); intrinsics `llvm.nvvm.*` (e.g. `llvm.nvvm.barrier0`, `llvm.nvvm.read.ptx.sreg.tid.x`). — [NVVM IR Spec 13.4](https://docs.nvidia.com/cuda/nvvm-ir-spec/index.html)
- nvJitLink 13.4 links CUBIN / PTX / LTOIR / FATBIN / OBJECT / LIBRARY / INDEX / ANY into a cubin loadable by the driver API: `nvJitLinkCreate` -> `nvJitLinkAddData`/`AddFile` -> `nvJitLinkComplete` -> `nvJitLinkGetLinkedCubin` (or `GetLinkedPtx` with `-lto`); options `-arch=sm_<N>` (required), `-lto`, `-ptx`, `-O0|-O3`, `-g`, `-lineinfo`, `-split-compile=<N>`, `-maxrregcount`, `-ftz`, `-prec-div`, `-prec-sqrt`, `-fma`, `-kernels-used`, `-variables-used`, `-optimize-unused-variables`, `-no-cache`, `-r`, `-Xptxas`; the `cuLink*` driver APIs are deprecated for LTO-IR. — [nvJitLink 13.4](https://docs.nvidia.com/cuda/nvjitlink/index.html)

**Inspecting outputs**

**What ptxas does (no official internals; forum evidence)**
- "ptxas, the part of the compiler that transforms PTX into machine code (SASS), is an optimizing compiler. One of the optimizations ptxas applies is scheduling loads early. The drawback of early loads is an increase in register pressure". — [NVIDIA forum: PTX instructions are reordered](https://forums.developer.nvidia.com/t/ptx-instructions-are-reordered/197973)
- "The PTX produced by nvcc uses static-single assignment form, and final register allocation is done by ptxas when it produces a cubin"; `ptxas -v` / `nvcc --ptxas-options=-v` prints the register count. — [NVIDIA forum: ptxas optimization](https://forums.developer.nvidia.com/t/ptxas-optimization/7127); [llvm-dev 2011](https://lists.llvm.org/pipermail/llvm-dev/2011-May/040160.html)
- With `maxrregcount` "It almost looks like the compiler assigns registers using its normal algorithm, then applies a post-processing pass to fit into the available registers specified and can pick poor choices to spill." — [NVIDIA forum: Feedback on PTXAS](https://forums.developer.nvidia.com/t/feedback-on-ptxas/2322)
- The maxas author worked out "the op and control codes to all the instructions" to bypass ptxas's scheduling/register decisions (control codes = per-instruction scheduling fields in SASS; details belong to the SASS track). — [maxas wiki](https://github.com/NervanaSystems/maxas/wiki/Introduction)
- Triton's production ptxas invocation (a good "known-good" flag set): `ptxas -lineinfo [--fmad=false] -v [--opt-level 0] --regAllocOptLevel=2 [extra] --gpu-name=sm_XX in.ptx -o out.o`; the comment says `--regAllocOptLevel=2` works around a "ptxas 13.x bug" and ConSan kernels use `--opt-level 1` because `-O3` "miscompiles some large ConSan kernels". Triton post-processes LLVM's PTX by rewriting `.version` and `.target sm_NN` and strips the `debug` flag "that prevents ptxas from optimizing the code". — `triton/third_party/nvidia/backend/compiler.py` lines 539-612

### Inferences
- `cicc` is where almost all "classical" compiler optimization happens on NVIDIA (it is the LLVM-based NVVM front end: `-ftz/-prec_div/-prec_sqrt/-fmad` flags and `NVVMIR_LIBRARY_DIR=.../nvvm/libdevice` in the dryrun show it links libdevice bitcode); `ptxas` is a second full optimizing back end (SSA PTX -> physical registers, SASS scheduling, spills, control codes). This is why `-O3` on the nvcc line affects host code while device optimization is controlled by cicc defaults and `-Xptxas -O`.
- The documented LLVM-22.1-based "modern NVVM dialect, compute_100+" strongly suggests cicc in CUDA 13.x carries a recent LLVM; the exact LLVM version inside cicc remains unverified (see Gaps).
- For the RTX 5060 Ti (sm_120, Blackwell GB206): `-gencode arch=compute_120,code=sm_120` gives a cubin usable on sm_120/121 family members only per the `f`/`a` rules; `code=compute_120` additionally embeds PTX for JIT on future architectures; `sm_120a` locks to the exact architecture. llama.cpp chose `120a-real` (see KQ3).

### Gaps
- NVIDIA documents neither cicc's nor ptxas's internal pass pipeline nor the LLVM version inside cicc; `cicc --version` could not be run here (no CUDA install).
- The exact `.target` grammar / `sm_120f` rules and the PTX-ISA-version <-> CUDA-version table are in PTX ISA sections 11-13, which the fetched page truncated at ~470k characters; only the TOC and PTX 9.4 notes (adds `sm_107f`) were visible.
- The nvcc dryrun transcript is CUDA 9.2 (file naming `compute_70.cpp1.ii` etc.); 13.x adds `__CUDA_ARCH_LIST__`, `-t` parallelism and `tileiras`, but a 13.x dryrun could not be captured.

## KQ2. AMD: hipcc as a clang driver, host/device split, AMDGPU backend passes, lld, code objects, device libs, hipRTC/comgr, attributes

### Takeaway
On AMD the whole pipeline is open source: `hipcc` is a thin wrapper that invokes `clang++ -x hip --offload-arch=gfx1100 -O3 ...`; clang compiles device code to LLVM IR, links the ROCm device-libs bitcode (ocml/ockl/oclc controls), runs the AMDGPU backend (SelectionDAG/GlobalISel, GCN max-occupancy scheduler, SGPR/WWM/VGPR allocation, `SIInsertWaitcnts`, hazard recognizer, `s_delay_alu`, VOPD for wave32 on gfx11), then `lld -flavor gnu -m elf64_amdgpu -shared` produces an HSA code object (ELF, code object V5 default, msgpack metadata note), and `clang-offload-bundler` packs it with the host object; every stage is dumpable with `-save-temps`, `-emit-llvm`, `-mllvm -print-after-all`, `llc`, `llvm-objdump`.

### Cited Findings

**hipcc -> clang**

### Inferences
- Because the entire AMD path is LLVM + lld + comgr, "reverse engineering" ROCm's compiler means reading `llvm/lib/Target/AMDGPU` and `amd/comgr`; the only non-LLVM step is the clang HIP front end (host/device split + `__hipRegisterFatBinary` stub emission in `CGCUDANV.cpp`) and the final `clang-offload-bundler`.
- The same gfx1100 code object is produced regardless of entry point (hipcc offline, hipRTC via comgr `CODEGEN_BC_TO_RELOCATABLE` + lld, Triton via in-process LLVM + `lld::elf::link`, OpenCL via comgr with `AMD_COMGR_LANGUAGE_OPENCL_2_0` in `rocclr/device/devprogram.cpp`), so one set of inspection tools (`llvm-objdump -d --mcpu=gfx1100`, `llvm-readelf --notes`) serves all of them.
- Occupancy steering on AMD is explicit in IR: `__launch_bounds__(N)` becomes `"amdgpu-flat-work-group-size"="1,N"`, `__attribute__((amdgpu_waves_per_eu(m,n)))` becomes `"amdgpu-waves-per-eu"="m,n"`, and Triton sets exactly these attributes plus `"amdgpu-sched-strategy"` and `denormal-fp-math-f32` on the kernel function (`compiler.py` lines 650-660).

## KQ3. Other front ends: Triton, OpenCL, Vulkan (NVIDIA proprietary vs RADV/ACO), WebGPU/wgpu, and how llama.cpp builds CUDA/HIP/Vulkan kernels

### Takeaway
Triton lowers Python -> TTIR -> TTGIR -> LLVM IR in-process (MLIR), then uses LLVM's NVPTX backend + the external `ptxas` binary on NVIDIA, or LLVM's AMDGPU backend + in-process `ld.lld` on AMD, with every stage dumpable via env vars and cached under `~/.triton/cache`. Vulkan on AMD goes SPIR-V -> NIR -> ACO (default; LLVM only for bring-up) inside Mesa with `RADV_DEBUG=shaders` printing the ISA; on NVIDIA the SPIR-V compiler lives inside the closed driver with no public IR. llama.cpp compiles the same `.cu` files with nvcc or (through `vendors/hip.h` macro shims) with clang HIP, and precompiles ~hundreds of GLSL compute shader variants to SPIR-V with `glslc` at build time, leaving final ISA generation to the Vulkan driver at runtime.

## KQ4. Compiler optimizations that matter for kernels and how to recognize them; known weaknesses and escape hatches

### Takeaway
The optimizations that decide kernel speed are mostly back-end decisions you can see directly in the ISA: vector loads (`LDG.E.128` / `global_load_b128`, `ds_read2_b32`), load hoisting and software pipelining (loads scheduled far ahead of use, more registers), occupancy-vs-registers trade-offs (`ptxas -v`, `-Rpass-analysis=kernel-resource-usage`), unrolling/inlining (no loop back-edges, no `call`), strength reduction and offset folding (immediate offsets on loads, `s_movk_i32` bases), and hazard/wait management (`s_waitcnt`, `s_delay_alu`, `s_clause`, SASS control codes). Both vendors expose explicit overrides (`__launch_bounds__`, `maxrregcount`/`amdgpu-waves-per-eu`, `#pragma unroll`, `__restrict__`, inline PTX / `__builtin_amdgcn_*`) for the cases where heuristics are wrong.

### Cited Findings
- Vectorized access: scalar copies compile to `LDG.E`/`STG.E` (32-bit); `reinterpret_cast<int2*>`/`int4`/`float4` dereferences compile to `LDG.E.64`/`LDG.E.128` and `STG.E.64`/`STG.E.128`; check with `cuobjdump -sass executable`; the int4 kernel executes about a quarter of the instructions; vector loads "raise register pressure and can reduce parallelism"; pointers must stay aligned to the vector size. — [NVIDIA blog: vectorized memory access (updated 2025-08-04)](https://developer.nvidia.com/blog/cuda-pro-tip-increase-performance-with-vectorized-memory-access/)
- On AMD the same transformation is the IR-level `LoadStoreVectorizer` pass in the AMDGPU pipeline, and post-ISel `SILoadStoreOptimizer` merges adjacent DS/SMEM/VMEM ops (`ds_read_b32 x2` -> `ds_read2_b32`, `s_buffer_load_dword x2` -> `s_buffer_load_dwordx2`) and folds constant offsets into 13-bit immediates. — `AMDGPUTargetMachine.cpp` line 1681; `SILoadStoreOptimizer.cpp` header
- Straight-line scalar optimizations shared by NVPTX and AMDGPU: `SeparateConstOffsetFromGEP`, `StraightLineStrengthReduce`, `NaryReassociate`, `EarlyCSE`/`GVN` (`addStraightLineScalarOptimizationPasses`); clang's CUDA docs list "Straight-line scalar optimizations, aggressive speculative execution, memory space inference, bypassing 64-bit divides, and aggressive loop unrolling and inlining" as the GPU-specific optimizations. — `AMDGPUTargetMachine.cpp` lines 1548-1562; [Compiling CUDA with clang](https://llvm.org/docs/CompileCudaWithLLVM.html)
- Inlining: AMDGPU runs `AMDGPUAlwaysInline` + `AlwaysInliner` early; the legacy hipcc option `-mllvm -amdgpu-early-inline-all=true -mllvm -amdgpu-function-calls=false` forced whole-kernel inlining (function calls on AMDGPU were unsupported for years and are still expensive); lld ThinLTO needs `-force-import-all` because "AMDGPU backend currently does not support ISA-level linking". — `AMDGPUTargetMachine.cpp` 1594-1595; [hipBin_amd.h](https://raw.githubusercontent.com/ROCm/llvm-project/amd-staging/amd/hipcc/src/hipBin_amd.h); `HIPAMD.cpp` 86-92
- Register allocation vs occupancy: GCN's scheduler is explicitly an occupancy-maximizing multi-stage scheduler that relaxes register pressure only in regions where it does not limit occupancy; `"amdgpu-waves-per-eu"` is "an optimization hint"; VGPR allocation granularity depends on wave size; ptxas warns on spills (`--warn-on-spills`), and `--maxrregcount` on NVIDIA tends to produce "poor choices to spill" per user reports. — `GCNSchedStrategy.cpp` header; `AMDGPUUsage.rst` 2648-2654; `AMDGPUBaseInfo.cpp` 1296-1340; [NVCC v13.4](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html); [NVIDIA forum: Feedback on PTXAS](https://forums.developer.nvidia.com/t/feedback-on-ptxas/2322)
- Load hoisting / latency hiding: ptxas "scheduling loads early" at the cost of register pressure; ACO's scheduler "only aims to move up memory loads as far as possible without exceeding the maximum register limit for the pre-calculated wave count". — [NVIDIA forum](https://forums.developer.nvidia.com/t/ptx-instructions-are-reordered/197973); ACO README
- Software pipelining exists as `MachinePipeliner` in the AMDGPU pipeline (gated, line 1852); the `GCNMaxOccupancy`/`MaxILP`/`MaxMemoryClause` strategies and the `SIInsertHardClauses` pass shape memory clauses that appear as `s_clause N` in gfx10+ ISA. — `AMDGPUTargetMachine.cpp` 1852, 2045
- Wait/hazard management visible in the ISA: `s_waitcnt vmcnt/lgkmcnt/expcnt` (SIInsertWaitcnts, conservative per-counter), `s_nop`/`v_nop` from the hazard recognizer, `s_delay_alu` on gfx11+, VOPD dual-issue pairs on gfx11 wave32 (`GCNCreateVOPD` after post-RA scheduling); on NVIDIA the equivalent per-instruction stall/barrier information is encoded in SASS control codes set by ptxas (not documented; see maxas). — pass headers above; [maxas wiki](https://github.com/NervanaSystems/maxas/wiki/Introduction)
- Alloca and LDS: `AMDGPUPromoteAlloca` turns private arrays into vectors (registers) or LDS; `AMDGPULowerModuleLDS` packs per-kernel LDS structs and "exceeding it halts compilation"; `AMDGPUAtomicOptimizer` rewrites wave-uniform atomics into one-lane DPP/iterative reductions. — pass headers
- Numerical knobs that change codegen: nvcc/cicc `-ftz`, `-prec_div`, `-prec_sqrt`, `-fmad` (dryrun shows `cicc ... -ftz=0 -prec_div=1 -prec_sqrt=1 -fmad=1`), `-use_fast_math` (llama.cpp), ptxas `--fmad`; clang `-ffp-contract=fast` default for CUDA, `-fcuda-flush-denormals-to-zero`; AMD device-lib controls `__oclc_finite_only_opt`, `__oclc_unsafe_math_opt`, `__oclc_daz_opt` selected by `-ffast-math`/`-fno-honor-nans`/`-fgpu-flush-denormals-to-zero` equivalents in `AMDGPU.cpp` lines 54-82; Triton `enable_fp_fusion` -> `--fmad=false`. — [dryrun.txt](https://samestep.com/blog/parallelizing-nvcc/assets/dryrun.txt); `llama.cpp/ggml/src/ggml-cuda/CMakeLists.txt` 196; [Compiling CUDA with clang](https://llvm.org/docs/CompileCudaWithLLVM.html); `AMDGPU.cpp`; `triton/.../nvidia/backend/compiler.py` 587
- Escape hatches used by production code: `__launch_bounds__(threads, min_blocks)` in 19 ggml-cuda files; Triton forces `"amdgpu-waves-per-eu"="N,N"`, `inreg` kernel args and alternative scheduler strategies via function attributes; Triton's `TRITON_SWAP_MIR` lets a human edit the pre-scheduler MIR and feed it back; CuAssembler/maxas replace the `ptxas` step with a hand-assembled cubin in an otherwise unchanged nvcc build. — `llama.cpp` grep; `triton/third_party/amd/backend/compiler.py` 650-700, 760-770; [CuAssembler Tutorial](https://github.com/cloudcores/CuAssembler/blob/master/Tutorial.md)

### Inferences
- The two back ends are weak in different, recognizable ways: ptxas's register allocation under `maxrregcount` and its latency-hiding scheduler (hence SASS-level assemblers), and the AMDGPU backend's conservative waitcnt insertion (per-counter timelines), lack of ISA-level linking (everything must be inlined/imported) and the occupancy-first scheduler that can leave ILP on the table (hence Triton's explicit `max-ilp`/`coexec` strategies and MIR swapping).
- Unrolling/inlining are IR-level (cicc / LLVM) decisions on both vendors; vectorization, scheduling, spilling and wait insertion are back-end decisions (ptxas / AMDGPU MI passes). Therefore on NVIDIA you can inspect the former in the PTX (`--keep`, `.ptx`) and must inspect the latter in SASS; on AMD both are visible in `-print-after-all` output and the final `.s`.

### Gaps
- No primary NVIDIA source quantifies ptxas's unrolling/scheduling heuristics; evidence is forum-level.
- No measurements were made here (no GPU in the research environment).

### Inferences
- On AMD the single most informative command for a kernel author is `clang++ -x hip --offload-arch=gfx1100 --cuda-device-only -O3 -Rpass-analysis=kernel-resource-usage -save-temps -c k.cu`: it gives IR, asm, object and the VGPR/SGPR/LDS/occupancy remark in one run; llama.cpp wraps exactly this as `GGML_HIP_EXPORT_METRICS`.
- On NVIDIA the equivalent is `nvcc --keep -Xptxas -v` plus `cuobjdump -sass`; the only stage you cannot open is cicc's internal LLVM IR (the PTX it emits is the first visible device artifact).

### Gaps
- None of the commands were executed (no CUDA/ROCm/GPU in the container); flag spellings follow the cited docs but a few are version-sensitive (`-Xptxas --warn-on-spills` name, `-ir-dump-directory` requires a recent LLVM, `llvm-objdump --offloading` requires ROCm 6.x+ LLVM).
- clang `-save-temps` output names for HIP are inferred, not verified from source.
