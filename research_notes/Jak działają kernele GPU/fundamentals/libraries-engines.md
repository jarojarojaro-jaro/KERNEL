## KQ1. The "kernel zoo" pattern: cuBLAS/cuBLASLt, rocBLAS/Tensile, hipBLASLt, cuDNN/MIOpen — how a library picks a kernel and how to watch it

### Takeaway
Every vendor math library is a *database of precompiled kernels plus a selection function*: a problem descriptor (shape, dtypes, transposes, epilogue) is mapped by heuristics/tuning tables to one of hundreds or thousands of kernel variants, each a fixed combination of tile shape, split-K, stages, cluster shape etc. Observability is via per-library env vars (`CUBLASLT_LOG_LEVEL`, `CUBLAS_LOGINFO_DBG`, `CUDNN_LOGLEVEL_DBG`, `ROCBLAS_LAYER`, `TENSILE_DB`, `HIPBLASLT_LOG_LEVEL/MASK`, `MIOPEN_LOG_LEVEL`, `MIOPEN_FIND_MODE`).

### Cited Findings

**cuBLAS / cuBLASLt (NVIDIA, closed source; API surface is the only window)**
- `cublasLtMatmulAlgoGetHeuristic()` takes `requestedAlgoCount` ("Size of heuristicResultsArray (in elements) and requested maximum number of algorithms to return") and fills `cublasLtMatmulHeuristicResult_t` entries "ordered in increasing estimated compute time"; each result has fields `algo`, `workspaceSize`, `state`, `wavesCount` ("Waves count - a device utilization metric", 1.0f = a launch would fully occupy the GPU) and `int reserved[4]` — [cublasLt.h header (mirror of the CUDA 12 header)](https://decoder-genetics.wustl.edu/software/conda/lib/python3.1/site-packages/nvidia/cublas/include/cublasLt.h)
- The algorithm descriptor is a *configuration tuple* exposed through `cublasLtMatmulAlgoConfigAttributes_t`: `CUBLASLT_ALGO_CONFIG_ID` ("algorithm index, see cublasLtMatmulAlgoGetIds()"), `CUBLASLT_ALGO_CONFIG_TILE_ID` (`cublasLtMatmulTile_t`, "Tile size (in C/D matrix Rows x Cols)", e.g. `CUBLASLT_MATMUL_TILE_64x64 = 15`, `CUBLASLT_MATMUL_TILE_128x128 = 20`, `CUBLASLT_MATMUL_TILE_256x128 = 24`), `CUBLASLT_ALGO_CONFIG_SPLITK_NUM`, `CUBLASLT_ALGO_CONFIG_REDUCTION_SCHEME`, `CUBLASLT_ALGO_CONFIG_CTA_SWIZZLING` ("change mapping from CUDA grid coordinates to parts of the matrices"), `CUBLASLT_ALGO_CONFIG_CUSTOM_OPTION`, `CUBLASLT_ALGO_CONFIG_STAGES_ID`, `CUBLASLT_ALGO_CONFIG_INNER_SHAPE_ID`, `CUBLASLT_ALGO_CONFIG_CLUSTER_SHAPE_ID` ("Thread Block Cluster shape id"). Capabilities per algo id are queried with `CUBLASLT_ALGO_CAP_TILE_IDS`, `CUBLASLT_ALGO_CAP_STAGES_IDS`, `CUBLASLT_ALGO_CAP_SPLITK_SUPPORT`, `CUBLASLT_ALGO_CAP_CTA_SWIZZLING_SUPPORT`, `CUBLASLT_ALGO_CAP_EPILOGUE_MASK` — [cublasLt.h](https://decoder-genetics.wustl.edu/software/conda/lib/python3.1/site-packages/nvidia/cublas/include/cublasLt.h)
- Search mode: `CUBLASLT_MATMUL_PREF_SEARCH_MODE` with `CUBLASLT_SEARCH_BEST_FIT` (0, "ask heuristics for best algo for given usecase") or `CUBLASLT_SEARCH_LIMITED_BY_ALGO_ID` (1); `CUBLASLT_MATMUL_PREF_MAX_WORKSPACE_BYTES` defaults to 0 (no workspace). Epilogues are fused into the GEMM kernel: `CUBLASLT_EPILOGUE_DEFAULT`=1, `_RELU`=2, `_BIAS`=4, `_GELU`=32, plus `_AUX` and `_BGRAD` variants — [cublasLt.h](https://decoder-genetics.wustl.edu/software/conda/lib/python3.1/site-packages/nvidia/cublas/include/cublasLt.h)
- cuBLASLt logging levels (`cublasLtLoggerSetLevel`): 0 Off, 1 Errors, 2 Performance Trace, 3 Performance Hints, 4 Heuristics Trace, 5 API Trace; `cublasLtLoggerSetMask` uses bits 1,2,4,8,16 for the same categories — [cublasLt.h](https://decoder-genetics.wustl.edu/software/conda/lib/python3.1/site-packages/nvidia/cublas/include/cublasLt.h). (The env-var spellings `CUBLASLT_LOG_LEVEL`, `CUBLASLT_LOG_MASK`, `CUBLASLT_LOG_FILE` are documented in the cuBLAS docs' "cuBLASLt Logging" section, which the fetch tool could not reach — see Gaps.)
- Classic cuBLAS logging: `CUBLAS_LOGINFO_DBG=1` turns logging on, `CUBLAS_LOGDEST_DBG=stdout|stderr|<file>` sets destination; programmatic: `cublasLoggerConfigure(logIsOn, logToStdOut, logToStdErr, logFileName)`, `cublasSetLoggerCallback` — [cuBLAS docs](https://docs.nvidia.com/cuda/cublas/index.html)
- cuBLAS workspace: recommended 32 MiB for "NVIDIA Hopper Architecture and newer (sm90+)" and 4 MiB for others; `CUBLAS_WORKSPACE_CONFIG=:16:8` for deterministic behaviour (may limit performance) or `:4096:8` (~24 MiB extra footprint); the library "will pick a Tensor Core enabled implementation wherever it determines that it would provide the best performance"; with multiple streams "the library may optimize total performance by picking different internal implementations"; no more than 32 concurrent kernels — [cuBLAS docs §2.1/2.4](https://docs.nvidia.com/cuda/cublas/index.html)
- Autotuning practice on top of the heuristic: the CUDA-L2 paper (arXiv 2512.02551, Dec 2025) describes the common approach of taking heuristic result index 0 per shape, and an "AutoTuning" variant that requests up to 100 candidates from `cublasLtMatmulAlgoGetHeuristic` and benchmarks them — [arXiv 2512.02551](https://arxiv.org/pdf/2512.02551)

**rocBLAS / Tensile (AMD, open source)**
- Tensile is "a tool for creating a benchmark-driven backend library for GEMM"; the host library (`TensileHost`) selects kernels via "Solution selection" through a hierarchical, serialized "solution selection catalog" (YAML in docs, MessagePack `.dat` in practice). Hierarchy: Level 1 Hardware (GFX arch), Level 2 Operation (Einstein notation e.g. `Contraction_l_Alik_Bjlk_Cijk_Dijk`), Level 3 Problem (types, HPA, stochastic rounding predicates), Level 4 Exact solution ("Each kernel has an index and a performance ranking. During solution selection, the highest-ranked kernel from this pool is selected") — [Tensile docs: solution-selection-catalogs.rst](https://github.com/ROCm/Tensile/blob/develop/docs/src/conceptual/solution-selection-catalogs.rst)
- Build artifacts with `--lazy-library-loading`: parent `TensileLibrary_lazy_<gfx>.yaml`/`.dat`, children `TensileLibrary_Type_<precision>_<problem type>_<gfx>.yaml` (e.g. `TensileLibrary_Type_HH_Contraction_l_Alik_Bjlk_Cijk_Dijk_<gfx>` = HGEMM TT), kernels in `.co` (assembly kernels) and `.hsaco` (HIP-source fallback kernels) per gfx; `--merge-files` mode (deprecated) produces one `TensileLibrary_<gfx>.co/.yaml` — [same doc](https://github.com/ROCm/Tensile/blob/develop/docs/src/conceptual/solution-selection-catalogs.rst)
- Host-side selection is implemented as a library-of-libraries: `MasterSolutionLibrary`, `ExactLogicLibrary`, `MatchingLibrary` (distance-based), `DecisionTreeLibrary`, `GranularitySelectionLibrary`, `CachingLibrary`, `PlaceholderLibrary` (lazy load) in `Tensile/Source/lib/include/Tensile/*.hpp`, each exposing `findBestSolution(problem, hardware, fitness)` and `findAllSolutions(...)` — [Tensile repo: Tensile/Source/lib/include/Tensile/](https://github.com/ROCm/Tensile/tree/develop/Tensile/Source/lib/include/Tensile)
- A selected `ContractionSolution` carries a `SizeMapping` with `workGroupSize`, `threadTile`, `macroTile`, `staggerU`, `depthU`, `globalSplitU`, `workGroupMapping`, `packBatchDims`, `streamK`, `streamKAtomic` — [ContractionSolution.hpp](https://github.com/ROCm/Tensile/blob/develop/Tensile/Source/lib/include/Tensile/ContractionSolution.hpp)
- Library-logic YAML files (the tuning tables) are parsed positionally in `Tensile/LibraryIO.py::parseLibraryLogicData`: `data[0]` = version string (`MinimumRequiredVersion`), `data[1]` = scheduleName, `data[2]` = architectureName (may be a dict with `Architecture`, `CUCount`, `IsAPU`), `data[5]` = solutionStates, `data[6]` = indexOrder, `data[7]` = exactLogic, `data[8]` = rangeLogic, `data[10]` = `PerfMetric`; `LibraryType` defaults to `"Matching"` — [Tensile/LibraryIO.py](https://github.com/ROCm/Tensile/blob/develop/Tensile/LibraryIO.py)
- Kernel names encode the solution: `Solution.getNameMin()` emits `<ProblemType>_MT<MacroTile0>x<MacroTile1>x<DepthU>_MI<MatrixInstM>x<N>x<K>x<B>_` then `SE_`/`SN_` (LdcEqualsLdd) and then abbreviated `<param><value>` pairs for every required parameter (abbreviations = capital letters of the parameter name; bools as 0/1) — [Tensile/SolutionStructs.py](https://github.com/ROCm/Tensile/blob/develop/Tensile/SolutionStructs.py). Key tunable parameters in `Tensile/Common.py::validParameters` include `MacroTile`, `DepthU`, `ThreadTile`, `WorkGroup` ("(wg0 x wg1 x LocalSplitU)"), `WavefrontSize` [32, 64], `MatrixInstruction`, `PrefetchGlobalRead` [0,1,2], `PrefetchLocalRead` 0..128, `GlobalSplitU` 1..4096, `StreamK` [0..3] — [Tensile/Common.py](https://github.com/ROCm/Tensile/blob/develop/Tensile/Common.py)
- The assembly generator is Python: `Tensile/KernelWriterAssembly.py` + `KernelWriter.py` + `Tensile/Components/*.py` (`MFMA.py`, `MAC_F16.py`, `LocalRead.py`, `Signature.py`, ...) total ~26.6k lines; `TensileCreateLibrary.py` assembles `.o` and links them into `.co` with `kernelWriterAssembly.getLinkCodeObjectArgs(["$f.o"], "$f.co")` — [Tensile/TensileCreateLibrary.py](https://github.com/ROCm/Tensile/blob/develop/Tensile/TensileCreateLibrary.py)
- Runtime debugging: `TENSILE_DB` bit field — `0x2/0x4` solution selection, `0x8` hardware selection, `0x10` predicate evaluation, `0x20` code object library loading status, `0x40` kernel launch arguments, `0x1000` library loading (YAML/MessagePack), `0x4000` solution lookup efficiency, `0x8000` selected kernel names, `0x80000` detailed kernel parameters (MatrixInstruction, MacroTile...), `0xFFFF` all; also `TENSILE_DB2` (skip launches), `TENSILE_NAIVE_SEARCH`, `TENSILE_TAM_SELECTION_ENABLE` (tile-aware selection), `TENSILE_SOLUTION_INDEX`, `TENSILE_METRIC` (Euclidean/JSD/Manhattan/Ratio/Random distance for matching), `TENSILE_SOLUTION_SELECTION_TRACE`, `TENSILE_EXPERIMENTAL_SELECTION` — [docs/src/reference/environment-variables.rst](https://github.com/ROCm/Tensile/blob/develop/docs/src/reference/environment-variables.rst) and [Tensile/Source/lib/source/Debug.cpp](https://github.com/ROCm/Tensile/blob/develop/Tensile/Source/lib/source/Debug.cpp)
- rocBLAS logging: `ROCBLAS_LAYER` bit mask — 1 trace (function + args), 2 bench (lines replayable with `rocblas-bench`), 4 profile (YAML summary at exit), 8 internal API ("such as the GEMM backend used for a call"); paths `ROCBLAS_LOG_TRACE_PATH`, `ROCBLAS_LOG_BENCH_PATH`, `ROCBLAS_LOG_PROFILE_PATH`; `ROCBLAS_VERBOSE_TENSILE_ERROR` / `ROCBLAS_VERBOSE_HIPBLASLT_ERROR` with `ROCBLAS_LAYER=8` (rocBLAS can route GEMMs to a hipBLASLt backend) — [rocBLAS logging docs](https://rocm.docs.amd.com/projects/rocBLAS/en/latest/reference/logging.html)

**hipBLASLt (AMD's cuBLASLt analogue)**
- Heuristic selection "run[s] on the host CPU and can take tens of microseconds" — call `hipblasLtMatmulAlgoGetHeuristic()` once and reuse. Logging: `HIPBLASLT_LOG_LEVEL` 0 Off, 1 Error, 2 Trace (kernel-launching API calls + params), 3 Hints, 4 Info ("including heuristic status"), 5 API trace; `HIPBLASLT_LOG_MASK` bits 1 Error, 2 Trace, 4 Hints, 8 Info, 16 API trace, 32 Bench, 64 Profile, 128 Extended profile; `HIPBLASLT_LOG_FILE` (`%i` = pid); `HIPBLASLT_ENABLE_MARKER=1` for rocprof markers — [hipBLASLt logging & heuristics](https://rocm.docs.amd.com/projects/hipBLASLt/en/latest/logging-heuristics.html)
- Offline tuning workflow: `HIPBLASLT_LOG_MASK=32` emits bench command lines; `HIPBLASLT_TUNING_FILE=<file>` records best solution indices; `HIPBLASLT_TUNING_OVERRIDE_FILE=<file>` replays them, overriding the heuristic; `HIPBLASLT_TUNING_USER_MAX_WORKSPACE` default 128 MiB; indices are not portable across library releases or architectures — [hipBLASLt offline tuning (1.2.2 docs)](https://rocm.docs.amd.com/projects/hipBLASLt/en/develop/how-to/how-to-use-hipblaslt-offline-tuning.html). Newer PRs in `ROCm/rocm-libraries` add `HIPBLASLT_TUNING_MODE=cache` and kernel-name validation of tuning entries ([PR #12587](https://github.com/ROCm/rocm-libraries/pull/12587), [PR #12590](https://github.com/ROCm/rocm-libraries/pull/12590)) — release status unverified.

**cuDNN (graph API) / MIOpen**
- cuDNN graph API: user builds an *operation graph*; *engines* are candidate implementations with *knobs*; *heuristics* return ranked engine configs — Mode A ("fast", handles most patterns), Mode B (more accurate, higher CPU latency, may fall back to A), Fallback mode. Engine classes: pre-compiled single-op engines (`ConvolutionFwd`, `ConvolutionBwdFilter`, `ConvolutionBwdData`, `ConvolutionBwBias`), *generic runtime fusion engines* (generate kernels at runtime; `CUDNN_BEHAVIOR_NOTE_RUNTIME_COMPILATION`), specialized runtime fusion engines (NormAddRelu, DReluForkDNorm), specialized pre-compiled fusion engines; fusion patterns grouped by "support surfaces 90, 80, 70" (compute capability) — [cuDNN Graph API docs](https://docs.nvidia.com/deeplearning/cudnn/latest/developer/graph-api.html)
- cuDNN logging: `CUDNN_LOGLEVEL_DBG` = 0 (off, no perf cost), 1 errors, 2 +warnings, 3 +info; `CUDNN_LOGDEST_DBG` = NULL|stdout|stderr|<path>; read once at init; legacy `CUDNN_LOGERR_DBG/LOGWARN_DBG/LOGINFO_DBG` deprecated in v9; frontend uses `CUDNN_FRONTEND_LOG_INFO` / `CUDNN_FRONTEND_LOG_FILE` — [cuDNN troubleshooting](https://docs.nvidia.com/deeplearning/cudnn/backend/latest/reference/troubleshooting.html)
- MIOpen: Find mode (`miopenFindConvolutionForwardAlgorithm` benchmarks candidates, returns `miopenConvAlgoPerf_t` fastest-first) vs Immediate mode (`miopenConvolutionForwardGetSolutionCount/GetSolution/Immediate`, solutions `miopenConvSolution_t` sorted best-first, optional `...CompileSolution`); immediate mode is backed by FindDb; on a miss, `MIOPEN_ENABLE_AI_IMMED_MODE_FALLBACK=ON` (default) uses an AI heuristic (~90% accurate per docs), else a weighted throughput index. `MIOPEN_FIND_MODE`: `NORMAL`/1, `FAST`/2, `HYBRID`/3, `DYNAMIC_HYBRID`/5 (docs say this is the default, inconsistently also listing HYBRID as "unset"), `TRUST_VERIFY`/6, `TRUST_VERIFY_FULL`/7. Shipped FindDb only populated for gfx906/gfx900 — [MIOpen find & immediate](https://rocm.docs.amd.com/projects/MIOpen/en/latest/how-to/find-and-immediate.html)
- MIOpen FindDb: System FindDb (install location) + User FindDb (home dir, "always takes precedence"); `MIOPEN_DEBUG_DISABLE_FIND_DB=1` — [MIOpen FindDb](https://rocm.docs.amd.com/projects/MIOpen/en/latest/conceptual/finddb.html). `MIOPEN_LOG_LEVEL` 1 (off) .. 7 (trace), default 4 release / 5 debug; `MIOPEN_DEBUG_FIND_ONLY_SOLVER=<id|name>` forces one solver; `MIOPEN_FIND_ENFORCE` NONE/1, DB_UPDATE/2, SEARCH/3, SEARCH_DB_UPDATE/4, DB_CLEAN/5; compiled kernels cached in `~/.cache/miopen/` (`MIOPEN_DISABLE_CACHE=1`) — [MIOpen env variables](https://rocm.docs.amd.com/projects/MIOpen/en/develop/reference/env_variables.html), [MIOpen debug-log](https://rocm.docs.amd.com/projects/MIOpen/en/develop/how-to/debug-log.html)

### Inferences
- cuBLASLt and hipBLASLt expose the same mental model: *algo id × (tile, stages, split-K, swizzle, cluster)* = one precompiled kernel; the heuristic is a CPU-side lookup/model, which is why both docs tell you to cache the heuristic result (hipBLASLt: tens of µs per query). Tensile's `.dat` catalogs and `TENSILE_DB=0x8000` are the AMD-side equivalent of reading cuBLASLt kernel names in a profiler.
- For the reader's RX 7900 XTX (gfx1100): rocBLAS/hipBLASLt kernels for gfx1100 are assembly `.co` files generated by `KernelWriterAssembly.py` from library-logic YAML; `TENSILE_DB=0x8000` (or 0x80000) prints the exact kernel name and MT/MI/DepthU parameters chosen for a given GEMM — the readable "why this kernel" trace that NVIDIA only gives via `CUBLASLT_LOG_LEVEL=4` (heuristics trace).
- The naming convention is the reverse-engineering key: a Tensile kernel name literally spells its tile (`MT128x128x32`), matrix-instruction shape (`MI16x16x16x1`), prefetch depth (`PGR`, `PLR`), split-K (`GSU`), etc.; cuBLASLt names are not documented but tile enums (`128x128`, `256x128`...) and `splitK` show up in nsys kernel names.

## KQ2. Template libraries as readable vendor kernels: CUTLASS 3/4 + CuTe, Composable Kernel / CK-Tile, ThunderKittens, rocWMMA

### Takeaway
Template libraries make the structure of a vendor GEMM/attention kernel explicit as C++ types: a *layout algebra* (CuTe `Layout`/`Tensor`), a *collective mainloop* (producer/consumer pipeline over TMA/cp.async + MMA atoms), an *epilogue*, a *tile scheduler*, and a *kernel schedule tag* (warp-specialized, ping-pong, cooperative). What they generate is one kernel per instantiation; what they abstract is the thread→data mapping and the async pipeline.

### Cited Findings
- CUTLASS 3.0 "detaches its interface layers from the hardware, centering them instead around the natural structure of GEMM algorithms"; the hierarchy is Device → Kernel → Collective; CuTe provides `Layout` and `Tensor` objects that "compactly package the type, shape, memory space, and layout of data"; all 2.x iterators are replaced by `cute::Tensor`s and mainloops/epilogues are dispatched on tag policies — [media/docs/cpp/cutlass_3x_design.md](https://github.com/NVIDIA/cutlass/blob/main/media/docs/cpp/cutlass_3x_design.md)
- Collective API: `cutlass::gemm::collective::CollectiveMma` is "the largest collection of threads" cooperating on a tile; a collective uses `TiledMma` and `TiledCopy`; `CollectiveBuilder<..., TileShape_MNK, ClusterShape_MNK, StageCount, KernelScheduleType>::CollectiveOp` picks an implementation; kernel schedule tags: `KernelCpAsyncWarpSpecializedPingpong`, `KernelCpAsyncWarpSpecializedCooperative`, `KernelTmaWarpSpecialized`, `KernelTmaWarpSpecializedPingpong`, `KernelTmaWarpSpecializedCooperative`, or `KernelScheduleAuto` — [media/docs/cpp/gemm_api_3x.md](https://github.com/NVIDIA/cutlass/blob/main/media/docs/cpp/gemm_api_3x.md)
- The concrete mainloops are one file per (arch × data path): e.g. `include/cutlass/gemm/collective/sm90_mma_tma_gmma_ss_warpspecialized.hpp`, `sm90_mma_tma_gmma_rs_warpspecialized_mixed_input.hpp`, `sm100_mma_warpspecialized.hpp`, `sm100_blockscaled_mma_warpspecialized.hpp`, `sm120_mma_tma.hpp`, `sm120_blockscaled_mma_tma.hpp`, `sm80_mma_multistage.hpp`, `sm70_mma_twostage.hpp` (58 files at commit 78e4622) — [include/cutlass/gemm/collective/](https://github.com/NVIDIA/cutlass/tree/main/include/cutlass/gemm/collective). Note: `sm120_*` (consumer Blackwell, the reader's RTX 5060 Ti) uses TMA + `mma` (not the `sm100` tcgen05/TMEM path) — inferred from file names.
- Pipelines: `cutlass::PipelineAsync<NumStages>` / `PipelineTmaAsync` with `producer_acquire`, `producer_commit`, `consumer_wait`, `consumer_release`, `make_producer_start_state`; `params.producer_arv_count`, `consumer_arv_count` — [media/docs/cpp/pipeline.md](https://github.com/NVIDIA/cutlass/blob/main/media/docs/cpp/pipeline.md)
- CUTLASS kernels support Programmatic Dependent Launch: build with `-DCUTLASS_ENABLE_GDC_FOR_SM90=1` / `CUTLASS_ENABLE_GDC_FOR_SM100`, run with `gemm.run(stream, nullptr, /*launch_with_pdl=*/true)`; example 63 prefetches weights during the prologue before `cudaGridDependencySynchronize` — [media/docs/cpp/dependent_kernel_launch.md](https://github.com/NVIDIA/cutlass/blob/main/media/docs/cpp/dependent_kernel_launch.md)
- CuTe tutorial sequence: `01_layout.md`, `02_layout_algebra.md`, `03_tensor.md`, `04_algorithms.md`, `0t_mma_atom.md`, `0x_gemm_tutorial.md`, `0y_predication.md`, `0z_tma_tensors.md` — [media/docs/cpp/cute/](https://github.com/NVIDIA/cutlass/tree/main/media/docs/cpp/cute)
- CuTe DSL (Python): "With the release of 4.0, we released the first of these in CuTe DSL", exposing "layouts, tensors, hardware atoms, and full control over the hardware thread and data hierarchy" consistent with CuTe C++; targets Ampere/Hopper/Blackwell; 4.3 added Apache TVM-FFI to reduce host JIT overhead; repo dir `python/CuTeDSL/` — [CUTLASS Python DSL overview](https://docs.nvidia.com/cutlass/media/docs/pythonDSL/overview.html), [PyPI nvidia-cutlass-dsl](https://www.pypi.org/project/nvidia-cutlass-dsl-libs-base)
- Composable Kernel (AMD): "Tensor Coordinate Transformation" + tile-based programming; four layers "Templated Tile Operators", "Templated Kernel and Invoker", "Instantiated Kernel and Invoker", Client API; build with `GPU_TARGETS` (examples `gfx908;gfx90a;gfx942`, also `gfx1030`, `gfx1100`, `gfx1101`, `gfx1151`); each `-j` thread may use ~2 GB RAM; `DTYPES`, `DISABLE_DL_KERNELS`, `DISABLE_DPP_KERNELS` — [composable_kernel README](https://github.com/ROCm/composable_kernel/blob/develop/README.md)
- ThunderKittens: header-only CUDA framework; tiles "no smaller than 16x16 values" — register tiles `kittens::rt` (e.g. `rt_bf<32,16>`), shared tiles `st` (e.g. `st_hf<32,64>`); warp-level ops by default, `kittens::group<N>` / `warpgroup::mma_AB` for WGMMA; `tma::load_async`/`store_async`; "Load-Store-Compute-Finish" template with `producer`/`consumer` structs; H100 matmul "about 855 TFLOPs on an H100 (86% of theoretical max)"; "built from the hardware up; we do what the silicon tells us"; AMD via separate HipKittens — [ThunderKittens README](https://github.com/HazyResearch/ThunderKittens/blob/main/README.md)
- Helion (Meta/PyTorch, blog 2025-10-22, 1.0 GA 2026-04-07): Python-embedded DSL that compiles to Triton; "the programmer only specifies to tile the iteration space", autotuner picks tile sizes/order/layouts; AMD guide reports ~10 min autotuning over hundreds of Triton variants — [PyTorch Helion blog](https://pytorch.org/blog/helion/), [PyPI helion](https://pypi.org/project/helion), [ROCm Helion notebook](https://rocm.docs.amd.com/projects/ai-developer-hub/en/v14.0/notebooks/gpu_dev_optimize/helion_gpu_kernel_dev.html)

### Inferences
- The per-arch mainloop files are the "readable cuBLAS": the same tile/stage/cluster knobs that cuBLASLt exposes as opaque `CUBLASLT_ALGO_CONFIG_*` ids appear in CUTLASS as template parameters (`TileShape`, `ClusterShape`, `StageCount`, `KernelSchedule`). Reading `sm120_mma_tma.hpp` is the most direct way to learn what a Blackwell-consumer GEMM does.
- On AMD the equivalent "readable rocBLAS" is CK/CK-Tile (HIP C++), not Tensile (which emits assembly from Python); CK's `gfx1100` target is listed, so RDNA3 kernels can be built and read.
- ThunderKittens and CuTe both converge on "tile as the unit, warp as the actor, async pipeline between load and MMA"; this is the structure a hand-written fast kernel has regardless of DSL.

### Gaps
- rocWMMA (AMD's WMMA C++ wrapper) was not reached by any fetch; its role (a thin `wmma::` intrinsic layer for RDNA3/CDNA, used by llama.cpp's HIP flash-attention via `GGML_HIP_ROCWMMA_FATTN`) is only inferred from the ggml-hip CMake option name.
- CK-Tile internals (pipelines, warp-gemm ops) were not read; only the README layering.
- CUTLASS 4.x "Gluon-like" explicit-layout DSL comparison not done.

## KQ3. Generators and compilers: Triton, Gluon, Tensile, TVM/Ansor, Halide, Mojo, Pallas, Helion, CuTe DSL; AI-driven generation

### Takeaway
Kernel generators split into (a) *schedule-search* systems that enumerate tile/pipeline parameters and benchmark (Tensile, TVM/Ansor/MetaSchedule, Helion autotuner, cuBLASLt/hipBLASLt offline tuning), and (b) *tile-level compilers* that lower a block-level program through MLIR to PTX/AMDGCN (Triton → Gluon for explicit layouts; CuTe DSL; Pallas/Mosaic). AI-driven loops (AlphaEvolve) sit on top of (a): they mutate the heuristic/tiling code and keep what benchmarks faster.

### Cited Findings
- Triton pipeline: Python AST → Triton-IR (TTIR, "unoptimized, machine independent"), → TritonGPU-IR (TTGIR, adds layouts: `#blocked` with `sizePerThread`, `threadsPerWarp`, `warpsPerCTA`, `order`; MMA/dot-operand layouts chosen here; coalescing and software pipelining passes), → LLVM-IR → PTX (then `ptxas` → cubin) or AMDGCN — [PyTorch blog: Triton kernel compilation stages](https://pytorch.org/blog/triton-kernel-compilation-stages/); dialect sources in the Triton repo under `lib/Dialect/{Triton,TritonGPU,TritonNvidiaGPU,Gluon,TritonInstrument}` and backends `third_party/{nvidia,amd}` (verified in the local clone).
- Gluon exists as `python/triton/experimental/gluon/` with `_compiler.py`, `_runtime.py`, `language/{_core.py,_layouts.py,_semantic.py,...}`, `language/nvidia`, `language/amd` and a `lib/Dialect/Gluon` MLIR dialect — local Triton clone (path `scratchpad/stack_fund/triton`); no official doc page was fetched (Gap).
- Tensile = YAML-driven benchmark+generate: `Tensile/Configs/` holds problem/solution configs (`mfma/`, `miopen/`, `deep_bench_*.csv`), `BenchmarkProblems.py` runs the sweep, `KernelWriterAssembly.py` emits GCN/RDNA assembly, `TensileCreateLibrary.py` assembles/links `.co` and writes the `.dat` catalogs; `ReplacementKernels.py` / `CustomKernels/` allow hand-written assembly to be dropped in under a `CustomKernelName` — [ROCm/Tensile tree](https://github.com/ROCm/Tensile/tree/develop/Tensile)
- torch.compile: default backend Inductor lowers a TorchDynamo FX graph through its own IR, applies fusion passes and emits Triton kernels for GPU (C++ for CPU); `TORCH_COMPILE_DEBUG=1` dumps generated kernels; `mode="max-autotune"` benchmarks multiple implementations — [torch.compiler get started](https://docs.pytorch.org/docs/2.3/torch.compiler_get_started.html), [TorchInductor design thread](https://dev-discuss.pytorch.org/t/torchinductor-a-pytorch-native-compiler-with-define-by-run-ir-and-symbolic-shapes/747)
- Helion: higher-level than Triton, autotunes "tile sizes, iteration order, and memory layout" — [PyTorch Helion blog](https://pytorch.org/blog/helion/)
- CuTe DSL: Python JIT exposing CuTe layouts/atoms; first released with CUTLASS 4.0 — [CUTLASS Python DSL overview](https://docs.nvidia.com/cutlass/media/docs/pythonDSL/overview.html)
- AlphaEvolve (DeepMind, 2025-05-14): "By finding smarter ways to divide a large matrix multiplication operation into more manageable subproblems, it sped up this vital kernel in Gemini's architecture by 23%, leading to a 1% reduction in Gemini's training time"; also "up to a 32.5% speedup for the FlashAttention kernel implementation" — [DeepMind blog](https://deepmind.google/blog/alphaevolve-a-gemini-powered-coding-agent-for-designing-advanced-algorithms/)
- CUDA-L2 (arXiv 2512.02551, Dec 2025): RL-driven generation that beats cuBLAS on matmul, using cuBLASLt heuristic candidates as the baseline — [arXiv](https://arxiv.org/pdf/2512.02551)

### Inferences
- Tensile and cuBLASLt offline tuning are the same idea at different layers: both reduce "which kernel" to a lookup table keyed by (arch, dtype, transpose, M/N/K) that was filled by benchmarking.
- Triton's `#blocked`/MMA layouts are the compiler-internal version of CuTe `Layout`; Gluon exposes them to the user, so Triton (Gluon) and CuTe DSL converge on "explicit layouts + explicit async pipelines" for Blackwell/Hopper.
- For the reader: Triton's AMD backend emits AMDGCN for gfx1100 via LLVM, so Triton is the fastest path to generating *readable* RDNA3 kernels and dumping their ISA; Tensile is the path to understanding how rocBLAS's *production* kernels were made.

- No primary sources fetched for TVM/Ansor/MetaSchedule, Halide, Mojo, Pallas/Mosaic, XLA fusion; they are only placed in the taxonomy from prior knowledge (flag as unverified in the report).
- Gluon official tutorials and Blackwell-specific API (TMEM, tcgen05 wrappers) not fetched.
- Sakana "AI CUDA Engineer" / KernelBench results not fetched.

## KQ4. Fusion and graphs: why launch overhead matters, kernel fusion, CUDA Graphs / hipGraph, persistent kernels & megakernels, PDL, stream concurrency

### Takeaway
A decode step of a small LLM at batch 1 is ~100 kernels each lasting a few µs, so per-kernel launch/drain costs (~2 µs H100 stream launch, ~1.3 µs with CUDA graphs, plus "tail" idle SMs) can eat 30-50% of the step; the remedies, in increasing aggressiveness, are fusion (fewer kernels), CUDA/HIP graphs (one launch per step, `cudaGraphExecUpdate` for parameter changes), PDL (overlap prologue of kernel N+1 with epilogue of N), multi-stream concurrency, and megakernels (one persistent kernel interpreting an instruction stream with counters in global memory).

### Cited Findings

**Launch overhead numbers**
- Hazy Research (2025-05-27, H100): "dummy kernel" launch cost ≈ 2.1 µs on a CUDA stream, ≈ 1.3 µs with CUDA graphs; a Llama-3.2-1B forward is ~7 kernels × 16 layers (~112 kernels); memory-bound bound 3.35 TB/s ÷ 2.48 GB ≈ 1350 passes/s, but with ~5 µs stall per kernel the estimate drops to ~770/s; tail effect example: a 512-block down-projection on a 148-SM B200 "we end up with 80 empty SM's at the end"; PDL's `cudaGridDependencySynchronize` is "coarse" (attention must wait for all of Q, K, V) — [Look Ma, No Bubbles!](https://hazyresearch.stanford.edu/blog/2025-05-27-no-bubbles)
- NVIDIA on llama.cpp (A100, Llama 7B Q4, nsys): gaps between kernels within a token come from *GPU-side* launch overhead (the CPU launched well ahead); with CUDA graphs "the gap between each kernel within the graph is now very small"; best speedup 1.2x (Llama 7B on H100); CUDA graphs enabled by default for batch size 1 — [NVIDIA blog: Optimizing llama.cpp with CUDA Graphs](https://developer.nvidia.com/blog/optimizing-llama-cpp-ai-inference-with-cuda-graphs/)
- Forum/community datapoints (lower confidence): ~2.9 µs between successive kernels under nsys ([NVIDIA forum](https://forums.developer.nvidia.com/t/kernel-switch-latency-successive-kernels-switch-latency/309504)); ~3-7 µs null-kernel launch in public measurements, ~5 µs on Kepler in 2012 ([NVIDIA forum](https://forums.developer.nvidia.com/t/any-way-to-measure-the-latency-of-a-kernel-launch/221413)); an RTX 5070 Ti / CUDA 13.0 community test shows naive ≈ 52.9 µs/kernel vs ≈ 47.0 µs with graphs for its specific tiny-kernel loop (ranking, not absolute, is what the author stresses) ([search summary; source not fetched](https://forums.developer.nvidia.com/t/any-way-to-measure-the-latency-of-a-kernel-launch/221413)).
- AMD: a 2020 LLVM patch reported HIP "typical kernel launching latency is about 500us" with ~60 µs from `__hipPushConfigure/__hipPopConfigure` (old ROCm, before the patch) — [D86376](https://lists.llvm.org/pipermail/cfe-commits/Week-of-Mon-20200824/335286.html). No current RDNA3 `hipLaunchKernel` measurement found (Gap). A secondary blog summarizing an IBM paper claims full HIP graphs cut MI300 decode latency ~2x vs ~6% for CUDA graphs on H100 — unverified.

**CUDA Graphs / hipGraph API**
- A graph is "a series of operations (such as kernel launches and data movement) connected by dependencies, defined separately from its execution"; stages: definition → instantiation (`cudaGraphInstantiate` → executable graph) → execution (`cudaGraphLaunch(graphExec, stream)`, repeatable); node types: kernel, host function, memcpy, memset, empty, event record/wait, external semaphore, conditional (IF/WHILE/SWITCH via `cudaGraphConditionalHandleCreate` + device `cudaGraphSetConditional`), memory, child graph; stream capture: `cudaStreamBeginCapture()/cudaStreamEndCapture()`, `cudaStreamBeginCaptureToGraph()`, cross-stream fork/join via `cudaEventRecord`/`cudaStreamWaitEvent`, all streams must rejoin before end-capture; synchronizing a capturing stream invalidates the capture; benefits: "reduced CPU launch cost" and "whole-workflow optimizations" — [CUDA Programming Guide §4.2 CUDA Graphs](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cuda-graphs.html)
- Updating: `cudaGraphExecUpdate()` requires a topologically identical graph; node params (kernel args, addresses) may change, topology/node types may not; per-node `cudaGraphExecKernelNodeSetParams()`, `cudaGraphNodeSetEnabled()`; device graph launch needs `cudaGraphInstantiateFlagDeviceLaunch` with modes `cudaStreamGraphFireAndForget`, `cudaStreamGraphTailLaunch`, `cudaStreamGraphFireAndForgetAsSibling` (up to 120 fire-and-forget graphs per execution); edge data since CUDA 12.3, only non-default type `cudaGraphDependencyTypeProgrammatic` (PDL inside graphs) — [same page](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cuda-graphs.html)
- hipGraph: same model — `hipStreamBeginCapture()/hipStreamEndCapture()`, `hipStreamBeginCaptureToGraph()`, explicit `hipGraphAddKernelNode()`/`hipGraphAddDependencies()`, `hipGraphInstantiate()` → `hipGraphExec_t`, `hipGraphLaunch()`; node types per `hipGraphNodeType` (empty, child graph, kernel, host, memcpy/memset, event, external semaphore); synchronous `hipMalloc/hipMemcpy/hipFree` on the default stream are illegal during capture (use `*Async`); graph memory pools `hipDeviceGetGraphMemAttribute()`, `hipDeviceGraphMemTrim()`; stated benefit: launch overhead reduced because "most initialization is done ahead of time", only worthwhile for many iterations; no numbers given — [HIP graphs docs](https://rocm.docs.amd.com/projects/HIP/en/latest/how-to/hip_runtime_api/hipgraph.html)

**Programmatic Dependent Launch (PDL)**
- Available from compute capability 9.0; the secondary kernel is launched with `cudaLaunchKernelEx` carrying `cudaLaunchAttributeProgrammaticStreamSerialization`; the primary calls `cudaTriggerProgrammaticLaunchCompletion()` (implicit at block exit otherwise); the secondary must call `cudaGridDependencySynchronize()` before consuming primary results ("will block until all primary kernels the secondary kernel is dependent on have completed"); overlap is opportunistic — relying on it "is unsafe and can lead to deadlock"; in graphs: edge type `cudaGraphDependencyTypeProgrammatic` with ports `cudaGraphKernelNodePortProgrammatic` / `cudaGraphKernelNodePortLaunchCompletion`; capture attribute `cudaLaunchAttributeProgrammaticEvent` with `triggerAtBlockStart` — [CUDA Programming Guide §4.5 PDL](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/programmatic-dependent-launch.html)
- llama.cpp uses PDL: `ggml/src/ggml-cuda/common.cuh` wraps `cudaGridDependencySynchronize()` / `cudaTriggerProgrammaticLaunchCompletion()` (lines ~136/142), sets `attr.id = cudaLaunchAttributeProgrammaticStreamSerialization` (~1615), reads env `GGML_CUDA_PDL` (~1703) and launches via `cudaLaunchKernelEx(&pdl_cfg.cfg, kernel, args...)` (~1710); host-side needs CUDART ≥ 11.8 — [ggml-cuda/common.cuh](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/common.cuh)

**Fusion in production engines**
- llama.cpp ggml-cuda fuses op patterns at graph-compute time with `ggml_cuda_can_fuse(cgraph, i, {ops...}, {unary ops...})`: `{RMS_NORM, MUL}`, `{RMS_NORM, MUL, ADD}`, `{RMS_NORM, MUL, ROPE}`, `{RMS_NORM, MUL, ROPE, VIEW, SET_ROWS}`, `{ROPE, VIEW, SET_ROWS}`, `{RMS_NORM, SCALE}`, `{SSM_CONV, ADD, UNARY(SILU)}`, `{UNARY(SILU|SIGMOID|SOFTPLUS), MUL}`, `{UNARY(RELU), SQR}`, `{SCALE, UNARY(TANH), SCALE}`, and MoE/FFN `{MUL_MAT_ID, bias, MUL_MAT_ID, bias, GLU}` / `{op, op, GLU}` paths that call `ggml_cuda_mul_mat_vec_q(..., &fusion_data)` with the GLU fused into the matvec; `GGML_CUDA_DISABLE_FUSION` env disables; `ggml_backend_cuda_graph_optimize()` adds allocation dependencies for "performance positive fusions" — [ggml-cuda.cu](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/ggml-cuda.cu) (lines ~3464-4520, ~4847)
- cuDNN runtime fusion engines generate fused kernels at runtime for Matmul/Conv/Pointwise patterns — [cuDNN Graph API](https://docs.nvidia.com/deeplearning/cudnn/latest/developer/graph-api.html); cuBLASLt fuses epilogues (bias/ReLU/GELU) into the GEMM — [cublasLt.h](https://decoder-genetics.wustl.edu/software/conda/lib/python3.1/site-packages/nvidia/cublas/include/cublasLt.h)

**Megakernels / persistent kernels**
- Hazy Research megakernel: one persistent kernel per forward pass; each SM runs an *interpreter* over a pre-generated (Python, reused across hundreds of passes) instruction stream of 7 instruction types (fused RMSnorm+QKV+RoPE; attention; attention reduction; O-proj+residual; fused RMSnorm+up-gate+SiLU; down-proj+residual; RMSnorm+LM head); shared memory paged as 13 × 16 KiB pages in the first 213 kB of H100 smem; dependencies via a global-memory counter array (instruction completion increments; consumers spin until targets reached); MLP split into 4 chunks each with its own counter. Results: H100 < 1 ms per bf16 forward of Llama-1B, 78% of memory bandwidth, ~2.5× vLLM, >1.5× SGLang; B200 < 680 µs, ~3.5× vLLM. B200 breakdown of 600 µs: 250 µs activation store/consistency/load (each ~500 ns), 200 µs RMSnorm+matvec (95% matvec), 30 µs waiting on weight loads (40% in LM head), 40 µs warp sync (async barriers ~60 ns each), 80 µs setup/instruction barriers/page bookkeeping — [Look Ma, No Bubbles!](https://hazyresearch.stanford.edu/blog/2025-05-27-no-bubbles); follow-up for larger models/TP: [How Many Llamas Can Dance in the Span of a Kernel?](https://hazyresearch.stanford.edu/blog/2025-09-28-tp-llama-intro)
- Mirage Persistent Kernel (MPK, CMU; arXiv 2512.22219, OSDI'26): "a compiler and runtime system that automatically transforms LLM inference into a single megakernel"; SM-level task graph; `mi.PersistentKernel(world_size, mpi_rank, num_workers=96, num_local_schedulers=48, num_remote_schedulers=0, meta_tensors=[step, tokens], ...)` where `num_workers + (num_local_schedulers + num_remote_schedulers)/4` must equal the SM count; fused ops like `mpk.rmsnorm_linear_layer(input, weight_norm, weight_linear, output, grid_dim=(96,1,1), block_dim=(128,1,1))`; each fused op's `grid_dim` = number of tasks; `mpk.compile(); mpk()`; README claims 1.2×-6.7× latency reduction (paper abstract: up to 1.7× vs kernel-per-operator systems); demo `python demo/qwen3/demo.py --use-mirage` compiles Qwen3-8B — [mirage mpk README](https://raw.githubusercontent.com/mirage-project/mirage/mpk/README.md), [arXiv 2512.22219](https://arxiv.org/pdf/2512.22219)

**Stream concurrency inside an engine**
- ggml-cuda runs independent graph regions on multiple streams: `ggml_cuda_concurrent_event` with `fork_event`, `n_streams`, `original_order`; at a fork node it records `fork_event` on stream 0 and `cudaStreamWaitEvent` on streams 1..n (`GGML_CUDA_MAX_STREAMS`), controlled by env `GGML_CUDA_GRAPH_OPT`; these forks are captured into the CUDA graph when graphs are enabled — [ggml-cuda.cu](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/ggml-cuda.cu) (lines ~4524-4600, ~4970, ~5160)

### Inferences
- The numbers line up: ~100 kernels × ~2 µs launch ≈ 200 µs vs a ~600-800 µs H100 step for a 1B model → launch/drain is 25-40% of batch-1 decode; for a 27B model on a 7900 XTX (≈ 15 GB of weights at Q4 over ~960 GB/s ≈ 16 ms/step) the same ~100-200 kernels × even 10 µs HIP launch is only ~1-2 ms, i.e. ≤10% — so on the reader's main card graphs/fusion matter less than bandwidth-efficient matvec kernels, while on the 5060 Ti with a small model they matter a lot. (Inference; weight/bandwidth figures need the hardware track.)
- CUDA graphs remove CPU and most GPU launch gaps but not the *tail effect* (SM idle while the last blocks finish) nor the drain/fill between dependent kernels; PDL addresses fill/drain; only megakernels address all three, at the cost of a custom scheduler.
- hipGraph exists but AMD provides no latency numbers and has no PDL equivalent documented; the llama.cpp HIP build has `GGML_HIP_GRAPHS` as an opt-in (`USE_CUDA_GRAPH` is defined when `GGML_CUDA_USE_GRAPHS || GGML_HIP_GRAPHS || GGML_MUSA_GRAPHS`, `common.cuh` ~1260), so the reader can A/B this on gfx1100.

### Gaps
- No verified current `hipLaunchKernel` latency on RDNA3; needs a microbenchmark (empty kernel, 10k launches, `hipEventElapsedTime` and rocprof) — belongs to the microbenchmark track.
- The llama.cpp HIP-graphs commit (llama/11362) was found but its before/after `llama-bench` numbers were not fetched.
- The IBM MI300 vs H100 graph-speedup claim is secondhand.

## KQ5. LLM inference engines as kernel orchestrators: llama.cpp/ggml, vLLM, SGLang, TensorRT-LLM, ExLlama; where decode time goes

### Takeaway
An inference engine is a *graph builder + backend scheduler + kernel-selection policy + graph-replay cache*: llama.cpp builds a ggml compute graph per batch, `ggml_backend_sched` splits it across backends, ggml-cuda (shared with HIP through `vendors/hip.h` macros) picks matmul kernels by (quant type, batch size, compute capability), fuses op patterns, and replays a CUDA graph keyed by the graph; vLLM/SGLang wrap a PyTorch model with torch.compile piecewise graphs split at the attention custom op, select an attention backend by priority/arch, and capture CUDA graphs per batch-size bucket.

### Cited Findings

**llama.cpp / ggml structure**
- Backend interface `struct ggml_backend_i` (ggml/src/ggml-backend-impl.h): `get_name`, `free`, `set_tensor_async`, `get_tensor_async`, `set_tensor_2d_async`, `cpy_tensor_async`, `synchronize`, `graph_plan_create/free/update/compute`, `graph_compute(backend, cgraph)`, `event_record/event_wait`, `graph_optimize(backend, cgraph, params)`; device interface has `get_name`, `get_description`, `get_memory`, `get_type`, `get_props` — [ggml-backend-impl.h](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-backend-impl.h)

**Matmul kernel selection in ggml-cuda (the policy)**
- `ggml_cuda_mul_mat(ctx, src0, src1, dst)` (ggml-cuda.cu ~1956): order of checks — (0) FWHT special case; (1) if `bad_padding_clear` or src1/dst not F32 → `ggml_cuda_mul_mat_cublas`; (2) `ggml_cuda_should_use_mmvf(src0->type, cc, warp_size, ne, nb, ne11)` → `ggml_cuda_mul_mat_vec_f` ("only faster for GPUs without tensor cores or with a thin src0 matrix (particularly KQV in attention)"); (3) transposed-vector MMVF path when `ne01 == 1 && ne11 > MMVF_MAX_BATCH_SIZE`; (4) `ggml_cuda_should_use_mmf` → `ggml_cuda_mul_mat_f`; (5) `ggml_cuda_should_use_mmvq(src0->type, cc, ne11)` → `ggml_cuda_mul_mat_vec_q`; (6) `ggml_cuda_should_use_mmq(src0->type, cc, ne11, 0)` → `ggml_cuda_mul_mat_q`; (7) else cuBLAS/hipBLAS — [ggml-cuda.cu](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/ggml-cuda.cu)
- Thresholds: `MMVQ_MAX_BATCH_SIZE 8` (mmvq.cuh), `MMVF_MAX_BATCH_SIZE 8` (mmvf.cuh), `MMQ_DP4A_MAX_BATCH_SIZE 64` ("Max. batch size to use for dp4a MMQ kernels when FP16 tensor cores are available"), `MMQ_ITER_K 256`, `MMQ_NWARPS 8`, `MMQ_TILE_NE_K 32` — [mmvq.cuh](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/mmvq.cuh), [mmq.cuh](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/mmq.cuh)
- `ggml_cuda_should_use_mmq(type, cc, ne11, n_experts)` (mmq.cu ~355): `GGML_CUDA_FORCE_CUBLAS` → false; supported types Q1_0/Q2_0/Q4_0/Q4_1/Q5_0/Q5_1/Q8_0, Q2_K..Q6_K, IQ1_S/IQ2_XXS/IQ2_XS/IQ2_S/IQ3_XXS/IQ3_S/IQ4_XS/IQ4_NL, MXFP4, NVFP4; requires ≥ 48 KiB shared memory per block; `turing_mma_available(cc)` → true; else on CUDA `!fp16_mma_hardware_available(cc) || ne11 < MMQ_DP4A_MAX_BATCH_SIZE`; on AMD `(!GGML_CUDA_CC_IS_CDNA(cc)) || ne11 < MMQ_DP4A_MAX_BATCH_SIZE` (i.e. RDNA3 always prefers MMQ over hipBLAS for supported quant types); `GGML_CUDA_FORCE_MMQ` forces — [mmq.cu](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/mmq.cu)

- Flash attention selection `ggml_cuda_get_best_fattn_kernel(device, dst)` (fattn.cu ~540): returns `BEST_FATTN_KERNEL_VEC` (100), `TILE` (200), `MMA_F16` (400) or `NONE`; computes `gqa_ratio = Q->ne[2]/K->ne[2]`, `gqa_opt_applies = gqa_ratio >= 2 && mask && max_bias == 0 && K->ne[1] % FATTN_KQ_STRIDE == 0`; `can_use_vector_kernel = Q->ne[0] <= 256 && Q->ne[0] % 64 == 0 && Q->ne[0] != 192 && K->ne[1] % FATTN_KQ_STRIDE == 0`; on Turing+ MMA: vec kernel for batch-1 decode (`Q->ne[1] == 1`, Ada+; or `Q->ne[1] <= 2`) unless `gqa_ratio > 4 && (Q->ne[0] >= 256 || K->ne[1] >= 8192)` or a "sparse decode" MMA variant applies, else MMA_F16; Volta: VEC if `Q->ne[1]*gqa_ratio_eff <= 2`, TILE if `<= 16`, else MMA; AMD/non-tensor-core paths fall to VEC/TILE (lines ~683-718) — [fattn.cu](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/fattn.cu)

**CUDA graph lifecycle in ggml-cuda**
- `ggml_backend_cuda_graph_compute()` (~4759): key = `cgraph->nodes[0]` (`ggml_cuda_graph_get_key`); `ggml_cuda_graph_set_enabled()`; `ggml_cuda_graph_check_compability()` (MUL_MAT_ID sync fallback disables); `ggml_cuda_graph_update_required()` compares per-node `ggml_cuda_graph::node_properties`; first call or changed properties → execute directly; stable → capture (`ggml_cuda_graph_evaluate_and_capture`), `cudaGraphInstantiate(&graph->instance, graph->graph, NULL, NULL, 0)`, on later changes `cudaGraphExecUpdate(graph->instance, graph->graph, &result_info)` and only on failure `cudaGraphExecDestroy` + re-instantiate; then `cudaGraphLaunch(graph->instance, cuda_ctx->stream())` — [ggml-cuda.cu](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/ggml-cuda.cu) (~2736-2807, ~4524-4830)

**What a Qwen3-class decode step is made of (graph level)**
- `src/models/qwen3.cpp::build_backbone`: per layer `build_norm(..., LLM_NORM_RMS)` → `build_qkv` (Q/K/V projections) → `build_norm` on Q and K (`attn_q_norm`, `attn_k_norm`) → `ggml_rope_ext` on Q and K → `build_attn(inp_attn, wo, ...)` (→ `GGML_OP_FLASH_ATTN_EXT` when flash attention is enabled; `LLAMA_FLASH_ATTN_TYPE_AUTO` default in llama-context.cpp ~3991) → `ggml_add` residual → `build_norm` → `build_ffn(up, gate, down, LLM_FFN_SILU, LLM_FFN_PAR)` (parallel gate/up → `ggml_swiglu_split` in llama-graph.cpp ~1988) → `ggml_add`; final `build_norm` + `build_lora_mm(model.output, ...)` for logits. Layer counts: 28 (0.6B/1.7B), 36 (4B/8B), 40 (14B), 64 (32B) — [src/models/qwen3.cpp](https://github.com/ggml-org/llama.cpp/blob/master/src/models/qwen3.cpp). Qwen3-MoE / Qwen3-Next (`qwen3moe.cpp`, `qwen3next.cpp`) add `GGML_OP_MUL_MAT_ID` expert matmuls and `GGML_OP_GATED_DELTA_NET`; the CUDA backend has dedicated `gated_delta_net.cu` / `gated-delta-net-mma.cu`. (The user's "Qwen3.8-27B" naming does not match any `qwen3.cpp` size table; see Gaps.)
- Op enum entries relevant per token: `GGML_OP_RMS_NORM`, `GGML_OP_MUL_MAT`, `GGML_OP_MUL_MAT_ID`, `GGML_OP_ROPE`, `GGML_OP_FLASH_ATTN_EXT`, `GGML_OP_GATED_DELTA_NET`, `GGML_OP_GLU` with `GGML_GLU_OP_SWIGLU` — [ggml.h](https://github.com/ggml-org/llama.cpp/blob/master/ggml/include/ggml.h)
- With fusion, a dense Qwen3 layer at batch 1 on CUDA collapses to roughly: fused `{RMS_NORM, MUL}` (attn norm) → 3 (or 1 fused) `mul_mat_vec_q` for QKV → fused `{RMS_NORM, MUL, ROPE, VIEW, SET_ROWS}` for Q/K-norm+RoPE+KV write → `flash_attn_ext_vec` → `mul_mat_vec_q` (wo) with fused bias/add → fused `{RMS_NORM, MUL}` → `mul_mat_vec_q` gate+up with fused GLU → `mul_mat_vec_q` down with fused residual add — inferred from the `ggml_cuda_can_fuse` pattern list above; exact count must be confirmed with `GGML_CUDA_GRAPH_DEBUG=1`/nsys (Gap).

**SGLang / TensorRT-LLM / ExLlama**
- SGLang piecewise CUDA graph: torch.compile custom backend traces the forward, splits at registered split ops; split-op submodules run eagerly while `CUDAPiecewiseBackend` submodules go through compile warmup → capture → replay; custom kernels must be wrapped with `register_custom_op`; "Breakable CUDA Graph" (BCG) instead marks `@eager_on_graph` breaks (521 lines vs 1,771 for the torch.compile path), default on prefill — [SGLang piecewise CUDA graph docs](https://docs.sglang.io/advanced_features/piecewise_cuda_graph.html), [LMSYS blog 2026-08-17](https://www.lmsys.org/blog/2026-08-17-advanced-cuda-graph)
- LMSYS numbers (gpt-oss-120b, TP4, 4×GB300, prefill one request at a time): full CUDA graph 1.93× vs eager, BCG 1.70×, TC-piecewise 1.45×; "latency stays flat across a 32× range in prompt length", attributed to launch overhead; 42 captured prefill shapes add 2.4 GB graph memory on GLM-5.2; torch.compile is 78-86% of prefill graph prep time (~90 s on a 235B MoE) — [LMSYS blog](https://www.lmsys.org/blog/2026-08-17-advanced-cuda-graph)
- TensorRT-LLM (classic engine path): `gpt_attention_plugin` ("auto" default) "for GPT-like decoder models", updates the KV cache in place; `gemm_plugin` options `auto|float16|float32|bfloat16|int32|fp8|nvfp4` backed by cuBLASLt; separate BERT attention plugin — [tensorrt_llm.plugin.plugin source](https://nvidia.github.io/TensorRT-LLM/1.3.0rc13/_modules/tensorrt_llm/plugin/plugin.html); TRT-LLM also has a torch.compile + piecewise CUDA graph feature page — [TRT-LLM docs](https://nvidia.github.io/TensorRT-LLM/1.3.0rc26/features/torch_compile_and_piecewise_cuda_graph.html)
- ExLlamaV2: compiles its own CUDA extensions at install; requires EXL2-quantized weights — [tutorial (secondary)](https://aiindigo.com/tutorials/getting-started-with-exllamav2-high-performance-llm-inference-on-consumer-gpus)

**Where decode time goes (numbers)**
- Hazy B200 megakernel breakdown (600 µs, Llama-1B bf16): 42% activation store/load + consistency waits, 33% norm+matvec compute, 5% weight-load waits, 7% warp sync, 13% scheduling overhead — [No Bubbles](https://hazyresearch.stanford.edu/blog/2025-05-27-no-bubbles)
- Hazy: vLLM/SGLang reach ≤ 50% of H100 bandwidth on this workload because of ~100 small kernels per pass — [No Bubbles](https://hazyresearch.stanford.edu/blog/2025-05-27-no-bubbles)
- NVIDIA/llama.cpp: before graphs, inter-token gaps = CPU graph build + sampling; intra-token gaps = GPU launch overhead; graphs give up to 1.2×; a further "~10%" expected from CPU-side work — [NVIDIA blog](https://developer.nvidia.com/blog/optimizing-llama-cpp-ai-inference-with-cuda-graphs/)

### Inferences
- The engine's kernel policy is *static heuristics keyed on (dtype/quant, batch, arch)* in llama.cpp (readable `if` chains with hard thresholds 8/64) vs *priority-ordered backend registries + per-shape graph caches* in vLLM/SGLang; neither benchmarks at runtime (unlike cuBLASLt/hipBLASLt "autotune" or MIOpen Find).
- On the reader's 7900 XTX with a Q4-class GGUF: every weight matmul at batch 1 goes to `mul_mat_vec_q` (ne11 ≤ 8), prompt processing (ne11 ≥ 9) goes to MMQ (RDNA3 is not CDNA, so MMQ is preferred over hipBLASLt for all batch sizes for supported quant types), and attention goes to the VEC/TILE flash-attention kernels (no `turing_mma`/`volta_mma` on AMD; the `RDNA3` macro path in `common.cuh`). hipBLAS/rocBLAS/Tensile kernels are only reached for F16/F32 weights or unsupported types.
- vLLM's `FULL_AND_PIECEWISE` and SGLang's BCG are the practical compromise between "graph everything" (needs static shapes) and "attention is dynamic": they graph the dense parts and leave attention as an eager custom op.

### Gaps
- "Qwen3.8-27B" does not correspond to any size in `qwen3.cpp` (28/36/40/64 layers = 0.6B..32B); the exact architecture file (`qwen3.cpp` vs `qwen3moe.cpp`/`qwen35*.cpp`/`qwen3next.cpp`) and thus whether `MUL_MAT_ID`/`GATED_DELTA_NET` kernels run must be checked against the GGUF metadata (`general.architecture`).
- The precise kernel count per decode step for a Qwen3-class model on ggml-cuda was not measured; `GGML_CUDA_GRAPH_DEBUG=1`, `GGML_SCHED_DEBUG=2`, or `nsys`/`rocprofv3 --kernel-trace` on `llama-bench -n 32` would give it.
- vLLM's exact backend priority order per compute capability (e.g. FlashInfer vs FlashAttention on sm_120 / Blackwell consumer) was not extracted from `cuda.py` (the function delegates to per-backend `priority` and validation helpers); for ROCm the AITER backends gate on `VLLM_ROCM_USE_AITER` (not verified in this read).
- No end-to-end "kernels vs launch gaps vs sync" breakdown for a 27B-class model on either of the reader's GPUs exists in the sources; only the 1B/H100/B200 megakernel breakdown and the A100 llama.cpp qualitative profile.
