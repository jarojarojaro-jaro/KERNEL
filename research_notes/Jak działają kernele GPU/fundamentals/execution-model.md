## KQ1. Definition and anatomy of a kernel (grid hierarchy, arguments, host stub, runtime kernel object)

### Takeaway
A kernel is one function body instantiated over an N-dimensional index space; the hardware only ever sees "a code entry address + a descriptor of resources + a pointer to an argument buffer + grid/workgroup sizes". On AMD all of that is literally one 64-byte AQL packet (`hsa_kernel_dispatch_packet_t`) pointing to a 64-byte kernel descriptor; on NVIDIA the same information is carried by `cuLaunchKernel(CUfunction, grid, block, smem, stream, kernelParams, extra)` and the closed driver builds the equivalent packet.

### Cited Findings
- PTX definition of the hierarchy: "A grid consists of either cooperative thread arrays or clusters of cooperative thread arrays"; a CTA is "an array of threads that execute a kernel concurrently or in parallel"; "Cluster is a group of CTAs that run concurrently or in parallel", supported only on sm_90+; threads in a CTA execute "in groups called warps, typically 32 threads each" — [PTX ISA 9.4 §2.1–2.3](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html)
- HIP vocabulary: "The smallest unit of execution in the HIP programming model is a thread, also called a work-item"; "The innermost grouping of threads is called a warp (HIP terminology) or wavefront (AMD ISA terminology)"; "thread block (or work-group in OpenCL terminology)"; "A grid represents the total collection of blocks (work-groups) launched for a single kernel execution" — [HIP 7.16.0 programming model](https://rocm.docs.amd.com/projects/HIP/en/latest/understand/programming_model.html)
- Vulkan vocabulary: "Compute workloads are formed from groups of work items called workgroups ... A workgroup is a collection of shader invocations that execute the same shader, potentially in parallel. Compute shaders execute in _global workgroups_ which are divided into a number of _local workgroups_ with a size that can be set by assigning a value to the LocalSize [or LocalSizeId] execution mode or via an object decorated by the WorkgroupSize decoration" — [Vulkan-Docs chapters/shaders.adoc `[[shaders-compute]]`](https://raw.githubusercontent.com/KhronosGroup/Vulkan-Docs/main/chapters/shaders.adoc); `vkCmdDispatch(commandBuffer, groupCountX, groupCountY, groupCountZ)`: "When the command is executed, a global workgroup consisting of groupCountX × groupCountY × groupCountZ local workgroups is assembled" — [chapters/dispatch.adoc](https://raw.githubusercontent.com/KhronosGroup/Vulkan-Docs/main/chapters/dispatch.adoc). Vulkan's `SubgroupSize` "must be a power-of-two value between minSubgroupSize and maxSubgroupSize" when varying subgroups are allowed; "Full subgroups are required when the X dimension of the workgroup size is a multiple of the reported value of SubgroupSize" — [shaders.adoc `[[shaders-varying-subgroup-size]]`, `[[shaders-full-subgroups]]`](https://raw.githubusercontent.com/KhronosGroup/Vulkan-Docs/main/chapters/shaders.adoc)
- CUDA built-ins: `dim3 gridDim`, `dim3 blockDim`, `uint3 blockIdx`, `uint3 threadIdx`, `int warpSize` ("A run-time value defined as the number of threads in a warp, commonly 32"); limits per CC 8.9/9.0/10.0/12.x: max threads/block 1024, grid x up to 2^31−1, y/z up to 65535, max z per block 64 — [CUDA PG 13.4.2 §5.4.2.2](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/cpp-language-extensions.html), [§5.1 Compute Capabilities](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/compute-capabilities.html)
- AMD dispatch packet (the exact runtime "launch record"): `hsa_kernel_dispatch_packet_t { uint16_t header; uint16_t setup /* dimensions, 2 bits */; uint16_t workgroup_size_x,y,z; uint16_t reserved0; uint32_t grid_size_x,y,z /* in work-items, not groups */; uint32_t private_segment_size /* bytes per work-item */; uint32_t group_segment_size /* bytes per work-group */; uint64_t kernel_object /* "Opaque handle to a code object that includes an implementation-defined executable code for the kernel" */; void* kernarg_address /* "Pointer to a buffer containing the kernel arguments ... must be allocated using hsa_memory_allocate, and must not be modified once the kernel dispatch packet is enqueued until the dispatch has completed" */; uint64_t reserved2; hsa_signal_t completion_signal; }` (64 bytes). `HSA_PACKET_TYPE_KERNEL_DISPATCH = 2`, `HSA_PACKET_TYPE_BARRIER_AND = 3`; header bits `HSA_PACKET_HEADER_SCACQUIRE_FENCE_SCOPE = 9`, `HSA_PACKET_HEADER_SCRELEASE_FENCE_SCOPE = 11`, scopes `HSA_FENCE_SCOPE_AGENT = 1`, `HSA_FENCE_SCOPE_SYSTEM = 2` — [ROCR-Runtime `runtime/hsa-runtime/inc/hsa.h` lines ~2825–3075](https://github.com/ROCm/ROCR-Runtime/blob/master/runtime/hsa-runtime/inc/hsa.h)
- `kernel_object` points at the 64-byte **kernel descriptor** ("A kernel descriptor consists of the information needed by CP to initiate the execution of a kernel, including the entry point address"; "CP microcode requires the Kernel descriptor to be allocated on 64-byte alignment"). Fields: bits 31:0 `GROUP_SEGMENT_FIXED_SIZE`, 63:32 `PRIVATE_SEGMENT_FIXED_SIZE`, 95:64 `KERNARG_SIZE`, 191:128 `KERNEL_CODE_ENTRY_BYTE_OFFSET` (signed offset from the descriptor to the first instruction), 415:384 `COMPUTE_PGM_RSRC1`, 447:416 `COMPUTE_PGM_RSRC2`, then `KERNEL_CODE_PROPERTIES` bits such as `ENABLE_SGPR_KERNARG_SEGMENT_PTR` (bit 451), `ENABLE_WAVEFRONT_SIZE32` (bit 458, GFX10+), `USES_DYNAMIC_STACK` (bit 459) — [AMDGPUUsage "Kernel Descriptor"](https://llvm.org/docs/AMDGPUUsage.html#kernel-descriptor). The ROCR C mirror is `amd_kernel_code_t` with `kernel_code_entry_byte_offset`, `compute_pgm_rsrc1/2`, `workitem_private_segment_byte_size`, `workgroup_group_segment_byte_size`, `kernarg_segment_byte_size`, `wavefront_sgpr_count`, `workitem_vgpr_count` — [`inc/amd_hsa_kernel_code.h` ~L231–244](https://github.com/ROCm/ROCR-Runtime/blob/master/runtime/hsa-runtime/inc/amd_hsa_kernel_code.h)
- How AMD kernel arguments reach the wave: "Kernel argument values are assigned to the kernel argument memory allocation ... For AMDGPU the kernel execution directly accesses the kernel argument memory in the same way constant memory is accessed"; the kernarg buffer "must be at least 16-byte aligned"; CP preloads SGPRs: "Kernarg Segment Ptr (2 SGPRs) 64-bit address of Kernarg segment. This is directly copied from the kernarg_address in the kernel dispatch packet. Having CP load it once avoids loading it at the beginning of every wavefront." Newer HW can preload argument *values* into up to 16 User SGPRs ("Preloaded Kernel Arguments", `kernarg_preload_spec_length`) — [AMDGPUUsage "Kernel Dispatch", "Initial Kernel Execution State"](https://llvm.org/docs/AMDGPUUsage.html#initial-kernel-execution-state)
- AMD hidden arguments: besides the user's parameters the compiler appends metadata-declared hidden args that the runtime fills: `hidden_block_count_x/y/z`, `hidden_group_size_x/y/z`, `hidden_remainder_x/y/z`, `hidden_global_offset_x`, `hidden_grid_dims`, `hidden_heap_v1`, `hidden_dynamic_lds_size`, `hidden_private_base`, `hidden_shared_base`, `hidden_queue_ptr`, `hidden_hostcall_buffer`, `hidden_default_queue`, `hidden_completion_action`, `hidden_multigrid_sync_arg` — [AMDGPUUsage code-object metadata (v5)](https://llvm.org/docs/AMDGPUUsage.html#code-object-v5-metadata); CLR fills them in `VirtualGPU::submitKernelInternal` → loop `for (i = signature.numParameters(); i < signature.numParametersAll(); ++i)` with `WriteAqlArgAt(hidden_arguments, global[0] / local[0], ...)` for `HiddenBlockCountX`, `local[0]` for group size, `global[0] % local[0]` for remainder etc. — [`clr/rocclr/device/rocm/rocvirtual.cpp` ~L3932–4090](https://github.com/ROCm/clr/blob/develop/rocclr/device/rocm/rocvirtual.cpp)
- NVIDIA arguments: `cuLaunchKernel(CUfunction f, gridDimX,Y,Z, blockDimX,Y,Z, sharedMemBytes, hStream, void **kernelParams, void **extra)`: "If f has N parameters, then kernelParams needs to be an array of N pointers. Each of kernelParams[0] through kernelParams[N-1] must point to a region of memory from which the actual kernel parameter will be copied"; parameter count/offsets/sizes "do not need to be specified as that information is retrieved directly from the kernel's image"; alternatively `extra` with `CU_LAUNCH_PARAM_BUFFER_POINTER` / `CU_LAUNCH_PARAM_BUFFER_SIZE` ("places the burden on the application of knowing each kernel parameter's size and alignment/padding"); `cuLaunchKernelEx` attributes include `CU_LAUNCH_ATTRIBUTE_CLUSTER_DIMENSION`, `CU_LAUNCH_ATTRIBUTE_COOPERATIVE`, `CU_LAUNCH_ATTRIBUTE_PROGRAMMATIC_STREAM_SERIALIZATION` — [CUDA Driver API 13.4, cuLaunchKernel](https://docs.nvidia.com/cuda/cuda-driver-api/group__CUDA__EXEC.html)
- PTX `.param` state space: kernel parameters are "defined per-grid"; "in some implementations kernel parameters reside in global memory"; `.const` is "currently limited to 64 KB" plus "640 KB of constant memory, organized as ten independent 64 KB regions" — [PTX ISA 9.4 §5.1](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html). `__grid_constant__` "prevents the compiler from creating a per-thread copy of the parameter" — [CUDA PG §5.4.1.5](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/cpp-language-extensions.html)
- HIP host stub / registration (what `<<<>>>` compiles to): the compiler emits a host-side stub function whose address is the key; at program load `__hipRegisterFatBinary(const void* data)` checks `__CudaFatBinaryWrapper{version==1, magic}` (magic `__hipFatMAGIC2` = normal HIPF; `kHipkMagic` = kpack'd binary) and calls `PlatformState::Instance().StatCO().AddFatBinary(...)`; then `__hipRegisterFunction(void** modules, const void* hostFunction, char* deviceFunction, const char* deviceName, unsigned threadLimit, uint3* tid, uint3* bid, dim3* blockDim, dim3* gridDim, int* wSize)` creates `new hip::Function(std::string(deviceName), fat_binary_modules)` and `StatCO().RegisterFunction(hostFunction, func)`; loading is deferred unless `HIP_ENABLE_DEFERRED_LOADING=0` — [`clr/hipamd/src/hip_platform.cpp` L180–240](https://github.com/ROCm/clr/blob/develop/hipamd/src/hip_platform.cpp). `__hipRegisterVar(modules, var, hostVar, deviceVar, ext, size, constant, global)` registers `__device__`/`__constant__` globals with host shadows — same file.
- What `hipFunction_t` is at runtime: `class hip::Function { Function(const std::string& name, FatBinaryInfo** modules); hipError_t GetDynFunc(hipFunction_t*, hipModule_t); hipError_t GetStatFunc(hipFunction_t*, int deviceId); ... amd::Kernel* BuildKernel(hipModule_t) const; std::vector<...> dFunc_; }` — [`clr/hipamd/src/hip_global.hpp` L35–50](https://github.com/ROCm/clr/blob/develop/hipamd/src/hip_global.hpp); the launch path `hipLaunchKernel(hostFunction, gridDim, blockDim, args, sharedMem, stream)` (L788) and `hipModuleLaunchKernel` (L492) both end in `ihipModuleLaunchKernel(hipFunction_t f, amd::LaunchParams&, hipStream_t, void** kernelParams, void** extra, hipEvent_t start, stop, flags, params, gridId, numGrids, prevGridSum, allGridSum, firstDevice)` which does `amd::Kernel* kernel = hip::asKernel(f);` then `ihipLaunchKernel_validate(...)` and clamps `local_` to `global_` — [`clr/hipamd/src/hip_module.cpp` L403–445](https://github.com/ROCm/clr/blob/develop/hipamd/src/hip_module.cpp)

### Inferences
- Both stacks reduce a launch to the same tuple {code entry, resource descriptor, argument buffer pointer, grid/block dims, completion object}; AMD exposes it (AQL packet + kernel descriptor in an ELF symbol `<name>.kd`), NVIDIA hides it behind `CUfunction` (the CUDA track should confirm the driver-side equivalent, e.g. QMD, out of scope here).
- "Kernel arguments are constant memory" is literally true on AMD (kernarg segment read with scalar loads `s_load_*` from the SGPR pair set up by CP) and effectively true on NVIDIA (PTX `.param` → constant bank; see the SASS track for `c[0x0][...]`).
- Because grid sizes in the AQL packet are in work-items (not groups), HIP computes `global = grid*block` on the host; the hidden `hidden_block_count_*` args are what `gridDim` reads on AMD (the hardware only supplies work-group IDs in SGPRs, not the grid size).

### Gaps
- NVIDIA's on-device launch descriptor (QMD) layout and the exact constant-bank placement of kernel params are not in public docs; left to the CUDA/SASS tracks.
- Kernel-parameter size limit (4 KB historically; 32 KB on Volta+ with CUDA ≥12.1 as I recall) was NOT found on the fetched driver-API page — unverified, flag.

## KQ2. SIMT execution: warps/wavefronts, divergence, schedulers, latency hiding, occupancy, block scheduling, tail effects

### Takeaway
A warp (32) or wavefront (32 on RDNA, 64 on CDNA) is the hardware's unit of instruction issue; per-lane predication (NVIDIA per-thread PCs since Volta; AMD a 32/64-bit `EXEC` mask) implements divergence; each SM has 4 sub-partition schedulers issuing ≤1 instruction/cycle each, each RDNA3 CU has 2 SIMD32s; latency is hidden purely by having many resident warps/waves, which is bounded by registers, shared memory/LDS and fixed slot counts (48 warps/SM on sm_120; 16 waves/SIMD on RDNA3) – i.e. "occupancy".

### Cited Findings
- NVIDIA SIMT: "Each SM creates, manages, schedules, and executes threads in groups of 32 parallel threads called warps"; divergent paths are executed one at a time with non-participating threads disabled; a block of T threads yields ceil(T/32) warps and "each warp contains threads of consecutive, increasing thread IDs with the first warp containing thread 0"; registers are partitioned among warps, shared memory among blocks; "If there are not enough resources available per SM to process at least one block, the kernel will fail to launch" — [CUDA PG 13.4.2 §3.2.2.1–3.2.2.2](https://docs.nvidia.com/cuda/cuda-programming-guide/03-advanced/advanced-kernel-programming.html)
- Independent Thread Scheduling (CC ≥ 7.0): "the GPU maintains execution state per thread, including a program counter and call stack"; execution can yield "at a per-thread granularity"; "A schedule optimizer determines how to group active threads from the same warp together into SIMT units"; before Volta warps "used a single shared program counter" — [PTX ISA 9.4 §3.2](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html); CUDA PG: "threads can now diverge and reconverge at sub-warp granularity" and legacy warp-synchronous code must "explicitly synchronize such code using __syncwarp()" — [CUDA PG §3.2.2.1.1](https://docs.nvidia.com/cuda/cuda-programming-guide/03-advanced/advanced-kernel-programming.html)
- NVIDIA schedulers: each SM has four sub-partitions ("SM sub partitions"); each scheduler keeps a pool of warps, those "active and not stalled" are *eligible*, and if none is eligible "the issue slot is skipped and no instruction is issued"; Turing pool = 8 warps per sub-partition — [Nsight Compute Profiling Guide 2026.3.1, Scheduler Statistics](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html). Blackwell: "Each of the SM's four partitions has a private L0 instruction cache"; "Nvidia's dispatch unit is limited to one instruction per cycle"; register file "remains a 64 KB per partition" (256 KB/SM); each partition tracks "up to 12 waves" (⇒ 48 warps/SM), so with 8-register allocation granularity (author's assumption) a kernel "can't use more than 40 registers" to fill all 12 slots; FP32 and INT32 share "one 32-wide execution pipe" per partition; 128 KB L1/shared per SM; GB202 GPC:SM = 1:16 — [Chips and Cheese, Blackwell, 2025-06-29](https://chipsandcheese.com/p/blackwell-nvidias-massive-gpu)
- NVIDIA per-CC resources (8.9 / 9.0 / 10.0 / 12.x): warp size 32; 64 K 32-bit registers per SM; 64 K per block; 255 per thread; max 1024 threads/block; unified L1/shared data cache 128 KB (8.9, 12.x) or 256 KB (9.0, 10.0); SMEM capacity options for 12.x: 0/8/16/32/64/100 KB; 32 shared-memory banks; constant memory 64 KB; local memory 512 KB/thread. Max resident warps/SM row was not readable from the flattened table (see Gaps) — [CUDA PG §5.1](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/compute-capabilities.html). Carveout example: "on compute capability 12.0 (100 KB maximum), a 50% carveout yields 64 KB, because the next larger supported capacity is used"; >48 KB/block needs dynamic shared memory + `cudaFuncAttributeMaxDynamicSharedMemorySize` — [CUDA PG §3.2.6](https://docs.nvidia.com/cuda/cuda-programming-guide/03-advanced/advanced-kernel-programming.html)
- Occupancy definition (NVIDIA): "the ratio of the number of active warps to the maximum number of active warps supported by the SM"; limits are `maxBlocksPerMultiProcessor`, `maxThreadsPerMultiProcessor`, `sharedMemPerBlock`, registers; use `nvcc --resource-usage` — [CUDA PG §2.3.7](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html); Nsight: "Occupancy is the ratio of the number of active warps per multiprocessor to the maximum number of possible active warps", limiting factors reported separately (registers, shared memory, block size, barriers, blocks per SM) — [Nsight Compute PG](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html)
- Block scheduling (NVIDIA): "The details of which thread blocks are scheduled to execute on which SMs cannot be controlled or queried by the application"; "programs cannot rely on a specific scheduling order or scheme for correct execution" — [CUDA PG §2.3.7](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html); forward progress: "If it is part of a Cooperative Grid, all device threads in its grid shall eventually make progress. Otherwise, all device threads in its thread-block cluster shall eventually make progress"; "Threads in other thread-block clusters are not guaranteed to eventually make progress" — [CUDA PG §5.8.2](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/cuda-cpp-execution-model.html)
- Waves / tail effect / wave quantization: "We use the term wave to refer to a set of thread blocks that run concurrently"; example "12 thread blocks with an occupancy of 1 block/SM" on an 8-SM GPU "execute in 2 waves, the first wave utilizes 100% of the GPU, while the 2nd wave utilizes only 50%" — [NVIDIA DL Performance GPU Background, 2023-02-01](https://docs.nvidia.com/deeplearning/performance/dl-performance-gpu-background/index.html); "the total number of tiles is quantized to the number of multiprocessors on the GPU: Wave quantization"; A100 108 SMs ⇒ "wave size of 108 tiles"; 117 tiles = full wave + tail of 9 that "takes nearly the same time to execute as the full 108-tile wave ... but uses only 9/108 = 8.33% of A100's SMs" — [NVIDIA Matrix Multiplication Background, 2023-02-01](https://docs.nvidia.com/deeplearning/performance/dl-performance-matrix-multiplication/index.html); Nsight metric `launch__waves_per_multiprocessor`: "Partial waves can lead to tail effects where some SMs become idle" — [Nsight Compute PG](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html)
- AMD hierarchy: "Each agent has multiple shader arrays (SA). Each SA has multiple work-group processors (WGP). Each WGP has multiple compute units (CU). Each CU has multiple SIMDs that execute wavefronts. The wavefronts for a single work-group are executed in the same WGP. In CU wavefront execution mode the wavefronts may be executed by different SIMDs in the same CU. In WGP wavefront execution mode the wavefronts may be executed by different SIMDs in different CUs in the same WGP." — [AMDGPUUsage "Memory Model GFX10-GFX11"](https://llvm.org/docs/AMDGPUUsage.html#memory-model-gfx10-gfx11). HIP docs: RDNA "work group processor (WGP) pairs two CUs. Each CU has two 32-wide SIMDs"; RDNA uses 32-thread warps, CDNA 64; CDNA CUs have four SIMDs of 16 lanes — [HIP 7.16.0 hardware implementation](https://rocm.docs.amd.com/projects/HIP/en/latest/understand/hardware_implementation.html)
- AMD work distribution: the command processor has a fetcher (CPF) and packet processor (CPC); kernel launches go to asynchronous compute engines (ACEs), "with each ACE capable of dispatching one kernel at a time"; ACEs break kernels into workgroups for the shader processor input (SPI, "workgroup manager"), which "Ensures all warps of a workgroup execute on the same CU for synchronization", tracks four limits (warp slots, VGPRs, SGPRs, LDS), and "Workgroup-to-CU mapping is non-deterministic and based on available resources" — [HIP 7.16.0 hardware implementation](https://rocm.docs.amd.com/projects/HIP/en/latest/understand/hardware_implementation.html). LLVM: "For AMD GPUs the packet processor is implemented by the hardware command processor (CP), asynchronous dispatch controller (ADC) and shader processor input controller (SPI)" — [AMDGPUUsage "Kernel Dispatch"](https://llvm.org/docs/AMDGPUUsage.html#kernel-dispatch)
- AMD divergence = EXEC mask: the compiler-visible model is that every wave carries an EXEC mask; the kernel descriptor/initial-state docs say CP/SPI set up SGPRs/VGPRs and the ISA executes vector ops only for lanes with EXEC=1 (source: RDNA3 ISA guide — NOT fetched, amd.com returned 503/HTML; see Gaps). What *is* verifiable from HIP headers: `__activemask()` is implemented as `__ballot(true)` and `__lane_id()` as `__builtin_amdgcn_mbcnt_lo(-1,0)` (wave32) / `mbcnt_hi(-1, mbcnt_lo(-1,0))` (wave64), i.e. lane masks are first-class 32/64-bit values — [`clr/hipamd/include/hip/amd_detail/amd_warp_functions.h` L108–123](https://github.com/ROCm/clr/blob/develop/hipamd/include/hip/amd_detail/amd_warp_functions.h)
- RDNA3 dual issue: "VOPD" packs two operations in one 8-byte instruction (two sources + one destination each), only in wave32; operands in the same position "can't read from the same register bank"; in wave64 the SIMD "will naturally try to start executing a 64-wide wavefront over a single cycle" when an instruction can dual issue; common FP ops take 5 cycles latency (NVIDIA: 4); 7900 XTX has 48 WGPs, LDS 128 KB per WGP built from two 64 KB blocks each "affiliated with one CU", 32 banks per 64 KB block; vector L0 32 KB per CU, L1 256 KB per shader array, L2 6 MB, Infinity Cache 96 MB — [Chips and Cheese RDNA3 (2023)](https://chipsandcheese.com/p/microbenchmarking-amds-rdna-3-graphics-architecture)
- AMD occupancy math (the compiler's own model): `getWavesPerWorkGroup = ceil(FlatWorkGroupSize / wavefrontSize)`; `getMaxWorkGroupsPerCU = min(MaxWavesPerEU * NumWorkGroupSIMDs / wavesPerWG, MaxBarriers)` where `MaxBarriers = 16`, or 32 on GFX10+ in WGP mode (`!FeatureCuMode`), and single-wave workgroups "don't consume barrier resources"; VGPR allocation granule `getVGPRAllocGranule`: gfx90a 8; targets with `Feature1536VGPRs` 24 (wave32) / 12 (wave64); gfx10.3+ 16/8; older 8/4; waves-per-SIMD from VGPRs: `min(max(TotalNumVGPRs / alignTo(NumVGPRs, Granule), 1), MaxWaves)`; SGPRs on GFX10–12: "Reserved, must be 0. (128 SGPRs always allocated.)"; addressable VGPRs 256 (or 512/1024 with `Feature1024AddressableVGPRs`, 512 on gfx90a) — [LLVM `AMDGPUBaseInfo.cpp` L1165–1200, L1296–1372](https://github.com/llvm/llvm-project/blob/main/llvm/lib/Target/AMDGPU/Utils/AMDGPUBaseInfo.cpp), [AMDGPUUsage kernel descriptor `GRANULATED_WORKITEM_VGPR_COUNT`](https://llvm.org/docs/AMDGPUUsage.html#kernel-descriptor). Physical VGPR file: `getTotalNumVGPRs`: gfx90a 512; pre-GFX10 256; `FEAT_1536_PHYSICAL_VGPRS` ⇒ 1536 (wave32) / 768 (wave64); other GFX10+ ⇒ 1024 / 512. LDS: "gfx10/11/12: 128 KiB physical and 64 KiB addressable" (per WGP; a work-group can allocate at most 64 KiB), `getLocalMemorySize` halves in CU mode — [LLVM `AMDGPUTargetParser.cpp` L441–490](https://github.com/llvm/llvm-project/blob/main/llvm/lib/TargetParser/AMDGPUTargetParser.cpp), [`AMDGPUBaseInfo.cpp` L1116–1160](https://github.com/llvm/llvm-project/blob/main/llvm/lib/Target/AMDGPU/Utils/AMDGPUBaseInfo.cpp)
- CDNA slot counts (for contrast): sequencer "groups warps into four pools, each with slots for up to ten warps (eight on the CDNA2 MI200 Series)" ⇒ "up to 40 concurrent warps per CU"; "256-512 KiB of VGPR storage split across the four SIMDs", "12.5 KiB of SGPR storage per CU" — [HIP 7.16.0 hardware implementation](https://rocm.docs.amd.com/projects/HIP/en/latest/understand/hardware_implementation.html)

### Inferences
- RX 7900 XTX (gfx1100) occupancy envelope, derived from the LLVM model: 48 WGPs × 2 CUs × 2 SIMD32 = 192 SIMDs; if gfx1100 carries `FEAT_1536_PHYSICAL_VGPRS` and MaxWavesPerEU = 16 (both believed true for RDNA3 but the per-GPU table is TableGen-generated and was not fetched — flag), then full occupancy (16 waves/SIMD) needs ≤ 96 VGPRs/wave in wave32 (1536/16, granule 24) and e.g. 128 VGPRs ⇒ 12 waves, 256 ⇒ 6 waves. Verify with `rocprofv3`/`--save-temps` `.s` `.amdhsa_next_free_vgpr`.
- RTX 5060 Ti (sm_120): 48 warps/SM × 32 = 1536 threads/SM, 64 K regs ⇒ ≤ 40 regs/thread for 100% occupancy (Chips and Cheese's number, rounding to 8); 100 KB max SMEM/SM.
- The "one instruction per cycle per scheduler" on NVIDIA vs RDNA3's VOPD co-issue explains why RDNA3 needs the compiler to pair FP32 ops to reach peak, whereas NVIDIA reaches peak with plain ILP across warps.
- Tail/wave quantization is identical in nature on AMD (grid split into work-groups across 96 CUs / 192 SIMDs); the "wave size" is `#CU × workgroups-per-CU` as computed by `getMaxWorkGroupsPerCU`.

## KQ3. Memory spaces and their hardware; consistency model basics; atomics

### Takeaway
Both vendors expose the same ladder — registers → (spill) local/scratch → shared/LDS → L0/L1 → L2 → VRAM, plus a read-only constant/scalar path — and both define correctness with *scoped* acquire/release semantics (CTA/workgroup, cluster, GPU/agent, system); on AMD the compiler must emit explicit `s_waitcnt` and cache invalidates/writebacks (`buffer_gl0_inv`, `buffer_gl1_inv`) because L0/L1 are not coherent across CUs/shader arrays.

### Cited Findings
- PTX state spaces: `.reg` "Registers, fast"; `.sreg` "Special registers. Read-only; pre-defined"; `.const` 64 KB + 640 KB in ten 64 KB regions; `.global` "accessible by all threads in a context"; `.local` "private memory for each thread"; `.param` per-grid (kernel) / per-thread (function); `.shared` "accessible to all threads in the cluster throughout the lifetime of the CTA that defines it", default sub-qualifier `::cta` (vs `::cluster`); each multiprocessor has on-chip registers, shared memory, a constant cache that "speeds up reads from the constant memory space", and a texture cache — [PTX ISA 9.4 §3.3, §5.1](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html)
- CUDA: "the physical location of local memory is in the global memory space"; "Register spilling means that values currently stored on-chip in registers must be written out to global memory"; "Constant memory is useful for small amounts of data that each thread will use in a read-only fashion" — [CUDA PG §2.3.3.3–2.3.3.5](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html)
- NVIDIA coalescing: "Global memory is accessed via 32-byte memory transactions"; "Coalesced memory access occurs provided different threads in the warp access elements from the same 32-byte segments"; for consecutive 4-byte words "the warp will request 128 bytes of memory total" (four 32-byte transactions) — [CUDA PG §2.3.4.1](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html); Nsight: a sector is an "Aligned 32 byte-chunk of memory in a cache line or device memory", an L1/L2 line is four sectors = 128 bytes — [Nsight Compute PG](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html)
- NVIDIA shared memory: "Shared memory has 32 banks that are organized such that successive 32-bit words map to successive banks"; "Each bank has a bandwidth of 32 bits per clock cycle"; "When multiple threads in the same warp attempt to access different elements in the same bank, a bank conflict occurs"; "For read accesses, the word is broadcast to the requesting threads" — [CUDA PG §2.3.4.2](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html)
- NVIDIA scopes & point of coherence: block (`.cta`, point of coherency L1), cluster (`.cluster`, L2), device (`.gpu`, L2), system (`.sys`, L2 plus connected caches) — [CUDA PG §3.2.3 "Thread Scopes"](https://docs.nvidia.com/cuda/cuda-programming-guide/03-advanced/advanced-kernel-programming.html); PTX scope definitions: `.cta` "The set of all threads executing in the same CTA", `.cluster` "... same cluster", `.gpu` "all threads in the current program executing on the same compute device", `.sys` "all threads in the current program" incl. all grids and the host; "morally strong" = related by program order or both strong with inclusive scopes, same proxy, completely overlapping; a memory fence is `membar`, `fence.sc` or `fence.acq_rel`; only `fence.sc` restores SC in the SB litmus test — [PTX ISA 9.4 §8.5–8.10](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html)
- CUDA C++ memory model: `cuda::thread_scope_system / _device / _block / _thread`; device scope relates GPU threads "in the same CUDA device and within the same memory synchronization domain"; data race = conflicting accesses "at least one of which is not atomic at a scope that includes the thread that performed the other operation" ⇒ UB; system-scope atomicity holds only under conditions (`pageableMemoryAccess`, `concurrentManagedAccess`, `hostNativeAtomicSupported`, P2P native atomics) — [CUDA PG §5.7](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/cuda-cpp-memory-model.html); `__threadfence_block()/__threadfence()/__threadfence_system()` order "All writes to all memory made by the calling thread" before the call at block/device/system scope; legacy atomics: no suffix = device scope, `_block` = block scope, `_system` = system scope "if they meet particular conditions"; they "only support memory_order_relaxed" and do not introduce fences — [CUDA PG §5.4.4.3, §5.4.5](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/cpp-language-extensions.html)
- HIP implementation of the same fences: `__threadfence()` = `__builtin_amdgcn_fence(__ATOMIC_SEQ_CST, "agent")`; `__threadfence_block()` = `__builtin_amdgcn_fence(__ATOMIC_SEQ_CST, "workgroup")`; `__threadfence_system()` = `__builtin_amdgcn_fence(__ATOMIC_SEQ_CST, "")` (empty = system scope) — [`amd_device_functions.h` L666–674](https://github.com/ROCm/clr/blob/develop/hipamd/include/hip/amd_detail/amd_device_functions.h)
- AMD address spaces: "The region address space uses the hardware Global Data Store (GDS)" (not implemented for AMDHSA); local = LDS, "allocated when a work-group's wavefronts are created and freed when they terminate"; global and constant "use global virtual addresses", constant data "treated as unchanging during kernel execution, which allows scalar reads"; private "uses the hardware scratch memory support", allocated per wavefront; generic "uses the hardware flat address support, with fixed apertures for private and local memory" — [AMDGPUUsage "Address Spaces"](https://llvm.org/docs/AMDGPUUsage.html#address-spaces); LLVM sync scopes `wavefront`, `workgroup`, `agent`, `system` (+ `one-as` variants); model "based on the HSA memory model ... based in turn on HRF-indirect with scope inclusion"; "Concurrent atomic operations only operate atomically with respect to each other if they are included in each other's sync scope" — [AMDGPUUsage "Memory Scopes"](https://llvm.org/docs/AMDGPUUsage.html#memory-scopes)
- AMD GFX10/11 cache hierarchy and what the compiler must emit: "Each WGP has a single LDS memory"; "All LDS operations of a WGP are performed as wavefront wide operations in a global order and involve no caching"; "A s_waitcnt lgkmcnt(0) is required to ensure synchronization between LDS operations and vector memory operations between wavefronts of a work-group"; "There is a single L0 cache per CU ... a buffer_gl0_inv is required for coherence between wavefronts executing in the same work-group as they may be executing on SIMDs of different CUs"; "The vector and scalar memory L0 caches use an L1 cache shared by all WGPs on the same SA ... a buffer_gl1_inv is required for coherence between wavefronts executing in different work-groups"; "A s_waitcnt vmcnt(0) & vscnt(0) is required to ensure synchronization between vector memory operations of different wavefronts"; "The L1 caches use an L2 cache shared by all SAs on the same agent"; "On GFX10.3 and GFX11 a memory attached last level (MALL) cache exists for GPU memory ... fully coherent with GPU memory"; scalar cache is used only for memory "proven to not change during the execution of the kernel dispatch" and "The scalar and vector caches are invalidated between kernel dispatches by CP"; kernarg memory is MTYPE UC on dGPU, CC on APU; scratch is MTYPE NC — [AMDGPUUsage "Memory Model GFX10-GFX11"](https://llvm.org/docs/AMDGPUUsage.html#memory-model-gfx10-gfx11)
- AMD LDS banks: "32 (CDNA, CDNA 2, and CDNA 3) or 64 (CDNA 4 and RDNA 2, RDNA 3, and RDNA 4) banks"; LDS bandwidth 128 B/cycle on CDNA1–3, 256 B/cycle on CDNA4 and RDNA2–4; vector L1 (vL1D) per CU is write-through, "typically 16 KB" (CDNA); L2 "is the coherence point for all CUs", 32 channels × 256-byte interleave on CDNA — [HIP 7.16.0 hardware implementation](https://rocm.docs.amd.com/projects/HIP/en/latest/understand/hardware_implementation.html); Chips and Cheese measured RDNA3 LDS as "32 banks per 64 KB block, each bank handling a 32-bit access" — [Chips and Cheese RDNA3](https://chipsandcheese.com/p/microbenchmarking-amds-rdna-3-graphics-architecture) (note the two sources phrase the bank count differently: 2×32 vs 64)
- Unified/managed memory: CUDA 13.4.2 dedicates chapters "Unified and System Memory" (`02-basics/understanding-memory.html`) and "Unified Memory" (`04-special-topics/unified-memory.html`); system-scope atomic conditions above reference `pageableMemoryAccess`/`concurrentManagedAccess` — [CUDA PG TOC](https://docs.nvidia.com/cuda/cuda-programming-guide/index.html) (content not extracted; see Gaps)

### Inferences
- "Scoped" is the single most important concept for the reader: a `__syncthreads()`/`s_barrier` only orders within a workgroup; cross-workgroup communication needs device-scope atomics/fences, which on AMD turn into `buffer_gl0_inv`/`buffer_gl1_inv` + `s_waitcnt`, visible in disassembly, and on NVIDIA into `MEMBAR.GPU`-class SASS (SASS track).
- Scalar (SGPR) loads on AMD are *the* constant path (kernargs, `const __restrict__` uniform data): the compiler can only use them when it can prove uniformity and immutability.

### Gaps
- Did not extract unified-memory page details (page budget); the CUDA track should cover HMM/ATS and `cudaMallocManaged` on consumer Blackwell; on ROCm, XNACK/HMM for gfx1100 is unsupported in practice (not verified here).
- NVIDIA L1 coherence rules (`__ldg`/read-only cache, `volatile`) were not present on the pages fetched.

## KQ4. Synchronization and cooperation (barriers, warp/wave primitives, cooperative groups, clusters/DSMEM, async copies, mbarrier, named barriers)

### Takeaway
Intra-block barrier + intra-warp data exchange are universal (`__syncthreads` ↔ `s_barrier`, `__shfl_sync` ↔ `ds_bpermute`/DPP); NVIDIA adds a second hardware layer since Ampere/Hopper — async copies (LDGSTS, TMA), transaction mbarriers and thread-block clusters with distributed shared memory — that AMD RDNA3 has no equivalent for (CDNA3 has `buffer_load ... lds`; not covered here).

### Cited Findings
- `__syncthreads()` "blocks all threads in the thread block until all threads have reached the call"; after it "memory updates that happened before the synchronization point are guaranteed to be visible" to the block; allowed in conditionals only if the condition "evaluates uniformly across the entire thread block"; variants `__syncthreads_count/and/or(int predicate)`; `__syncwarp(unsigned mask = 0xFFFFFFFF)` provides memory ordering among the named lanes — [CUDA PG §2.3.3.2, §3.2.4.2, §5.4.4.1–5.4.4.2](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/cpp-language-extensions.html). PTX: `bar{.cta}.sync/.red/.arrive` synchronize with `bar{.cta}.sync/.red` on the same barrier (named barriers = barrier id operand) — [PTX ISA 9.4 §8.9.4](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html)
- HIP implementation: `__syncthreads()` = `__barrier(__CLK_GLOBAL_MEM_FENCE | __CLK_LOCAL_MEM_FENCE)` → `__builtin_amdgcn_fence(__ATOMIC_RELEASE, "workgroup"); __builtin_amdgcn_s_barrier(); __builtin_amdgcn_fence(__ATOMIC_ACQUIRE, "workgroup");` (variants with `"global"`/`"local"` address-space fences); `__named_sync()` = bare `__builtin_amdgcn_s_barrier()` — [`amd_device_functions.h` L639–697](https://github.com/ROCm/clr/blob/develop/hipamd/include/hip/amd_detail/amd_device_functions.h). LLVM notes the s_barrier only matters when a work-group has >1 wavefront ("Single-wave workgroups don't consume barrier resources") — [`AMDGPUBaseInfo.cpp` L1174–1176](https://github.com/llvm/llvm-project/blob/main/llvm/lib/Target/AMDGPU/Utils/AMDGPUBaseInfo.cpp)
- Warp primitives (NVIDIA): `T __shfl_sync(unsigned mask, T value, int srcLane, int width=warpSize)`, `__shfl_up_sync`/`__shfl_down_sync(…, unsigned delta, …)`, `__shfl_xor_sync(…, int laneMask, …)`, width "must be a power of two in the range [1, warpSize]"; votes `__all_sync`, `__any_sync`, `__ballot_sync(unsigned mask, int predicate)`, `__activemask()` ("cannot be used to determine which warp lanes execute a given branch"), "These intrinsics do not provide any memory ordering"; `__match_any_sync/_all_sync`; `__reduce_{add,min,max,and,or,xor}_sync` "Supported by devices of compute capability 8.x or higher" — [CUDA PG §5.4.6](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/cpp-language-extensions.html)
- Wave primitives (AMD/HIP): `__shfl*` are built on `__builtin_amdgcn_ds_bpermute(index << 2, var)` (LDS crossbar, byte addresses) with `self = __lane_id()`; DPP path `__builtin_amdgcn_mov_dpp(src, dpp_ctrl, row_mask, bank_mask, bound_ctrl)`; `__ballot(int)` returns 64-bit; `__activemask()` = `__ballot(true)`; `readfirstlane` used for uniform broadcast in `amd_warp_sync_functions.h` — [`amd_warp_functions.h` L27–129, `amd_warp_sync_functions.h` L89–90](https://github.com/ROCm/clr/blob/develop/hipamd/include/hip/amd_detail/amd_warp_functions.h)
- Cooperative groups: `thread_block` — "all threads in the group must participate in collective operations, or the behavior is undefined"; `thread_block_tile` shfl "For sizes larger than 32 all threads in the group have to specify the same src_rank"; `cluster_group::query_shared_rank` "Obtain the block rank to which a shared memory address belongs", `map_shared_rank` "Obtain the address of a shared memory variable of another block in the cluster"; `%smid`/`%warpid` are "unsafe to rely upon ... remaining unchanged across the lifetime of a thread or thread block" — [CUDA PG §5.6.3–5.6.4](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/device-callable-apis.html); HIP: "The Cooperative groups API introduces new functions to launch, group, subdivide, synchronize and identify threads" — [HIP 7.16.0 programming model](https://rocm.docs.amd.com/projects/HIP/en/latest/understand/programming_model.html)
- Clusters & DSMEM: launched with `cudaLaunchKernelEx` + `attribute[0].id = cudaLaunchAttributeClusterDimension` or `__cluster_dims__`; DSMEM access `int *dst_smem = cluster.map_shared_rank(smem, dst_block_rank);` — [CUDA PG §2.3.3.8, §5.4.3.1](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html); register→DSMEM copies use STAS (9.0+), shared::cta→shared::cluster bulk copies use TMA (`cuda::ptx::cp_async_bulk`) — [CUDA PG §3.2.5, §4.12](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/async-copies.html); forward progress is guaranteed within a cluster — [§5.8.2](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/cuda-cpp-execution-model.html)
- Async copies: LDGSTS (CC 8.0+) copies 4/8/16 bytes global→shared, "copying 16-bytes enables the L1 BYPASS mode, in which case the L1 is not polluted"; "The only direction supported ... with LDGSTS is from global to shared memory"; APIs `cuda::memcpy_async`, `cooperative_groups::memcpy_async`, `__pipeline_memcpy_async`/`__pipeline_commit`/`__pipeline_wait_prior(N)`; TMA requires "compute capability 9.0 (Hopper) and later", `cp.async.bulk` (1D, no tensor map) and `cp.async.bulk.tensor` (up to 5 dims, tensor map "typically created on the host using the cuTensorMapEncodeTiled driver API" and passed as `const __grid_constant__` parameter), swizzle 32B/64B/128B; completion via shared-memory mbarrier with transaction counts ("tells the barrier how many transactions (tx) are expected to arrive" — `mbarrier_expect_tx`), "The barrier will only flip once all threads have arrived" and all bytes landed; shared→global uses bulk async-groups where "only the initiating thread can wait"; generic-proxy writes need `fence_proxy_async` + `__syncthreads()`; `cp.async.wait_group` and `cp.async.bulk.wait_group` are separate — [CUDA PG §4.12](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/async-copies.html); async barriers: available on 7.0+, block-scope HW-accelerated on 8.0+, cluster-scope on 9.0+, "Remote shared memory allows arrive but not wait", "The arrive point carries an implicit memory fence"; `__mbarrier_inval`: "Invalidation of *bar is required before the corresponding shared memory can be repurposed" — [CUDA PG §3.2.4.2, §5.6.1.2](https://docs.nvidia.com/cuda/cuda-programming-guide/03-advanced/advanced-kernel-programming.html)
- Grid-wide sync on AMD: HIP's `hidden_multigrid_sync_arg` and CLR's `Device::MGSyncInfo` allocation for cooperative launches (`allocKernArg(Device::kSGInfoSize, 64)`, `WriteAqlArgAt(hidden_arguments, syncInfo, ...)`) — [`rocvirtual.cpp` ~L4025–4040](https://github.com/ROCm/clr/blob/develop/rocclr/device/rocm/rocvirtual.cpp); cooperative launch on NVIDIA is `CU_LAUNCH_ATTRIBUTE_COOPERATIVE` ("exactly the same usage and semantics of cuLaunchCooperativeKernel") — [CUDA Driver API 13.4](https://docs.nvidia.com/cuda/cuda-driver-api/group__CUDA__EXEC.html)

### Inferences
- `__shfl` on AMD costs an LDS-crossbar instruction (`ds_bpermute_b32`, lgkmcnt-tracked) unless the compiler can use DPP/`v_permlane`; on NVIDIA `SHFL` is a dedicated datapath. This matters for llama.cpp reduction kernels on gfx1100.
- RDNA3 has no TMA/mbarrier/cluster analogue; the vendor-neutral "async copy" concept on RDNA3 is just plain `global_load` with deep ILP; CDNA3's `buffer_load ... lds` / `global_load_lds` is the closest AMD equivalent (not verified in this note).

### Gaps
- Max portable cluster size (8) / non-portable (16) and GPC co-scheduling statements were not on the fetched pages (page budget) — well known but unverified here.
- Named barriers (`bar.sync id, count`) semantics only partially captured (PTX §8.9.4 line).

## KQ5. Lifecycle of one kernel launch, end to end (shared stages, vendor mechanism per stage)

### Takeaway
Both vendors implement the same pipeline — compile → bundle → load → launch API → command packet in a user-space ring → doorbell → command processor firmware → work distributor → waves → completion signal/fence → host — and on AMD every stage is open source and readable (CLR → ROCR → AQL → CP/ADC/SPI), which is the "reverse-engineerable" skeleton to map NVIDIA onto.

| 10 Wave start | CP/ADC/SPI initialise SGPRs (private segment buffer, dispatch ptr, queue ptr, kernarg ptr, dispatch id, flat scratch init, workgroup ids) and VGPRs (work-item ids); then the compiler-generated prolog runs — [AMDGPUUsage "Initial Kernel Execution State", "Kernel Prolog"](https://llvm.org/docs/AMDGPUUsage.html#initial-kernel-execution-state) | warp launch with `%tid`, `%ctaid`, param constant bank populated |
| 11 Execute | waves on SIMD32s (KQ2) | warps on SM sub-partitions (KQ2) |
| 12 Completion | "When the kernel dispatch has completed execution, CP signals the completion signal specified in the kernel dispatch packet if not 0" — [AMDGPUUsage](https://llvm.org/docs/AMDGPUUsage.html#kernel-dispatch); release fence scope from the packet header | semaphore release / completion record |
| 13 Host sees it | `hsa_signal_wait_scacquire` → `signal->WaitAcquire(...)`; `InterruptSignal::WaitRelaxed` spins then blocks in `hsaKmtWaitOnEvent_Ext(event_, wait_ms, &event_age)` (KFD interrupt event from `Runtime::GetEventPool()`), woken via `hsaKmtSetEvent` — [`core/runtime/hsa.cpp` L1247–1260, `core/runtime/interrupt_signal.cpp` L100–205, L376](https://github.com/ROCm/ROCR-Runtime/blob/master/runtime/hsa-runtime/core/runtime/interrupt_signal.cpp); HIP events/streams map on top | `cudaStreamSynchronize`/`cudaEventSynchronize` on the semaphore |

- Stream ordering on AMD is expressed in the packet header barrier bit and `HSA_PACKET_TYPE_BARRIER_AND` packets (CLR defines several barrier-AND headers with `(1 << HSA_PACKET_HEADER_BARRIER)`) — [`rocvirtual.cpp` L66–94](https://github.com/ROCm/clr/blob/develop/rocclr/device/rocm/rocvirtual.cpp); NVIDIA: "This function uses standard default stream semantics"; `CU_LAUNCH_ATTRIBUTE_PROGRAMMATIC_STREAM_SERIALIZATION` lets a grid overlap with the previous kernel — [CUDA Driver API 13.4](https://docs.nvidia.com/cuda/cuda-driver-api/group__CUDA__EXEC.html)
- CUDA 13.4.2 adds "Work Stealing with Cluster Launch Control" (`04-special-topics/cluster-launch-control.html`) and "Green Contexts" — [CUDA PG TOC](https://docs.nvidia.com/cuda/cuda-programming-guide/index.html) (not extracted)
- Device-side enqueue on AMD: CLR builds a device "virtual queue" of `AmdAqlWrap` slots each pre-pointing `slot->aql.kernarg_address` at a per-slot argument area (`header->arg_size = maxParameterSize_ + 64`) — [`rocvirtual.cpp` L3790–3820](https://github.com/ROCm/clr/blob/develop/rocclr/device/rocm/rocvirtual.cpp); AMDGPUUsage: dispatch "can occur in the CPU host program, or from an HSA kernel executing on a GPU".

### Inferences
- On AMD every launch is ~1 memcpy of 64 bytes + 1 atomic + 1 MMIO write from user space; the kernel driver (KFD) is only involved at queue creation (`hsaKmtCreateQueue`) and for interrupt-based completion. This is why `rocprof`/`ROCR` tracing can see each packet and why a user can write their own dispatcher against `hsa.h`.
- NVIDIA's equivalent ring (GPFIFO/pushbuffer + USERD doorbell) is undocumented but structurally the same; the open-source `nvidia` kernel module and `nouveau` headers (CUDA track) are the place to confirm.

### Gaps
- NVIDIA stage mechanisms are named from general knowledge, not from fetched sources — the CUDA track must source them (open-gpu-kernel-modules headers, Nouveau docs).
- KFD side (`hsaKmtCreateQueue`, MES/HWS vs direct ring) not covered here; belongs to the ROCm track.

## KQ6. Terminology mapping table: NVIDIA / AMD HIP / Vulkan–OpenCL

### Takeaway
The three vocabularies are 1:1 for the hierarchy and memory spaces; the real asymmetries are PTX (no AMD equivalent — LLVM IR/SPIR-V play the "portable IR" role), clusters/DSMEM/TMA (NVIDIA only), and AMD's user-space AQL queue + signal (NVIDIA hides streams/events).

### Cited Findings
Sources for each column: CUDA PG 13.4.2 §5.4.2.2 and PTX ISA 9.4 §2 (NVIDIA); HIP 7.16.0 programming model + hardware implementation and ROCR `hsa.h` (AMD); Vulkan-Docs shaders.adoc/dispatch.adoc (Vulkan); OpenCL names as used by the HIP docs ("work-item", "work-group").
